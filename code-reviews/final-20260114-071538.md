NOT-COMPLETE

- **B1 Stream payload typing (still inconsistent):** `spec/06-rfcs/RFC-0002-transport.md` §6.3/§6.3 table still specifies **0x03 Message** and **0x04 Sync** payloads as **UTF-8 JSON** with a `type` field. This contradicts `spec/00-shared/layer-integration.md` (0x03 = **Binary PUSE**, 0x04 = **Binary CBOR**) and `spec/03-messaging-sync/overview.md` / `secure-envelope.md` (PUSE is binary).  
- **B2 Invalid IID examples remain (forbidden chars i/l/o/u):** Multiple example IIDs still contain excluded Crockford characters (notably **`u`**, also `i/l/o` in trustee placeholders). Example: `spec/02-identity-trust/identity-document-schema.md` and `spec/04-app-runtime/manifest-schema.md` include `...t2u3...`. `spec/02-identity-trust/recovery-mechanisms.md` includes trustee IID placeholders with `i`/`l`. These violate the normative Crockford alphabet.  
- **B3 Test vector generator still uses RFC4648 Base32 (not Crockford):** In `spec/00-shared/test-vectors.md` “Reference Generator”, `base32_encode()` uses `base64.b32encode(...)` (RFC4648 alphabet) and `derive_iid()` uses that result. This contradicts the normative Crockford Base32 requirement and the earlier correct Crockford encoder in the same file.  
- **B4 Mailbox spec not fully singular/consistent:** `spec/00-shared/layer-integration.md` still defines a separate binary “Mailbox Envelope (outer layer)” format, while RFC-0003 §7 specifies mailbox storage of **PUSE envelope bytes** via HTTP. This violates the “only ONE mailbox spec” requirement and creates wire-format ambiguity.  
- **B5 `device_transport_key` removal incomplete:** `spec/01-transport-connectivity/interfaces.md` still defines `DeviceDocument.deviceTransportKey` and `deviceTransportKey` fields, contradicting the canonical device document (and the stated removal) in `spec/00-shared/layer-integration.md` and `spec/02-identity-trust/identity-document-schema.md`.  

- **H1 App manifest signing text/code inconsistency:** `spec/04-app-runtime/manifest-schema.md` still contains embedded `signature` examples and a `verifyManifestSignature()` routine that assumes a `manifest.signature` field, contradicting the SIGNATURE-file-only model in `spec/05-ux-packaging/app-distribution.md` and the manifest-schema’s own “SIGNATURE file approach” notes.
