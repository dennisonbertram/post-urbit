## 1) Remaining **BLOCKING** issues?

### B1 — Recovery cooldown state transition is underspecified (interop + safety)
You embed `recovery_proof.status: "pending|active|contested"` in the Identity Document / revocation documents and say:

- “Document is pending for cooldown_hours”
- “After cooldown, document becomes active”

But an identity document is immutable once published (sequence is the replay/ordering primitive). The spec does **not** clearly define how the network ever observes `"active"`:

- If you require republishing the same document with `status="active"`, that implies **same-sequence update**, which is explicitly treated as a serious conflict elsewhere.
- If you require publishing a *new* document just to flip status, that implies a **sequence bump**, which is heavy and changes chain semantics.
- If verifiers are supposed to treat `pending` as effectively active once `now >= cooldown_expires_at`, then `status` is informational and should not gate validity—yet several places imply it does (e.g., `cooldown: recovery_proof.status === 'pending'`).

**Why this is blocking:** different implementations will make different choices (“status gates validity” vs “time gates validity”), producing inconsistent acceptance of recovered identities.

**Fix (normative):** specify one of:
- “`status` is non-normative; verifiers MUST treat recovery as active iff `now >= cooldown_expires_at` and proofs verify” (recommended), or
- “activation requires a follow-up document at `sequence+1` that references the pending recovery doc hash”.
