## BLOCKING inconsistencies

### 1) Sync stream framing is inconsistent (double-framing / conflicting payload definition)
- **Global framing rule** (normative, repeated in `spec/00-shared/layer-integration.md` and `spec/06-rfcs/RFC-0002-transport.md`):  
  Each QUIC stream begins with **1 byte stream type**, then repeated **(u32 length || payload)** frames. For **0x04 Sync**, payload is described as “Binary (CBOR)” / “CBOR-encoded sync operation/message”.
- **But** `spec/03-messaging-sync/sync-protocol.md` defines **another** framing inside the sync stream:
  ```
  Sync Message:
    Message Type (1 byte)
    Length (4 bytes)
    Payload (CBOR)
  ```
  This implies either:
  - redundant length fields (outer frame length + inner length), or
  - a different framing than the transport RFC mandates.

**Fix (choose one, make consistent everywhere):**
- Recommended: keep **only the transport frame length**, and make the **payload** a CBOR structure with a `type` field (or CBOR tag), e.g. `{type: SYNC_REQUEST, ...}`. Remove the inner `Length` from `sync-protocol.md`.
- If you insist on a 1-byte message-type prefix, then define the **stream-frame payload** as: `msg_type_byte || cbor_bytes` (no inner length), and update RFC-0002 + layer-integration text to match.

### 2) PUSE header-extension requirements conflict (zero-length vs exactly-one)
- `spec/06-rfcs/RFC-0003-messaging.md` is explicit and normative:
  - **Exactly ONE** header extension MUST be present.
  - `ext_len` MUST match the fixed size for that extension type.
  - Reject `ext_len == 0`.
- But `spec/03-messaging-sync/secure-envelope.md` still describes:
  - header extension length can be **0**, and even computes a minimum size assuming `ext_len = 0`.

**Fix:**
- Update `secure-envelope.md` to match RFC-0003:
  - Require exactly one extension, `ext_len ∈ {33, 41, 21}` for v1.
  - Update the min-size computation accordingly.

### 3) Message size limits: Transport (0x03) vs PUSE vs mailbox are inconsistent
- `spec/06-rfcs/RFC-0003-messaging.md` and `spec/03-messaging-sync/secure-envelope.md` set **PUSE max envelope size = 1 MB**.
- Mailbox also permits **1 MB** envelopes.
- But `spec/06-rfcs/RFC-0002-transport.md` §6.4 sets **Message stream (0x03) Max Message Size = 256 KB**.

This creates an actual interoperability problem: a valid PUSE envelope may be deliverable via mailbox but not deliverable in real-time over QUIC message stream.

**Fix (pick one and align all three):**
- Recommended: raise RFC-0002 §6.4 “Message (0x03) max message size” to **≥ 1 MB**, matching PUSE and mailbox.
- Alternatively: reduce PUSE max to 256 KB everywhere (and update mailbox limits + messaging constants). This is a larger behavioral change.
