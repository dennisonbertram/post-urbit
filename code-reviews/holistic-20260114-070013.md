NOT-COMPLETE

- **B1**: **QUIC stream payload typing is inconsistent across specs.**  
  - `00-shared/layer-integration.md` defines stream 0x03 **Message** as **binary PUSE**, 0x04 **Sync** as **CBOR**, and 0x05 **Bulk** as binary.  
  - `06-rfcs/RFC-0002-transport.md` §6.1–6.3 instead says streams 0x03 and 0x04 are **UTF-8 JSON**.  
  This is interop-blocking for any transport implementation.

- **B2**: **Crockford Base32 alphabet is declared, but normative examples violate it.**  
  - `06-rfcs/RFC-0002-transport.md` §2.1 example IID `abzy73bycgb9ybrgi2tynyxgkfzyh3bk` contains `i` (excluded by the stated alphabet).  
  - Multiple example IIDs elsewhere include `u` (also excluded).  
  Implementers cannot safely validate identifiers or reproduce examples.

- **B3**: **`00-shared/test-vectors.md` is internally inconsistent and does not match the stated Crockford Base32 requirement.**  
  - Test Vector 1 “Expected Output” gives IID `b1anasr5h0bj3832xqexwy0f0987e1xb`, but the included Python “Verify” assert expects `lbvhmpzmqkzrudc55hok54a6ajq6a6c3` (different value).  
  - The Python reference uses `base64.b32encode` (RFC4648 Base32 alphabet), not Crockford Base32.  
  This blocks implementers from using the test vectors as a conformance oracle.

- **B4**: **Domain separator strings are inconsistent between documents (interoperability-breaking).**  
  Examples:  
  - `01-transport-connectivity/peer-handshake.md` uses `post-urbit-device-handshake-v1` for device proof, while the normative registry (`00-shared/layer-integration.md`) and RFC-0002 use `post-urbit-device-v1`.  
  - `01-transport-connectivity/relay-protocol.md` uses `post-urbit-relay-allocate-v1` while the registry + RFC-0002 specify `post-urbit-relay-alloc-v1`.  
  These must be identical byte-for-byte across all implementations.

- **B5**: **Mailbox protocol is duplicated and incompatible between `00-shared/layer-integration.md` and `06-rfcs/RFC-0003-messaging.md`.**  
  Mismatches include at least:
  - Endpoint schema (`host`/`port`/`transport` vs `url`)
  - HTTP routes (`/store/{recipient_iid}` + `/retrieve/...` vs `/messages`)
  - Bearer token format and signature input (different fields and signing constructions)
  - Whether an additional “Mailbox Envelope” wrapper exists vs storing raw PUSE
  This is a hard blocker for offline delivery.

- **B6**: **Device Document schema is contradictory re `device_transport_key`.**  
  - `00-shared/layer-integration.md` explicitly says `device_transport_key` is removed in v1.  
  - `02-identity-trust/identity-document-schema.md`, `06-rfcs/RFC-0001-identity-document.md`, and `01-transport-connectivity/interfaces.md` still include it.  
  Implementers cannot know what to publish/verify/store in DHT for devices.

- **H1**: **Domain separator byte counts contain at least one incorrect value in a “Normative” registry.**  
  In `00-shared/layer-integration.md`, `post-urbit:devices-for:` is listed as **22** bytes, but the literal string length is **23** bytes. (If byte counts are used for validation/tests, implementations will diverge.)

- **H2**: **PUSE signature verification guidance mismatches the signing-key-history schema.**  
  `03-messaging-sync/secure-envelope.md` shows comparing an “envelope_timestamp” to `keys.signing.history[].valid_from` / `valid_until`, but those fields are defined as **sequence numbers** (not timestamps) in `02-identity-trust/identity-document-schema.md`. This needs a clarified, implementable rule (e.g., “try current/previous/history without timestamp filtering” unless the message carries an IDOC-sequence hint).

- **H3**: **“No placeholders / complete test vectors” criterion is not met in RFCs and examples.**  
  `RFC-0002` test vectors still contain `[compute with reference implementation]`, and many examples use `<...>` placeholders. This won’t always block implementation, but it blocks interoperability testing and conformance verification as stated in success criteria.
