## Overall assessment

RFC-0002 is close to implementable for **direct QUIC + identity handshake** and a **relay framing concept**, but there are several **interop-breaking inconsistencies** (within the RFC and vs the accompanying spec docs), plus **critical ambiguities** around Base32 encoding, anonymous handshakes, and relay encapsulation semantics. The test vector section is currently not usable to validate independent implementations.

Below are issues categorized by severity. Each includes **location**, **description**, and a **recommended fix**.

---

## BLOCKING issues (must fix)

### B1 — Handshake stream identification contradicts itself (and other spec)
- **Location**
  - `spec/06-rfcs/RFC-0002-transport.md` §5.2 (“Stream 0: Control (0x01)”)
  - `spec/06-rfcs/RFC-0002-transport.md` §5.3 (“first bidirectional stream opened by the client”)
  - `spec/01-transport-connectivity/peer-handshake.md` (“NOT a specific QUIC stream ID”)
- **Problem**
  - QUIC stream numbering is deterministic, but the documents conflict on whether the handshake is strictly **stream ID 0** or simply the **first client-initiated bidi stream**.
  - This becomes interop-breaking once you introduce **0-RTT**, “pre-auth” control messages, or libraries that auto-open streams.
- **Recommended fix**
  - Pick one normative rule and align all docs:
    - Option A (best): “Handshake MUST run on the **first client-initiated bidirectional stream**; implementations MUST NOT open any other application stream before handshake completes.” (Avoids hardcoding `0`.)
    - Option B: “Handshake MUST run on **stream ID 0**.” Then remove contrary language elsewhere.

---

### B2 — Application error code registry conflict (0x105 means two different things)
- **Location**
  - `spec/06-rfcs/RFC-0002-transport.md` §9.2: `0x105 = REVOKED_IDENTITY`
  - `spec/01-transport-connectivity/interfaces.md` `CONNECTION_DEDUP.DUPLICATE_CONNECTION_CODE: 0x105`
- **Problem**
  - Two different semantics for the same numeric code is a guaranteed cross-implementation failure.
- **Recommended fix**
  - Create a single authoritative registry (likely in RFC-0002) and update `interfaces.md` + `00-shared/layer-integration.md` to match.
  - E.g. keep `0x105` for `DUPLICATE_CONNECTION` and move revocation errors to unused codes (say `0x110/0x111`), or vice versa.

---

### B3 — PURL packet type registry is inconsistent across documents
- **Location**
  - `spec/01-transport-connectivity/relay-protocol.md` “Packet Types: … 0x07 = ERROR”
  - `spec/06-rfcs/RFC-0002-transport.md` §7.5: `0x07 = REBIND`, `0x08 = ERROR`
- **Problem**
  - Interop-breaking: implementations will parse the same byte differently.
- **Recommended fix**
  - Unify packet type values in **one** place (RFC should win), then update the other doc.
  - If you need REBIND, define it consistently in both, and make ERROR consistently `0x07` or `0x08`.

---

### B4 — Relay ERROR payload format conflicts
- **Location**
  - `spec/01-transport-connectivity/relay-protocol.md` “ERROR Packet” (no message length field shown)
  - `spec/06-rfcs/RFC-0002-transport.md` §7.11 (adds `Message Length` u16)
- **Problem**
  - Without an agreed payload format, receivers cannot parse relay errors reliably.
- **Recommended fix**
  - Decide the canonical ERROR payload format (recommend the RFC’s version with explicit length), and update the other doc.
  - Also specify whether the **outer PURL payload length** must equal the ERROR payload length (it should).

---

### B5 — Base32 encoding is underspecified and examples appear incompatible with RFC4648 Base32
- **Location**
  - `spec/06-rfcs/RFC-0002-transport.md` throughout (IIDs are “32-char base32”)
  - Examples like `h7ab3d9k...0xvs7yfn` include digits `0,1,8,9` which RFC4648 Base32 **does not allow**.
- **Problem**
  - This is *foundational*: if implementations disagree on the alphabet/variant, **nothing interoperates** (IID parsing, DHT keys, signature inputs, relay dest IID decoding, etc.).
- **Recommended fix**
  - Specify a single Base32 variant **normatively**:
    - Alphabet, case, padding rules, and whether ambiguous chars are allowed.
  - Then ensure all examples conform, and add test vectors for Base32 decode/encode of a known 20-byte IID.

---

### B6 — Domain separator byte-length annotations are wrong (breaks test vectors and risks mismatched implementations)
- **Location**
  - `spec/06-rfcs/RFC-0002-transport.md` §5.6, §5.7, §7.7 show comments like “// 24 bytes ASCII”, “// 31 bytes”, “// 29 bytes”.
- **Problem**
  - The literal strings shown do not match those byte counts (e.g., `"post-urbit-handshake-v1"` is 23 bytes ASCII).
  - Implementers may “fix” strings to match the stated length, causing signature mismatches.
- **Recommended fix**
  - Remove length comments entirely **or** correct them to the exact ASCII byte length of the literal string.
  - Add a normative statement: “Domain separator is the exact ASCII bytes of the literal string shown; no NUL terminator.”

---

### B7 — Anonymous handshake is not fully defined but referenced as supported
- **Location**
  - `spec/01-transport-connectivity/peer-handshake.md` “Anonymous Connections” section (client_iid null)
  - RFC-0002 §5.4 (“client_iid is null → anonymous”)
  - RFC-0002 §5.6 requires `decode_base32(client_iid)` for challenge signature input
- **Problem**
  - If `client_iid` is null, the challenge signature construction is undefined (what bytes go into the transcript?).
  - This is an interop + security issue (different transcripts → signatures won’t verify; or some parties skip checks).
- **Recommended fix**
  - Either:
    1) Remove anonymous handshake from RFC-0002 scope (treat relay/discovery as separate protocols), **or**
    2) Define anonymous mode precisely, e.g.:
       - `client_iid_raw = 20*0x00` and client does not send `ClientAuth`
       - server either omits `challenge_signature` or signs a transcript that excludes client_iid
  - State clearly what “authenticated” means in anonymous mode (it should be “server-authenticated only”, or “neither authenticated”).

---

### B8 — Stream framing vs payload typing is contradictory (JSON “type field” vs binary payloads)
- **Location**
  - RFC-0002 §6.3: “Payload (UTF-8 JSON or binary)”
  - RFC-0002 §5.3/§6.3: “Message type is in JSON `type` field”
  - `spec/00-shared/layer-integration.md` “All stream types” uses JSON payload with `type`
- **Problem**
  - If Sync/Bulk can be binary, the “JSON `type` field” rule cannot apply universally.
  - Implementers won’t know how to demux message kinds on binary streams, or whether binary is even allowed.
- **Recommended fix**
  - Define per-stream payload rules:
    - Control/Identity/Message: **JSON only**
    - Sync: either JSON-only (simplest) *or* define a binary envelope with a 1-byte opcode + varint fields
    - Bulk: define a binary format (chunking, hashes, resumability)
  - Update `layer-integration.md` to stop claiming “all stream types are JSON” if that’s not true.

---

### B9 — Relay encapsulation/forwarding semantics are ambiguous (critical for implementability)
- **Location**
  - RFC-0002 §3.2 stack diagram shows **QUIC above PURL** (“PURL Framing (if relayed)” below QUIC).
  - RFC-0002 §7.4 says PURL payload contains a QUIC packet, but does not specify what the relay forwards onto the wire to the recipient.
- **Problem**
  - Two plausible designs exist, and they are incompatible:
    1) Relay forwards **full PURL packets** to clients; clients decapsulate then feed QUIC.
    2) Relay strips PURL and forwards **raw QUIC**; clients never see PURL inbound.
  - This affects sockets, demuxing, keepalives, and whether relay control packets can coexist with QUIC traffic.
- **Recommended fix**
  - Specify one model normatively. Suggested:
    - “On the client↔relay link, all UDP datagrams are PURL-framed.”
    - “Relay forwards the entire PURL packet unchanged to the destination allocation.”
    - “Destination client MUST decapsulate PURL and pass the inner payload to QUIC.”
  - Then specify how non-DATA packet types (PING/PONG/ERROR/REBIND) are processed (they must not be passed to QUIC).

---

### B10 — Test vectors are placeholders and also violate the RFC’s own encoding rules
- **Location**
  - RFC-0002 §11.1–§11.4
- **Problem**
  - Values are `"...“` placeholders for hash/signature outputs, so independent implementers cannot validate.
  - Nonces in §11.2 use Base64 with `=` padding, while RFC elsewhere says Base64 **without padding**.
- **Recommended fix**
  - Provide complete, deterministic vectors:
    - Exact Base32 decode results (20-byte hex) for the example IIDs
    - Exact `challenge_data_hex`, `sha256_hex`, `signature_base64(no padding)`
    - Full PURL packet bytes (header + payload) for a short known payload
    - Allocation signature output (`sha256_hex`, signature)
  - Ensure vectors use the **same Base32/Base64 variants** mandated by the RFC.

## HIGH issues (serious)

### H1 — RFC scope claims “Discovery” and “Mailbox” but RFC-0002 does not specify them
- **Location**
  - RFC-0002 §1.1 includes “Discovery services”
  - RFC-0002 §3.1 includes “Mailbox | HTTPS | Bearer token”
  - No further normative specification in RFC-0002
- **Problem**
  - As written, implementers can’t build the full “transport layer” described by the RFC without out-of-band documents.
- **Recommended fix**
  - Either:
    - Add normative sections for discovery (DHT record format, lookup rules) and mailbox, **or**
    - Explicitly move them out-of-scope and normatively reference other RFCs/specs (e.g., “See RFC-000X Discovery”, “See RFC-000Y Mailbox”), and remove them from “specified here” tables.

---

### H2 — `identity_doc_sequence` type is inconsistent with global conventions and risks overflow
- **Location**
  - RFC-0002 §7.7 allocation request JSON: `"identity_doc_sequence": 42`
  - `spec/00-shared/layer-integration.md` “Sequence numbers: Decimal string”
- **Problem**
  - If sequences are uint64, JSON numbers will break in JS and other environments.
- **Recommended fix**
  - Make `identity_doc_sequence` a **decimal string** everywhere, and include it (optionally) in signature input if you intend it to be integrity-protected.

---

### H3 — Timestamp canonicalization for signature inputs is not defined
- **Location**
  - RFC-0002 §5.6, §7.7, §7.10: signature inputs include `timestamp` as UTF-8
- **Problem**
  - RFC3339 has multiple equivalent textual encodings (`Z` vs `+00:00`, fractional seconds, etc.). Different encodings will produce different signatures.
- **Recommended fix**
  - Define a canonical timestamp format for signed fields, e.g.:
    - `YYYY-MM-DDTHH:MM:SSZ` (UTC only, no fractional seconds)
  - Require rejecting non-canonical forms for signed timestamps.

---

### H4 — TLS “accept any self-signed cert” needs tighter constraints to avoid downgrade/weird cert parsing bugs
- **Location**
  - RFC-0002 §4.3, §10.1
- **Problem**
  - “Any valid self-signed cert” is ambiguous:
    - What signature algorithms are allowed?
    - Are expired/not-yet-valid certs accepted?
    - Are cert key usage / SAN rules ignored?
  - Different TLS stacks behave differently → interop and security footguns.
- **Recommended fix**
  - Add a minimal verification profile, aligned with `00-shared/layer-integration.md`:
    - Allow only Ed25519 or ECDSA P-256
    - Require time validity within bounds (or explicitly ignore validity)
    - Require leaf cert only (self-signed), no chain
    - Explicitly state SNI handling expectations

---

### H5 — 0-RTT/resumption is underspecified for the identity handshake transcript and replay handling
- **Location**
  - RFC-0002 §8.3–§8.4
- **Problem**
  - QUIC 0-RTT data is replayable. The RFC restricts application operations but doesn’t specify:
    - whether the identity handshake itself may be sent in 0-RTT
    - whether servers MUST use QUIC Retry/address validation to control replay/DoS
    - whether servers cache client nonces to detect replays within ±5 minutes
- **Recommended fix**
  - Specify:
    - “Identity handshake messages MUST be sent after 1-RTT keys are available” **or** define server-side anti-replay expectations.
    - “Servers SHOULD enable QUIC Retry / address validation when under load.”

## MEDIUM issues (cleanup / clarity)

### M1 — Stream naming inconsistencies (“Message” vs “Messaging”)
- **Location**
  - `spec/00-shared/layer-integration.md` stream type table: “Messaging”
  - RFC-0002 §6: “Message”
  - `spec/01-transport-connectivity/interfaces.md`: `StreamType = 'message'`
- **Problem**
  - Mostly editorial but causes confusion in docs and implementations.
- **Recommended fix**
  - Standardize on one term across all documents (recommend “Message” / `'message'`) and keep numeric code mapping stable.

---

### M2 — Device document schema mismatches across layers (will break device binding)
- **Location**
  - `spec/00-shared/layer-integration.md` says `device_transport_key removed in v1`
  - `spec/01-transport-connectivity/interfaces.md` `DeviceDocument` includes `deviceTransportKey`
  - Field casing differs (`device_name` vs `deviceName`, etc.)
- **Problem**
  - Implementers won’t know which schema is canonical; device handshake verification depends on exact fields.
- **Recommended fix**
  - Define a canonical device doc schema in one place and reference it.
  - If over-the-wire JSON uses `snake_case`, make that explicit and avoid mixing with `camelCase` “interface” forms (or define a mapping).

---

### M3 — DHT signature policy is inconsistent (even though it’s “glue” it affects transport discovery)
- **Location**
  - `spec/00-shared/layer-integration.md`: “No separate DHT signature required.”
  - Same file: `publishIdentity()` example signs and passes `signature` to `dht.put`
- **Problem**
  - Conflicting requirements for DHT record acceptance.
- **Recommended fix**
  - Either remove the outer signature entirely (and remove it from the example/API), **or** make it required and specify exactly what is signed (key+value+ttl?) and by which key.

- **Location**

- **Problem**
  - Even when harmless, incorrect byte counts undermine implementer confidence.
- **Recommended fix**

## Missing test vectors (summary)

At minimum, to make RFC-0002 independently implementable, add **fully specified** vectors for:

1. **Base32 variant**: encode/decode a known 20-byte IID (hex ↔ string).
2. **Challenge signature**:
   - exact `challenge_data_hex`
   - exact `sha256_hex`
   - exact `ed25519_signature_hex` and Base64(no-pad)
3. **PURL**:
   - full packet bytes for a small payload (e.g., payload = 0x00010203…)
4. **Relay allocation signature**:
   - exact signature input bytes (hex)
   - sha256 + signature

## Security highlights (summary)

- Optional `expected_server_iid` is risky (unknown-key-share / user-error). For `connect(iid)` it should effectively be **MUST**.
- 0-RTT needs explicit replay/DoS handling guidance (Retry, nonce caches, or “no handshake in 0-RTT”).
- Relay encapsulation ambiguity has security consequences (e.g., whether relay control packets can be injected into the QUIC receive path).
