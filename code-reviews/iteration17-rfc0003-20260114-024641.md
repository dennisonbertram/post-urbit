## (1) BLOCKING — ambiguities/bugs that will break interop or block implementation

### B1. Double Ratchet header fields `PN` and `N` are underspecified and the pseudocode is off-by-one
**Where:** §4.4/§4.5 and Ratchet Header Extension (§3.4.3)  
**Problem:** The spec does not define whether `N` is **0-based** or **1-based**, and the send/receive pseudocode is inconsistent:

- Sender sets `pn = state.sending_chain_index` (but `PN` is supposed to be *previous sending chain length*, not the current index).
- Sender increments `sending_chain_index` and then sets `header.n = state.sending_chain_index`, which makes the *first* message have `N=1`.
- Receiver skip/decrypt logic then derives/stores skipped keys in a way that won’t match the sender’s derived key for the same message.

**Interop impact:** Different implementations will derive different message keys → permanent decryption failure.

**Actionable fix:**
- Normatively define:
  - `N`: “message number in this sending chain, starting at 0”
  - `PN`: “number of messages sent in the previous sending chain”
- Provide corrected reference pseudocode (and test vectors) consistent with that definition.
- Add an explicit “message key for message number N is the (N+1)th application of `kdf_chain_step` starting from the chain key created by `kdf_root`”.

---

### B2. Initial message key derivation and initial ratchet state are not fully defined
**Where:** §5.3, §4.3–§4.5, Initial extension (§3.4.2)  
**Problems:**
- §5 says the initial message is “encrypted with key derived from `initial_chain_key`” but never specifies *how* (is it `kdf_chain_step(initial_chain_key)`? direct use? what is `N`?).
- Initial messages use extension type `0x00` which contains no `N`/`PN`, so the receiver has no defined counters for the first chain.
- It’s unclear what the initial `dhSendingKey` / `dhReceivingKey` should be on each side after X3DH:
  - Does Alice’s `dhSendingKey` become `EK_A`?
  - Is Bob’s `dhReceivingKey` set to `EK_A_public` immediately?
  - When does Bob generate his first DH ratchet key?

**Interop impact:** first message and first reply are likely to diverge across implementations.

**Actionable fix:**
- Add a normative “Initial state setup” subsection specifying exact initial values for:
  - `rootKey`, `sendingChainKey`, `receivingChains`, `sendingChainIndex`, and the DH keys.
- Specify the first-message key derivation precisely (e.g., “message_key = HMAC(chain_key, 0x01) and chain_key = HMAC(chain_key, 0x02)” with counters initialized to 0).
- Consider including a minimal counter (`N=0`) in the Initial header extension to remove guesswork.

---

### B3. PUSE Header Extension structure: single extension vs. multiple extensions is undefined
**Where:** §3.4, §3.8  
**Problem:** `Header Extension Length` implies variable data, but the “extensions” are described like a single typed struct starting with `Extension Type`. There’s no TLV framing to support multiple extensions, yet the plural “extensions” is used.

**Interop impact:** Some implementations will assume “exactly one extension”, others may try to parse a sequence.

**Actionable fix (choose one):**
- **Option A (simple):** Normatively state: “Exactly one header extension MUST be present. `ext_len` MUST equal the fixed size for the given type.” (and delete references implying multiples)
- **Option B (extensible):** Define a TLV list:
  - `ext = repeated { type:1, length:2, value:length }`
  - and define canonical ordering rules.

---

### B4. “Empty header extension” is allowed by size constraints but unusable cryptographically
**Where:** §3.2 “Minimum envelope size: … empty extension …”  
**Problem:** For all defined session modes (Initial/Ratchet/Group), decryption needs parameters from the extension. Allowing empty extension conflicts with §3.8 step 9 (“derive message key based on extension type”).

**Interop impact:** Some implementations will reject ext_len=0; others might accept and then fail later.

**Actionable fix:** Specify whether `ext_len=0` is:
- **Forbidden** (most likely), or
- Allowed only for a future mode (then specify flags/type mapping and how key derivation works).

---

### B5. UUID v4 byte order in the wire format is not specified
**Where:** §3.2 “Message ID (UUID v4) 16 bytes” and throughout message examples  
**Problem:** UUID libraries disagree on byte order (RFC4122/network order vs “mixed-endian” internal layouts).

**Interop impact:** recipients will compute different UUID strings/cache keys for the same 16 bytes → replay detection and references (`reply_to`) break.

**Actionable fix:** Normatively specify RFC 4122 network byte order for the 16 bytes and the canonical hex string mapping.

---

### B6. Mailbox authentication token semantics are internally inconsistent (sender vs recipient)
**Where:** §7.3–§7.4  
**Problems:**
- Token payload uses `"iid": "<sender-iid-base32>"`, but `GET /messages` logically authenticates the **recipient** retrieving their mailbox.
- It’s unclear whether the mailbox is a per-identity inbox (recipient-authenticated) or a submission endpoint (sender-authenticated), or both, and whether tokens carry scopes.

**Interop impact:** clients won’t know which IID to put in tokens; mailbox operators won’t know what to authorize.

**Actionable fix:**
- Define token subject as `"sub_iid"` (the authenticated client) and add `"scope": ["store","retrieve","delete"]` (or separate token types).
- Define:
  - `POST /messages` authorization: does it require sender auth? or allow anonymous submission? if sender-authenticated, require envelope.sender_iid == token.sub_iid.
  - `GET/DELETE` authorization: token.sub_iid is the mailbox owner (recipient).

## (2) HIGH — security issues / missing edge cases likely to cause compromise or serious failure

### H1. The “X3DH” described is not X3DH and lacks prekeys → weaker async security than claimed
**Where:** §5  
**Problem:** Standard X3DH uses signed prekeys and optionally one-time prekeys to provide stronger forward secrecy for the receiver’s side in asynchronous settings. Here both DHs use Bob’s long-term static IK (`IK_B`), so compromise of `IK_B_private` can retrospectively compute DH1 and DH2 for captured initial messages.

**Security impact:** Initial messages (and potentially early ratchet state) become decryptable after receiver key compromise; the “X3DH” label overstates properties.

**Actionable fix:**
- Either:
  - Implement real X3DH-style prekeys (SPK + optional OPK) and specify how they’re published in RFC-0001, consumed, and depleted; **or**
  - Rename the protocol (e.g., “2DH-IK + ephemeral”) and downgrade the stated guarantees in §5.4 and §10.1 accordingly.

---

### H2. Nonce timestamp verification requirement is incompatible with offline mailboxes and will cause message loss
**Where:** §3.5 (“Timestamp MUST be current time (±5 minutes tolerance for verification)”)  
**Problem:** Offline recipients may retrieve messages hours/days later; even normal transport delay can exceed ±5 minutes.

**Security/availability impact:** trivial DoS (delay messages → forced rejection), and guaranteed failures for offline delivery.

**Actionable fix:**
- Remove the “±5 minutes verification” requirement entirely.
- If you want to prevent “far-future” weirdness, only reject timestamps *too far in the future* (e.g., >24h) but accept old timestamps.
- Or better: don’t embed timestamp in nonce at all—use 96-bit random nonces with collision mitigation (see H3).

---

### H3. Nonce uniqueness strategy is probabilistic and not tied to key schedule; (key,nonce) reuse risk is not handled
**Where:** §3.5, §3.6  
**Problem:** 8 random bytes gives birthday-bound collisions at high volume; the spec does not require per-key tracking or deterministic nonces.

**Security impact:** (key,nonce) reuse with ChaCha20-Poly1305 is catastrophic.

**Actionable fix:**
- Normatively require one of:
  - deterministic counter-based nonces per sending chain/message number, or
  - 96-bit random nonces *plus* a per-(message_key or chain) “nonce reuse guard” (store recently used nonces) and explicit volume guidance.
- If you already have `N` in ratchet/group headers, deriving nonce from `N` (and a per-chain random prefix) is a common approach.

---

### H4. Mailbox token signing contradicts envelope signing rules (raw vs prehash) and the token canonicalization is underspecified
**Where:** §3.7 vs §7.3  
**Problems:**
- PUSE signature: “NOT over a hash; signs raw bytes”
- Mailbox token: `ed25519_sign(signing_key, sha256(signature_input))` (prehash)
- `expires_at.encode('utf-8')  # 20 bytes canonical` is not actually guaranteed by RFC3339 unless constrained (fractional seconds, offsets).
- URL normalization is unspecified (trailing slashes, default ports, case).

**Security impact:** verification mismatches; token replay/cross-service confusion; implementations will diverge.

**Actionable fix:**
- Pick one signing mode for all Ed25519 signatures:
  - Prefer signing raw bytes (consistent with §3.7), with clear byte concatenation rules.
- Specify strict formatting:
  - `expires_at` MUST be RFC3339 UTC with no fractional seconds: `YYYY-MM-DDTHH:MM:SSZ` (20 bytes).
  - `mailbox_url` MUST be normalized (define exact normalization or require exact string match as published).
- Add domain separation and context binding fields (audience, scope).

---

### H5. Skipped-key TTL (7 days) conflicts with mailbox retention (30 days)
**Where:** §4.6 vs §7.5  
**Problem:** Messages stored up to 30 days may arrive after skipped-key expiry.

**Security/interop impact:** recipients can’t decrypt old but still-delivered messages, causing persistent failures and confusing UX.

**Actionable fix:** Align these values or define expected behavior:
- either reduce mailbox retention,
- or increase skipped-key TTL / add “session reinit” flow for old messages,
- or specify that mailbox SHOULD prioritize delivery within skipped-key TTL.

---

### H6. Group replay/out-of-order handling is effectively “reject if not strictly increasing”
**Where:** §6.7 (`if header.iteration <= last_seen_iteration: raise ReplayDetectedError()`)  
**Problem:** Real transports/mailboxes can reorder. Current logic rejects any out-of-order group message permanently.

**Security/availability impact:** easy DoS by reordering; message loss in normal conditions.

**Actionable fix:**
- Either explicitly state “group messages MUST be delivered in-order” (hard to guarantee), or
- add skipped-key style buffering for group sender chains (bounded window), or
- rely on `message_id` replay cache rather than strict monotonic iteration checks.

---

## (3) MEDIUM — unclear semantics / incomplete definitions that risk inconsistent implementations

### M1. Mapping to RFC-0001 identity document keys is not explicit
**Where:** §3.7, §5.2  
**Problem:** The spec says “sender_signing_key” and “keys.encryption.current” but does not normatively name the exact fields/IDs from RFC-0001 (e.g., key IDs, rotations, how to pick “current”, how to validate document authenticity).

**Actionable fix:** Add explicit references:
- “Use `identityDocument.keys.signing.current` (Ed25519) for envelope signatures”
- “Use `identityDocument.keys.encryption.current` (X25519) for DH”
- Define behavior on key rotation: accept previous keys for X days? require key IDs in headers?

---

### M2. Flags semantics are mostly undefined (ACK, priority, forward)
**Where:** §3.3  
**Problem:** Bits exist but there’s no protocol behavior: what is an ACK message type? who sends it? how does `forward` affect multi-device routing?

**Actionable fix:** Either define behavior (including message types and state machine), or mark bits reserved for future use and require senders set them to 0.

---

### M3. AEAD AAD is only the header extension, not the fixed header
**Where:** §3.6  
**Problem:** The fixed header (sender/recipient/message_id/flags) is authenticated only by the Ed25519 signature, not by AEAD. That’s not necessarily wrong, but it creates two different authentication layers with different verification timing and might complicate implementations (e.g., “decrypt-then-verify” vs “verify-then-decrypt”).

**Actionable fix:** Specify a recommended verification order and rationale, and consider including the fixed header (or at least flags + IDs + msgid) in AEAD AAD as well for tighter binding:
- `aad = fixed_header || header_extension`

---

### M4. Group KDF “info” concatenation uses separators with binary fields; parsing rules are implicit
**Where:** §6.3  
**Problem:** It’s safe because lengths are fixed, but it’s still better to specify exact byte layout (length-prefixing or fixed-length concatenation) rather than relying on `b":"` with arbitrary bytes.

**Actionable fix:** Define:
- `info = "post-urbit-sender-key-v1" || group_id(20) || sender_iid(20) || key_id(16)` (no separators)

---

### M5. Media encryption is not fully specified (algorithm, nonce/key rules)
**Where:** §8.4  
**Problem:** Says “encrypted separately” but does not specify AEAD algorithm, AAD, nonce uniqueness, chunking, or how `hash` is computed (over ciphertext or plaintext).

**Actionable fix:** Add a short normative media encryption section:
- algorithm (e.g., ChaCha20-Poly1305),
- hash definition (e.g., SHA-256 of ciphertext),
- nonce generation and uniqueness requirements,
- optional chunking/framing for large files.

---

### M6. Error handling lacks normative “MUST reject vs SHOULD ignore” rules
**Where:** §9  
**Problem:** Tables list errors but don’t always specify mandatory behavior (e.g., reserved flag bits set, unknown recipient type, ext_len mismatch).

**Actionable fix:** For each parsing/validation rule add “MUST reject with error X” or “MUST ignore”.

---

## (4) LOW — documentation/consistency issues

### L1. Signature guidance is inconsistent across the RFC
**Where:** §3.7 vs §7.3  
Even aside from security, this will confuse implementers. Standardize wording and provide one Ed25519 usage profile.

### L2. Pseudocode uses mixed conventions and undefined helpers
**Where:** §4.5 references `skip_message_keys()` but it’s not defined; Maps vs dict indexing varies.  
Add complete reference algorithms or remove partial pseudocode and replace with a precise state machine description.

### L3. Base64 vs Base64url usage is inconsistent
**Where:** §2.1, §7.3 (base64url for nonce/token wrapper; base64 for signature)  
Add a “Encoding Profiles” subsection that clearly states which fields use base64 vs base64url and whether padding is accepted.

### L4. Field size calculations and limits should be expressed as formulas
**Where:** §3.2 size constraints  
Provide exact formula for `total_len` and explicitly state whether `ct_len` includes the Poly1305 tag (it appears to, but should be explicit).
