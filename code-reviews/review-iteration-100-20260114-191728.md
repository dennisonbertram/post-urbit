## Summary
The spec set is close to implementable, but there are still a couple of cross-document gaps where the authoritative RFCs omit (or contradict) security-critical discovery/propagation behavior that other documents assume exists. These will lead to conforming-but-incompatible implementations, especially around revocation and recovery contestation.

## Issues Found

### BLOCKING

- **Revocation DHT record is specified outside the authoritative RFC, leaving revocation discovery undefined for RFC-only implementers**
  - **What conflicts (quotes)**
    - Layer doc requires DHT publication for revocations:  
      From `spec/02-identity-trust/revocation.md` (section “DHT Storage (Normative)”):  
      > “Revocations MUST be stored in DHT for later discovery …”  
      > “**DHT Key for Revocations:** `Key = SHA256("post-urbit:revocation:" || iid)`”
    - Integration doc also allocates the keyspace:  
      From `spec/00-shared/layer-integration.md` (section “DHT Key Encoding (Normative)”):  
      > `SHA256("post-urbit:revocation:" || iid)` → 32 bytes for identity/key revocation lookup
    - But the authoritative RFC DHT section does **not** define any DHT record for key/identity revocations; it only defines identity/genesis/device(-revocation) keys:  
      From `spec/06-rfcs/RFC-0001-identity-document.md` §12 (“DHT Storage”):  
      > “DHT Key: SHA256("post-urbit:identity:" || iid) …” (§12.2)  
      > “DHT Key: SHA256("post-urbit:genesis:" || iid) …” (§12.3)  
      > “DHT Key: SHA256("post-urbit:device-revocation:" || did) …” (§12.6)  
      (No corresponding `post-urbit:revocation:` record defined in RFC-0001.)
  - **Why this breaks interop**
    - Two implementations can both claim conformance while behaving incompatibly:
      - Implementation A (RFC-0001-only) will not publish/query `post-urbit:revocation:` and therefore may accept connections/messages signed by revoked keys indefinitely.
      - Implementation B (layer docs) will publish/query and enforce revocations.
    - This is both an interoperability failure (different acceptance behavior) and a security failure (revocation not reliably discoverable).
  - **Concrete file paths and section numbers**
    - `spec/02-identity-trust/revocation.md` — “DHT Storage (Normative)”
    - `spec/00-shared/layer-integration.md` — “DHT Key Encoding (Normative)” + Domain Separator Registry row “DHT revocation key”
    - `spec/06-rfcs/RFC-0001-identity-document.md` — §12 (notably §12.2–§12.7)
  - **Suggested fix**
    - Update the authoritative RFC to make revocation discovery interoperable:
      - Add a new subsection to **RFC-0001 §12** (e.g., “§12.8 Revocation Records”) that normatively defines:
        - DHT key: `SHA256("post-urbit:revocation:" || iid)` (identifier is the 32-char lowercase IID string, UTF-8/ASCII)
        - value encoding (JCS-canonical JSON for `key_revocation` and `identity_revocation`)
        - TTL (365 days) and tie-breaking (e.g., highest `effective_at`)
        - required signature verification rules (referencing RFC-0001 §10 signature schemes)
      - Then make `spec/02-identity-trust/revocation.md` and `spec/00-shared/layer-integration.md` explicitly reference that new RFC section (and remove any “see …” that implies the RFC already contains it).
