## Summary
The core RFCs are generally consistent and implementation-ready, but there are several cross-document mismatches where non-RFC layer docs contradict RFC requirements, plus at least one internal RFC inconsistency. These issues are blocking because they cause conforming implementations to reject each other’s records/messages (DHT revocations/genesis/refresh) or to diverge on critical parsing/validation behavior (message sequence numbers).

## Issues Found

### BLOCKING

- **Device revocation verification refers to a non-existent field name (`signature` vs `signature_by_identity`)**
  - **What conflicts (quotes)**
    - RFC-0001 device revocation schema uses:
      - `spec/06-rfcs/RFC-0001-identity-document.md` §13.5:  
        > `"signature_by_identity": "<base64-sig>"`
    - But the DHT verification text says:
      - `spec/06-rfcs/RFC-0001-identity-document.md` §12.6:  
        > “DHT nodes MUST verify the `signature` field using the identity's signing key…”
  - **Why this breaks interop**
    - Producers will emit `signature_by_identity` (per §13.5), while verifiers implementing §12.6 literally will look for `signature` and reject all valid device revocations. Device revocation is part of connection acceptance logic, so nodes will disagree on whether a device is revoked.
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0001-identity-document.md` §12.6, §13.5
  - **Suggested fix**
    - In RFC-0001 §12.6, replace “verify the `signature` field” with “verify the `signature_by_identity` field”.
    - Add a one-line cross-reference: “See §13.5 for schema and signature scheme.”

- **DHT “current identity” record TTL refresh semantics conflict between authoritative RFC and integration glue**
  - **What conflicts (quotes)**
    - RFC-0001 explicitly allows refreshing the *current identity* record without sequence bumps:
      - `spec/06-rfcs/RFC-0001-identity-document.md` §12.2:  
        > “DHT nodes MUST accept byte-identical writes as TTL refresh operations (idempotent writes extend TTL without requiring sequence increment).”
      - And again in the update rules:
        - `spec/06-rfcs/RFC-0001-identity-document.md` §12.7 step 2:  
          > “If incoming document is **byte-identical** to stored document: Accept as TTL refresh…”
    - Layer integration’s DHT update authorization omits this exception and requires strictly increasing sequence:
      - `spec/00-shared/layer-integration.md` “DHT Record Format” → “Update Authorization (Existing Records)”:  
        > “Compare `sequence` numbers: new sequence MUST be > existing sequence”
  - **Why this breaks interop**
    - Implementations that follow the integration doc for DHT node behavior will reject RFC-conforming refresh writes for `post-urbit:identity:` (sequence unchanged, bytes identical). Other implementations will rely on refresh to keep records alive without sequence churn. This produces inconsistent DHT availability and forces divergent publish behavior (some nodes bump sequence just to refresh; others don’t), which impacts discovery and identity update propagation.
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0001-identity-document.md` §12.2, §12.7  
    - `spec/00-shared/layer-integration.md` “DHT Record Format” → “Update Authorization (Existing Records)”
  - **Suggested fix**
    - Update `spec/00-shared/layer-integration.md` to match RFC-0001 §12.7:
      - Insert an explicit step before sequence comparison:  
        “If incoming value is byte-identical to stored value, accept as TTL refresh and extend expiry.”
    - Make it explicit this applies to the mutable identity key (`post-urbit:identity:`), not just genesis.

- **Genesis IDOC acceptance rules in layer-integration are weaker than RFC-0001 and can lead to incompatible stored genesis records**
  - **What conflicts (quotes)**
    - Layer integration defines “basic verification” for DHT storage as:
      - `spec/00-shared/layer-integration.md` “DHT Record Format” → “Verification (New Records)”:  
        > “Verify `iid == derive_iid(...)` … Verify `signatures.current` …”
    - And then states for genesis:
      - `spec/00-shared/layer-integration.md` “DHT Record Format” → “Genesis Document”:  
        > “DHT nodes accept genesis documents that pass basic verification.”
    - RFC-0001 requires additional genesis invariants:
      - `spec/06-rfcs/RFC-0001-identity-document.md` §12.7 “Genesis Document Verification”:  
        > “Verify `sequence == "0"`”  
        > “Verify `keys.signing.genesis == keys.signing.current`”  
        > “Verify `keys.signing.previous == null`”
  - **Why this breaks interop**
    - A DHT node implemented from layer-integration could accept and store a “genesis” document that RFC-conforming clients must reject (e.g., `sequence="0"` but `genesis != current`). Clients that rely on the genesis record for bootstrap verification (RFC-0001 §7.3) will fail to anchor trust consistently across implementations.
  - **Concrete file paths and section numbers**
    - `spec/00-shared/layer-integration.md` “DHT Record Format” → “Verification (New Records)”, “Genesis Document”
    - `spec/06-rfcs/RFC-0001-identity-document.md` §12.7
  - **Suggested fix**
    - In `spec/00-shared/layer-integration.md`, add an explicit “Genesis document verification” subsection that normatively lists the RFC-0001 §12.7 genesis invariants.
    - Replace the phrase “pass basic verification” with “pass RFC-0001 §12.7 genesis verification”.

- **PUSE plaintext `sequence` is under-specified in RFC-0003 (canonical form/range), enabling divergent accept/reject behavior**
  - **What conflicts (quotes)**
    - RFC-0003 defines plaintext field but does not specify canonical numeric-string constraints:
      - `spec/06-rfcs/RFC-0003-messaging.md` §8.1:  
        > `"sequence": "<uint64-string>"`
    - The rest of the spec ecosystem *does* define strict canonical requirements for “SequenceNumber” strings:
      - `spec/00-shared/layer-integration.md` “Common TypeScript Types” → `SequenceNumber`:  
        > “MUST be encoded as ASCII decimal with NO leading zeros (except "0" itself)… MUST be compared NUMERICALLY… Receivers MUST reject any non-canonical or out-of-range value.”
      - RFC-0001 similarly defines strict constraints for `sequence` strings:
        - `spec/06-rfcs/RFC-0001-identity-document.md` §6.4
  - **Why this breaks interop**
    - Because RFC-0003 is authoritative for messaging, two conforming implementations can disagree on whether `"01"` is valid, whether values above 2^53 may appear, whether to parse as JSON number vs string, and how to compare/order. This affects replay/ordering logic and any protocol behaviors keyed off `sequence` (receipts/order windows) and will cause inconsistent behavior across implementations.
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0003-messaging.md` §8.1  
    - `spec/00-shared/layer-integration.md` “Common TypeScript Types” → `SequenceNumber`  
    - `spec/06-rfcs/RFC-0001-identity-document.md` §6.4
  - **Suggested fix**
    - Add a normative subsection to RFC-0003 §8.1 (or §2 Conventions) stating:
      - `sequence` MUST be a decimal string in range [0, 2^64-1]
      - MUST be canonical (no leading zeros except `"0"`)
      - MUST NOT be encoded as a JSON number
      - Comparison MUST be numeric
    - Reference RFC-0001 §6.4 verbatim (or duplicate its exact regex/range wording) to avoid drift.

### HIGH

- **Layer doc `secure-envelope.md` omits RFC-0003’s strict header-extension length rules (and max extension size), risking divergent parsers**
  - **What conflicts (quotes)**
    - RFC-0003 requires strict extension sizing and a max extension length:
      - `spec/06-rfcs/RFC-0003-messaging.md` §3.2:  
        > “Maximum header extension: 1024 bytes”
      - `spec/06-rfcs/RFC-0003-messaging.md` §3.4:  
        > “The `Header Extension Length` field MUST equal the fixed size for the given extension type… reject … where `ext_len` does not match…”
    - Layer doc describes extensions and sizes but does not restate the strict validation requirement:
      - `spec/03-messaging-sync/secure-envelope.md` “Envelope Structure” and “Header Extension (AAD)” sections (descriptive, but no explicit MUST reject when ext_len != expected, and no 1024-byte cap).
  - **Why this hurts interop**
    - Implementers following the layer doc may accept envelopes that RFC-conforming implementations reject (or vice versa), especially if extension parsing is permissive. This is likely to produce hard-to-debug incompatibilities around malformed/edge-case messages.
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0003-messaging.md` §3.2, §3.4  
    - `spec/03-messaging-sync/secure-envelope.md` “Envelope Structure”, “Header Extension (AAD)”
  - **Suggested fix**
    - Add a short “Validation (Normative)” subsection to `secure-envelope.md` explicitly mirroring RFC-0003:
      - max extension length 1024
      - ext_len MUST equal the fixed size for the extension type
      - reject unknown extension types and ext_len==0

- **Terminology drift: “X3DH” vs “2DH” across messaging documents**
  - **What conflicts (quotes)**
    - Layer docs and test vectors still use “X3DH” naming:
      - `spec/03-messaging-sync/double-ratchet.md` includes sections titled “Initial Key Derivation (X3DH)” and “Session Initialization (X3DH)”.
      - `spec/00-shared/test-vectors.md` “Test Vector 6: X3DH Key Agreement”
    - RFC-0003 explicitly defines the initial exchange as 2DH and explains why:
      - `spec/06-rfcs/RFC-0003-messaging.md` §5: “Initial Key Exchange (2DH)” and the note “This protocol is intentionally simpler than Signal’s X3DH… Post-Urbit v1 uses 2DH…”
  - **Why this hurts implementers**
    - Not a wire-format mismatch, but it’s a repeated conceptual divergence that can lead to incorrect assumptions (e.g., expecting signed prekeys, prekey bundles, or different DH mixes).
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0003-messaging.md` §5  
    - `spec/03-messaging-sync/double-ratchet.md` (initial exchange sections)  
    - `spec/00-shared/test-vectors.md` “Test Vector 6”
  - **Suggested fix**
    - Rename the layer-doc sections and the test vector label to “2DH” (keep the domain separator string `post-urbit-x3dh-v1` unchanged unless you intentionally rev the protocol).
    - Add a one-line note: “Despite the historical label in the domain separator, v1 performs 2 DH operations (2DH).”
