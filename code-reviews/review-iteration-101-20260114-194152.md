## Summary
Across the authoritative RFCs and the layer documents, the core wire formats (IDOC, QUIC stream framing, PUSE, PURL) are mostly consistent. However, there are several cross-document contradictions and a few missing *RFC-level* normative definitions that can lead two “conforming” implementations to make incompatible choices, especially around relays, revocation distribution, and group membership updates.

## Issues Found

### BLOCKING

- **Relay routing identifier is IID-only in RFC-0002, but non-RFC docs imply DID routing and device-level relay endpoints**
  - **What conflicts (quotes)**  
    - RFC-0002 defines the PURL destination field as IID-only:  
      - `spec/06-rfcs/RFC-0002-transport.md` §7.4: **“Destination IID (raw bytes) 20 bytes”**  
    - Non-RFC relay docs suggest recipients may treat destination as IID *or DID*:  
      - `spec/01-transport-connectivity/relay-protocol.md` §Encapsulation Model (Normative): **“Destination IID sanity check: Receivers SHOULD verify the destination IID matches their own IID (or one of their DIDs)”**  
      - `spec/00-shared/layer-integration.md` §Relay Protocol Encapsulation Model: **“Destination IID sanity check … matches their own IID (or one of their DIDs)”** (same idea)
    - Device documents reuse the same shared `Endpoint` schema that allows `"type": "relay"` (so implementers may publish relay endpoints per-device):  
      - `spec/02-identity-trust/identity-document-schema.md` §Endpoint Object (Normative, shared with Transport layer): **`"type": "direct|relay|mailbox"`**  
      - Device documents contain `endpoints: Endpoint[]` (no prohibition on relay endpoints).
  - **Why this breaks interop**  
    If an implementer follows the non-RFC guidance, they may attempt “device-specific relay reachability” by treating the 20-byte destination field as a DID in some cases (or by publishing relay endpoints in device documents). An RFC-0002-conforming implementation will treat the destination strictly as an IID and route/validate accordingly. This yields failed connections and non-deterministic routing behavior in multi-device scenarios.
  - **Concrete file paths and sections**  
    - `spec/06-rfcs/RFC-0002-transport.md` §7.4, §7.6  
    - `spec/01-transport-connectivity/relay-protocol.md` §Encapsulation Model (Normative)  
    - `spec/00-shared/layer-integration.md` §Relay Protocol / Encapsulation Model (Normative)  
    - `spec/02-identity-trust/identity-document-schema.md` §Endpoint Object; §Device Document
  - **Suggested fix**  
    - Align all non-RFC docs to RFC-0002 by removing DID language from relay destination validation and explicitly stating: **PURL Destination field is always the destination *IID* (20 bytes).**  
    - Add a normative statement in `identity-document-schema.md` and `layer-integration.md` for v1: **Device documents MUST NOT include `relay` endpoints** (or MUST treat `relay` endpoints as identity-level only, not DID-addressable).  
    - Optionally add a “Future work” note describing how DID-addressed relay routing would require a new PURL field (e.g., destination-type discriminator) and an RFC revision.

- **Relay allocation multiplicity is ambiguous/contradictory: stable port model implies one active inbound allocation per IID, but RFC permits multiple (and does not define selection)**
  - **What conflicts (quotes)**  
    - RFC-0002 stable port model assumes a single lookup by IID:  
      - `spec/06-rfcs/RFC-0002-transport.md` §7.3: **“Relay … Routing key: Destination IID in packet header … Relay looks up active allocation for that IID”**  
    - RFC-0002 also states an explicit policy that allows multiple allocations per IID:  
      - `spec/06-rfcs/RFC-0002-transport.md` §7.13: **“Allocations per IID | 5”**  
    - Transport layer constants similarly imply multiple allocations:  
      - `spec/01-transport-connectivity/interfaces.md` Constants: **`MAX_RELAY_ALLOCATIONS: 5`**
  - **Why this breaks interop**  
    With multiple allocations for the same IID on the same relay, the relay has no normative rule for *which allocation/binding* receives forwarded traffic for that IID. Different relays (or different implementations of the same relay) could forward to different bound addresses, causing intermittent reachability and connection flapping. This is especially damaging when multiple devices under one IID are online.
  - **Concrete file paths and sections**  
    - `spec/06-rfcs/RFC-0002-transport.md` §7.3, §7.8–§7.10, §7.13  
    - `spec/01-transport-connectivity/interfaces.md` constants (`MAX_RELAY_ALLOCATIONS`)
  - **Suggested fix**  
    Choose **one** v1 model and make it explicit in RFC-0002:
    1. **Single-allocation-per-(relay,iid)** model (recommended for v1):  
       - Change §7.13 “Allocations per IID” from 5 → **1 per relay** (or “1 active inbound allocation per (relay,iid)”).  
       - Specify: a new successful `/allocate` **replaces** the prior allocation (or is rejected with a specific error).  
    2. If multiple allocations must remain supported, then RFC-0002 MUST define a deterministic selection rule for inbound routing, e.g.:  
       - “Forward to the allocation with the most recent valid UDP binding/rebind timestamp” (and define tie-breaking).  
       - And clarify what “active allocation” means precisely.

- **Recovery contestation is defined in layer docs + integration registry, but RFC-0001 defines contestation differently and does not define “contest documents”**
  - **What conflicts (quotes)**  
    - RFC-0001 defines contestation via a higher-sequence IDOC update:  
      - `spec/06-rfcs/RFC-0001-identity-document.md` §9.6: **“Contestation: During cooldown, the original key holder may publish a higher-sequence update signed with the old key. If valid, this supersedes the recovery attempt.”**  
    - Layer doc introduces a separate contest document and DHT key:  
      - `spec/02-identity-trust/recovery-mechanisms.md` §Contestation: **“publish a contest document”** and **“DHT Key: `SHA256("post-urbit:contest:" || iid)`”**  
    - Integration doc “Domain Separator Registry (Normative)” includes contest separators/keys not present in RFC-0001:  
      - `spec/00-shared/layer-integration.md` §Domain Separator Registry: entries for **`post-urbit:recovery-contest:v1:`** and **`post-urbit:contest:`**
  - **Why this breaks interop**  
    One implementation may treat a “contest document in DHT” as a protocol-valid reason to reject/hold a recovery update, while another implementation (following RFC-0001 only) will not check for it and will accept the recovery once `cooldown_expires_at` passes. That creates divergent views of identity validity (a hard interop and security failure).
  - **Concrete file paths and section numbers**  
    - `spec/06-rfcs/RFC-0001-identity-document.md` §9.6  
    - `spec/02-identity-trust/recovery-mechanisms.md` §Contestation  
    - `spec/00-shared/layer-integration.md` §Domain Separator Registry (Normative)
  - **Suggested fix**  
    - Align to RFC-0001: remove contest documents from `recovery-mechanisms.md` and remove the contest-related entries from `layer-integration.md`’s registry **OR** explicitly mark them **non-normative / experimental** and state: “contest documents MUST NOT affect identity validity in v1.”  
    - If contest documents are desired, they must be added to **RFC-0001** with complete normative processing rules (including whether they override cooldown).

- **Revocation discovery/storage is normative in layer docs but missing in RFC-0001 DHT storage section**
  - **What conflicts (quotes)**  
    - Layer revocation spec requires DHT storage for revocations:  
      - `spec/02-identity-trust/revocation.md` §DHT Storage (Normative): **“Revocations MUST be stored in DHT … Key = SHA256("post-urbit:revocation:" || iid)”**, TTL 365 days, and client lookup behavior.  
    - RFC-0001 DHT storage section defines identity/genesis/device records and device revocation, but does not define DHT records for `key_revocation` / `identity_revocation`:  
      - `spec/06-rfcs/RFC-0001-identity-document.md` §12.2–§12.6 covers identity, genesis, device index, device docs, and **device revocation** only.
  - **Why this breaks interop**  
    Revocation status affects transport security decisions (RFC-0002 includes `REVOKED_IDENTITY` / `REVOKED_KEY` errors), mailbox verification windows, and identity acceptance. If revocation storage/discovery is not specified in the authoritative RFC, implementations can (and will) diverge on where to publish/find revocations. Nodes will disagree on whether an identity/key is revoked, leading to incompatible connection acceptance and message verification outcomes.
  - **Concrete file paths and section numbers**  
    - `spec/02-identity-trust/revocation.md` §DHT Storage (Normative)  
    - `spec/06-rfcs/RFC-0001-identity-document.md` §12 (missing key/identity revocation DHT records)
  - **Suggested fix**  
    - Add to **RFC-0001** §12 a new subsection (e.g., “12.8 Revocation Records”) defining:  
      - DHT key derivation prefix `post-urbit:revocation:`  
      - Value format (JCS JSON) for both revocation types  
      - TTL and conflict rules  
      - Required verification steps for DHT nodes  
    - Then update `revocation.md` to explicitly say it is aligned with RFC-0001 §12.8 and remove any divergences.

- **RFC-0003 does not specify the wire schema for `group_state_update`, but includes it in the normative message type registry**
  - **What conflicts (quotes)**  
    - RFC-0003 lists `group_state_update` but punts to a non-RFC doc:  
      - `spec/06-rfcs/RFC-0003-messaging.md` §8.2: **“`group_state_update` … See `spec/03-messaging-sync/group-messaging.md` §GroupStateUpdate”**
  - **Why this breaks interop**  
    The message *type registry* is part of the wire protocol. If the authoritative RFC does not define the schema, validation rules, and ordering/conflict rules for that type, two implementations can produce different plaintext JSON for the same logical operation while still claiming RFC-0003 compliance. Group membership convergence and authorization checks will then diverge.
  - **Concrete file paths and section numbers**  
    - `spec/06-rfcs/RFC-0003-messaging.md` §8.2  
    - The referenced non-authoritative definition: `spec/03-messaging-sync/group-messaging.md` §GroupStateUpdate and §Conflict Resolution
  - **Suggested fix**  
    - Move the `GroupStateUpdate` plaintext schema + required fields + version ordering and conflict resolution rules into **RFC-0003** (either §6 Group Messaging or §8 Message Types).  
    - Alternatively (less desirable): remove `group_state_update` from RFC-0003’s v1 registry and mark group membership operations out-of-scope for RFC-0003 v1.

### HIGH

- **Stream initiation and stream multiplicity rules are defined in `layer-integration.md` but not in RFC-0002**
  - **What conflicts (quotes)**  
    - Non-RFC doc defines stream lifecycle and “duplicate stream type” behavior:  
      - `spec/00-shared/layer-integration.md` §QUIC Stream Initiation Rules (Normative): **“Each peer MAY open at most one outgoing bidirectional stream of each type… Opening a second stream… is a protocol error (close with DUPLICATE_STREAM_TYPE 0x108 per RFC-0002 §9.2).”**  
    - RFC-0002 defines the error code registry including `0x108 DUPLICATE_STREAM_TYPE`, but does **not** define the “at most 1 per direction for Identity/Sync” rule:  
      - `spec/06-rfcs/RFC-0002-transport.md` §9.2 includes `0x108` but §6 does not define stream multiplicity constraints.
  - **Why this risks interop**  
    Two implementations both “RFC-0002 compliant” could choose different stream usage patterns (single long-lived Identity/Sync streams vs. multiple per operation). One may close connections with `0x108`, another may accept. That won’t necessarily break bytes-on-wire compatibility, but it can break real interoperability at the session level.
  - **Concrete file paths and sections**  
    - `spec/00-shared/layer-integration.md` §QUIC Stream Initiation Rules  
    - `spec/06-rfcs/RFC-0002-transport.md` §6, §9.2
  - **Suggested fix**  
    Add a short normative subsection to RFC-0002 §6 (e.g., “6.5 Stream Multiplicity Rules”) that either:
    - formally adopts the “at most one long-lived Identity/Sync stream per direction” rule, or  
    - explicitly allows multiple and defines receiver behavior.
