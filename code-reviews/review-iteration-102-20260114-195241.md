## Summary
Several core specs are very close to implementable, but there are still a few places where two conforming implementations could generate incompatible bytes or accept/reject different artifacts. The most serious problems are around **group membership update semantics** (RFC‑0003 vs layer docs, plus missing signature rules), **package signature verification when manifest extensions are present**, and **NAT hole‑punch probe wire encoding ambiguity**.

## Issues Found

### BLOCKING

- **Group State Update format is inconsistent across specs, and RFC‑0003’s definition is internally inconsistent**
  - **What conflicts (quotes)**
    - RFC‑0003 defines `group_state_update` as:
      - `spec/06-rfcs/RFC-0003-messaging.md` §8.6:
        ```json
        {
          "type": "group_state_update",
          ...
          "content": {
            "action": "add_member",
            "group_id": "<20-char-base32>",
            "target_iid": "<32-char-base32>",
            "version": "5",
            "signature": "<base64-ed25519-sig>"
          }
        }
        ```
        And the table states: “`group_id` … **20-char Crockford Base32 group identifier**”.
    - Group layer doc defines GroupId as 20 bytes ⇒ 32 chars:
      - `spec/03-messaging-sync/group-messaging.md` **Group Identifier (Normative)**:
        > “A Group Identifier (GroupId) is a **20-byte value encoded as a 32-character** lowercase Crockford Base32 string…”
    - Group layer doc also forbids any content signature field:
      - `spec/03-messaging-sync/group-messaging.md` **Wire Format (Normative)**:
        > “**No separate signature field exists in the content** – authentication is via the **PUSE envelope signature**”
    - Group versioning/conflict rules differ completely:
      - `spec/03-messaging-sync/group-messaging.md` **Version Format (Normative)**:
        > `"<logical_clock>.<first_8_chars_of_actor_iid>"`
      - vs RFC‑0003 §8.6: `version` is just `"5"` and conflict resolution references “lexicographically lowest IID” but does not define the signature scheme.
  - **Why this breaks interop**
    - Implementations following RFC‑0003 will produce/expect:
      - a **different `group_id` string length** (20 chars vs 32 chars),
      - a **different `version` type/ordering**, and
      - a **required `signature` field** that other implementations (following layer docs) will not include and/or will reject.
    - Even within RFC‑0003, “20‑char Base32” contradicts the rest of the system’s encoding rules (20 bytes → 160 bits → **32 Base32 chars**). This makes it impossible to implement consistently.
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0003-messaging.md` §8.6
    - `spec/03-messaging-sync/group-messaging.md` “Group Identifier (Normative)”, “Membership Operations”, “Wire Format (Normative)”
    - (Also impacted: `spec/03-messaging-sync/interfaces.md` where `GroupId` is documented as 32‑char Base32.)
  - **Suggested fix**
    - Update **RFC‑0003 §8.6** to align with the intended v1 group model (and then align layer docs to the RFC text):
      1. Define `group_id` as **32‑character Crockford Base32** (representing 20 raw bytes).
      2. Remove the `content.signature` field entirely and normatively state that **PUSE envelope signature** authenticates group state updates (consistent with the rest of RFC‑0003).
      3. Pick exactly one versioning scheme:
         - Either adopt `group-messaging.md`’s `"<logical_clock>.<actor_suffix>"` + conflict ordering rules, **or** specify a purely numeric version and remove HLC-style rules from the layer doc.
      4. Ensure `action` naming matches exactly one registry (either the RFC list or the layer union types), with normative “MUST/ MUST NOT” language.

- **RFC‑0003 includes a cryptographic field (`content.signature`) without a normative signing/verification construction**
  - **What conflicts (quotes)**
    - `spec/06-rfcs/RFC-0003-messaging.md` §8.6:
      > “`signature`: Base64 Ed25519 signature by admin”
    - No domain separator, canonicalization (JCS vs raw JSON), or byte construction is defined for that signature.
    - Contradicts `spec/03-messaging-sync/group-messaging.md` which states there is no separate signature and relies on PUSE.
  - **Why this breaks interop**
    - Two implementations could both “support” RFC‑0003 yet sign different bytes (e.g., JCS vs non‑canonical JSON vs concatenated fields), making signatures unverifiable cross‑implementation.
    - Others may ignore `content.signature` and accept messages that strict implementations reject (and vice‑versa).
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0003-messaging.md` §8.6
    - Related: `spec/03-messaging-sync/group-messaging.md` “Membership Operations” and “Wire Format (Normative)”
  - **Suggested fix**
    - Preferred: **remove** `content.signature` from RFC‑0003 and make PUSE signature the sole authentication mechanism for group state updates.
    - If you keep it: add a **fully specified signature scheme** (domain separator, canonicalization, exact fields, and rejection criteria) and explain how it composes with the PUSE signature (to avoid “double-sign” confusion).

- **App package signature verification is ambiguous when `manifest.json` contains extension fields**
  - **What conflicts (quotes)**
    - `spec/04-app-runtime/manifest-schema.md` **Forward Compatibility (Normative)**:
      > “**Unknown fields MUST be ignored:** Validators MUST ignore unrecognized top-level and nested fields in `manifest.json`.”
    - `spec/05-ux-packaging/app-distribution.md` **Manifest Extensions for Distribution** introduces new top-level fields:
      ```json
      {
        "distribution": { ... },
        "files": { ... }
      }
      ```
    - `spec/05-ux-packaging/app-distribution.md` **Signing Process**:
      > “Canonicalize `manifest.json` (JCS)… compute `SHA256(canonical_manifest_bytes)`…”
  - **Why this breaks interop**
    - A conforming validator might “ignore unknown fields” by parsing into a fixed struct and **dropping** `distribution` (or any future extension) before hashing → signature verification fails.
    - Another conforming implementation that preserves all fields (generic JSON map) will compute a different manifest hash and accept the package. Result: different nodes accept/reject the same `.postapp`.
  - **Concrete file paths and section numbers**
    - `spec/04-app-runtime/manifest-schema.md` “Forward Compatibility (Normative)”
    - `spec/05-ux-packaging/app-distribution.md` “Manifest Extensions for Distribution”, “Signing Process”, “Verification Process”
  - **Suggested fix**
    - Add a **normative rule** to `manifest-schema.md` and/or `app-distribution.md`:
      - For signature verification, implementations **MUST compute the manifest hash over the complete manifest JSON object including all fields**, even those “unknown” to the validator.
      - Therefore verifiers **MUST parse `manifest.json` into a representation that preserves unknown fields** (e.g., a generic JSON value tree/map), and only apply “ignore unknown fields” to *semantic validation*, not to hashing.
    - Optionally: formally incorporate `distribution` into the manifest schema (still allowing future unknowns).

- **Hole-punch “probe packet” wire format is underspecified/ambiguous**
  - **What conflicts (quotes)**
    - `spec/01-transport-connectivity/nat-traversal.md` **Probe Packet Format**:
      > “Sender IID (truncated, first 8 bytes) 8 bytes”
      and
      > “Transaction ID (from coordination) 16 bytes”
    - But coordination messages earlier use JSON strings:
      ```json
      "transaction_id": "..."
      ```
      with no encoding rules, and the Transport TS interface uses:
      - `spec/01-transport-connectivity/interfaces.md` **HolePunchRequest**:
        ```typescript
        interface HolePunchRequest {
          transactionId: string;
          ...
        }
        ```
  - **Why this breaks interop**
    - “first 8 bytes” is ambiguous: first 8 bytes of **raw IID (20 bytes)**? or first 8 bytes of the **Base32 string**? or hash prefix?
    - `transaction_id` is “16 bytes” in the UDP probe but “string” in the coordination JSON, with no specified encoding (hex? base64? uuid?). Two implementations can’t interoperate reliably for NAT hole punching.
  - **Concrete file paths and section numbers**
    - `spec/01-transport-connectivity/nat-traversal.md` “Hole Punching” → “Probe Packet Format”
    - `spec/01-transport-connectivity/interfaces.md` “Hole Punching Interface” → `HolePunchRequest`
  - **Suggested fix**
    - Define transaction ID encoding end-to-end:
      - e.g., `transaction_id` in JSON MUST be **base64url(no padding) of 16 raw bytes**, and probe packet’s 16 bytes are `base64url_decode(transaction_id)`.
    - Define “Sender IID truncated” precisely:
      - e.g., `sender_iid_trunc = decode_base32(sender_iid)[0:8]` (first 8 bytes of the 20-byte raw IID).
    - Add explicit “MUST reject” rules for malformed lengths/encodings.

### HIGH

- **QUIC/TLS certificate wording is inconsistent and can mislead implementers**
  - **What conflicts (quotes)**
    - `spec/01-transport-connectivity/quic-integration.md` **TLS Configuration**:
      > “Signature: Ed25519 (for identity binding)”
    - But the integration glue and RFC are explicit that certificate algorithms are not used for identity:
      - `spec/00-shared/layer-integration.md` **Certificate Acceptance (Client MUST)**:
        > “Clients MUST accept ANY certificate… Signature algorithm (RSA, ECDSA, Ed25519, etc. all acceptable)”
      - `spec/06-rfcs/RFC-0002-transport.md` §4.3:
        > “Implementations MUST accept any valid self-signed certificate…”
  - **Why this breaks interop**
    - Not a wire-format break, but it can cause implementers to incorrectly restrict TLS certificate algorithms and reject otherwise-conforming peers.
  - **Concrete file paths and section numbers**
    - `spec/01-transport-connectivity/quic-integration.md` “TLS Configuration”
    - `spec/00-shared/layer-integration.md` “QUIC TLS Certificate Policy”
    - `spec/06-rfcs/RFC-0002-transport.md` §4.3
  - **Suggested fix**
    - Edit `quic-integration.md` to clarify that Ed25519 refers to **Post‑TLS identity handshake signatures**, not TLS certificate signature requirements. Explicitly state “TLS cert algorithm is unrestricted”.

- **Discovery (PUDS) response port endianness relies on a global convention but is not referenced locally**
  - **What conflicts (quote)**
    - `spec/01-transport-connectivity/nat-traversal.md` Discovery Response includes:
      > “Observed Port 2 bytes”
    - Endianness is only specified globally:
      - `spec/00-shared/layer-integration.md` “Endianness: All multi-byte integers … big-endian unless explicitly stated otherwise.”
  - **Why this breaks interop**
    - Many implementers will follow the global rule, but some will treat “2 bytes” as host-endian or little-endian unless locally specified; this can break NAT discovery interoperability.
  - **Concrete file paths and section numbers**
    - `spec/01-transport-connectivity/nat-traversal.md` “Discovery Protocol (STUN-like)”
    - `spec/00-shared/layer-integration.md` “Global Conventions → Endianness”
  - **Suggested fix**
    - Add “Observed Port: uint16 big-endian” explicitly in `nat-traversal.md`.
