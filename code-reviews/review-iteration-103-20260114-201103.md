## Summary
The spec is close to implementable, but there are a couple of cross-document contradictions that will cause two “conforming” implementations to produce incompatible wire plaintext and/or make different revocation decisions. Because the RFCs in `spec/06-rfcs/` are authoritative, the non-RFC layer docs must be aligned to those RFC definitions.

## Issues Found

### BLOCKING

- **Group membership update wire schema contradicts RFC-0003 (different JSON shape + different action vocabulary)**
  - **What conflicts (quotes)**
    - RFC (authoritative) defines `group_state_update` as:
      - `spec/06-rfcs/RFC-0003-messaging.md` §8.6:
        ```json
        {
          "type": "group_state_update",
          "timestamp": "2025-01-15T12:00:00Z",
          "sequence": "100",
          "content": {
            "action": "add_member",
            "group_id": "<32-char-base32>",
            "target_iid": "<32-char-base32>",
            "version": "5.b1anasr5"
          }
        }
        ```
        And states:
        > `action`: one of `add_member`, `remove_member`, `promote_admin`, `demote_admin`, `update_info`, `rotate_sender_key`
    - Layer doc defines a different content object and different action naming:
      - `spec/03-messaging-sync/group-messaging.md` “Membership Operations”:
        ```ts
        interface GroupStateUpdate {
          group_id: string;
          version: string;
          actor_iid: IdentityIdentifier;
          action: GroupAction;
          timestamp: string;
          previous_version: string | null;
        }

        type GroupAction =
          | { type: 'member_added'; ... }
          | { type: 'member_removed'; ... }
          | { type: 'member_left'; ... }
          | { type: 'role_changed'; ... }
          | { type: 'settings_changed'; ... };
        ```
      - And further mandates:
        - `spec/03-messaging-sync/group-messaging.md` “Wire Format (Normative)”:
          > “Action types MUST match the `GroupAction` union: `member_added`, `member_removed`, `member_left`, `role_changed`, `settings_changed`”
  - **Why this breaks interop**
    - The PUSE plaintext JSON is part of the AEAD plaintext and is signed/verified as a semantic payload by applications. If one implementation follows RFC-0003 and sends `content.action: "add_member"` with `target_iid`, while another expects `content.action: { type: "member_added", ... }` with different fields (`actor_iid`, `previous_version`), they will not understand each other’s group state updates. This is a hard interoperability break for group membership convergence.
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0003-messaging.md` §8.6 (authoritative)
    - `spec/03-messaging-sync/group-messaging.md` “Membership Operations” and “Wire Format (Normative)”
  - **Suggested fix**
    - Choose **one** wire schema. Since RFCs are authoritative, update `spec/03-messaging-sync/group-messaging.md` to match RFC-0003 §8.6 exactly:
      - Replace the `GroupStateUpdate` content schema to use RFC fields (`action`, `group_id`, `target_iid` when applicable, `version`) and RFC action vocabulary.
      - If the richer DAG/HLC model from `group-messaging.md` is desired, then **RFC-0003 must be updated** to carry those fields; but as written, layer docs must align “down” to RFC.
    - Add an explicit mapping section if you want to preserve richer internal state:
      - e.g., “internal model MAY maintain `previous_version` and `actor_iid`, but wire format MUST be RFC-0003 §8.6; `actor_iid` is derived from PUSE sender IID.”

- **Revocation DHT “multiple records” resolution is inconsistent (earliest vs highest timestamp, and field name mismatch)**
  - **What conflicts (quotes)**
    - Layer doc says:
      - `spec/02-identity-trust/revocation.md` “DHT Storage (Normative)”:
        > “Multiple revocations for same IID: keep highest `effective_at` timestamp”
    - RFC says (and uses a different field name):
      - `spec/06-rfcs/RFC-0001-identity-document.md` §12.7:
        > “**Multiple Records:** If multiple revocations exist for the same IID (due to network partitions), accept the one with the earliest `revoked_at` timestamp.”
    - But the key/identity revocation schemas in both RFC-0001 §10 and `spec/02-identity-trust/revocation.md` use `effective_at`, not `revoked_at`.
  - **Why this breaks interop**
    - Two implementations can both be “conforming” to their chosen doc and still make opposite choices about which revocation is authoritative when multiple values exist in the DHT:
      - Impl A (revocation.md) picks the *latest* effective time.
      - Impl B (RFC-0001) picks the *earliest* time (and may even fail because it looks for `revoked_at` that doesn’t exist).
    - This affects whether identities/keys are considered revoked, which directly impacts transport acceptance and message verification across nodes—an interoperability and security-critical behavior.
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0001-identity-document.md` §12.7 (authoritative, but internally inconsistent with its own schema field names)
    - `spec/02-identity-trust/revocation.md` “DHT Storage (Normative)”
  - **Suggested fix**
    - Fix **RFC-0001** first (authoritative) to be internally consistent:
      - Replace `revoked_at` with `effective_at` in RFC-0001 §12.7 for key/identity revocations (device revocation can keep `revoked_at`).
      - Specify a single deterministic rule, e.g.:
        - “If multiple valid revocations exist for the same IID, select the revocation with the **earliest** `effective_at` timestamp” (security-conservative), **or** explicitly justify and standardize “latest wins”.
    - Then update `spec/02-identity-trust/revocation.md` to match RFC-0001’s corrected rule.

### HIGH

- **Test vectors contradict the ratchet header placement (even though labeled “placeholder”), increasing implementation risk**
  - **What conflicts (quotes)**
    - `spec/00-shared/test-vectors.md` Test Vector 11 (Placeholder) says:
      > “The encrypted header (inside ciphertext) contains: Ratchet Header: …”
    - But the messaging layer docs state the opposite:
      - `spec/03-messaging-sync/double-ratchet.md` “Header Format”:
        > “The ratchet header is placed in the **PUSE header extension** … and is **NOT encrypted**.”
      - RFC-0003 §3.4 and §4.* are consistent with “header extension (AAD)”.
  - **Why this matters**
    - Even with a warning, this is a common “footgun”: implementers often copy test-vector sections. This inconsistency can lead to incompatible encoders/decoders or incorrect AAD construction.
  - **Concrete file paths and section numbers**
    - `spec/00-shared/test-vectors.md` Test Vector 11
    - `spec/03-messaging-sync/double-ratchet.md` “Header Format”
    - `spec/06-rfcs/RFC-0003-messaging.md` §3.4 (authoritative)
  - **Suggested fix**
    - Edit Test Vector 11 placeholder text to explicitly match RFC-0003:
      - Replace “encrypted header (inside ciphertext)” with “ratchet header extension (AAD, not encrypted)”.
    - Or remove the placeholder entirely and only reference RFC-0003 until real vectors exist.

- **Device “transport key” appears in node-daemon key hierarchy but is explicitly removed/unused in v1 elsewhere**
  - **What conflicts (quotes)**
    - `spec/05-ux-packaging/node-daemon.md` “Key Hierarchy” includes:
      > “Device transport key (X25519)”
    - While the integration/identity docs state v1 does not use it:
      - `spec/00-shared/layer-integration.md` “Device Document Structure (canonical)” note:
        > “`device_transport_key` removed in v1 (unused; handshake uses device signing key)”
      - `spec/02-identity-trust/identity-document-schema.md` “Device Document”:
        > “Note: `device_transport_key` (X25519) is not included. Transport-level key exchange uses the device signing key via the identity handshake protocol.”
  - **Why this matters**
    - Not a wire-format break, but it will confuse implementers and risks divergent behavior (some may try to use a device X25519 for handshake/transport auth).
  - **Concrete file paths and section numbers**
    - `spec/05-ux-packaging/node-daemon.md` “Key Hierarchy”
    - `spec/00-shared/layer-integration.md` “Device Document Structure (canonical)” note
    - `spec/02-identity-trust/identity-document-schema.md` “Device Document”
  - **Suggested fix**
    - In `node-daemon.md`, mark “device transport key” as **reserved for future** and **NOT USED in v1**, or remove it from the v1 hierarchy section.

- **Packaging docs don’t consistently restate the global “Base64 no padding” requirement**
  - **What conflicts**
    - Global convention:
      - `spec/00-shared/layer-integration.md` “Encoding”:
        > “Keys/signatures … Base64 standard (no padding)”
    - Packaging signing sections (e.g., `spec/05-ux-packaging/app-distribution.md`) describe `signature` as base64 but don’t always explicitly say “no padding” in the local section.
  - **Why this matters**
    - Likely fine if implementers follow the shared conventions, but packaging is often implemented by a separate team; restating avoids accidental padded Base64 emission.
  - **Concrete file paths**
    - `spec/00-shared/layer-integration.md` “Encoding”
    - `spec/05-ux-packaging/app-distribution.md` “SIGNATURE File Format (JSON)”
  - **Suggested fix**
    - Add one explicit sentence in each packaging signature format section: “`signature` MUST be Base64 standard alphabet with no padding.”
