## Summary
The three authoritative RFCs (RFC-0001/2/3) are broadly consistent with each other and with most layer documents. However, there is at least one remaining **wire-level canonicalization ambiguity in an RFC** that can cause two conforming implementations to generate/verifiy different bytes for the same logical mailbox endpoint, breaking interoperability.

## Issues Found

### BLOCKING

- **Mailbox token URL canonicalization is not fully canonical (IDNA + percent-encoding ambiguity)**
  - **What conflicts (quote specific text from documents)**
    - RFC-0003 defines mailbox URL canonicalization but does not define IDNA handling and explicitly says to preserve percent-encoding:
      - `spec/06-rfcs/RFC-0003-messaging.md` §7.3 “URL Canonicalization (Normative)”:
        - “**Host:** Lowercase, no trailing dot; IPv6 literals MUST be bracketed…”
        - “**Percent-encoding:** **Preserve existing percent-encoding; do NOT decode or re-encode**”
      - It then requires canonicalization before signing, and later requires strict field-encoding compliance:
        - `spec/06-rfcs/RFC-0003-messaging.md` §7.3 “Signature construction”:
          - `mailbox_url = canonicalize_mailbox_url(mailbox_url)  # MUST canonicalize`
        - `spec/06-rfcs/RFC-0003-messaging.md` §7.3 “Bearer Token Wire Format (Normative)”:
          - “Servers MUST reject tokens where any field encoding differs from these rules.”
  - **Why this breaks interop**
    - The mailbox token signature binds `mailbox_url` bytes. Without a single, fully specified canonicalization:
      - **IDNA/Unicode hostnames:** One implementation may accept and sign `https://müller.example/` (Unicode) while another normalizes to punycode `https://xn--mller-kva.example/` (or rejects). Token verification will fail across implementations.
      - **Percent-encoding normalization:** “Preserve existing percent-encoding” allows multiple “canonical” byte strings for equivalent URLs (e.g., `%2F` vs `%2f`). If verifiers enforce canonicalization (as required), different canonicalizers can reject each other’s tokens.
    - This is a **wire compatibility** problem: two conforming implementations can produce different bytes for the “same” mailbox URL, and then fail verification.
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0003-messaging.md` §7.3 (URL Canonicalization; Bearer Token Wire Format; Signature construction)
  - **Suggested fix**
    - Tighten RFC-0003 §7.3 to make `mailbox_url` canonicalization truly canonical:
      1. **Define hostname requirements**: either
         - (Preferred) **MUST be ASCII A-label (punycode) only**; reject non-ASCII hosts, **or**
         - **MUST apply IDNA ToASCII (UTS #46, transitional=false)** and lowercase the resulting A-label.
      2. **Define percent-encoding canonicalization**:
         - Either **forbid percent-encoding entirely** in `mailbox_url` (simplest: constrain to `https://host[:port]/` with path exactly `/`), **or**
         - Require normalizing percent-escapes to **uppercase hex** and forbidding non-normalized forms.
      3. State explicitly that verifiers MUST:
         - Reject tokens where `mailbox_url` is not already in canonical form, and
         - Use the canonical form when reconstructing signature input.

### HIGH

- **`group-messaging.md` contains post-RFC normative text but still shows deprecated on-wire examples**
  - **What conflicts (quote specific text from documents)**
    - The layer doc states the RFC wire format is normative and deprecated formats MUST NOT be used:
      - `spec/03-messaging-sync/group-messaging.md` under “Wire Format (Normative per RFC-0003 §8.6)”:
        - “All group membership operations MUST be sent as PUSE messages with `"type": "group_state_update"`”
        - “Implementations MUST reject messages with `"type": "group_event"`”
        - “Action types MUST match RFC-0003 §8.6: `add_member`, `remove_member`, …”
    - But later examples show a different (older) structure with nested `action: { type: "member_left", ... }` and fields like `previous_version`, `actor_iid` inside content:
      - `spec/03-messaging-sync/group-messaging.md` “Leave” example:
        - `"action": { "type": "member_left", ... }`
      - `spec/03-messaging-sync/group-messaging.md` “Remove (Kick)” example:
        - `"action": { "type": "member_removed", ... }`
    - RFC-0003’s authoritative schema uses `action` as a string and does not include these nested action objects:
      - `spec/06-rfcs/RFC-0003-messaging.md` §8.6:
        - `"action": "add_member" | ...`
  - **Why this breaks interop**
    - Even if the RFC is authoritative, these examples are in a file that claims to describe the protocol; implementers often copy examples. If implemented, recipients that follow RFC-0003 will reject these messages, causing group membership divergence.
  - **Concrete file paths and section numbers**
    - `spec/03-messaging-sync/group-messaging.md` “Membership Operations” and the “Leave” / “Remove (Kick)” examples
    - `spec/06-rfcs/RFC-0003-messaging.md` §8.6
  - **Suggested fix**
    - Replace or clearly label the “Leave” and “Remove” examples as **obsolete** and provide RFC-0003-compliant examples:
      - Use `"type": "group_state_update"` with `content: { action: "remove_member", group_id, target_iid, version }`.
    - Add a short “DO NOT IMPLEMENT” banner above any legacy examples (or delete them).

- **IDOC envelope parsing guidance omits mandatory canonical-JCS enforcement and trailing-bytes handling**
  - **What conflicts (quote specific text from documents)**
    - RFC-0001 requires JCS-canonical JSON inside the IDOC envelope:
      - `spec/06-rfcs/RFC-0001-identity-document.md` §6.2:
        - “The JSON inside IDOC envelopes … MUST also be JCS-canonicalized…”
    - The parsing algorithm example does not check JCS canonicality and does not require `len(data) == 9 + length`:
      - `spec/06-rfcs/RFC-0001-identity-document.md` §11.4:
        - `assert len(data) >= 9 + length, "Truncated"` (no equality check; no canonicality check)
    - Layer identity doc reiterates canonical-JCS rejection:
      - `spec/02-identity-trust/identity-document-schema.md` “JSON Canonicalization (Normative)”:
        - “Implementations MUST reject IDOC envelopes where the JSON is not JCS-canonical”
  - **Why this breaks interop**
    - Conforming implementations must reject non-JCS-canonical envelope JSON. If implementers follow the RFC parsing snippet literally, they may accept and store non-canonical or “extra trailing bytes” variants, undermining:
      - Byte-identical DHT refresh semantics (genesis and identity),
      - Stable byte equality expectations across nodes, and
      - Consistent canonical wire bytes in test vectors.
    - This is primarily a **spec clarity / implementer trap**, not a logical RFC contradiction.
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0001-identity-document.md` §6.2 and §11.4
    - `spec/02-identity-trust/identity-document-schema.md` “JSON Canonicalization (Normative)”
  - **Suggested fix**
    - Amend RFC-0001 §11.4 to either:
      - Mark the code explicitly “NON-NORMATIVE (omits canonicality checks)”, **or**
      - Add explicit steps:
        - Reject if `len(data) != 9 + length`
        - Reject if `json_bytes` are not exactly `JCS(parse(json_bytes))`

### MEDIUM

- **Duplicated shared types risk drift (`DhtResult`, endpoint shapes, etc.)**
  - **What conflicts (quote specific text from documents)**
    - Shared type defined as authoritative in glue doc:
      - `spec/00-shared/layer-integration.md` “DhtResult” interface.
    - Transport redefines it and says it “MUST match shared definition”:
      - `spec/01-transport-connectivity/interfaces.md`:
        - “DhtResult is defined in … layer-integration.md (authoritative) … Duplicated here … MUST match shared definition”
  - **Why this breaks interop**
    - Not an immediate wire break, but duplications commonly diverge over time (field additions/renames), causing implementation incompatibilities at API boundaries between layers/modules.
  - **Concrete file paths and section numbers**
    - `spec/00-shared/layer-integration.md` (Common TypeScript Types)
    - `spec/01-transport-connectivity/interfaces.md` (Discovery Service Interface)
  - **Suggested fix**
    - Define shared types once (or generate) and have other docs reference by inclusion/link.
    - If duplication must remain, add a small “checksum” section or a CI lint rule comparing the duplicated blocks.

- **Some layer docs restate RFC-defined wire rules without consistently pointing to the RFC sections**
  - **What conflicts (quote specific text from documents)**
    - Multiple places say “see RFC … authoritative” but then include partial framing/format rules (risking divergence).
  - **Why this breaks interop**
    - Medium risk of future drift; readers may implement from layer docs and miss subtle RFC constraints.
  - **Concrete file paths and section numbers**
    - `spec/01-transport-connectivity/quic-integration.md` (stream framing summary)
    - `spec/00-shared/layer-integration.md` (stream framing summary)
  - **Suggested fix**
    - Replace restated rules with short references and only include deltas/implementation notes.
