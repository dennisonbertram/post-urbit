## Summary
Across the three authoritative RFCs, the core wire formats (IDOC, QUIC stream framing, PURL, PUSE) are mostly consistent with the layer docs. However, there are several **BLOCKING** gaps/ambiguities in the authoritative RFCs that would allow two “conforming” implementations to make incompatible choices—most notably around **Mailbox addressing**, **2DH initial decrypt key selection across key rotations**, **timestamp acceptance rules in IDOCs**, and **group state update conflict ordering**.

## Issues Found

### BLOCKING

- **Mailbox protocol cannot be implemented interoperably (recipient/inbox addressing undefined; group messages make it worse)**
  - **What conflicts (quotes)**
    - RFC defines mailbox store/retrieve endpoints without any recipient/inbox discriminator:
      - `spec/06-rfcs/RFC-0003-messaging.md` §7.4.1:  
        > `POST /messages ... <PUSE envelope bytes>`
      - `spec/06-rfcs/RFC-0003-messaging.md` §7.4.2:  
        > `GET /messages?cursor=<opaque-cursor>&limit=100`
    - Token schema frames `iid` as the caller identity, and store adds a sender-binding check:
      - `spec/06-rfcs/RFC-0003-messaging.md` §7.4.1:  
        > “Mailbox servers MUST validate that the sender IID in the PUSE envelope header matches the IID in the authenticated bearer token…”
    - But PUSE “recipient” is not necessarily a recipient IID (group messages use group_id in the recipient field):
      - `spec/06-rfcs/RFC-0003-messaging.md` §3.2:  
        > `Recipient IID/GroupID (raw bytes)      │ 20 bytes`
    - Layer docs explicitly say offline group delivery uses mailbox:
      - `spec/03-messaging-sync/group-messaging.md` §Delivery:  
        > “For each offline member: … determine mailbox … send to mailbox”
  - **Why this breaks interop**
    - A mailbox server must know **which inbox** to store into and later retrieve from. The current RFC does not normatively define whether:
      1) a mailbox endpoint is **single-tenant** (one identity per host), or  
      2) the mailbox is **multi-tenant** and indexes by some value (recipient IID?) extracted from the request.
    - Even if you assume “index by recipient from the envelope header,” that fails for **group envelopes**, whose recipient field is a **group_id**, not the identity who is retrieving. So two conforming mailbox implementations could:
      - (A) store by `token.iid`,
      - (B) store by PUSE `recipient` field,
      - (C) be single-tenant and store everything,
      and clients cannot reliably interoperate across these choices.
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0003-messaging.md` §3.2, §7.4.1–§7.4.3
    - `spec/03-messaging-sync/group-messaging.md` §Delivery
  - **Suggested fix**
    - Make mailbox addressing explicit in **RFC-0003 (authoritative)** by adding one of:
      1) **Path-based tenanting (recommended for clarity):**  
         - `POST /messages/{recipient_iid}` store, `GET /messages/{recipient_iid}` retrieve, `DELETE /messages/{recipient_iid}` delete, where `{recipient_iid}` is the mailbox owner IID (Base32).  
         - Require `token.iid == {recipient_iid}` for retrieve/delete, and require `PUSE.sender_iid == token.iid` only on store **when the token is a sender-auth token** (or define a separate sender token vs recipient token).
      2) **Header-based tenanting:**  
         - Add required header `X-Post-Urbit-Recipient-IID: <iid>` and define inbox selection from it.
      3) If you truly intend single-tenant mailboxes: **normatively require** mailbox endpoints to be unique per identity (e.g., per-identity hostname) and state that `/messages` always refers to the one identity bound to that endpoint.
    - Also update the layer docs (`spec/00-shared/layer-integration.md` mailbox section) to match the chosen RFC behavior.

- **2DH “initial message” decrypt algorithm is incomplete for recipient encryption-key rotation (common case)**
  - **What conflicts (quotes)**
    - RFC claims recipients can decrypt if senders used old recipient keys:
      - `spec/06-rfcs/RFC-0003-messaging.md` §5.2:  
        > “If the recipient rotated keys and the sender has an outdated identity document, the recipient can still decrypt using keys from `previous[]`…”
    - But the actual “Bob receives initial message” algorithm only describes trying **Alice’s** keys:
      - `spec/06-rfcs/RFC-0003-messaging.md` §5.3:  
        > “Bob tries Alice’s encryption keys in order until decryption succeeds… `keys.encryption.current` … `keys.encryption.previous[]`…”
  - **Why this breaks interop**
    - In the 2DH initial exchange, the initiator uses **Bob’s encryption public key** (`IK_B`) from Bob’s IDOC. If Bob rotates his encryption key and the sender is stale, the sender will use **Bob’s old public key**.
    - The recipient must therefore attempt decryption using **its own** candidate private keys (`IK_B_private` current + retained previous), not only the sender’s historical public keys. This is not spelled out normatively, so:
      - one implementation will only try sender keys (fails to decrypt after recipient key rotation),
      - another will try recipient private key history (succeeds),
      and the system becomes unreliable and non-interoperable across key rotations.
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0003-messaging.md` §5.2–§5.3
  - **Suggested fix**
    - In RFC-0003 §5.3 add a **normative bounded trial-decrypt matrix**:
      - Receiver MUST attempt 2DH derivation over combinations of:
        - recipient private keys: `{current} ∪ {previous entries not expired}`
        - sender public keys
