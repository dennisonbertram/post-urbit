## Summary
The spec is close to implementable, but there are several **authoritative RFC** gaps/ambiguities where two conforming implementations could compute different bytes (handshake signatures, 2DH salt ordering, group conflict ordering) or could fail to connect due to differing TLS certificate acceptance policies. These are **BLOCKING** because they can produce incompatible signatures/keys or non-convergent group state across implementations.

## Issues Found

### BLOCKING

- **Device-signature transcript ordering is ambiguous in the authoritative RFC (handshake can fail)**
  - **What conflicts (quotes)**
    - RFC-0002 defines device signature input with ambiguous role variables:
      > `device_challenge_data = concat( ... decode_base64(their_nonce), decode_base64(my_nonce), ... decode_base32(my_iid), decode_base32(my_did) )`  
      (spec/06-rfcs/RFC-0002-transport.md §5.8)
    - The non-authoritative layer doc provides explicit direction-specific ordering (and does not match the RFC’s “their/my” ambiguity):
      > Server device signature uses `client_nonce` then `server_nonce` …  
      > Client device signature uses `server_nonce` then `client_nonce` …  
      (spec/01-transport-connectivity/peer-handshake.md, “Device Signature (if DID provided)” and “ClientAuth”)
  - **Why this breaks interop**
    - If one implementation interprets `their_nonce` as “peer’s nonce” and another as “signer’s nonce”, they will hash different transcripts and produce/verify different signatures. Handshake will reliably fail for DID-authenticated sessions.
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0002-transport.md` §5.8
    - `spec/01-transport-connectivity/peer-handshake.md` (Device Signature sections)
  - **Suggested fix**
    - In **RFC-0002 §5.8**, replace the role-variable pseudocode with **two explicit, normative formulas** (mirroring §5.7’s server vs client challenge signatures), e.g.:
      - Server `device_signature` signs `DEVICE_DOMAIN || client_nonce || server_nonce || tls_binding || server_iid || server_did`
      - Client `device_signature` signs `DEVICE_DOMAIN || server_nonce || client_nonce || tls_binding || client_iid || client_did`
    - Add a small test vector for device signature analogous to `spec/00-shared/test-vectors.md` Test Vector 7.

- **2DH / kdf_initial IID “sorting” order is underspecified (session keys can diverge)**
  - **What conflicts (quotes)**
    - RFC-0003 says IIDs are raw bytes but uses an undefined ordering operator:
      > “IIDs are raw 20-byte identifiers (not Base32 strings).”  
      > `if iid_a < iid_b: salt = iid_a + iid_b else: salt = iid_b + iid_a`  
      (spec/06-rfcs/RFC-0003-messaging.md §4.2.3)
    - The test vector text implies some lexicographic ordering but does not normatively define *bytes vs strings*:
      > “Since Alice < Bob lexicographically: Salt = Alice || Bob …”  
      (spec/00-shared/test-vectors.md, Test Vector 6)
  - **Why this breaks interop**
    - Implementers may:
      1) compare **raw 20-byte IID bytes lexicographically**, or  
      2) compare **32-char Base32 strings lexicographically**, or  
      3) compare as big-endian integers.  
    - These are **not guaranteed equivalent**. If different, peers derive different HKDF salt → different root/chain keys → decryption failures for initial messages.
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0003-messaging.md` §4.2.3 and §5 (2DH)
    - `spec/00-shared/test-vectors.md` Test Vector 6
  - **Suggested fix**
    - In **RFC-0003 §4.2.3** (and any other place using “sorted IIDs”), add a normative definition:
      - “Sort by **bytewise lexicographic ascending order of the 20 raw IID bytes** (compare index 0..19, first differing byte wins).”
    - Add an explicit note: “Do **not** sort by Base32 string ordering.”
    - Add/extend a test vector that demonstrates the ordering rule (e.g., two IIDs where Base32-string order differs from raw-byte order, if applicable).

- **Group state conflict ordering is incomplete in the authoritative RFC (non-convergent group membership state)**
  - **What conflicts (quotes)**
    - RFC-0003 defines ordering only up to `(logical_clock, actor_suffix)` and then punts to “admin resolution”:
      > “Version Ordering: … If equal, compare `actor_suffix` lexicographically”  
      > “Conflicting changes at the same version MUST be resolved by the admin with lexicographically lowest actor_suffix”  
      (spec/06-rfcs/RFC-0003-messaging.md §8.6)
    - The layer doc defines a fully deterministic tie-break chain:
      > “If same `logical_clock`: lexicographically smaller `actor_suffix` wins …  
      > If same `version`: lexicographically smaller `actor_iid` wins …  
      > If same `actor_iid`: lexicographically smaller `action.type` wins”  
      (spec/03-messaging-sync/group-messaging.md, “Conflict Resolution (Normative)”)
  - **Why this breaks interop**
    - RFC-0003’s ordering is not total:
      - `actor_suffix` is only **first 8 chars** of an IID → collisions are possible.
      - Even without collisions, duplicate `version` strings can happen via retries/duplication.
    - Without a total, deterministic ordering, replicas can apply different operation orders and **diverge** in membership/roles.
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0003-messaging.md` §8.6
    - `spec/03-messaging-sync/group-messaging.md` “Conflict Resolution (Normative)”
  - **Suggested fix**
    - Update **RFC-0003 §8.6** to include the full deterministic tie-break rules (at least those already written in `group-messaging.md`), **or** change the `version` format to include sufficient entropy to avoid collisions (e.g., full actor IID instead of 8-char suffix).
    - If “admin resolution” is intended, then the protocol must specify how nodes represent and reconcile “pending conflicts” without diverging (currently unspecified).

- **TLS certificate acceptance policy is looser in layer docs than in the authoritative RFC (connections may fail)**
  - **What conflicts (quotes)**
    - RFC-0002 says:
      > “Implementations MUST accept any valid self-signed certificate …”  
      (spec/06-rfcs/RFC-0002-transport.md §4.3, and reiterated in §10.1)
    - Layer integration is much more explicit and broader:
      > “Clients MUST accept ANY certificate … MUST NOT reject … expired or not-yet-valid … self-signed … no CA verification …”  
      (spec/00-shared/layer-integration.md, “QUIC TLS Certificate Policy”)
  - **Why this breaks interop**
    - “valid self-signed certificate” is ambiguous: some implementations will still enforce NotBefore/NotAfter, EKU, or chain properties by default library behavior. Others will not. A server using short-lived/expired/self-issued certs (explicitly allowed by layer docs) could be rejected by a “RFC-conforming” client that interpreted “valid” strictly.
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0002-transport.md` §4.3 and §10.1
    - `spec/00-shared/layer-integration.md` “QUIC TLS Certificate Policy”
  - **Suggested fix**
    - Make **RFC-0002** match the explicit rule set from `layer-integration.md`, e.g.:
      - “Clients MUST disable certificate validation (no chain, no hostname/SNI, no validity period checks) and accept any certificate that allows the TLS 1.3 handshake to complete.”
    - Optionally keep a security note that identity authentication is performed only by the post-TLS handshake transcript.

### HIGH

- **Relay allocation routing tie-break rules still leave “lexicographic” undefined for allocation_id**
  - **What conflicts (quotes)**
    - RFC-0002 defines relay routing selection:
      > “If timestamps are equal (within 1 second), route to the allocation with the lexicographically smallest allocation_id”  
      (spec/06-rfcs/RFC-0002-transport.md §7.13)
    - No RFC section defines the `allocation_id` character set/normalization or comparison basis (ASCII/UTF-8, case sensitivity).
  - **Why this risks interop**
    - In the (common) case of multiple devices per IID creating allocations close in time, different relay implementations could pick different “winners” under tie, causing traffic to reach different devices unpredictably.
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0002-transport.md` §7.13
  - **Suggested fix**
    - Specify `allocation_id` as an ASCII string (e.g., `[a-z0-9-]{...}`) and define comparison as **bytewise lexicographic over ASCII/UTF-8 bytes**, case-sensitive, with normalization forbidden.

- **Revocation “earliest timestamp wins” comparisons aren’t explicitly defined as instant comparisons**
  - **What conflicts (quotes)**
    - RFC-0001:
      > “accept the one with the earliest `effective_at` timestamp”  
      (spec/06-rfcs/RFC-0001-identity-document.md §12.7)
    - RFC-0001 also allows RFC3339 timestamps generally (including offsets) (e.g., §7.4), but does not say whether ordering is string-lexicographic vs parsed-time.
  - **Why this risks interop**
    - If any implementer compares timestamps lexicographically as strings, offsets/fractional seconds can misorder. This is primarily a security/conservatism issue, but could also create divergent revocation status across nodes.
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0001-identity-document.md` §7.4 and §12.7
  - **Suggested fix**
    - State explicitly: “Compare timestamps by parsing RFC3339 into an instant (UTC) and comparing instants; do not compare timestamp strings.”

### MEDIUM

- **Minor RFC-0002 internal reference typo in handshake verification steps**
  - **What conflicts (quotes)**
    - RFC-0002 says:
      > “If `client_did` provided, verify device signature per §5.7”  
      (spec/06-rfcs/RFC-0002-transport.md §5.11)
    - Device signatures are in §5.8, not §5.7.
  - **Why this matters**
    - Doesn’t change wire bytes, but it increases implementer error probability.
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0002-transport.md` §5.11
  - **Suggested fix**
    - Correct the section reference to §5.8 (and similarly check any other cross-references).
