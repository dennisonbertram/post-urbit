## Interoperability Review (Authoritative docs: `spec/06-rfcs/*.md`)

### Summary of issues found

**BLOCKING**
1. `spec/06-rfcs/RFC-0002-transport.md` §7.8–§7.10: Relay “first UDP packet establishes binding” is underspecified (which packet types count; whether a PING-only client will bind; whether REFRESH/REBIND count; whether invalid-dest DATA counts). This can cause spec-conformant client/relay pairs to fail to establish a working relay path.
2. `spec/06-rfcs/RFC-0002-transport.md` §7.13: Relay “multiple allocations for same IID” routing selection uses “most recent successful UDP binding or rebind timestamp” but does not normatively define *which* timestamp is used (relay receive time vs signed `timestamp` inside REBIND JSON; what granularity; what “equal within 1 second” means). Two spec-conformant relay implementations can route the same inbound traffic to different allocations/devices, leading to connectivity failures/state divergence at the transport layer.
3. `spec/06-rfcs/RFC-0001-identity-document.md` §12.4–§12.5 and §13.4 (plus §12.8 “Device Documents/Device Index” verification rules): Device Document and Device Index DHT records have no normative conflict resolution / update selection rules (unlike IDOC’s monotonic `sequence`). With `getAll`/replicated DHT semantics, clients can legitimately see multiple different-but-valid device docs/indexes and choose different endpoints, causing “can’t connect” behavior between spec-conformant implementations.

**HIGH**
1. `spec/06-rfcs/RFC-0002-transport.md` §5.5–§5.6 and §5.9: Optional handshake fields are expressed as `field: "<...>|null"` but the RFC does not explicitly state “MAY be omitted” vs “MUST be present and MAY be null” on the wire. Strict implementations may reject the other’s encoding choice even while both believe they’re conformant.
2. `spec/06-rfcs/RFC-0003-messaging.md` §3.8: Parsing/verification step ordering implies signature verification before identity-document lookup (“Verify signature … then fetch identity document”), but signature verification requires the sender’s signing key(s) from that identity document. This is unlikely to break interop if implemented sensibly, but the normative procedure is internally inconsistent and can drive divergent error-handling/connection behavior.

**MEDIUM**
- None that rise to interop risk beyond the above within the RFC set.

## BLOCKING issues (details + why they break interop)

### B1 — Relay UDP binding establishment is ambiguous
**Where:** `spec/06-rfcs/RFC-0002-transport.md` §7.8, §7.10  
**Problem:** The RFC states:

- “First valid PURL packet from client establishes UDP binding” (§7.8)
- “binding … when the first valid UDP PURL packet is received” (§7.10)

…but does not normatively specify what counts as “valid” for purposes of *initial binding*. Key ambiguities:

- Does a `PING` (0x02) establish binding, or only `DATA` (0x01)?
- Does a `REFRESH` (0x05) establish binding?
- Does a `REBIND` (0x08) establish binding if currently `pending`, or is REBIND only allowed after a bind exists?
- Must `Destination IID` be all-zero for binding packets, or can a client’s first packet be `DATA` to some peer IID?
- If the token is correct but `Destination IID` is malformed/misrouted, is the packet still “valid enough” to bind?

**Interop impact:**  
Two implementations can both be “conformant” yet not interoperate:

- Client A sends `PING` first to establish binding (reasonable, since DATA requires a destination peer). Relay R1 binds on any control packet; Relay R2 binds only on DATA → Client A cannot receive inbound traffic on R2, failing relay connectivity.
- Client B sends first `DATA` with some destination; Relay R3 binds on any valid token; Relay R4 requires destination IID to match allocation owner IID (nonsensical for DATA) → inconsistent behavior.

**Minimal normative fix needed:**  
Add a precise rule, e.g.:

- “A relay MUST establish initial binding on receipt of any well-formed PURL packet whose header token matches an existing allocation, regardless of Packet Type, provided the packet passes header validation (magic/version/type/length) and (for REBIND) payload signature validation; Destination IID is ignored for binding purposes.”

Or, if you want to restrict:

- “A relay MUST establish initial binding on first `PING` or `DATA` with valid token; MUST ignore REFRESH/RELEASE for binding; MUST reject REBIND when binding is pending.”

But it must be one or the other, explicitly.

### B2 — Relay routing selection uses an undefined “timestamp”
**Where:** `spec/06-rfcs/RFC-0002-transport.md` §7.13  
**Problem:** The RFC’s deterministic routing selection for multiple allocations says:

1. “Route to the allocation with the most recent successful UDP binding … or rebind … timestamp”
2. “If timestamps are equal (within 1 second) … lexicographically smallest allocation_id”

But it does not define:

- Whether the “timestamp” is **relay local receive time** (when the packet arrived) or the **signed RFC3339 timestamp inside the REBIND JSON payload**.
- If using the signed timestamp, what to do with clock skew / non-monotonic client clocks (REBIND accepts ±5 min).
- What “within 1 second” means for RFC3339 strings (parsing to instants? truncation? rounding?).
- Whether initial-bind “timestamp” is the first packet’s receive time or derived from anything in the packet (there is no timestamp field in PURL header).

**Interop impact:**  
Two relay implementations can both meet the *current* text but make different choices:

- Relay A uses receive time; Relay B uses signed REBIND `timestamp`. With multiple devices (multiple allocations) rebinding frequently, inbound packets can be routed to different devices depending on relay implementation. From the network’s perspective, this is a hard connectivity failure (wrong device gets the forwarded QUIC packet; correct device never sees it).
- Even within one relay implementation, if “equal within 1 second” is interpreted via different time parsing/truncation approaches, tie-breaking differs and routing flips.

**Minimal normative fix needed:**  
Define a single timestamp source and comparison method, e.g.:

- “Relays MUST maintain a `last_bound_at` monotonic value per allocation equal to the relay’s local receipt time of the packet that established/updated the binding, measured as Unix milliseconds. Routing selection uses this value. The signed `timestamp` inside REBIND is validated for authorization but MUST NOT be used for routing selection.”

And define tie-break precisely (milliseconds integer equality, not “within 1 second”).

### B3 — Device Document / Device Index DHT conflicts: no selection rules
**Where:** `spec/06-rfcs/RFC-0001-identity-document.md` §12.4–§12.5, §13.4, and §12.8 (device docs/index verification)  
**Problem:** The RFC defines:

- Device Document record: `DHT Key = SHA256("post-urbit:device:" || did)`; Value is JCS-canonical JSON (§12.5, §13.2)
- Device Index record: `DHT Key = SHA256("post-urbit:devices-for:" || iid)`; Value is JCS-canonical JSON (§12.4, §13.4)

…but unlike identity documents, device docs/indexes have **no monotonic `sequence`** and the RFC provides **no conflict resolution / “choose latest”** algorithm when multiple valid values exist (a normal condition in replicated DHTs and “getAll” discovery models).

Even if a DHT implementation tries to store “one value,” clients still commonly receive multiple candidates from different peers during convergence/partitions.

**Interop impact:**  
Two spec-conformant implementations can make different choices (first-seen, last-seen, smallest hash, newest `updated_at`, etc.) and therefore attempt different endpoints for the same DID/IID:

- Client X chooses device doc A (endpoint set A) and fails to connect.
- Client Y chooses device doc B (endpoint set B) and succeeds.

This creates real “can’t connect” interoperability failures that are purely due to underspecified selection rules.

**Minimal normative fix needed:**  
Either:

- Add a monotonic `sequence` (or `updated_at` + strict monotonicity constraints) to Device Documents and Device Indexes, and specify “highest sequence wins; same-sequence conflict => TOFU conflict state” (mirroring IDOC), **or**
- Specify selection rules based on existing fields, e.g.:
  - For Device Index: choose highest `updated_at` as an instant; tie-break by lexicographically smallest JCS bytes; if tie and different bytes → conflict state.
  - For Device Document: add `updated_at` (currently only `created_at` exists) or define that device docs are immutable and endpoint changes require a new DID (but then discovery flow must be updated accordingly).

Right now, the protocol implies endpoint changes per device are expected, but the DHT record format doesn’t support deterministic “latest” selection.

## HIGH issues (details)

### H1 — Optional handshake fields: absent vs null not explicitly allowed
**Where:** `spec/06-rfcs/RFC-0002-transport.md` §5.5, §5.6, §5.9  
**Problem:** Fields are shown as `"<...>|null"` but the RFC does not normatively say whether senders:

- MUST include the field and use JSON `null`, or
- MAY omit the field entirely.

The table says “MAY” for `client_did` and “SHOULD” for `expected_server_iid`, but without a hard “MUST accept omitted and null equivalently” parsing rule, strict implementations can diverge.

**Interop impact:** Potential handshake failures between independently implemented parsers.

**Fix:** Add an explicit rule: “Optional fields MAY be omitted; if present they MUST be either the specified type or null; receivers MUST treat omitted and null equivalently.”

---

### H2 — PUSE signature verification procedure ordering is internally inconsistent
**Where:** `spec/06-rfcs/RFC-0003-messaging.md` §3.8  
**Problem:** The steps say “Verify signature … then fetch identity document,” but the key material to verify comes from that identity document.

**Interop impact:** Mostly divergent error paths and potential deadlocks/timeout differences (e.g., one implementation blocks on identity fetch before signature verification; another tries and fails immediately). Not typically a wire mismatch, but can cause different connect/accept behaviors.

**Fix:** Reorder the normative procedure: fetch/resolve sender keys first, then verify signature, then derive/decrypt.

---

## Verdict

The RFC set is close, but the relay binding/routing ambiguities and the device-record conflict handling gaps are directly capable of causing spec-conformant implementations to fail to connect in real deployments.
