## Interop Review (Authoritative: `spec/06-rfcs/*.md` only)

### Summary of issues found

**BLOCKING**
1. `spec/06-rfcs/RFC-0002-transport.md` §4.3 — TLS 1.3 cipher suite requirements are ambiguous (mandatory-to-implement set not defined). Can cause two conformant implementations to negotiate no common suite → TLS/QUIC handshake failure.
2. `spec/06-rfcs/RFC-0003-messaging.md` §7.4.1–§7.4.3 — Mailbox API does not normatively define how the server determines *which recipient inbox* a stored PUSE envelope is associated with (routing/storage key). Two conformant mailbox implementations can store under different keys → clients “successfully store” but recipient can’t retrieve, or retrieves wrong set.

**HIGH**
1. `spec/06-rfcs/RFC-0002-transport.md` §5.11 — Handshake verification steps use `derive_iid(identity_document.keys.signing.genesis)` and signature verification “using keys.signing.current” without explicitly stating Base64 decoding to raw 32-byte keys. This is easy to misread and can lead to handshake interop failures across independently built “spec-following” implementations.
2. `spec/06-rfcs/RFC-0001-identity-document.md` §7.5 and §9.5 — “Normative” pseudocode for signature verification uses Base64-encoded key strings directly (no explicit Base64 decode step). Same ambiguity as above, but impacts message verification / recovery verification behavior.
3. `spec/06-rfcs/RFC-0003-messaging.md` §7.3 — Mailbox URL canonicalization rules are complex and the included reference code does not implement all normative requirements (notably percent-encoding normalization rules). High risk of token-signature mismatch → mailbox auth failures.

**MEDIUM**
1. `spec/06-rfcs/RFC-0001-identity-document.md` §12.8 — Genesis document verification text references “steps 1-4 above” in a way that is unclear (which numbered list is being referenced). Risk: inconsistent DHT-node behavior around genesis acceptance rules.

## Details & recommended spec fixes

### BLOCKING 1 — TLS cipher suite interoperability not guaranteed
**Where:** `spec/06-rfcs/RFC-0002-transport.md` §4.3 (TLS Configuration)

**Problem:** The RFC lists two cipher suites:
- `TLS_CHACHA20_POLY1305_SHA256`
- `TLS_AES_256_GCM_SHA384`

…but does not state whether implementations MUST support **both**, or MAY support **any subset**. Two independently developed implementations could each pick only one (e.g., one “ChaCha-only” for performance, another “AES-only” for policy/FIPS reasons) while still believing they meet the “Cipher suites: …” line.

**Interop impact:** QUIC/TLS handshake can fail outright due to no shared cipher suite (no bytes on the wire beyond failed handshake).

**Suggested RFC change (normative):**
- Define a **mandatory-to-implement** cipher suite set (at least one, ideally two). For example:
  - “Implementations MUST support `TLS_AES_128_GCM_SHA256` and `TLS_CHACHA20_POLY1305_SHA256`; implementations SHOULD support `TLS_AES_256_GCM_SHA384`.”
  - Or “Implementations MUST support both suites listed here.”
- Explicitly state negotiation requirements: “Peers MUST offer all mandatory suites.”

### BLOCKING 2 — Mailbox storage keying/routing is underspecified
**Where:** `spec/06-rfcs/RFC-0003-messaging.md` §7.4.1 (Store), §7.4.2 (Retrieve), §7.4.3 (Delete)

**Problem:** The API is multi-tenant-shaped (`POST /messages`, `GET /messages`, `DELETE /messages`) but the RFC never *normatively* states how the mailbox associates an uploaded envelope with the correct recipient inbox.

You do specify sender binding (`PUSE.sender_iid` MUST match `token.iid`) in §7.4.1, but:
- There is no normative statement like “Mailbox stores under recipient extracted from PUSE recipient field,” nor
- “GET returns messages where PUSE.recipient_iid == token.iid,” nor
- Any requirement that the mailbox reject stores where the envelope recipient does not match the mailbox being addressed (if the mailbox is meant to be per-identity).

**Interop impact:**
- Mailbox implementation A might store by `token.iid` (requester), which is the **sender** during `POST /messages` → message goes into sender’s inbox, never retrievable by intended recipient.
- Mailbox implementation B might store by `PUSE.recipient_iid` (recipient) → works.
Both can plausibly claim conformance from the current text, yet they will not interoperate.

**Suggested RFC change (normative):**
Add explicit routing/storage semantics:
- **On `POST /messages`:**
  - Mailbox MUST parse PUSE header and extract `recipient_iid` (bytes 26–45).
  - Mailbox MUST store the envelope in the inbox keyed by that recipient IID.
  - Mailbox MUST treat `(recipient_iid, message_id)` as idempotency key.
- **On `GET /messages` and `DELETE /messages`:**
  - Mailbox MUST treat `token.iid` as the **inbox owner**, and only return/delete messages whose `recipient_iid == token.iid`.
- Optional but clarifying:
  - Whether mailbox accepts storing messages for recipients that have not “registered” (policy), and how it signals that (`404`, `403`, etc.).

### HIGH 1 — Base64 decoding steps are implicit in critical handshake verification
**Where:** `spec/06-rfcs/RFC-0002-transport.md` §5.11

**Problem:** Verification text uses phrases like:
- “Verify `client_iid == derive_iid(identity_document.keys.signing.genesis)`”
- “Verify `challenge_signature` using `identity_document.keys.signing.current`”

But `keys.signing.*` fields in RFC-0001 are Base64 strings of raw 32-byte keys. RFC-0002 does not explicitly say “Base64-decode to raw 32 bytes before derive/verify” in these verification procedures.

**Interop impact:** Independently built implementations can disagree about whether these fields are already raw bytes vs Base64 strings, causing handshake verification failures.

**Suggested RFC change (normative):**
In §5.11, rewrite the checks explicitly:
- `derive_iid(Base64Decode(identity_document.keys.signing.genesis))`
- `Ed25519_Verify(Base64Decode(identity_document.keys.signing.current), ...)`
…and similarly for device document signature checks.

### HIGH 2 — RFC-0001 “normative” pseudocode omits Base64 decoding
**Where:** `spec/06-rfcs/RFC-0001-identity-document.md` §7.5, §9.5 (and other verification pseudocode snippets)

**Problem:** The RFC marks some pseudocode as “Normative” but uses `signing["current"]` / `att["signature"]` directly without explicitly decoding Base64 strings to raw bytes.

**Interop impact:** Implementers who follow these “normative” algorithms literally can end up with non-interoperable verification behavior (rejecting valid signatures).

**Suggested RFC change:**
- In every “normative” verification algorithm, explicitly show `Base64Decode(key)` and `Base64Decode(signature)` (or clarify that helper functions accept encoded strings and MUST decode internally).
- Prefer one style consistently across RFC-0001/2/3.

### HIGH 3 — Mailbox URL canonicalization mismatch between prose and reference code
**Where:** `spec/06-rfcs/RFC-0003-messaging.md` §7.3

**Problem:** The prose includes strict canonicalization requirements (notably percent-encoding normalization and “unreserved MUST NOT be percent-encoded”), but the provided `canonicalize_mailbox_url()` example does not actually implement all of them.

**Interop impact:** Different implementations may canonicalize differently → token signature mismatch → mailbox authentication fails (store/retrieve/delete fail).

**Suggested RFC change:**
- Either (a) replace the pseudocode with a complete, test-vector-driven algorithm, or (b) normatively reference an existing URL canonicalization standard/profile and specify *exactly* which transformations are applied/forbidden.
- Add at least 3–5 canonicalization test vectors that cover:
  - `%41` vs `A` normalization
  - mixed-case percent hex
  - trailing slash behavior
  - default port elision
  - punycode-only host requirement

### MEDIUM 1 — Genesis verification step reference ambiguity
**Where:** `spec/06-rfcs/RFC-0001-identity-document.md` §12.8 (Genesis Document Verification)

**Problem:** The text references “steps 1-4 above” but it’s unclear which list is being referenced (and which steps are intended as “basic verification”).

**Interop impact:** Could lead to divergent DHT-node acceptance/rejection behavior for genesis records in edge cases (less likely to break day-1 interoperability than the items above, but still worth tightening).

**Suggested RFC change:**
- Inline the exact checks (parse envelope, IID binding, signature.current verification, sequence==0, genesis invariants) without cross-referencing list step numbers.
