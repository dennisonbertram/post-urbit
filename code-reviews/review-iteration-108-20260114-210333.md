## Interoperability Review (authoritative: `spec/06-rfcs/*`)

### Summary of issues found

#### **BLOCKING**
1. **Mailbox URL canonicalization has an underspecified “trailing slash” rule that can change the signed bytes and break mailbox auth**
   - **File/section:** `spec/06-rfcs/RFC-0003-messaging.md` §7.3 “URL Canonicalization (Normative)”, rule #4 (Path)
   - **Why this is interop-breaking:** The mailbox bearer token signature covers `mailbox_url` bytes. Two independently written implementations can canonicalize paths with **multiple trailing slashes** differently (e.g., `/api//` → `/api/` vs `/api`), producing different signature inputs and therefore different signatures/tokens. A client and mailbox server could both be “spec-conformant” under the current text yet fail to authenticate.
   - **What’s ambiguous today:** “remove trailing slash unless path is `/`” does not specify whether to remove **exactly one** trailing `/` or **all** trailing `/` bytes. The illustrative pseudocode uses `rstrip('/')` (remove all), but the normative rule text doesn’t say that.
   - **Concrete fix recommendation (normative text):** Replace rule #4 with something equivalent to:
     - “Normalize empty path to `/`. Then, if the path is not exactly `/`, remove **all** trailing `/` (0x2F) bytes so the path does not end with `/`.”
     - Also explicitly state whether internal `//` sequences are preserved (recommended: preserved) and whether dot-segments are normalized (recommended: **no** dot-segment normalization unless explicitly required), because those too affect signed bytes.

#### **HIGH**
1. **Base32 bit ordering / byte-to-string mapping is not explicitly specified in the transport RFC, yet handshake signatures depend on it**
   - **File/section:** `spec/06-rfcs/RFC-0002-transport.md` §2.1 “Base32 Encoding (Normative)”
   - **Why this is interop-risky:** The handshake challenge transcript in RFC-0002 requires `decode_base32(iid)` → 20 raw bytes. If two implementations interpret “standard 5-bit grouping per Crockford Base32” differently (notably bit/byte ordering), they will compute different `challenge_data`, producing signature verification failures and handshake failure.
   - **What to tighten:** Add an explicit algorithm statement (or pseudocode) defining:
     - input as a 160-bit big-endian bitstring of the 20 raw IID bytes,
     - emit 32 5-bit groups from MSB→LSB, mapping each 0..31 to the Crockford alphabet,
     - decoding as the inverse; reject non-canonical forms.
   - **Note:** RFC-0001 contains a reference implementation for Crockford encoding, but RFC-0002 labels its own §2.1 as “Normative” and is commonly the only doc a transport implementer will read.

#### **MEDIUM**
1. **PUSE `ciphertext_length` could still be misread as “plaintext length” or “ciphertext excluding tag”**
   - **File/section:** `spec/06-rfcs/RFC-0003-messaging.md` §3.2 and §3.6
   - **Interop impact:** Misinterpretation changes framing (where the signature starts), causing parse failure and message rejection. The RFC does say “The 16-byte Poly1305 tag is included in the ciphertext”, which strongly implies `ct_len` includes the tag, but it would be safer to add a single explicit sentence:  
     - “`ct_len` MUST equal the length in bytes of `(ciphertext || tag)` produced by ChaCha20-Poly1305.”
   - **Severity rationale:** The current text is *likely* sufficient for careful readers, but this is a historically common implementer mistake and does directly affect bytes-on-wire parsing.

---

## Overall assessment

The RFC set is very close to interoperable-as-written, but the **mailbox URL canonicalization trailing-slash ambiguity** is a clear, direct source of **token signature mismatches** and thus mailbox communication failure between independently implemented clients/servers.
