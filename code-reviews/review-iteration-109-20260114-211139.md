## Interop review focus (authoritative only)

Reviewed **only** the authoritative specs in `spec/06-rfcs/` (RFC-0001/2/3) for places where two independently developed implementations could (a) emit different bytes for the “same” semantic artifact, (b) reject each other’s handshakes/messages, or (c) diverge in state selection in a way that breaks communication.

---

## Summary of issues found (by severity)

### BLOCKING
1. **IDOC “defaults are semantic” permits multiple valid wire encodings for the “same” identity state**, which interacts badly with same-sequence conflict handling and DHT TTL refresh semantics.  
   - `spec/06-rfcs/RFC-0001-identity-document.md` §6.6 (defaults), plus downstream effects in §12.2 (TTL refresh), §12.8 (update rules), §14.6 (same-sequence conflicts)

2. **QUIC connection resumption / abbreviated handshake is underspecified on the wire** (message schema + required transcript steps), so two conformant implementations can fail to connect when one tries to use it.  
   - `spec/06-rfcs/RFC-0002-transport.md` §8.4 (abbreviated handshake), §15.3 (ResumeAccepted listed but not specified)

### HIGH
3. **Mailbox URL canonicalization does not specify what to do with invalid percent-escapes / URI parsing edge cases**, yet verification requires strict canonical form; different parsers/canonicalizers can accept vs reject the same token.  
   - `spec/06-rfcs/RFC-0003-messaging.md` §7.3 (URL Canonicalization rules + illustrative reference code)

4. **“Ed25519_Sign(SHA256(...))” does not explicitly disallow Ed25519ph / clarify the exact signing API expectations** in the RFCs that use hash-then-sign (handshake, relay allocation/rebind, mailbox token). This is a common real-world footgun across crypto libraries and leads to non-interoperable signatures.  
   - `spec/06-rfcs/RFC-0002-transport.md` §5.7, §7.8, §7.11  
   - `spec/06-rfcs/RFC-0003-messaging.md` §7.3

### MEDIUM
5. **`resume_accepted` is referenced as a message type but lacks a schema and required fields (e.g., version, server_iid, server_nonce, challenge_signature)**, making it unclear whether resumption still binds the session cryptographically to IIDs. Different “reasonable” completions will not interoperate.  
   - `spec/06-rfcs/RFC-0002-transport.md` §8.4, §15.3

## Detailed findings

### BLOCKING 1 — RFC-0001 defaults allow multiple valid bytes for the “same” IDOC version
**Where:** `spec/06-rfcs/RFC-0001-identity-document.md` §6.6 (and consequences in §12.2/§12.8/§14.6)

**What’s ambiguous / why it breaks interop**
- RFC-0001 explicitly says defaults are “semantic only” and **verifiers MUST NOT materialize defaults before verification** (§6.6).
- Producers are only told they **SHOULD** include default-valued fields, not MUST (§6.6).
- Therefore, two implementations can both be “RFC-conformant” yet produce different signed bytes for what many developers will treat as the same identity document “state” (e.g., omitting `endpoints` vs including `endpoints: []`, omitting `claims` vs `claims: {}`).

**Why this becomes a wire-level compatibility problem**
- DHT semantics rely on **byte-identical** refreshes without sequence bump (§12.2) and treat **same-sequence, different-content** as a serious conflict (§14.6).
- If an identity is re-emitted by a different implementation version (or different JSON struct defaults) with the **same `sequence`** but different presence/absence of default fields:
  - DHT nodes that enforce §12.8/§12.2 will reject it as not a TTL refresh (not byte-identical) and not a valid update (sequence not higher).
  - Clients can observe multiple “valid” same-sequence documents (from partitions, caches, backups restored, multi-device publication), triggering §14.6 conflict behavior and potentially suspending operations.

**Concrete example**
- Sequence `"7"` document A omits `"endpoints"` and `"claims"`; document B includes `"endpoints":[],"claims":{}`. Both sign correctly (signature input differs), both pass §7.2 signature verification, but are different bytes and can conflict at same sequence.

**Fix direction (normative)**
Choose one of:
1. **Make a canonical “full” field presence mandatory for v1 IDOC** (recommended): define that all fields in §4.1 must be present on wire, with explicit empty/null values for defaults; verifiers reject missing fields.  
2. Or **define a “signature normalization” step that materializes defaults before signing and verification** (but this directly conflicts with current §6.6 language and would be a more invasive change).

As written, this is a interoperability blocker because it permits multiple valid encodings that the rest of the RFC treats as needing byte-identical behavior.

### BLOCKING 2 — RFC-0002 abbreviated handshake / resumption path is not wire-complete
**Where:** `spec/06-rfcs/RFC-0002-transport.md` §8.4 and §15.3

**What’s missing**
- §8.4 introduces `resume` in `client_hello` and a `resume_accepted` server response, but does not specify:
  - The **exact JSON schema** for `resume_accepted` (fields? `version`? `server_iid`?).
  - Whether the peers **still exchange challenge signatures** (§5.7) or whether resumption is purely “trust the TLS ticket”.
  - How a server that does not implement resumption must respond (ignore `resume` and proceed with normal `server_hello`? send an explicit rejection?).

**Why this can cause connection failures**
Two independently implemented stacks can both plausibly claim conformance yet:
- Client sends `client_hello` with `resume`, then expects `resume_accepted` and transitions immediately to CONNECTED.
- Server ignores `resume` and sends a normal `server_hello` expecting `client_auth`.
- The state machines deadlock or error because each side is waiting for a different next message.

Even if both support resumption, they may differ on whether to still require the challenge-signature exchange, producing handshake failures.

**Fix direction (normative)**
Either:
- **Mark abbreviated handshake / resumption out-of-scope for v1** (remove §8.4 and the `resume_accepted` message listing), or
- Fully specify a resumption transcript, e.g.:
  - `client_hello(resume)` → `server_hello(resume_accepted=true, server_nonce, challenge_signature, maybe omit identity_document)` → `client_auth(challenge_signature, maybe omit identity_document)` → `handshake_complete`
  - plus an explicit “resume_rejected” behavior.

As written, this is a blocking interoperability gap for any implementation that attempts to use the specified resumption feature.

### HIGH 3 — RFC-0003 mailbox URL canonicalization: invalid percent-escapes / parsing edge cases
**Where:** `spec/06-rfcs/RFC-0003-messaging.md` §7.3

**Problem**
Verification requires:
- mailbox_url **MUST** be canonical and verifiers **MUST reject** non-canonical forms.
- Verifiers “canonicalize before computing signature input for verification.”

But the canonicalization rules do not state what to do with malformed URI components, especially:
- A `%` not followed by two hex digits (`%`, `%G0`, `%0`, etc.)
- Ambiguities from differing URL parsers (especially around IPv6 literals, empty host, unusual paths)

The illustrative reference code even hints at “keep invalid escape as-is”, which contradicts a strict “MUST reject non-canonical” posture and will differ across implementations.

**Interop impact**
Two implementations can both believe they’re following §7.3, yet:
- One rejects a token because URL parsing/canonicalization errors out.
- Another accepts and verifies it (by preserving/normalizing differently).
This creates mailbox auth failures and therefore delivery failures.

**Fix direction**
Add explicit normative rules:
- Mailbox URLs MUST be valid per RFC 3986 parsing rules (or explicitly defined subset).
- Any `%` MUST be followed by exactly two hex digits; otherwise **REJECT**.
- Define whether to reject/accept unusual-but-parseable constructs (e.g., empty authority, IPv6 without brackets) rather than leaving it to library behavior.

### HIGH 4 — Hash-then-sign contexts don’t explicitly rule out Ed25519ph / clarify signing API semantics
**Where:**  
- `spec/06-rfcs/RFC-0002-transport.md` §5.7, §7.8, §7.11  
- `spec/06-rfcs/RFC-0003-messaging.md` §7.3

**Problem**
These sections specify signatures as `Ed25519_Sign(private_key, SHA256(input))`. Many ecosystems expose multiple Ed25519 modes (Ed25519, Ed25519ph, Ed25519ctx) or “prehash” wrappers. Without an explicit statement, independent implementations can choose incompatible APIs while believing they are still “signing the hash”.

**Interop impact**
Signature mismatch → handshake failure (RFC-0002) or mailbox auth failure (RFC-0003).

**Fix direction**
Add a short, explicit normative rule in each RFC (or one shared section) stating:
- “Use standard Ed25519 (RFC 8032 Ed25519), not Ed25519ph/ctx. When the RFC says `Ed25519_Sign(SHA256(x))`, the 32-byte SHA256 digest is the message input to standard Ed25519.”

## Conclusion

The RFC set is close, but the two BLOCKING issues above are sufficient for independently developed implementations to fail to interoperate (DHT identity handling and resumption handshake path). Additional HIGH issues remain around mailbox canonicalization edge cases and hash-then-sign signature API ambiguity.
