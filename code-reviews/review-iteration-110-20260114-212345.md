## Interoperability / Wire-Compatibility Review (authoritative: `spec/06-rfcs/*.md`)

### Executive finding
There are **BLOCKING** internal inconsistencies in **RFC-0001** about **which JSON members MUST be present** in an IDOC and, therefore, **what exact bytes are signed and stored**. Two independently implemented “spec-following” stacks could legitimately produce/accept different IDOC JSON objects, resulting in **signature verification failure**, **DHT TTL-refresh failure (byte-identical refresh)**, and downstream **handshake/connection failure** when identity documents are exchanged over RFC-0002.

---

## BLOCKING issues

### 1) RFC-0001 “required field presence” is internally inconsistent and conflicts with RFC’s own examples/vectors
**Where**
- `spec/06-rfcs/RFC-0001-identity-document.md`
  - §4.1 (schema includes fields)
  - §4.3 (fields described as optional with defaults)
  - **§6.6 (Field Presence and Defaults – “MUST be present”)**
  - §15.4 (Complete Genesis Document example)
  - §6.7 (Example input document)

**What / why this is BLOCKING**
RFC-0001 §6.6 states:

> “For v1 IDOC, **all fields defined in §4.1 and §4.2 MUST be present** in the wire encoding, even if they have default values.”

But the RFC’s own “complete genesis document” example (§15.4) and earlier examples omit fields that appear in §4.1, notably:
- `recovery_proof` (shown in §4.1 as top-level; omitted in §15.4)
- `keys.signing.history` (shown in §4.1; omitted in §15.4 and other examples)

Because IDOC signatures are computed over **JCS(doc_without_signatures)**, **presence vs absence** of these fields changes the canonical bytes and therefore changes the signature. As written, two implementations could each reasonably claim conformance while doing different things:
- Impl A follows §6.6 strictly and *requires/publishes* `recovery_proof: null` and `keys.signing.history: []`.
- Impl B follows the “Complete Genesis Document” (§15.4) and omits them entirely, and/or treats §4.3 “defaults” as implying omission is allowed.

These two implementations will compute **different signed bytes** (and potentially reject each other’s IDOCs as malformed), causing:
- **IDOC signature verification failures** (if a verifier enforces field presence before verification).
- **DHT byte-identical TTL refresh failures** (RFC-0001 §12.2/§12.3 and §12.8 rely on byte-identical refresh semantics; inconsistent field presence breaks “same document == same bytes”).
- **Transport handshake failures** in RFC-0002 §5.11 when peers exchange `identity_document` and validate it per RFC-0001.

**Concrete fix direction**
Pick **one** and make it consistent everywhere (schema + rules + examples + vectors):
- **Option A (recommended for your stated goals):** Define a **single canonical IDOC JSON member set** for v1:
  - Explicitly list every required top-level field, including `extensions` and `recovery_proof`.
  - Explicitly require `keys.signing.history` to be present (as `[]` if empty) if you want it canonicalized.
  - Update **all** examples and test vectors in RFC-0001 to include the required members (`recovery_proof: null`, `history: []`, etc.).
- **Option B:** Relax §6.6 and clearly allow omission of optional members (but then you must revise/limit the “byte-identical refresh” story, because semantically-equal docs can have multiple byte encodings).

Until this is resolved, the IDOC bytes-on-the-wire are not uniquely specified.

## HIGH issues

### 2) Bulk stream opcode endianness is not specified
**Where**
- `spec/06-rfcs/RFC-0002-transport.md` §6.3 (Bulk stream: “First 2 bytes = opcode (0x0001=…)”)

**What**
RFC-0002 defines Bulk stream payload as “first 2 bytes = opcode” and lists opcodes as `0x0001`, `0x0002`, etc., but **does not say whether that 16-bit value is big-endian or little-endian** on the wire.

**Why it matters**
Two independently developed implementations could both be “following the RFC” yet encode:
- DATA_CHUNK as bytes `00 01` (big-endian) vs `01 00` (little-endian),
leading to **opcode mismatch** and bulk-transfer failure.

**Concrete fix direction**
In RFC-0002 §6.3 or a new §6.x “Bulk opcode encoding” paragraph:
- Specify: “Bulk opcode is a uint16 **big-endian** (network byte order).”
- Add one byte-level example for at least one opcode.

### 3) Relay allocation request `nonce` base64url padding/canonical form is not fully nailed down
**Where**
- `spec/06-rfcs/RFC-0002-transport.md` §7.8 (Allocation Protocol)

**What**
The allocation request field is described as:
- `"nonce": "<16-bytes-base64url>"`

…but §7.8 does not explicitly say **“Base64url, no padding”** for this field (even though the protocol elsewhere is very explicit about base64/base64url no-padding rules).

**Why it matters**
If one implementation accepts padded base64url and another rejects it (or signs/verifies with differing decode rules), they can fail signature verification / allocation.

**Concrete fix direction**
In RFC-0002 §7.8:
- State `nonce` MUST be **Base64url (RFC 4648 §5), no padding**, exactly 22 chars for 16 bytes.
- State relays MUST reject non-canonical encodings (padding or wrong alphabet).

### 4) Mailbox “token IID string” vs “PUSE header IID raw bytes” comparison is underspecified
**Where**
- `spec/06-rfcs/RFC-0003-messaging.md` §7.4.1–§7.4.3

**What**
RFC-0003 correctly requires mailbox servers to enforce:
- `PUSE.sender_iid == token.iid` (store)
- `PUSE.recipient_iid == token.iid` (retrieve/delete ownership)

But it doesn’t explicitly specify the **exact conversion** step for comparing:
- `token.iid` is a **32-char Crockford Base32 string**
- PUSE header IIDs are **20 raw bytes**

**Why it matters**
A strict implementer needs the normative “decode token.iid Base32 → 20 bytes, then bytewise compare to PUSE header bytes” statement, otherwise there is room for inconsistent interpretations (string compare against re-encoded base32, normalization differences, etc.).

**Concrete fix direction**
Add explicit text in RFC-0003 §7.4:
- “Server MUST decode `token.iid` via RFC-0002 §2.1 Base32 decoding to 20 raw bytes, and compare bytewise to the 20-byte field in the PUSE header.”

## MEDIUM issues

### 5) RFC-0001 “signature is over literal JSON as received” phrasing is easy to misread given JCS-based signing
**Where**
- `spec/06-rfcs/RFC-0001-identity-document.md` §6.6 (last sentence)

**What**
§6.1 defines signing as `domain || JCS(doc_without_signatures)`. §6.6 then says “signature is over the literal JSON as received”, which can be misinterpreted as “sign raw bytes” (contrary to §6.1), especially in contexts where the IDOC is transported as a JSON object (RFC-0002 handshake) rather than as an IDOC envelope.

**Why it matters**
This is less likely to produce two *spec-conformant* implementations (since §6.1 is clear), but the phrasing is an avoidable footgun.

**Concrete fix direction**
Rephrase to something like:
- “Verifiers MUST NOT materialize default fields before computing JCS; signature verification uses JCS over the parsed JSON object with only `signatures` removed.”
