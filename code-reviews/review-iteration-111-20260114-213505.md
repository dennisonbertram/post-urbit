## Summary
The suite is close, but there is at least one **wire-byte/signature-critical contradiction**: the RFC-0001 IDOC “field presence” rule conflicts with RFC-0001’s own canonicalization example and the shared test vectors, so two implementations can compute **different IDOC signature bytes** and reject each other’s documents.

## Issues Found

### BLOCKING
- **IDOC signature input and canonical JSON are inconsistent across RFC-0001 and test vectors (field presence vs omitted fields)**
  - **What conflicts (quotes)**:
    - RFC-0001 requires fields to be present in the wire form:
      - `spec/06-rfcs/RFC-0001-identity-document.md` §6.6:
        > “**Wire Encoding Requirement:** For v1 IDOC, **all fields defined in §4.1 and §4.2 MUST be present in the wire encoding**, even if they have default values.”
    - RFC-0001’s *own* signing example input includes `history` and `recovery_proof`, but the shown JCS output omits them:
      - `spec/06-rfcs/RFC-0001-identity-document.md` §6.7 input includes:
        > `"history": []`  
        > `"recovery_proof": null`
      - Yet §6.7 “JCS output” is:
        > `... "signing":{"current":...,"genesis":...,"previous":null}} ...`  
        (no `"history": []`)  
        and it also omits `"recovery_proof":null`.
    - RFC-0001’s test vector canonical JSON used for the signature omits those same fields:
      - `spec/06-rfcs/RFC-0001-identity-document.md` §15.2 “Canonical JSON (no signatures field)”:
        > `...,"signing":{"current":...,"genesis":...,"previous":null}}...`
        (no `history`, no `recovery_proof`)
    - The shared test vectors likewise omit `keys.signing.history` and `recovery_proof` in the “Document (before signatures)” and the canonical JSON:
      - `spec/00-shared/test-vectors.md` “Test Vector 2: Identity Document Signature”:
        > Document (before signatures) contains  
        > `"signing": { "genesis": "...", "current": "...", "previous": null }`  
        (no `"history": []`)  
        and does not include `"recovery_proof": null`.
      - Same file, “Canonical JSON (JCS - RFC 8785)” similarly lacks `history` and `recovery_proof`.
  - **Why this breaks interop**:
    - IDOC signatures are computed over `domain || JCS(doc_without_signatures)` (RFC-0001 §6.1/§7.1).
    - If implementation A follows RFC-0001 §6.6 literally and **always includes** `keys.signing.history: []` and `recovery_proof: null`, it will sign different canonical bytes than implementation B that follows the RFC-0001 §6.7/§15.2 example and the shared test vectors (which omit them).
    - Result: **different Ed25519 signatures**, causing signature verification failure and **identity document rejection** (DHT storage rejection, handshake IDOC verification failure, cache update failure).
  - **Concrete file paths and section numbers**:
    - `spec/06-rfcs/RFC-0001-identity-document.md` §4.1, §6.6, §6.7, §15.2
    - `spec/00-shared/test-vectors.md` Test Vector 2 (“Identity Document Signature”)
  - **Suggested fix**:
    - Decide one rule and make *all* normative text + examples + vectors match it.
    - Recommended (for deterministic refresh/equality): make the “presence” rule explicit and complete:
      - In RFC-0001 §6.6, list **exactly which fields** must be present (including whether `keys.signing.history` and `recovery_proof` must be present as `[]`/`null`).
      - Update RFC-0001 §6.7 and §15.2 canonical JSON to include those fields if they are required.
      - Regenerate **Test Vector 2 signature** (and its canonical JSON) to match the corrected signature input.

### HIGH
- **Device Document `updated_at` is required by RFC-0001 but omitted in non-RFC “canonical” device doc definitions**
  - **What conflicts (quotes)**:
    - RFC-0001 requires `updated_at` in the Device Document:
      - `spec/06-rfcs/RFC-0001-identity-document.md` §13.2:
        > `"updated_at": "<RFC3339>",`  
        and the table states:
        > `updated_at` | **Yes** | “used for DHT conflict resolution (§12.5)”
    - The integration “canonical” device document omits it:
      - `spec/00-shared/layer-integration.md` “Device Document Structure (canonical)” shows fields including `created_at` and `expires_at`, but **no `updated_at`**.
    - The identity layer schema doc also omits `updated_at`:
      - `spec/02-identity-trust/identity-document-schema.md` “Device Document” example includes `created_at` and optional `expires_at`, but **no `updated_at`**.
  - **Why this breaks interop**:
    - RFC-0001 §12.5 defines conflict resolution for device documents based on parsing `updated_at`. If some implementations omit `updated_at` (because they followed the “canonical” non-RFC docs), other implementations following RFC-0001 may reject the document as malformed or be unable to apply the specified conflict resolution deterministically.
  - **Concrete file paths and section numbers**:
    - `spec/06-rfcs/RFC-0001-identity-document.md` §12.5, §13.2
    - `spec/00-shared/layer-integration.md` “Device Document Structure (canonical)”
    - `spec/02-identity-trust/identity-document-schema.md` “Device Document”
  - **Suggested fix**:
    - Update non-RFC docs to match RFC-0001:
      - Add `updated_at` to the device document schema/examples in `identity-document-schema.md` and `layer-integration.md`.
      - Explicitly state that `updated_at` is **required on wire** and must be included in the signed JCS payload for device docs.

- **RFC-0003 mailbox URL canonicalization: normative “reject invalid percent-escapes” conflicts with the included reference pseudocode**
  - **What conflicts (quotes)**:
    - Normative rule:
      - `spec/06-rfcs/RFC-0003-messaging.md` §7.3:
        > “**Invalid percent-escapes … MUST cause rejection**—do not attempt to preserve or normalize them.”
    - Reference code contradicts by “keeping as-is”:
      - Same section’s illustrative pseudocode (`normalize_percent_encoding`):
        > `except ValueError:`  
        > `    result.append(path[i])  # Invalid escape, keep as-is`
  - **Why this breaks interop**:
    - Mailbox bearer token signatures include `mailbox_url` bytes in the signed input. If one implementation follows the pseudocode behavior (tolerate invalid percent escapes) while another follows the normative rule (reject), tokens can be **accepted vs rejected** inconsistently, and signatures may be computed over **different canonical URL bytes**.
  - **Concrete file paths and section numbers**:
    - `spec/06-rfcs/RFC-0003-messaging.md` §7.3
  - **Suggested fix**:
    - Make the pseudocode match the normative rule: on any invalid `%` escape, raise an error and reject; do not “keep as-is”.
    - Consider adding an explicit negative test vector showing an invalid escape that MUST be rejected.

### MEDIUM
- **QUIC cipher suite list differs between RFC-0002 and non-RFC QUIC integration doc**
  - **What conflicts (quotes)**:
    - RFC requirement:
      - `spec/06-rfcs/RFC-0002-transport.md` §4.3:
        > “Implementations MUST support both: TLS_CHACHA20_POLY1305_SHA256 AND **TLS_AES_128_GCM_SHA256**”
    - Non-RFC doc lists a different AES suite:
      - `spec/01-transport-connectivity/quic-integration.md` “TLS Configuration”:
        > “Cipher suites: TLS_CHACHA20_POLY1305_SHA256, **TLS_AES_256_GCM_SHA384**”
  - **Why this breaks interop**:
    - Because RFC-0002 is authoritative, conforming implementations should follow it; however this mismatch is likely to cause implementers to ship a non-mandatory suite set, increasing negotiation failures in practice and creating confusion about required TLS support.
  - **Concrete file paths and section numbers**:
    - `spec/06-rfcs/RFC-0002-transport.md` §4.3
    - `spec/01-transport-connectivity/quic-integration.md` (TLS Configuration table)
  - **Suggested fix**:
    - Update `quic-integration.md` to match RFC-0002 exactly (list AES_128_GCM as mandatory; AES_256_GCM as optional).

- **Incorrect RFC section references in layer-integration DHT update note**
  - **What conflicts (quotes)**:
    - `spec/00-shared/layer-integration.md` (DHT Record Format → “Update Authorization” note):
      > “Note: Step 2 (byte-identical refresh) applies … **per RFC-0001 §12.2/§12.7** …”
    - In RFC-0001, update authorization logic is in §12.8 (and genesis in §12.3/§12.8), while §12.7 is revocations.
  - **Why this breaks interop**:
    - Not directly wire-breaking, but it increases the odds implementers consult the wrong RFC section and implement the wrong update/refresh behavior.
  - **Concrete file paths and section numbers**:
    - `spec/00-shared/layer-integration.md` “DHT Record Format” (Update Authorization note)
    - `spec/06-rfcs/RFC-0001-identity-document.md` §12.2, §12.8
  - **Suggested fix**:
    - Correct the reference to RFC-0001 §12.8 (and/or §12.3 for genesis refresh immutability semantics).
