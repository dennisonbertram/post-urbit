## Summary
The RFCs are close to wire-complete for IDOC/handshake/PUSE/PURL, but there are still places where **two independent implementations can legitimately produce different bytes or fail to interoperate** due to (a) **broken/contradictory test vectors** and (b) **missing authoritative (RFC-level) definitions for some on-wire messages that the suite clearly expects to exist**.

## Issues Found

### BLOCKING

- **IDOC signature test vector contradicts the canonicalization it claims to use (no implementation can both follow RFC-0001 and match the published signature bytes)**
  - **What conflicts (quotes)**:
    - `spec/00-shared/test-vectors.md` (Test Vector 2, “Canonical JSON” section) provides a canonical JCS string that **includes** `keys.signing.history` and `recovery_proof`, then states:
      > **“Note:** The signature value below was computed over the legacy canonical form (without `history` and `recovery_proof`). Implementations MUST recompute signatures over the complete canonical form above. A future revision will provide updated signature values.”
    - However, the same file then still presents a concrete signature:
      > “Signature (base64, no padding): `HVVMMCJroKN8...`”
    - `spec/06-rfcs/RFC-0001-identity-document.md` presents the same signature as if it is a valid vector over the RFC’s canonicalization rules:
      > §15.2 “Canonical JSON (no signatures field, includes all required fields per §6.6): …”  
      > then “Signature (base64): `HVVMMCJroKN8...`”
  - **Why this breaks interop**:
    - Implementations using RFC-0001 §6 / §7 will compute `signatures.current` over `b"post-urbit:idoc:v1:" || JCS(doc_without_signatures)` including the now-required fields. If the published signature was generated over a *different* canonical byte sequence, verification will fail.
    - This is a **hard conformance blocker**: a conforming implementation cannot pass the suite’s own “known good” signature unless it intentionally deviates from RFC-0001 canonicalization/field-presence rules.
  - **Concrete file paths and section numbers**:
    - `spec/00-shared/test-vectors.md` — Test Vector 2 (“Identity Document Signature”), note immediately before the signature value
    - `spec/06-rfcs/RFC-0001-identity-document.md` — §15.2 “Document Signature”
    - Also implicated: `spec/06-rfcs/RFC-0001-identity-document.md` — §6.6 (field presence) and §6.1/§7.1 (signature input)
  - **Suggested fix**:
    - Regenerate and replace the published signature (and any derived hex/base64) so it **verifies against the exact JCS bytes shown** and the RFC-0001 signing procedure.
    - Alternatively, if the signature is intended to remain “legacy”, then update RFC-0001 §6.6 / vector canonical JSON accordingly (but that would re-open earlier interop problems around byte-identical refresh).

- **Test vector “Signed Document” example violates RFC-0001 §6.6 wire field-presence rules (encourages incompatible IDOC bytes)**
  - **What conflicts (quotes)**:
    - RFC-0001 makes wire presence mandatory:
      - `spec/06-rfcs/RFC-0001-identity-document.md` §6.6:
        > “**Wire Encoding Requirement:** For v1 IDOC, **all fields defined in §4.1 and §4.2 MUST be present in the wire encoding**, even if they have default values.”
    - But `spec/00-shared/test-vectors.md` (Test Vector 2, “Signed Document”) shows a “Signed Document” that omits fields that the vector earlier said must be present (notably `keys.signing.history` and `recovery_proof`):
      > In “Document (before signatures)” it includes `"history": []` and `"recovery_proof": null`  
      > In “Signed Document” it omits `"history"` and omits `"recovery_proof"`
  - **Why this breaks interop**:
    - If an implementer follows the “Signed Document” example literally, they will produce IDOC JSON bytes that a conforming verifier (enforcing RFC-0001 §6.6) **MUST reject**, and signatures computed over the missing-field form will not verify under the required-field form.
    - This can lead to two implementations producing different wire bytes for the “same” logical identity doc, and rejecting each other’s documents.
  - **Concrete file paths and section numbers**:
    - `spec/00-shared/test-vectors.md` — Test Vector 2 “Signed Document”
    - `spec/06-rfcs/RFC-0001-identity-document.md` — §6.6
  - **Suggested fix**:
    - Replace the “Signed Document” JSON example so it includes *all* required fields (including `keys.signing.history: []` and `recovery_proof: null`) and matches the canonical JSON used for signature generation.

- **Identity stream (0x02) wire messages are not specified in any RFC, but are required for interoperability**
  - **What conflicts (quotes)**:
    - RFC-0002 only specifies that Identity stream payloads are JSON with a `type` field, but does not define the message types/fields:
      - `spec/06-rfcs/RFC-0002-transport.md` §6.3:
        > “Identity (0x02) | UTF-8 JSON | Has `type` field in JSON”
    - The repository provides concrete schemas elsewhere:
      - `spec/00-shared/layer-integration.md` (“Identity Message JSON Schemas (Normative)”) defines `identity_update`, `identity_request`, `identity_response`, `identity_ack`, including base64 encoding rules for `idoc`.
    - But per the stated authority hierarchy, `spec/00-shared/*` is **non-authoritative explanatory material**.
  - **Why this breaks interop**:
    - Two implementations can be fully RFC-0002-conforming yet choose different JSON schemas, different `type` strings, or different base64 variants for embedded IDOC (because RFC-0002 doesn’t constrain them). They will then fail to interoperate on identity update exchange over QUIC.
  - **Concrete file paths and section numbers**:
    - `spec/06-rfcs/RFC-0002-transport.md` — §6.3 (payload typing for stream 0x02)
    - `spec/00-shared/layer-integration.md` — “Identity Message JSON Schemas (Normative)” (currently only defined outside RFCs)
  - **Suggested fix**:
    - Move the identity-stream message schemas (and their base64 rules) into an RFC (either RFC-0002 or RFC-0001), or publish an additional RFC that is authoritative for these messages.

- **Sync stream (0x04) CBOR schemas are not specified in any RFC (only in non-authoritative docs), enabling wire divergence**
  - **What conflicts (quotes)**:
    - RFC-0002 references sync but punts the actual structure:
      - `spec/06-rfcs/RFC-0002-transport.md` §6.3:
        > “Sync (0x04) | Binary | 1-byte type + CBOR (see sync-protocol.md)”
    - The CBOR schemas and canonicalization rules live in:
      - `spec/03-messaging-sync/sync-protocol.md` (“CBOR Schemas for Sync Messages”, “CBOR Canonicalization (Normative)”, etc.)
    - But `spec/03-messaging-sync/*` is non-authoritative under the stated hierarchy.
  - **Why this breaks interop**:
    - Two implementations can be RFC-0002-conforming while using different CBOR key choices, ordering rules, or even different message-type registries (since RFC-0002 only says “CBOR”). They will produce different bytes and fail to sync.
  - **Concrete file paths and section numbers**:
    - `spec/06-rfcs/RFC-0002-transport.md` — §6.3 (sync payload definition)
    - `spec/03-messaging-sync/sync-protocol.md` — “Sync Wire Protocol”, “CBOR Canonicalization (Normative)”, “CBOR Schemas for Sync Messages”
  - **Suggested fix**:
    - Promote the sync wire format into an RFC (new RFC-0004 “Sync”), or embed the normative CBOR schemas and canonical CBOR rules directly into an existing RFC and adjust references accordingly.

### HIGH

- **RFC-0001 has two competing “required field” definitions (schema §4.2 vs wire requirement §6.6), increasing risk of incompatible IDOC bytes**
  - **What conflicts (quotes)**:
    - `spec/06-rfcs/RFC-0001-identity-document.md` §4.2 “Required Fields” lists only a subset (e.g., it does **not** include `endpoints`, `claims`, `extensions`, `recovery`, `recovery_proof`, `keys.signing.history`).
    - `spec/06-rfcs/RFC-0001-identity-document.md` §6.6 then states:
      > “For v1 IDOC, **all fields defined in §4.1 and §4.2 MUST be present in the wire encoding**, even if they have default values.”
  - **Why this breaks interop**:
    - An implementer could reasonably read §4.2 as the definitive “required fields” list and omit fields (producing a signed document that still verifies under their own signing logic), but a conforming verifier enforcing §6.6 will reject it. This is exactly the failure mode shown by the current test vector examples.
  - **Concrete file paths and section numbers**:
    - `spec/06-rfcs/RFC-0001-identity-document.md` — §4.2 and §6.6
  - **Suggested fix**:
    - Rename §4.2 to “Semantically Required Fields” and add a separate explicit “Wire-Required Fields” table, or expand §4.2 to include all fields that §6.6 mandates on the wire (and ensure examples/vectors match).

- **Authority confusion: non-RFC documents use “Normative” language for wire contracts**
  - **What conflicts (quotes)**:
    - `spec/00-shared/layer-integration.md` begins:
      > “This document … provides **normative definitions** for cross-layer contracts.”
    - Yet the project’s declared authority hierarchy says only `spec/06-rfcs/*` are authoritative, while other directories are non-authoritative explanatory material.
  - **Why this breaks interop**:
    - This increases the probability that two teams will treat different documents as normative and implement different bytes on the wire (especially for identity/sync stream payloads, where the RFCs currently do not fully constrain the bytes).
  - **Concrete file paths and section numbers**:
    - `spec/00-shared/layer-integration.md` — “Overview” / “Normative Dependencies”
  - **Suggested fix**:
    - Either (a) remove “normative” wording from non-RFC files and move all normative wire definitions into RFCs, or (b) explicitly elevate specific non-RFC docs to normative status (but that would contradict the stated hierarchy and should be a conscious governance decision).

### MEDIUM

- **Conformance guidance in test-vectors mixes “normative” and “placeholder/illustrative” in a way that is easy to misread**
  - **What conflicts (quotes)**:
    - `spec/00-shared/test-vectors.md` includes a mix of:
      > “**HKDF Salt Handling (Normative)** …”  
      > “**IMPORTANT:** … placeholder … **Do NOT implement from this placeholder** …”
      > and the broken IDOC signature vector note described above.
  - **Why this breaks interop**:
    - While not directly changing the RFC-defined wire bytes, this increases the risk that implementations will build against vectors that cannot be satisfied or will implement placeholder formats.
  - **Concrete file paths and section numbers**:
    - `spec/00-shared/test-vectors.md` — “HKDF Salt Handling (Normative)”; Test Vectors 10–11 placeholders; Test Vector 2 note
  - **Suggested fix**:
    - Add an explicit “Vector Status” field per vector (`reproducible`, `illustrative`, `placeholder`, `known-broken`) and ensure the harness/conformance suite only gates on `reproducible` vectors. Fix/remove the known-broken IDOC signature vector immediately.
