## Summary
Several interop-critical ambiguities remain in the authoritative RFCs and the shared test vectors. Most notably: (1) the identity signature test vector is self-contradictory vs RFC-0001, (2) RFC-0001’s timestamp monotonicity rule is underspecified in a way that can cause different accept/reject decisions for valid documents, and (3) RFC-0003 underspecifies receiver state advancement after the initial (0x00) message, which can desynchronize ratchets immediately.

## Issues Found

### BLOCKING

- **Identity document signature test vector is internally contradictory and conflicts with RFC-0001**
  - **What conflicts (quotes)**:
    - From `spec/00-shared/test-vectors.md` (Test Vector 2):
      - “**Note:** The signature value below was computed over the legacy canonical form (without `history` and `recovery_proof`). Implementations MUST recompute signatures over the complete canonical form above. A future revision will provide updated signature values.”
      - In the “Signed Document” example:
        - `"current": "<REQUIRES-RECALCULATION>"`
    - From `spec/06-rfcs/RFC-0001-identity-document.md` (§15.2 / §15.4):
      - “Canonical JSON (no signatures field, includes all required fields per §6.6): …”
      - “Signature (base64): `HVVMMCJroKN8…EVB2Aw`”
      - And the “Complete Genesis Document” includes that signature as `signatures.current`.
  - **Why this breaks interop**:
    - Implementers relying on `spec/00-shared/test-vectors.md` will either (a) treat the provided signature as non-authoritative and recompute, or (b) try to verify the provided signature and potentially fail depending on what they believe the canonicalized input is.
    - This can lead to divergent “known-good” behavior in conformance suites (different “expected” signatures), and thus incompatible implementations or incompatible test harness verdicts.
  - **Concrete file paths and section numbers**:
    - `spec/00-shared/test-vectors.md` — “Test Vector 2: Identity Document Signature” (note + Signed Document section)
    - `spec/06-rfcs/RFC-0001-identity-document.md` — §15.2, §15.4
  - **Suggested fix**:
    - Make `spec/00-shared/test-vectors.md` Test Vector 2 fully consistent and executable:
      - Either remove the “legacy canonical form” note and set `signatures.current` to the concrete value already given, **or**
      - If the signature is actually wrong, update **both** the RFC-0001 test vector signature and `test-vectors.md` to the correct computed value, and remove `<REQUIRES-RECALCULATION>` placeholders entirely.

- **RFC-0001 timestamp monotonicity check is underspecified while fractional seconds are allowed**
  - **What conflicts (quotes)**:
    - From `spec/06-rfcs/RFC-0001-identity-document.md` (§7.4 Timestamp Rules):
      - “**Monotonicity** | MUST be >= previous document's timestamp (if known)”
      - “**Format** | RFC 3339 with `Z` suffix (UTC), fractional seconds OPTIONAL”
  - **Why this breaks interop**:
    - If fractional seconds are allowed, **string comparison is not order-preserving** for time instants (e.g., `"…00.1Z"` is lexicographically `<` `"…00Z"` because `'.' < 'Z'`), so two implementations could:
      - both enforce the MUST,
      - but choose different comparison semantics (lexicographic string vs parsed instant),
      - resulting in different accept/reject decisions for the same valid update.
    - That yields immediate interoperability failure (some nodes accept an update others reject), potentially partitioning identity state propagation.
  - **Concrete file paths and section numbers**:
    - `spec/06-rfcs/RFC-0001-identity-document.md` — §7.4
  - **Suggested fix**:
    - Make the monotonicity comparison algorithm explicit and total:
      - “Parse both RFC3339 timestamps to UTC instants and compare instants” (and specify rejection on parse failure), **or**
      - Require a canonical timestamp format for IDOC `timestamp` (e.g., exactly `YYYY-MM-DDTHH:MM:SSZ`, no fractional seconds) to make string comparison safe (and specify it).

- **RFC-0003 initial (0x00) message processing does not specify receiver chain advancement, risking immediate ratchet desynchronization**
  - **What conflicts (quotes)**:
    - From `spec/06-rfcs/RFC-0003-messaging.md` (§3.4.2 Initial Extension):
      - “The sender MUST derive the message key for the initial (0x00) message using `kdf_chain_step`…”
      - “After encrypting the initial message:  
        - Sender stores `new_chain_key` as `sendingChainKey` with `sendingChainIndex = 1`”
      - “Transition to Ratchet Messages (0x00 → 0x01) (Normative): … Message number N: Start at 1 …”
    - From `spec/06-rfcs/RFC-0003-messaging.md` (§5.5 Initial Ratchet State Setup, responder):
      - Initializes the responder receiving chain with:
        - `chainIndex: 0` and `chainKey: initial_chain_key`
  - **Why this breaks interop**:
    - The RFC normatively defines that the *next* message (0x01) from the initiator uses `n = 1` with the same DH public key.
    - If the responder does not advance its receiving chain state after decrypting the initial (0x00) message (i.e., does not store `new_chain_key` and increment `chainIndex` to 1), then deriving the key for `n = 1` will be off-by-one (or force the receiver to “skip” an `n=0` key that was already consumed by the initial message), causing decryption failure and ratchet divergence across implementations.
    - Because RFC-0003 never explicitly states the responder’s post-decrypt state update for the 0x00 message, two “conforming” implementations can make different choices and fail to interoperate.
  - **Concrete file paths and section numbers**:
    - `spec/06-rfcs/RFC-0003-messaging.md` — §3.4.2, §5.5
  - **Suggested fix**:
    - Add a **normative** “Initial (0x00) Receive Processing” rule (either in §3.4.2 or §5.3/§5.5), explicitly stating:
      - Receiver computes `new_chain_key, message_key = kdf_chain_step(initial_chain_key)`,
      - decrypts using `message_key`,
      - then stores `new_chain_key` as the receiving chain key for that DH public key and sets receiving `chainIndex = 1`,
      - so that the subsequent 0x01 message with `n=1` decrypts correctly.

### HIGH

- **RFC-0001 §6.6 “all top-level fields” list is incomplete vs §4.3 wire-required defaults**
  - **What conflicts (quotes)**:
    - From `spec/06-rfcs/RFC-0001-identity-document.md` (§4.3 Optional Fields (Wire-Required with Defaults)):
      - Includes wire-required defaults for `extensions` and `recovery_proof`:  
        - “`extensions` … Default `{}` … MUST be present in the wire encoding (see §6.6)”  
        - “`recovery_proof` … Default `null` … MUST be present in the wire encoding (see §6.6)”
    - From `spec/06-rfcs/RFC-0001-identity-document.md` (§6.6 Field Presence and Defaults (Normative)):
      - “Producers MUST include:  
        - All top-level fields (`version`, `iid`, `sequence`, `timestamp`, `keys`, `endpoints`, `claims`, `recovery`, `signatures`)”
      - (This “all top-level fields” list omits `extensions` and `recovery_proof`.)
  - **Why this breaks interop**:
    - A producer could plausibly read §6.6’s explicit list as exhaustive and omit `extensions`/`recovery_proof`, while another implementation (or DHT node) enforces §4.3’s requirement that those fields MUST be present.
    - That yields inconsistent accept/reject behavior and defeats “byte-identical refresh” semantics if some nodes store variants with missing fields.
  - **Concrete file paths and section numbers**:
    - `spec/06-rfcs/RFC-0001-identity-document.md` — §4.3, §6.6
  - **Suggested fix**:
    - In RFC-0001 §6.6, replace the partial parenthetical list with a complete normative list that explicitly includes `extensions` and `recovery_proof`, or point to a machine-checkable required-field set (e.g., “all fields in §4.1 schema are mandatory on wire”).

- **Duplicate-JSON-key rejection is required but not operationalized, enabling divergent parsing/verification outcomes on malicious inputs**
  - **What conflicts (quotes)**:
    - From `spec/06-rfcs/RFC-0001-identity-document.md` (§6.3 JCS Rules):
      - “**No duplicate object keys at any level** - implementations MUST reject documents containing duplicate member names before signature verification”
  - **Why this breaks interop**:
    - Many JSON parsers do not expose duplicate-key detection (they silently accept and take “last wins” or “first wins”).
    - If one implementation rejects and another “accepts” by silently collapsing duplicates, they will compute different canonical objects and therefore different signature inputs, producing different verification outcomes and different stored identity state.
    - While duplicates are invalid, the lack of a specified detection method is a practical interoperability hazard and a common divergence point.
  - **Concrete file paths and section numbers**:
    - `spec/06-rfcs/RFC-0001-identity-document.md` — §6.3
  - **Suggested fix**:
    - Add a normative implementation requirement: IDOC envelope JSON MUST be parsed with a duplicate-key-detecting parser, or the raw JSON bytes MUST be scanned to detect duplicates prior to normal parsing; specify that implementations unable to detect duplicates MUST treat any document as invalid unless parsed by a compliant duplicate-detecting mechanism.

### MEDIUM

- **RFC-0001 DHT verification section contains incorrect internal step cross-references**
  - **What conflicts (quotes)**:
    - From `spec/06-rfcs/RFC-0001-identity-document.md` (§12.8 DHT Verification Rules):
      - “Parse IDOC envelope and verify basic signature (steps 1-4 above)” (and similar phrasing in genesis verification)
    - But the immediately preceding list “Verification (New Identity Records)” enumerates only:
      - “1. Parse IDOC envelope  
        2. Verify iid == derive_iid(...)  
        3. Verify signatures.current …”
  - **Why this breaks interop**:
    - This is primarily editorial, but it creates ambiguity about whether an additional required check exists (a “missing step 4”), which can lead to inconsistent DHT acceptance criteria if implementers infer an unstated rule.
  - **Concrete file paths and section numbers**:
    - `spec/06-rfcs/RFC-0001-identity-document.md` — §12.8
  - **Suggested fix**:
    - Fix the references (“steps 1-3 above”), or explicitly list the intended additional step (if any).

- **Non-authoritative Double Ratchet doc is ambiguous about IID ordering, contradicting RFC-0003’s explicit raw-byte ordering**
  - **What conflicts (quotes)**:
    - From `spec/03-messaging-sync/double-ratchet.md` (kdf_initial):
      - “if iid_a < iid_b: salt = iid_a + iid_b …”
      - (Does not specify whether this is raw bytes, Base32 strings, or some parsed form.)
    - From `spec/06-rfcs/RFC-0003-messaging.md` (§4.2.3):
      - “IID Sorting (Normative): … MUST be performed as bytewise lexicographic comparison of the raw 20-byte IID values … MUST NOT sort by Base32 string representation”
  - **Why this breaks interop**:
    - Implementers reading the layer doc (even though non-authoritative) could sort by Base32 strings and derive different session keys, producing different ciphertext and signatures.
  - **Concrete file paths and section numbers**:
    - `spec/03-messaging-sync/double-ratchet.md` — “Initial Key Derivation (2DH)” section
    - `spec/06-rfcs/RFC-0003-messaging.md` — §4.2.3
  - **Suggested fix**:
    - Update the layer doc to explicitly mirror RFC-0003: “compare raw 20-byte IIDs bytewise lexicographically” (and add a warning not to compare Base32 strings).
