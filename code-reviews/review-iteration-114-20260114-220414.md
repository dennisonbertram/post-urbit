## Summary
The suite is close to implementable, but there are several places where the *normative* RFCs either contradict each other or leave a wire-encoding underspecified such that two independent “conforming” implementations could reject each other’s traffic or serialize different bytes for the same intended artifact.

## Issues Found

### BLOCKING
- **PUSE signature encoding contradicts between RFC-0001 and RFC-0003**
  - **What conflicts (quotes)**:
    - RFC-0001 (Identity) claims a Base64-encoded PUSE signature:
      - `def verify_puse_signature(sender_idoc: dict, signed_data: bytes, signature_b64: str) -> bool:`  
      - `signature = base64_decode(signature_b64)  # 64 bytes`
      - And text: “The `signature` parameter is also Base64-encoded (64 bytes raw).”
      - **Source:** `spec/06-rfcs/RFC-0001-identity-document.md` §7.5
    - RFC-0003 (Messaging) defines the PUSE signature as raw bytes in the binary envelope:
      - PUSE wire format includes `│ Signature │ 64 bytes`
      - `signed_data = envelope[0 : total_length - 64]`
      - `signature = Ed25519_Sign(sender_signing_key, signed_data)`
      - **Source:** `spec/06-rfcs/RFC-0003-messaging.md` §3.2 and §3.7
  - **Why this breaks interop**: An implementation following RFC-0001 §7.5 literally will attempt Base64-decoding a 64-byte binary signature extracted from the PUSE envelope and fail verification/reject messages, while an implementation following RFC-0003 will verify correctly. Two “conforming” implementations can therefore fail to interoperate on message verification.
  - **Concrete file paths and section numbers**:
    - `spec/06-rfcs/RFC-0001-identity-document.md` §7.5
    - `spec/06-rfcs/RFC-0003-messaging.md` §3.2, §3.7
  - **Suggested fix**:
    - In RFC-0001 §7.5, change the parameter to `signature_bytes: bytes` and remove Base64 language/decoding entirely (RFC-0001 should only specify *key selection order*, not a conflicting signature encoding for PUSE).
    - Optionally rename the helper to something like `select_signing_key_for_puse(sender_idoc, signed_data, signature_bytes)` to avoid implying PUSE defines Base64 signatures.

- **`sync_op` PUSE plaintext encoding is not specified (mailbox fallback cannot interoperate)**
  - **What conflicts (quotes)**:
    - RFC-0003 introduces `sync_op` as a real message type:
      - “`sync_op` … it MAY be encapsulated in PUSE with type `sync_op` … The content contains the raw sync operation as defined in `spec/03-messaging-sync/sync-protocol.md`.”
      - **Source:** `spec/06-rfcs/RFC-0003-messaging.md` §8.2
    - But the sync protocol is CBOR-on-stream with a 1-byte type prefix and CBOR payloads, not JSON, and RFC-0003 never defines *how* those bytes appear inside the JSON plaintext (`base64`? `base64url`? a CBOR diagnostic-to-JSON mapping? a nested JSON schema?).
  - **Why this breaks interop**: Two implementations can both “support sync_op” yet choose different encodings (e.g., embed CBOR as base64 string vs embed decoded JSON), causing the receiver to fail to parse/validate/apply the operation. This is a direct on-wire semantics ambiguity for a normative RFC feature.
  - **Concrete file paths and section numbers**:
    - `spec/06-rfcs/RFC-0003-messaging.md` §8.2
    - (Referenced) `spec/03-messaging-sync/sync-protocol.md` (CBOR schemas + type byte framing)
  - **Suggested fix**:
    - Define a **normative `sync_op` plaintext schema** in RFC-0003, e.g. one of:
      1) `{"content":{"sync_type":<u8>, "cbor":"<base64-std-no-pad of CBOR-bytes>"}}` (and explicitly whether the CBOR includes or excludes the 1-byte sync message type), **or**
      2) `{"content":{"frame":"<base64-std-no-pad of (type_byte || cbor_payload)>"}}`.
    - Also define size limits and canonical Base64 alphabet (standard vs url) for this field.

- **App-defined message payload mapping (CBOR→JSON) is underspecified and can be lossy**
  - **What conflicts (quotes)**:
    - RFC-0003 defines an on-wire transformation for app messages:
      - “For app-defined types … PUSE `type` field MUST be `"app"` … `data` MUST be: `{ "app_id": "<message_type>", "data": <CBOR-decoded-content> }`”
      - “CBOR↔JSON conversion … Byte strings: Base64 … prefixed with `"~b"` … Tags: `{ "~t": <tag_number>, "v": <value> }`”
      - **Source:** `spec/06-rfcs/RFC-0003-messaging.md` §8.2 (“Host API to PUSE Plaintext Mapping (Normative)”)
  - **Why this breaks interop**:
    - CBOR has multiple constructs without a single obvious JSON representation beyond the two listed (e.g., **maps with non-text keys**, big integers, floats/NaNs (if allowed), indefinite vs definite distinctions (if allowed by app runtime), bstr keys, etc.). The RFC only specifies bytestrings and tags.
    - Two independent implementations can therefore both be “conforming” while producing different plaintext JSON for the same CBOR input, causing:
      - different ciphertexts/signatures for semantically “same” app payloads, and more importantly
      - different decoded payloads delivered to apps on the receiving node, breaking cross-implementation app interoperability.
    - Additionally, decoding CBOR into JSON can be **information-losing** (notably for integers > 2^53 in common JSON stacks), making round-tripping impossible unless a complete canonical mapping is specified.
  - **Concrete file paths and section numbers**:
    - `spec/06-rfcs/RFC-0003-messaging.md` §8.2
    - (Interacts with) `spec/04-app-runtime/api-surface.md` (`messaging.send` uses `content: Uint8Array` CBOR) and `spec/04-app-runtime/abi.md` (CBOR as primary host IPC format)
  - **Suggested fix** (pick one approach and make it explicit):
    1) **Opaque CBOR-on-wire for app messages:** In RFC-0003, define `app` plaintext as `{"content":{"app_id": "...", "data_cbor": "<base64std(no-pad) of original CBOR bytes>"}}` and do **not** CBOR-decode to JSON for transport, OR
    2) **Fully specify a canonical CBOR→JSON mapping** for *all* CBOR types you allow apps to send, including map-key canonicalization rules and a lossless integer encoding (e.g., represent all integers as decimal strings, or use a tagged object form).
    - Also specify the reverse mapping (JSON→CBOR) if the receiving host API is expected to hand apps CBOR bytes.

### HIGH
- **IDOC envelope trailing bytes are not specified as valid/invalid**
  - **What conflicts (quotes)**:
    - RFC-0001 defines the envelope structure as exactly: magic + version + length + `<length>` bytes:
      - `│ Canonical JSON (UTF-8) │ <length> bytes`
      - **Source:** `spec/06-rfcs/RFC-0001-identity-document.md` §11.1
    - But the parsing algorithm only checks “at least”, not “exactly”:
      - `assert len(data) >= 9 + length, "Truncated"`
      - `json_bytes = data[9:9+length]`
      - **Source:** `spec/06-rfcs/RFC-0001-identity-document.md` §11.4
  - **Why this breaks interop**: One implementation may accept (and store/relay) IDOC envelopes with extra trailing bytes while another rejects them (or treats the extra bytes as a framing error). Since IDOC bytes are used for DHT byte-identical refresh semantics, allowing extra bytes also undermines deterministic equality.
  - **Concrete file paths and section numbers**:
    - `spec/06-rfcs/RFC-0001-identity-document.md` §11.1, §11.4
  - **Suggested fix**:
    - Make it explicit: **Receivers MUST reject any envelope where `len(data) != 9 + length`** (or, if concatenation is intended, define an outer framing and specify that extra bytes belong to subsequent frames, not the envelope).

- **Deterministic CBOR rule is ambiguous about which arrays must be sorted**
  - **What conflicts (quotes)**:
    - Sync protocol adds an extra determinism rule beyond RFC 8949:
      - “Arrays sorted by element bytes when order is not semantic”
      - **Source:** `spec/03-messaging-sync/sync-protocol.md` §“Deterministic Encoding Rules”
  - **Why this breaks interop**: Different implementations can legitimately disagree on whether a given array’s order is “semantic” (e.g., `operation_ids`, `wanted_ids`, `acked_ids`, `dependencies`). Some may sort and some may not; if any receiver enforces this as a validation requirement, it can reject otherwise-valid messages. Even if not rejected, it can break reproducible hashing/signing expectations for any construct that hashes CBOR message bytes.
  - **Concrete file paths and section numbers**:
    - `spec/03-messaging-sync/sync-protocol.md` §“Deterministic Encoding Rules” and §“CBOR Canonicalization (Normative)”
  - **Suggested fix**:
    - Enumerate per-field requirements, e.g.:
      - `dependencies`: MUST be sorted by bytewise operation_id
      - `operation_ids` / `wanted_ids` / `acked_ids`: MUST be sorted (or explicitly “order arbitrary; receivers MUST accept any order”)
    - If receiver validation requires sorting, state that explicitly as MUST/SHOULD.

- **Shared test vectors are internally inconsistent / non-actionable for IDOC signatures**
  - **What conflicts (quotes)**:
    - Test vectors explicitly admit the signature value is not for the stated canonical form:
      - “The signature value below was computed over the legacy canonical form … Implementations MUST recompute… A future revision will provide updated signature values.”
      - `signatures.current: "<REQUIRES-RECALCULATION>"`
      - **Source:** `spec/00-shared/test-vectors.md` §“Test Vector 2: Identity Document Signature”
    - RFC-0001 test vectors section repeats the same gap:
      - “Signature (ILLUSTRATIVE - requires recalculation)… `<REQUIRES-RECALCULATION-OVER-COMPLETE-CANONICAL-FORM>`”
      - **Source:** `spec/06-rfcs/RFC-0001-identity-document.md` §15.2
  - **Why this breaks interop**: While not a wire-format ambiguity per se, it blocks independent implementers from validating that they are computing the same signature inputs and bytes. In practice, this leads to divergent implementations and failed verification across nodes.
  - **Concrete file paths and section numbers**:
    - `spec/00-shared/test-vectors.md` Test Vector 2
    - `spec/06-rfcs/RFC-0001-identity-document.md` §15.2
  - **Suggested fix**:
    - Publish at least one complete “known good” IDOC signature vector where:
      - full document (with all §6.6 required fields) is given,
      - JCS canonical bytes are given,
      - `signatures.current` is the actual correct Base64 value for that canonical form.

- **Non-RFC identity schema docs conflict with RFC-0001’s wire-required field presence**
  - **What conflicts (quotes)**:
    - RFC-0001 requires all defaultable fields to be present in wire encoding:
      - “all fields listed in §4.2 and §4.3 MUST be present… Verifiers MUST reject documents missing any of these fields.”
      - **Source:** `spec/06-rfcs/RFC-0001-identity-document.md` §6.6
    - But the layer schema document presents `keys.signing.history` etc. as optional and shows examples omitting fields:
      - “Optional Fields … `keys.signing.history` | array | Max 10 entries”
      - And earlier example structure omits `history` in `keys.signing` in the main JSON structure example.
      - **Source:** `spec/02-identity-trust/identity-document-schema.md` (“Document Structure”, “Optional Fields”)
  - **Why this breaks interop**: Implementers relying on the schema docs (common) may omit fields and produce IDOCs that strict RFC-0001 verifiers reject, causing network partitioning between “schema-doc implementers” and “RFC implementers.”
  - **Concrete file paths and section numbers**:
    - `spec/06-rfcs/RFC-0001-identity-document.md` §6.6
    - `spec/02-identity-trust/identity-document-schema.md` (Document Structure + Optional Fields sections)
  - **Suggested fix**:
    - Update `identity-document-schema.md` to explicitly mirror RFC-0001 §6.6: mark the §4.3 “wire-required with defaults” fields as **wire-required** (even if semantically defaultable), and ensure examples include them (`history: []`, `recovery_proof: null`, etc.).

### MEDIUM
- **Packaging signature timestamp canonical form is not pinned, risking inconsistent acceptance**
  - **What conflicts (quotes)**:
    - App package signature uses a timestamp string inside the signed payload:
      - `payload = "postapp-signature-v1:" || manifest_hash_hex || ":" || timestamp`
      - SIGNATURE file says `timestamp` is “RFC3339 UTC timestamp when signed”
      - **Source:** `spec/05-ux-packaging/app-distribution.md` (“Signing Process”, “SIGNATURE File Format”)
    - Verification requires parsing timestamp for “not in future” checks, but does not specify whether non-canonical RFC3339 forms (fractional seconds, `+00:00`) are allowed or must be rejected.
  - **Why this breaks interop**: One implementation may accept and another may reject the *same signed package* based solely on timestamp syntax, even though the signature verifies (because the timestamp string is part of the signed payload).
  - **Concrete file paths and section numbers**:
    - `spec/05-ux-packaging/app-distribution.md` (“SIGNATURE File Format”, “Signing Process”, “Verification Process”)
  - **Suggested fix**:
    - Either (a) require **canonical** `YYYY-MM-DDTHH:MM:SSZ` for packaging timestamps and reject others, or (b) explicitly allow any RFC3339 form and require parsers to accept them for freshness checks (while still using the exact string for signature verification).

- **RFC-0001 “implementation-defined” language is dangling**
  - **What conflicts (quotes)**:
    - “Implementations SHOULD follow this document but MAY diverge where noted as implementation-defined.”
      - **Source:** `spec/06-rfcs/RFC-0001-identity-document.md` “Status of This Memo”
  - **Why this breaks interop**: This invites readers to believe there are permitted divergences, but the RFC does not clearly enumerate which parts are implementation-defined. That can lead to “conforming” yet divergent encodings/signature inputs.
  - **Concrete file paths and section numbers**:
    - `spec/06-rfcs/RFC-0001-identity-document.md` “Status of This Memo”
  - **Suggested fix**:
    - Either remove the sentence, or add an explicit list of implementation-defined items (ideally none for wire/signature constructions).
