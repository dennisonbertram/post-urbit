## Iteration 115 spec review — remaining interoperability risks

You noted fixes for: `sync_op` PUSE plaintext schema, CBOR→JSON mapping, IDOC envelope trailing-bytes rule, and IDOC field alignment. Those fixes appear present. The remaining issues below are the ones most likely to cause independent implementations to diverge on the wire or fail conformance in practice.

### BLOCKING-01: `sync_op` mailbox fallback uses undefined / conflicting `sync_type` codes
**Where**
- `spec/06-rfcs/RFC-0003-messaging.md` §8.2 (`sync_op` plaintext schema + “sync_type” registry)
- `spec/03-messaging-sync/sync-protocol.md` “Message Types” (0x01..0x07) and its CBOR schemas
- `spec/00-shared/layer-integration.md` “Sync stream (0x04): 1-byte message type …”

**Problem**
RFC-0003 defines `sync_op` plaintext `content.sync_type` with values:
- `0x00=full, 0x01=delta, 0x02=ack, 0x03=request` and says “see sync-protocol.md §3”.

But the Sync Protocol defines message type codes as:
- `0x01=SYNC_REQUEST`, `0x02=SYNC_OFFER`, `0x03=SYNC_ACCEPT`, `0x04=SYNC_OPERATIONS`, `0x05=SYNC_ACK`, `0x06=SYNC_SUBSCRIBE`, `0x07=SYNC_UNSUBSCRIBE`.

There is no “full/delta/ack/request” type registry in `sync-protocol.md`, and the numeric ranges overlap differently. Two correct implementations will therefore disagree on how to interpret `sync_op` messages delivered via mailbox.

**Why this breaks interop**
A sender encapsulating sync data for mailbox fallback will produce a PUSE plaintext the receiver cannot parse deterministically because the type byte is ambiguous and references a different registry.

**Required resolution (normative)**
Pick **one** of these and make it explicit:

1) **Mirror sync stream framing inside the plaintext**  
   - Define `sync_type` to be exactly the sync stream message type byte (`0x01..0x07`) and define `cbor` to be the **CBOR payload bytes only** (not including the type byte), *or* define `cbor` to include the leading type byte and rename field accordingly.
   - Add a table in RFC-0003 mapping `sync_type` to the exact schema section in `sync-protocol.md`.

2) **Define a separate mailbox-sync mini-registry**  
   - If you want `full/delta/request/ack`, then `sync-protocol.md` must define those message types and schemas, and the sync stream must reference them too. Today it does not.

Until this is resolved, mailbox-carried sync operations are not interoperable.

### HIGH-01: TypeScript “canonical” IdentityDocument interfaces conflict with RFC-0001/RFC-0001-derived wire requirements
**Where**
- `spec/02-identity-trust/interfaces.md`:
  - `keys.signing.history?: SigningKeyHistory[];` (optional)
  - `recoveryProof?: RecoveryProofEmbed;` (optional; also camelCase field)
- `spec/02-identity-trust/identity-document-schema.md` (wire-required fields + “Field Presence Rules”)
- `spec/06-rfcs/RFC-0001-identity-document.md` §6.6 (“all fields MUST be present in wire encoding”, including empty arrays/objects and nulls)

**Problem**
RFC-0001 and `identity-document-schema.md` require “wire-required” presence:
- `keys.signing.history` MUST be present (empty `[]` if none)
- `recovery_proof` MUST be present (`null` if absent)
- all top-level fields must exist, even if default/empty

But the TypeScript interfaces used across layers mark several of these as optional and do not encode the “MUST emit empty array/object/null” rule. An implementation that follows `interfaces.md` as “authoritative” (it is presented that way in several places) could legitimately omit these fields, producing IDOCs that RFC-0001-conforming verifiers MUST reject.

**Why this breaks interop**
Two implementations could both claim “spec compliant” while one emits IDOCs missing `history`/`recovery_proof`, and the other rejects them per RFC-0001 §6.6. That’s a direct interoperability failure.

**Required resolution**
Make the boundary explicit and consistent:

- Either (preferred) **split types** into:
  - `IdentityDocumentWire` (snake_case, all required fields present, `history: []`, `recovery_proof: null`, etc.)
  - `IdentityDocument` (in-memory convenience, optional fields allowed)
- Or change `spec/02-identity-trust/interfaces.md` to make wire-required fields non-optional and explicitly require emitting empty arrays/objects/nulls when serializing.

### HIGH-02: Transport-layer `DeviceDocument` interface omits `updated_at` which RFC-0001 makes conflict-resolution-critical
**Where**
- `spec/01-transport-connectivity/interfaces.md` `interface DeviceDocument { ... createdAt ... expiresAt? ... }` (no `updatedAt`)
- `spec/00-shared/layer-integration.md` canonical device doc includes `updated_at`
- `spec/06-rfcs/RFC-0001-identity-document.md` §12.5 requires `updated_at` and uses it for DHT conflict resolution; also states device doc updates MUST strictly increase `updated_at`

**Problem**
The transport interface model does not include `updatedAt`, but the wire format and DHT conflict resolution require it. Implementations using the transport interface as their “device document structure” may fail to store or propagate `updated_at`, making their device docs unverifiable or non-convergent under the RFC-0001 DHT conflict rules.

**Why this breaks interop**
Different clients will select different device documents from the DHT when multiple exist, because the required ordering key (`updated_at`) is missing or not enforced consistently.

**Required resolution**
Update `spec/01-transport-connectivity/interfaces.md` `DeviceDocument` to include `updatedAt: Timestamp` (and ideally `deviceName` mapping clarity), or explicitly state this interface is not the wire schema and must be derived from the RFC-0001 schema (but then remove/avoid calling it “DeviceDocument”).

### HIGH-03: Identity signature test vectors are internally inconsistent / not actually usable as conformance vectors
**Where**
- `spec/00-shared/test-vectors.md` Test Vector 2 (“Identity Document Signature”) contains a concrete signature but also states it was computed over a legacy canonical form and must be recomputed, and marks `signatures.current` as `<REQUIRES-RECALCULATION>`.
- `spec/06-rfcs/RFC-0001-identity-document.md` §15.2 repeats “requires recalculation”.

**Problem**
A “test vector” that provides a signature value that is known not to match the normative signing input is not a test vector—two implementations cannot use it to confirm interoperability without writing extra “vector repair” logic.

**Why this matters**
While not always wire-breaking by itself, this *does* break conformance harness interoperability: independent implementations cannot validate against a shared expected signature output, and will disagree about what “passes vectors”.

**Required resolution**
Publish one of:
- a corrected `signatures.current` computed over the exact canonical JSON shown, **or**
- remove the incorrect signature entirely and provide only the deterministic seed + explicit instruction “compute expected signature from seed”.

Right now it’s ambiguous and will cause false failures.

### MEDIUM-01: “1 MB message size” is ambiguous between plaintext vs envelope bytes across layers
**Where**
- `spec/06-rfcs/RFC-0003-messaging.md` §3.2 max envelope size = 1,048,576 bytes (envelope bytes)
- `spec/06-rfcs/RFC-0002-transport.md` §6.4 stream type 0x03 max message size = 1 MB (frame payload bytes)
- `spec/03-messaging-sync/interfaces.md` `MESSAGING_CONSTANTS.MAX_MESSAGE_SIZE = 1048576` (unclear whether plaintext or envelope)

**Problem**
Some implementations may enforce 1 MB on plaintext (post-decryption JSON bytes), others on envelope bytes (wire), others on QUIC frame payload. Near the limit, this leads to “send succeeds on one node, rejected by another” behavior.

**Suggested resolution**
State explicitly (normative) that:
- Transport limit applies to **frame payload bytes** (PUSE envelope bytes).
- Messaging API limit applies to **envelope bytes** (or provide a separate plaintext limit and show the derived maximum plaintext size given extension + nonce + tag + signature overhead).

### LOW-01: IID terminology differs between RFCs (20-byte vs 32-char) without consistent “raw IID” naming
**Where**
- `spec/06-rfcs/RFC-0002-transport.md` §2 defines IID as 20-byte hash
- `spec/06-rfcs/RFC-0001-identity-document.md` uses IID as the 32-char Crockford Base32 string

**Impact**
Mostly editorial/terminology, but can still confuse implementers around when to Base32-decode. Recommend standardizing on:
- `iid` (string form, 32 chars) and
- `iid_raw` (20-byte form)
