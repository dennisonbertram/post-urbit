## HIGH issues

### HIGH-1: **App/package signature “key valid at timestamp” is underspecified and currently not computable from a single IDOC**
**Where**
- `spec/05-ux-packaging/app-distribution.md` (§Verification Process step 9)
- `spec/04-app-runtime/manifest-schema.md` (signature verification pseudocode)
- Identity key history semantics in `spec/02-identity-trust/identity-document-schema.md` and `spec/06-rfcs/RFC-0001-identity-document.md` (§7.5)

**Problem**
App distribution verification requires: “Lookup key that was active at timestamp in identity document”. However:
- IDOC key history entries provide `valid_from`/`valid_until` **as sequence numbers**, not timestamps.
- The IDOC contains only the **current** document (plus genesis via separate DHT key). There is no normative mechanism guaranteeing availability of the historical IDOC versions needed to map a wall-clock `timestamp` → active `sequence`.
- As a result, two compliant implementers can make different choices:
  - A) “Try all available keys (current/previous/history) and accept if any verifies” (like PUSE verification).
  - B) “Attempt to select exactly one key based on timestamp” (but selection is underdetermined) and potentially reject.

This can lead to nodes disagreeing on whether the same `.postapp` / repository manifest / updates manifest is valid.

**Interoperability impact**
Different validators may accept vs reject the same signed artifact, fragmenting the app ecosystem.

**Fix (normative)**
Define a single interoperable algorithm for package/repo/update signature verification key selection. For example:

- **Option A (simplest, aligns with PUSE):** Verifiers MUST attempt signature verification with keys in order:
  1) `keys.signing.current`
  2) `keys.signing.previous` (if present)
  3) `keys.signing.history[]` (all entries; optionally allow filtering but must not reject solely because `expires_at` has passed unless the spec explicitly wants that)
  Accept if any verifies.

- **If timestamp-based filtering is desired**, the spec must also define how to map time→key, which likely requires either:
  - mandating retention/availability of historical IDOCs by sequence, or
  - adding timestamp ranges to history entries (not just sequence ranges).

### HIGH-2: **Glare resolution ordering is easy to mis-implement because other parts of the spec require raw-byte IID ordering**
**Where**
- Normative glare resolution: `spec/06-rfcs/RFC-0002-transport.md` §8.5 (lexicographic compare of `(iid, did)` **strings**)
- Elsewhere: multiple places mandate raw-byte comparisons for IIDs (e.g., RFC-0003 `kdf_initial` and Test Vector 6; `spec/03-messaging-sync/double-ratchet.md`)

**Problem**
The ecosystem uses **two different comparison domains**:
- For cryptographic salts (2DH): compare **raw 20-byte IID values** bytewise.
- For glare resolution (RFC-0002): compare **Base32 string** representations lexicographically.

Because both are “lexicographic IID comparisons” in English, an implementer may (reasonably) reuse the raw-byte comparison logic for glare resolution. If one peer uses raw-byte ordering and the other uses Base32 string ordering, they can disagree about which connection to keep, leading to persistent duplicate connections or both sides closing different connections.

**Interoperability impact**
Connection establishment instability and nondeterministic behavior under simultaneous connect (“glare”), especially in multi-device scenarios.

**Fix (normative, cross-doc)**
Make the glare ordering rule impossible to misread:
- State explicitly (in RFC-0002 and in `spec/01-transport-connectivity/interfaces.md`) that glare resolution uses **ASCII lexicographic ordering of the 32-char Crockford Base32 lowercase strings**, not decoded raw bytes.
- Add an explicit “MUST NOT decode to raw bytes for glare resolution ordering” note, since other parts of the spec do require decoding for ordering.

## MEDIUM issues

### MEDIUM-1: **Several examples contradict the “wire-required fields MUST be present” rule**
**Where**
- Normative rule: `spec/06-rfcs/RFC-0001-identity-document.md` §6.6 and `spec/02-identity-trust/identity-document-schema.md` (“All top-level fields MUST be present…”)
- Potentially non-conformant examples:
  - `spec/02-identity-trust/key-rotation.md` (rotation document snippet omits `keys.signing.history`, etc.)
  - `spec/02-identity-trust/recovery-mechanisms.md` (recovery-published IDOC example appears to omit some wire-required fields)
  - `spec/02-identity-trust/revocation.md` examples are not always explicit about required embedded IDOC fields inside `replacement_document`

**Problem**
The normative requirement is clear, but examples that omit required fields are a common source of implementer divergence (some will “materialize defaults before JCS/signing”; others will sign literal JSON). That difference breaks signature verification and byte-identical comparisons (e.g., DHT TTL refresh).

**Interoperability impact**
Risk of generating identity documents that strict verifiers reject, depending on which document an implementer followed.

**Fix**
Update all identity document examples outside RFC-0001 to include:
- `keys.signing.history: []`
- `keys.encryption.previous: []`
- `claims: {}` and `extensions: {}`
- `recovery_proof: null`
- `signatures.previous: null` (when appropriate)
…and any other RFC-0001 §6.6 wire-required fields.

(Alternatively, clearly label abbreviated examples as “non-wire, illustrative only; not valid for signing or DHT storage”.)

### MEDIUM-2: **Missing explicit “exact length / no trailing bytes” rules for PURL and PUSE parsing**
**Where**
- PURL format: `spec/06-rfcs/RFC-0002-transport.md` §7.4 (defines `Payload Length`, but does not explicitly require UDP datagram length == 44 + payload_length)
- PUSE format: `spec/06-rfcs/RFC-0003-messaging.md` §3.2/§3.8 (defines `ext_len` and `ct_len`, but does not explicitly require the container length to match exactly and to reject trailing bytes)

**Problem**
Some implementations will:
- accept packets/envelopes with trailing bytes (ignoring them),
- others will reject (treating as malformed).

Even if conformant senders never produce malformed lengths, explicit “reject trailing bytes” rules are important because these formats are used as payloads inside other framing contexts (QUIC frames, mailbox blobs, logs/wire captures). Ambiguity here can produce inconsistent accept/reject behavior and complicate conformance testing.

**Interoperability impact**
Divergent parsing strictness can cause one implementation to drop traffic another accepts (especially in presence of buggy intermediaries, partial reads, or malicious inputs).

**Fix (normative)**
- **PURL:** “Parsers MUST reject if datagram length != 44 + payload_length.”
- **PUSE:** “Parsers MUST reject if `len(envelope_bytes) != 64 + ext_len + 12 + 4 + ct_len + 64`.” (Given envelopes are length-delimited in QUIC frames and mailbox blobs, this is implementable and unambiguous.)

## LOW issues

### LOW-1: **Test vector messaging around IDOC signatures can still confuse implementers**
**Where**
- `spec/06-rfcs/RFC-0001-identity-document.md` §15.2 indicates signature values are illustrative / require recalculation.
- `spec/00-shared/test-vectors.md` Test Vector 2 provides deterministic construction but still uses `<computed-by-implementation>`.

**Problem**
This is not a wire-format ambiguity, but it undermines conformance reproducibility: some implementers will look for a concrete expected signature and not find one.

**Fix**
Provide the actual expected `signatures.current` value for the Test Vector 2 IDOC, or clearly label it as “intentionally omitted” and point to an authoritative generator output that includes the expected signature bytes.
