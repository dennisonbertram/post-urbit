## HIGH: Packaging signature verification contradicts identity key-expiry rules and itself

**Where**
- `spec/05-ux-packaging/app-distribution.md`:
  - “Verification Process” step 9: “Lookup key that was active at timestamp in identity document”
  - “Signature Key Selection (Normative)”: try `current`, `previous`, then **all** `history[]` “regardless of `expires_at`”
- `spec/06-rfcs/RFC-0001-identity-document.md` §7.5 and `spec/03-messaging-sync/secure-envelope.md` / `spec/06-rfcs/RFC-0003-messaging.md` §3.8:
  - history keys are tried **only if `expires_at` has not passed** (and RFC-0001 uses `expires_at` as a cutoff for “may reject”, but RFC-0003 makes it effectively required by saying “whose `expires_at` has not passed”).

**Why this breaks interop**
Two conforming nodes can disagree on whether an old package is installable:
- Implementation A follows app-distribution “regardless of expires_at” → accepts.
- Implementation B follows the identity/messaging rule “only if expires_at not passed” → rejects.

Also, “key active at timestamp” is not computable from a single current IDOC without an explicit timestamp→key mapping (IDOC history entries are keyed by **sequence windows**, not activation timestamps, and nodes may not have historic IDOCs).

**Fix**
Make one rule canonical across all consumers:
- Option 1 (recommended for install UX): **MUST** try `current`, `previous`, then all `history[]` **ignoring `expires_at`**, and treat `expires_at` as a **UI warning only** for packaging verification.
- Option 2: require packages to carry an **author IDOC sequence number** (or key fingerprint) and verify against that, with a precise retrieval procedure.

Right now the spec requires incompatible behaviors.

## HIGH: `test-vectors.md` claims reproducible IDOC signature verification but provides no expected signature

**Where**
- `spec/00-shared/test-vectors.md` “Test Vector 2: Identity Document Signature” uses:
  - `signatures.current: "<computed-by-implementation>"`
- “Verification Checklist” item 3: “Signature verification passes for Test Vector 2”

**Why this breaks interop**
Independent implementations cannot confirm they canonicalize/sign the same bytes. Self-verification (“signature verifies against the pubkey I just derived”) is not a cross-implementation test—any bug that is self-consistent passes.

**Fix**
Provide the **expected 64-byte signature** (hex and base64) for Test Vector 2, computed over the provided canonical JCS bytes with domain `post-urbit:idoc:v1:` and the given seed.

## HIGH: Mailbox HTTP protocol omits normative HTTP status codes and error body shapes

**Where**
- `spec/06-rfcs/RFC-0003-messaging.md` §7.4.1/7.4.2/7.4.3 specify requests and JSON bodies but do not normatively specify:
  - Status codes (200 vs 201 vs 204)
  - Content-Type on responses
  - Error response schema (JSON vs text) for each failure case (e.g., token invalid vs sender mismatch vs payload too large)

**Why this breaks interop**
Mailbox clients often branch on status code and may unconditionally JSON-decode error bodies. Different server choices here will cause client failures despite “conformance”.

**Fix**
For each endpoint, specify at minimum:
- Success status code (e.g., **POST 200**, **GET 200**, **DELETE 200** with JSON or **204** with empty body)
- Error status code mapping and a single required error JSON schema (or explicitly allow empty bodies and require clients to handle it).

## HIGH: IDOC rotation verification does not normatively bind `keys.signing.previous` to the prior document’s key

**Where**
- `spec/06-rfcs/RFC-0001-identity-document.md` §7.2 / §8.2
- `spec/02-identity-trust/identity-document-schema.md` “Key rotation invariants” (descriptive, but not enforced in the verifier algorithms)
- `spec/00-shared/layer-integration.md` DHT update authorization step 4 checks `signatures.previous` using stored `keys.signing.current`, but does not require `new_doc.keys.signing.previous == old_doc.keys.signing.current`.

**Why this breaks interop**
Some verifiers will enforce the structural invariant (`keys.signing.previous` must equal old current key), others will ignore it and accept based solely on `signatures.previous` verification. Documents with inconsistent `keys.signing.previous` would fork acceptance.

**Fix**
Add a normative verification step everywhere rotation is validated (RFC-0001 verifier, DHT update rules, and identity layer verifier):
- If `keys.signing.current` changed, `keys.signing.previous` **MUST be present and MUST equal** the previously accepted `keys.signing.current` (byte-identical Base64 string), and `signatures.previous` MUST verify with that key.

## MEDIUM: QUIC 0-RTT text is confusing vs the handshake’s “after TLS” requirements

**Where**
- `spec/06-rfcs/RFC-0002-transport.md` §8.3 discusses QUIC 0-RTT usage and safe operations.
- §5.2/§5.5 require the control stream and handshake messages after TLS completion and require `tls_binding` from exporter.

**Why this matters**
Some implementations may attempt to send handshake/control data in 0-RTT (or expect peers to accept it), while others cannot (library exporter availability, replay constraints). This is likely to produce connection failures if attempted.

**Fix**
Either:
- explicitly state that **no Post-Urbit application bytes are sent in QUIC 0-RTT in v1** (0-RTT only used for transport resumption but identity handshake still gates all streams), or
- define an “early binding” exporter mechanism and transcript rules (probably v2).
