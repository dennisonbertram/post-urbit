## Issues

### 1) QUIC 0-RTT policy contradicts itself across documents
**Severity: HIGH**

- **RFC-0002 §8.3**: “implementations MUST NOT send application-layer data … in QUIC 0-RTT early data” and states Post-Urbit protocol bytes must be 1-RTT+.
- **`spec/01-transport-connectivity/quic-integration.md`**: describes 0-RTT as usable for “SAFE_FOR_0RTT” operations like `identity_request`, `ping`, `presence`.

**Why this matters:** Independent implementations could diverge:
- Some may attempt to transmit Post-Urbit stream frames in 0-RTT (based on `quic-integration.md`), while others treat 0-RTT Post-Urbit bytes as forbidden (RFC-0002).
- Even if many QUIC stacks delay delivery until handshake completion, the spec contradiction itself is a compatibility risk: one stack may drop/disable early data; another may allow and process it.

**Fix:** Make non-RFC docs explicitly defer to RFC-0002 for 0-RTT, and remove/replace the “SAFE_FOR_0RTT” list with “0-RTT transport resumption is allowed, but **no Post-Urbit protocol bytes** may be sent before `tls_binding` is available.”

### 2) Mailbox token includes `mailbox_url` but server-side binding requirement is not explicit
**Severity: HIGH**

- **RFC-0003 §7.3** defines extremely detailed **mailbox_url canonicalization**, and the signature input includes the canonical `mailbox_url`.
- However, the spec does **not clearly require** the mailbox server to enforce that `token.mailbox_url` matches the mailbox server’s own canonical URL (scheme/host/port/path base used by that service).

**Why this matters:** Two independent mailbox implementations may differ:
- Server A **requires** `token.mailbox_url` to match its canonical base URL → rejects tokens created with an equivalent-but-different URL string (e.g., missing `/`, port normalization disagreements, reverse-proxy host differences).
- Server B does **not** check this → accepts the same token.

That yields real interoperability failures (client works with some mailbox servers but not others) even if both “follow” the spec as written.

**Fix (normative):** Add a requirement like:
- Mailbox server MUST compute its own canonical mailbox base URL (define inputs: scheme must be `https`, host from configured public hostname, port from configured public port, and an explicit base path if any).
- Server MUST reject tokens where `token.mailbox_url` ≠ that canonical base URL.
- Also specify how deployments behind reverse proxies determine the “public” host/port (configuration, not request headers).

### 3) IDOC signature test vector is not a concrete vector (cannot serve as conformance oracle)
**Severity: HIGH**

- `spec/00-shared/test-vectors.md` **Test Vector 2** (“Identity Document Signature”) states the signature is deterministic, but the “Signed Document” uses:
  - `signatures.current: "<computed-by-implementation>"`
- **RFC-0001 §15.2** similarly says the signature shown is “illustrative” and “requires recalculation”.

**Why this matters:** Canonicalization/signature interoperability failures are common, and without an explicit expected 64-byte signature value, independent implementations can each be “confident” while still producing incompatible signatures (due to subtle JCS differences, field omission/materialization bugs, UTF-8 details, etc.).

**Fix:** Provide at least one **fully specified expected** `signatures.current` (base64) for the canonical JSON shown (and ideally also provide the full IDOC envelope bytes and length). This should be treated as a normative MUST-match vector in the conformance suite.

### 4) `expires_at` enforcement semantics are inconsistent (MAY vs MUST) for signing-key history
**Severity: MEDIUM**

- `spec/02-identity-trust/identity-document-schema.md` says for signing key history entries: after `expires_at`, “verifiers **may** reject”.
- **RFC-0001 §7.5** and **RFC-0003 §3.8** define key-selection for message verification as:
  - try `history[]` entries whose `expires_at` has **not** passed (effectively **rejecting** expired history keys).

**Why this matters:** Different receivers may accept/reject the same delayed/archived message depending on whether they treat `expires_at` as advisory vs mandatory.

**Fix:** Make the policy explicit by context, e.g.:
- For **PUSE message verification**: receivers MUST NOT accept history keys past `expires_at` (or MUST accept; pick one).
- For **package signature verification**: expires_at MUST be ignored (already stated in `spec/05-ux-packaging/app-distribution.md`).
- For other contexts, define MAY/SHOULD accordingly.

Right now the documents imply different normative strength.

### 5) Stream “max message size” vs frame overhead is ambiguous at the byte boundary
**Severity: MEDIUM**

- RFC-0003: PUSE envelope max size is **1,048,576 bytes** total envelope.
- RFC-0002 §6.4: Message stream max message size is **1 MB** and “matches PUSE max”.

But QUIC stream framing adds a 4-byte length prefix per frame. It’s not stated whether the 1MB limit is:
- payload-only (PUSE bytes), or
- total frame (length-prefix + payload).

**Why this matters:** An implementation that enforces “frame total ≤ 1MB” will reject a valid max-sized PUSE envelope that another implementation sends.

**Fix:** State explicitly: stream limits apply to **frame payload length**, excluding the 4-byte length prefix (or include it; choose one). For PUSE, it should almost certainly be “payload length == envelope length”.

---

### 6) Optional handshake fields: RFC says “absent == null”, peer-handshake.md does not
**Severity: MEDIUM**

- **RFC-0002 §5.5**: optional fields MAY be omitted or present with `null`, and receivers MUST treat them equivalently.
- **`spec/01-transport-connectivity/peer-handshake.md`** shows schemas using `"<...>|null"` patterns, but does not clearly state the “absent vs null equivalence” rule.

**Why this matters:** Some implementations may require explicit `null` fields (or require presence), breaking handshake interop with implementations that omit optional keys.

**Fix:** Either (a) replicate RFC-0002’s explicit rule into `peer-handshake.md` (with a “non-authoritative; see RFC” note), or (b) strip normative schema language from `peer-handshake.md` and hard-link to RFC-0002 sections.
