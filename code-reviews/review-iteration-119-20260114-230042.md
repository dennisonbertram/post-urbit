Below are the remaining interoperability risks I see in the merged spec snapshot. I’m focusing on places where two independent implementations could both “follow the spec” yet still diverge (accept/reject different artifacts, parse different values, or compute different signatures).

---

## 1) BLOCKING — Conflicting normative rules for `keys.signing.history[].expires_at` in PUSE signature verification (mailbox vs realtime)

**Where**
- `spec/06-rfcs/RFC-0003-messaging.md` §3.8 “Signature Verification Key Selection (Normative)”
- `spec/06-rfcs/RFC-0003-messaging.md` §3.8 “`expires_at` Enforcement (Normative by Context)” table
- Also echoed in non-RFC docs (e.g. `spec/03-messaging-sync/secure-envelope.md` key selection example)

**What**
- RFC-0003 §3.8 says (normative) to try `keys.signing.history[]` **only** where `expires_at has not passed`.
- The later “Normative by Context” table says mailbox-delivered messages **SHOULD NOT** be rejected due to `expires_at` if the message was sent before expiry.

These are incompatible as written because the signature verification step occurs **before decryption**, and thus does not have access to the plaintext `timestamp`. The only available candidate “send time” is the nonce’s 4-byte timestamp component (unencrypted), but the spec explicitly discourages rejecting based on timestamp age, and it does not specify using it for key selection.

**Interop impact**
- Implementation A (following “history keys whose `expires_at` has not passed”) will reject some mailbox-delayed messages.
- Implementation B (following “mailbox should not reject”) will accept them.
- This creates real cross-node delivery failures and inconsistent user-visible behavior.

**Required fix**
Pick one normative rule set and make it algorithmically implementable **at signature-check time**. Options:
1) **Simplest (recommended for interop):** For PUSE signature verification, **ignore `expires_at` entirely** and try all keys in `current → previous → history[]`. Treat `expires_at` as UI/audit metadata only.  
2) **If you want context sensitivity:** Make the verification algorithm explicitly depend on delivery path:
   - If received via mailbox: try `current → previous → history[]` **without** `expires_at` filtering.
   - If received via realtime QUIC: MAY/SHOULD enforce `expires_at > now`.
   This still needs a normative definition of “received via mailbox” for the verifier.
3) **If you want “sent-before-expiry” semantics:** Normatively define using the **nonce timestamp seconds** as the “envelope timestamp” for this purpose (and explicitly acknowledge it is attacker-controlled, so it’s a best-effort hint). Then define:
   - accept history key if `nonce_timestamp <= expires_at + skew`.

## 2) BLOCKING — Package signature verification requires “key valid at timestamp” but provides no implementable key-selection rule consistent with that requirement

**Where**
- `spec/05-ux-packaging/app-distribution.md` “Verification Process” step 9 and “Timestamp Semantics” table
- `spec/05-ux-packaging/app-distribution.md` “Signature Key Selection (Normative)”
- `spec/02-identity-trust/identity-document-schema.md` signing history fields (`valid_from`/`valid_until` are sequences, not time)

**What**
- The verification process requires checking that “the author’s signing key at timestamp was valid” (and “not revoked before timestamp”).
- But the only structured “validity window” data you have for keys in IDOC is sequence-based (`valid_from`, `valid_until`) plus an `expires_at` timestamp which is explicitly treated as optional / policy-dependent elsewhere.
- The same doc later declares a different normative rule: try `current`, then `previous`, then **all** `history[]` “regardless of `expires_at`”, and accept if any verifies.

These are not the same requirement, and the “valid-at-timestamp” check is not specified in a way that an independent verifier can implement without access to historical IDOCs (which are generally *not* guaranteed to be fetchable by timestamp).

**Interop impact**
- Some implementations will implement strict “key must be the one active at timestamp” and reject packages that others accept (or vice versa).
- Repository ecosystems will fragment: installs/updates accepted on some nodes but rejected on others.

**Required fix**
Make the package signature acceptance rule precise and implementable with only the data you guarantee is available. For example:

- **Option A (most interoperable):**
  - A package signature is valid if it verifies under **any** of `{current, previous, history[]}` keys in the author’s *current* IDOC, **and** there is no applicable revocation record for that key with `effective_at <= signature.timestamp`.
  - Explicitly remove/replace the “lookup key active at timestamp” step.
- **Option B (if you truly require “active at timestamp”):**
  - Define a required mechanism to fetch the historical IDOC at or before a timestamp (e.g., DHT key namespace for IDOC history, or an append-only log). Nothing like this is currently defined, so this would be a larger change.

## 3) HIGH — Identity document signature test vector is non-concrete / self-contradictory across docs

**Where**
- `spec/00-shared/test-vectors.md` Test Vector 2 (“Expected Signature (Normative)” but omits the signature value)
- `spec/06-rfcs/RFC-0001-identity-document.md` §15.2 / §15.4 explicitly say signature values are illustrative / “REQUIRES-RECALCULATION”

**What**
- The shared test vectors document positions itself as “concrete, reproducible”, but for the IDOC signature it provides no expected signature bytes.
- RFC-0001 includes placeholders and says prior computed values were for an older canonical form.

**Interop impact**
- This is a major footgun: independent implementers are likely to get JCS, field inclusion, or domain-prefix handling slightly wrong and have no single authoritative reference output to detect it.
- Conformance harnesses cannot be deterministic here.

**Required fix**
- Publish the actual `signatures.current` Base64 value for Test Vector 2 (and, ideally, the full IDOC envelope bytes + hash).
- Remove “illustrative / requires recalculation” language from RFC-0001 test vector sections or clearly mark them non-normative and point exclusively to `spec/00-shared/test-vectors.md` as the single canonical source.

## 4) HIGH — Missing normative binding rule between PUSE header recipient (raw 20 bytes) and plaintext `group_id` fields

**Where**
- `spec/06-rfcs/RFC-0003-messaging.md` §3 (PUSE header) and §8.6 (`group_state_update` includes `content.group_id`)
- `spec/03-messaging-sync/group-messaging.md` (group operations embed `group_id` in plaintext examples)

**What**
For group-scoped messages (especially `group_state_update`), the group identity appears in two places:
- PUSE header: `recipient_iid/group_id` (20 raw bytes)
- Plaintext content: `content.group_id` (32-char Base32 string)

The spec does not state:
- whether receivers MUST reject if they don’t match,
- which one is authoritative if they differ,
- whether group_id must be omitted for some message types (to avoid duplication).

**Interop impact**
Two implementations may apply the same decrypted operation to different local groups if a buggy sender produces mismatched values (or if a relay/mailbox/wrapper bug swaps header fields). Even if you consider this “invalid sender behavior”, receivers still need deterministic handling rules to converge.

**Required fix**
Add an explicit rule, e.g.:
- For `recipient_type=group`, receivers MUST compute `Base32(recipient_raw)` and require it equals plaintext `content.group_id` for any plaintext type that includes a `group_id` field (at least `group_state_update`, `sender_key_share`, `group_invite`, etc.), otherwise reject with `INVALID_MESSAGE` / `INVALID_GROUP_ID_MISMATCH`.
- Alternatively, remove `group_id` from plaintext for group-addressed messages and declare the header recipient as the only source of truth (but this is a schema change).

## 5) MEDIUM — RFC-0003 mailbox URL canonicalization pseudocode contradicts the normative “reject invalid percent-escapes” rule

**Where**
- `spec/06-rfcs/RFC-0003-messaging.md` §7.3 “Reference Implementation (Illustrative)” `normalize_percent_encoding`

**What**
The normative text says invalid percent escapes MUST be rejected (including a bare `%` or truncated escape). The illustrative code only rejects when `%` is followed by at least two chars but not hex; if `%` occurs at the end (or `%` + one char), it falls through and does not raise.

**Interop impact**
Some implementers will copy the reference code and accept inputs that other implementations reject, causing mailbox token verification mismatches.

**Required fix**
Update the illustrative code to match the normative rule (reject `%` not followed by exactly 2 hex digits), or add an explicit warning that the pseudocode is incomplete and must not be used verbatim.

## 6) MEDIUM — “1 MB” limits are inconsistent in meaning across layers (plaintext vs envelope vs frame)

**Where**
- `spec/06-rfcs/RFC-0003-messaging.md` §3.2 (max envelope size = 1,048,576 total bytes)
- `spec/06-rfcs/RFC-0002-transport.md` §6.4 (Message stream frame payload max = 1,048,576 bytes)
- `spec/03-messaging-sync/interfaces.md` constants: `MAX_MESSAGE_SIZE: 1048576` described as “Message limits”
- `spec/04-app-runtime/api-surface.md` messaging APIs permit `content: Uint8Array` up to “1 MB” conceptually, but don’t specify whether that’s pre- or post-PUSE

**What**
The protocol-level limit is clearly defined for wire frames and PUSE envelopes. But the app/runtime layer surfaces “1 MB” without clarifying whether that is:
- app plaintext JSON size,
- CBOR `content` size,
- or final PUSE envelope size.

**Interop impact**
Not a wire-format mismatch, but it causes predictable cross-implementation behavioral divergence (some nodes will reject sends that others accept due to different preflight size checks).

**Required fix**
Normatively tie app/runtime limits to the wire envelope limit (e.g., host must ensure resulting PUSE envelope ≤ 1,048,576 and return `MESSAGE_TOO_LARGE` otherwise), and if desired define a recommended maximum plaintext size derived from worst-case overhead.

### Summary of severities
- **BLOCKING (2):**
  1) PUSE signature key selection vs `expires_at` mailbox policy contradiction (RFC-0003).
  2) Package signature “key valid at timestamp” requirement is not implementably specified and conflicts with alternative normative key-selection rules (app-distribution).
- **HIGH (2):**
  - Non-concrete/contradictory IDOC signature test vectors.
  - Missing binding rule between PUSE recipient raw group_id and plaintext `group_id`.
- **MEDIUM (2):**
  - Mailbox URL canonicalization reference code mismatch.
  - Ambiguous meaning of “1 MB” limits across app/runtime vs wire.

No other new contradictions stood out in the areas you called out (0-RTT prohibition is consistent across RFC-0002 + QUIC integration docs; absent/null equivalence is aligned; mailbox URL binding exists and is specified).

Since there are BLOCKING issues, I cannot mark the spec as complete.
