I found **BLOCKING** inconsistencies that would cause independent implementations to reject each other’s artifacts.

## BLOCKING-1: `expires_at` is still treated as normative in some places, but non-normative in others (signature key selection)

### Where it occurs (contradictory requirements)
- **RFC-0003 (Messaging) §3.8**: *Normative* key selection says verifiers **MUST** try:
  1) `keys.signing.current`, 2) `previous`, 3) **ALL** `history[]` entries **regardless of `expires_at`**, and **MUST NOT** reject based on `expires_at`.
- **spec/03-messaging-sync/secure-envelope.md**: signature verification example still filters history keys by:
  - “Only try keys that haven’t expired (`expires_at`)”
- **RFC-0001 (Identity) §7.5**: still specifies using history entries whose `expires_at` “has not passed” for delayed message verification.
- **RFC-0002 (Transport) §5.8 Device Verification**: references key lookup order as “current → previous → history entries not expired”.
- **spec/02-identity-trust/identity-document-schema.md**: says verifiers **MAY** reject signatures after `expires_at` (permission to reject creates interop divergence).

### Why this is interoperability-breaking
Two compliant implementations can legitimately diverge:
- Impl A follows RFC-0003 and accepts a mailbox-delivered PUSE signed with a historical key even if `expires_at` has passed.
- Impl B follows RFC-0001/secure-envelope.md and rejects the same envelope due to `expires_at`.

That’s a hard on-the-wire acceptance mismatch (messages fail to verify).

### Required spec fix
Pick one rule and apply it everywhere normative. If iteration 120’s intent is “`expires_at` is UI metadata only”, then:
- Remove/override **all** normative uses of `expires_at` in verification:
  - RFC-0001 §7.5
  - secure-envelope.md signature verification section
  - RFC-0002 device-doc signature key lookup rule
  - identity-document-schema.md “MAY reject after expires_at” language (or demote to purely informational UI guidance)

## BLOCKING-2: Mailbox URL canonicalization is internally inconsistent (rules vs pseudocode vs normative test vectors)

### Where it occurs
- **RFC-0003 §7.3 Mailbox URL Canonicalization (Normative)**:
  - States: “Unreserved characters MUST NOT be percent-encoded.”
  - Also provides **normative canonicalization test vectors** including:
    - Input: `https://example.com/%41%42%43`
    - Output: `https://example.com/ABC`  (**decodes** percent-encoded unreserved)
- **RFC-0003 §7.3 Reference Implementation (Illustrative)**:
  - `normalize_percent_encoding()` **only uppercases** hex in `%xx`, and **does not decode** percent-encoded unreserved bytes.
  - Therefore it would output `https://example.com/%41%42%43` (or `%41%42%43` with uppercase), not `.../ABC`.

### Why this is interoperability-breaking
Mailbox bearer tokens sign over the canonicalized `mailbox_url`, and **verifiers MUST reject non-canonical forms**. With the current contradiction:
- Impl A canonicalizes by *decoding* `%41`→`A` (per test vectors + “MUST NOT be percent-encoded” rule).
- Impl B canonicalizes by only *uppercasing* percent-escapes (per pseudocode / common implementations).

They will compute different `signature_input` bytes ⇒ mailbox token signature verification fails between implementations.

### Required spec fix
Make the percent-encoding normalization algorithm fully explicit and consistent with the normative vectors. Concretely, you need a single normative rule for:
- Whether to **decode** percent-encoded octets that correspond to RFC3986 “unreserved” characters (`ALPHA / DIGIT / "-" / "." / "_" / "~"`).
- Whether decoding applies only to those unreserved octets, and **never** to reserved/space (`%20` remains `%20`), etc.
- Whether decoding happens **before** or **after** uppercasing percent hex.
- How to handle percent-encoded bytes that are not valid UTF-8 sequences (your current rules operate at the URL-string level, but percent-escapes represent raw bytes).

At minimum:
- Either update the pseudocode to decode unreserved percent-escapes (to match the vectors), **or**
- change the test vectors and the “MUST NOT be percent-encoded” rule to match a “do-not-decode, only normalize hex” policy.

Right now the spec is self-contradictory.

## HIGH-1: IDOC signature test vector is not a concrete expected value (weak conformance / high risk of “looks right” divergence)

### Where it occurs
- **spec/00-shared/test-vectors.md**, Test Vector 2:
  - Provides deterministic inputs and the exact signing input bytes,
  - But explicitly omits the expected signature (“computed-by-implementation”).
- **RFC-0001 §15.2 / §15.4** similarly call signatures “illustrative” and “requires recalculation”.

### Why this matters for interoperability
Without a published expected signature value, an implementation can:
- accidentally use **Ed25519ph** (or wrong key derivation, wrong canonicalization),
- still “verify” its own outputs locally,
- and only discover incompatibility later.

You *do* provide concrete signatures for other vectors (handshake, PUSE), which is good; IDOC should be equally concrete.

### Recommended fix
Publish the deterministic `signatures.current` value (hex + base64) for Test Vector 2, derived from the already-specified signing input bytes. This is a conformance accelerant and prevents silent divergence.

## MEDIUM-1: “Packages must remain verifiable indefinitely” conflicts with IDOC signing-key history retention limits

### Where it occurs
- **spec/02-identity-trust/identity-document-schema.md**: signing history retention “at most 10 entries or 2 years”.
- **spec/05-ux-packaging/app-distribution.md**: says package signatures are a point-in-time assertion that “must remain verifiable indefinitely”, but also admits keys older than history retention can’t be verified.

### Interop impact
Not an immediate wire-format mismatch, but it creates diverging implementation strategies:
- Some will accept that old packages become unverifiable after history retention.
- Some may implement external key archival / historical-IDOC fetch to preserve indefinite verification.

Clarify the intended requirement (e.g., “verifiable for at least history retention window unless archival mechanisms are used”).

# Summary of required changes (to reach “iteration 120” consistency)

1. **Unify signature key selection** across RFC-0001, RFC-0002, secure-envelope.md, and identity-document-schema.md with RFC-0003’s rule *or* explicitly scope different rules by context. As written, it’s contradictory and interoperability-breaking.
2. **Fix mailbox URL canonicalization** to be internally consistent:
   - rules ↔ pseudocode ↔ normative test vectors must agree on percent-escape decoding of unreserved characters.
3. (Strongly recommended) Publish the missing concrete IDOC signature value in Test Vector 2.
