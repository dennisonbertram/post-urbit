## BLOCKING Issues (interop failures likely)

### BLOCKING-1: `expires_at` handling for **signing key history** is still contradictory in RFC-0001 DHT/device verification
**Where:**
- `spec/06-rfcs/RFC-0001-identity-document.md`
  - §7.5: explicitly says `expires_at` **MUST NOT** be used as a verification rejection criterion (“metadata only”).
  - §12.8 (DHT Verification Rules): says for **Device Documents** key lookup includes “history entries whose `expires_at` has not passed”.

**Why it breaks interop:**
Two compliant implementations can diverge:
- Impl A follows §7.5 and accepts a device document signed by a historical identity signing key even if that key’s `expires_at` is in the past.
- Impl B follows §12.8 and rejects it once `expires_at` passes.

This can prevent device discovery and/or device-authenticated handshakes in the wild, depending on which DHT nodes/clients are stricter.

**What to fix (normative):**
- Pick one rule and make it consistent. If the intent is “UI metadata only,” then RFC-0001 §12.8 MUST be updated to remove any `expires_at` gating and instead say “try all history entries regardless of `expires_at`”, matching §7.5 and RFC-0002 §5.8.

## HIGH Issues (significant ambiguity; interop risk)

### HIGH-1: Identity TS interface contradicts “`expires_at` is metadata only” for signing keys
**Where:**
- `spec/02-identity-trust/interfaces.md`
  - `interface SigningKeyHistory { expiresAt: Timestamp; // After this time, verifiers may reject signatures }`

**Why it breaks interop:**
This directly contradicts:
- `spec/02-identity-trust/identity-document-schema.md` (“MUST NOT be used as a signature rejection criterion”)
- `spec/03-messaging-sync/secure-envelope.md` (try all history keys regardless of `expires_at`)
- `spec/06-rfcs/RFC-0001-identity-document.md` §7.5 (metadata only)
- `spec/06-rfcs/RFC-0002-transport.md` §5.8 (device document verification: ignore `expires_at`)
- `spec/06-rfcs/RFC-0003-messaging.md` §3.8 (PUSE verification: MUST NOT reject based on `expires_at`)

Implementers who treat this TS comment as normative will reject otherwise-valid signatures and fail to interoperate with nodes that rotate keys and rely on history for delayed delivery.

**What to fix:**
- Update `SigningKeyHistory.expiresAt` comment to match the normative rule:
  - “UI/audit metadata only; MUST NOT be used to reject signatures.”

### HIGH-2: Packaging spec asserts message verification “MAY enforce `expires_at`” (contradicts RFC-0003)
**Where:**
- `spec/05-ux-packaging/app-distribution.md`
  - Under “Signature Key Selection” / `expires_at` handling:  
    > “This differs from real-time message verification (RFC-0003 §3.8) where `expires_at` MAY be enforced.”

**Why it breaks interop:**
RFC-0003 §3.8 and `secure-envelope.md` say the opposite: message verification **MUST NOT** reject based on `expires_at`. This statement invites implementations to do something that will cause cross-implementation message verification failures.

**What to fix:**
- Remove/replace the sentence. If you want a distinction, keep it strictly about **UI warning behavior**, not verification outcomes.

---

### HIGH-3: Messaging plaintext schema for `media` message content is inconsistent between RFC-0003 and Messaging interfaces (bytes vs JSON strings)
**Where:**
- `spec/03-messaging-sync/interfaces.md`:
  - `MediaContent.key: Uint8Array; nonce: Uint8Array;`
- `spec/06-rfcs/RFC-0003-messaging.md` §8.4:
  - `key` and `nonce` are shown as `"<...-base64>"` strings (JSON).

**Why it breaks interop:**
PUSE plaintext is specified as **UTF-8 JSON** (`secure-envelope.md` / RFC-0003 §8.1). JSON cannot carry `Uint8Array` natively. Without a normative mapping rule, independent implementations may serialize media keys differently (base64 string vs array of integers vs object wrapper), breaking message parsing at the application layer.

**What to fix (normative):**
- Declare the on-wire JSON types for `media.content.key` and `media.content.nonce` explicitly as:
  - Base64 standard (no padding) strings of lengths 32 bytes and 12 bytes respectively.
- Update `spec/03-messaging-sync/interfaces.md` to represent decrypted/in-memory form separately, or provide an explicit conversion rule (wire ↔ API).

## MEDIUM Issues (minor gaps, but can cause confusion/test failures)

### MEDIUM-1: IDOC signature test vector still lacks a concrete expected signature value
**Where:**
- `spec/00-shared/test-vectors.md` Test Vector 2: explicitly refuses to provide the final signature.
- `spec/06-rfcs/RFC-0001-identity-document.md` §15.2: “signature values … illustrative … requires recalculation”.

**Why it matters:**
For interoperability, canonicalization/signing are the most fragile. A concrete expected signature is the fastest way to detect divergent JCS canonicalization or domain-separator handling across implementations.

**What to fix:**
- Publish the computed 64-byte signature (hex + base64) for Test Vector 2 as normative.
- If you want cross-impl confirmation too, keep that *in addition* to a fixed value, not instead of it.

---

### MEDIUM-2: RFC-0001 pseudocode does not enforce the “JCS-canonical JSON in IDOC envelope” requirement
**Where:**
- `spec/06-rfcs/RFC-0001-identity-document.md`:
  - §6.2 says envelope JSON MUST be JCS-canonical.
  - §11.4 `parse_idoc_envelope()` pseudocode only `json.loads()`; no canonicality check.

**Why it matters:**
This is a “foot-gun”: implementers may copy pseudocode and accept non-canonical IDOCs, undermining byte-identical refresh semantics and conflict equivalence comparisons.

**What to fix:**
- Add an explicit canonicality verification step in parsing pseudocode (or explicitly label pseudocode as incomplete and non-normative).
