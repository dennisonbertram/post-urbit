## BLOCKING issues (prevent interoperable implementations)

### B1 — Group messages cannot be delivered via mailbox as specified (routing key mismatch)
**Where**
- **Group PUSE envelopes**: recipient field is **GroupID** when `flags.recipient_type = 0x01`  
  - RFC-0003 §3.3 “Recipient type values” + §3.4.4 Group extension (recipient is group ID)  
  - secure-envelope.md “Recipient IID (raw) … (or group ID)” and group-messaging.md
- **Mailbox storage/routing**: mailbox stores/retrieves by **recipient IID extracted from PUSE header bytes 26–45** and filters retrieval by `token.iid` == envelope recipient bytes  
  - RFC-0003 §7.4.1 “Storage Keying and Routing (Normative)” step 1–2 (recipient extracted from PUSE header)  
  - RFC-0003 §7.4.2 “Retrieval Filtering (Normative)” (recipient_iid must equal token.iid)

**Problem**
For a **group message**, PUSE header bytes 26–45 contain **group_id_raw**, not a recipient IID. Therefore:
- Storing a group envelope will store it under the **group ID**, not under the offline member’s IID.
- Retrieval for a user authenticated as `token.iid = <member IID>` will **never return** those stored group messages (recipient bytes won’t match).

Yet **group-messaging.md** explicitly says offline members should receive group messages via mailbox (“For each offline member: determine mailbox … send to mailbox”), which is impossible under the mailbox routing rules above.

**Interop impact**
Independent implementations will disagree on how to do offline group delivery; any implementation that follows RFC-0003 mailbox routing literally cannot deliver group messages offline.

**Required resolution (normative)**
Pick one mailbox routing model and make it consistent across RFC-0003 + layer docs:

Option A (minimal change to PUSE): **Mailbox store API must include an explicit inbox owner IID separate from the envelope recipient field**, e.g.
- `POST /messages/<recipient_iid>` or `POST /messages` with a required header/field `recipient_iid`
- Mailbox stores under that IID regardless of PUSE recipient bytes, while still validating sender binding vs token.

Option B (change group delivery format): define a **mailbox-specific group fanout envelope format** where the envelope is addressed to the recipient IID (so mailbox routing works) and carries group_id elsewhere (plaintext or a new header extension). This would require updating the “recipient_type ↔ extension type linkage” rules in RFC-0003 §3.3.

## HIGH issues (significant ambiguity; likely interop divergence)

### H1 — DHT update authorization is missing a required key-continuity check in the DHT-specific rules
**Where**
- RFC-0001 §7.2 “Key Continuity Binding (Normative)” requires:
  1) `keys.signing.previous` present  
  2) equals previously accepted `keys.signing.current`  
  3) `signatures.previous` verifies with that key
- RFC-0001 §12.8 “Update Authorization (Existing Identity Records)” describes DHT-node behavior but **does not explicitly require** checking that `keys.signing.previous` equals the stored document’s `keys.signing.current`.

Layer glue text mirrors this omission in its DHT-node “Update Authorization” procedure.

**Problem**
Some DHT storage nodes may implement only “verify `signatures.previous` using stored current key” and skip the explicit `keys.signing.previous` equality check, while others enforce §7.2 strictly. That yields inconsistent acceptance/rejection of the *same update* across DHT implementations.

**Interop impact**
- Network-level: different DHT nodes store different “latest” docs; clients see inconsistent sets.
- Client-level: clients that require §7.2 may reject documents stored by permissive DHT nodes, reducing discoverability and causing hard-to-diagnose failures.

**Required resolution**
Make RFC-0001 §12.8 explicitly include the §7.2 binding check for the DHT update case (and mirror in layer-integration.md):
- If signing key changed: `keys.signing.previous` MUST be present and MUST equal stored `keys.signing.current` (byte-identical Base64 string), and `signatures.previous` MUST verify with that key (or recovery proof path).

### H2 — Missing concrete IDOC signature value in “Test Vector 2” prevents deterministic cross-implementation conformance checking
**Where**
- spec/00-shared/test-vectors.md “Test Vector 2: Identity Document Signature” explicitly says the signature is deterministic and normative, but then intentionally omits the expected signature bytes.

**Problem**
This defeats the primary purpose of a crypto test vector: catching canonicalization/signing differences across independent implementations. Without a published expected signature, an implementation can “verify itself” and still be non-interoperable (e.g., if its JCS output differs subtly).

**Interop impact**
High probability of silent divergence in JCS/signing input handling, which will manifest as IDOC verification failures between implementations.

**Required resolution**
Publish the **exact** expected `signatures.current` for the given seed and signing input (hex + base64), similar to the already-concrete vectors (handshake, sync, PUSE).

### H3 — App Host API method status is internally inconsistent (`contacts.get`)
**Where**
- spec/04-app-runtime/abi.md method registry labels `contacts.get` as **reserved**
- spec/04-app-runtime/api-surface.md:
  - early section lists `contacts.get` among **reserved methods not specified**
  - but later in “Contacts API” method table lists `contacts.get` as a normal method with capability mapping (though without a schema)

**Problem**
Implementers cannot know whether:
- `contacts.get` MUST exist in v1 (and with what CBOR schema), or
- it MUST return `NOT_IMPLEMENTED` as a reserved method.

**Interop impact**
Apps compiled against one host may fail against another due to differing method availability and argument/result encoding.

**Required resolution**
Pick one:
- Make `contacts.get` v1: specify request/response CBOR schema and remove from “reserved” lists, or
- Keep it reserved: remove it from v1 tables and explicitly state it returns `NOT_IMPLEMENTED`.

## MEDIUM issues (edge-case gaps; can still cause divergence)

### M1 — Device-document expiry handling is not consistently specified for DHT storage vs handshake acceptance
**Where**
- Handshake device verification (peer-handshake.md / RFC-0002 §5.8) requires rejecting expired `device_document.expires_at` (if present).
- RFC-0001 DHT device-document verification sections emphasize signature validation but do not clearly state whether DHT nodes MUST reject expired device docs at store time.

**Problem**
Some DHT nodes may store expired device documents; others may reject. Clients may then:
- discover expired device docs and attempt to connect (failing later), or
- never discover any device endpoints depending on which DHT nodes they query.

**Suggested resolution**
Specify explicitly:
- Either “DHT nodes MUST reject storing expired device documents” (recommended for usability), or
- “DHT nodes MAY store them but clients MUST ignore expired device docs for connection attempts”.

### M2 — Sync `operation_id` uniqueness scope is unclear (document-scoped vs global)
**Where**
- sync-protocol.md defines `operation_id = SHA256(origin || timestamp_bytes || operation_bytes || dependencies_bytes)` (no `document_id`)
- Wire messages carry both `document_id` and `id`.

**Problem**
It’s not stated whether `operation_id` is:
- unique only within `(document_id, operation_id)`, or
- expected to be globally unique.

Some implementations will key storage by `operation_id` alone; others by `(document_id, operation_id)`. If document-scoped uniqueness is intended, it should be stated normatively.

**Suggested resolution**
Add a normative statement: operation identity is the tuple `(document_id, operation_id_bytes)`; dependencies MUST refer to operations within the same document; storage indexes MUST include `document_id`.
