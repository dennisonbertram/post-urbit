## Targeted consistency checks

### 1) Group mailbox delivery uses `POST /messages/{inbox_owner_iid}`
**Consistent across the three docs**:

- **RFC-0003 §7.4.1** defines `POST /messages/{inbox_owner_iid}` and explicitly states the mailbox MUST store by the **URL path inbox owner IID**, not the PUSE envelope recipient field (which is `group_id` for group messages).
- **spec/03-messaging-sync/group-messaging.md** (“Mailbox Delivery for Group Messages (Normative)”) uses `POST /messages/{member_iid}` and explains this is the *member’s inbox owner IID* (and that the PUSE recipient remains `group_id`). This is the same endpoint shape with different variable naming.
- **spec/00-shared/layer-integration.md** (“Mailbox Protocol”) lists `POST /messages/{inbox_owner_iid}` and repeats the group-message nuance (“PUSE recipient is group_id; inboxOwnerIid specifies which mailbox receives it”).

**No interop issue found** for this item.

### 2) DHT update authorization includes explicit key-continuity check
**Consistent between**:

- **RFC-0001 §12.8** (“Update Authorization (Existing Identity Records)”) and  
- **spec/00-shared/layer-integration.md** (“DHT Record Format” verification / update authorization)

Both specify, when `keys.signing.current` changes:
- `keys.signing.previous` MUST be present and MUST equal the stored document’s `keys.signing.current` (byte-identical Base64 string comparison), and
- `signatures.previous` MUST verify using the stored current signing key, **OR** a valid `recovery_proof` must be provided (in which case continuity binding is not required).

**No interop issue found** for this item.

### 3) Test Vector 2 has a concrete signature value
In **spec/00-shared/test-vectors.md**, Test Vector 2 **does** provide a concrete, normative `signatures.current` value (hex + Base64) and even the exact `signing_input` bytes.

However, **RFC-0001 §15.2 / §15.4** still says the signature values are “illustrative” and “require recalculation”, and shows placeholders like `<REQUIRES-RECALCULATION>`.

This is a **cross-document contradiction** about whether RFC-0001’s Test Vector section is authoritative/usable.

### 4) `contacts.get` is consistently reserved
Not fully consistent in this repository:

- **spec/04-app-runtime/abi.md**: `contacts.get` is listed as **reserved**.
- **spec/04-app-runtime/api-surface.md**: `contacts.get` is included in the **reserved methods** list and has **no v1 schema**.
- **spec/04-app-runtime/capability-system.md**: the `CAPABILITY_MAP` lists `'contacts.get': 'contacts:read'` and states “**This mapping is authoritative**”.

That combination creates a likely split: an implementer following “authoritative” `CAPABILITY_MAP` may assume `contacts.get` exists as a callable method (and implement it), while another implementer following `abi.md`/`api-surface.md` will return `NOT_IMPLEMENTED` for it.

## Issues found (interop-relevant)

### HIGH — RFC-0001 test vector text contradicts `test-vectors.md` for Test Vector 2
- **Where:** `spec/06-rfcs/RFC-0001-identity-document.md` §15.2 and §15.4 vs `spec/00-shared/test-vectors.md` Test Vector 2.
- **Problem:** `test-vectors.md` declares a *normative expected signature*; RFC-0001 declares its own signature content “illustrative / requires recalculation”.
- **Why it matters:** Independent implementers may treat different documents as the conformance oracle, leading to inconsistent verification tooling and potentially rejecting correct implementations during interoperability testing/certification.
- **Fix:** Make RFC-0001 §15.2/§15.4 either (a) copy the concrete signature from `test-vectors.md` and mark it normative, or (b) remove/replace the RFC’s signature placeholders and explicitly defer to `spec/00-shared/test-vectors.md` as the only authoritative test-vector source.

### HIGH — `contacts.get` reserved status is contradicted by “authoritative” capability mapping
- **Where:** `spec/04-app-runtime/abi.md` + `spec/04-app-runtime/api-surface.md` (reserved) vs `spec/04-app-runtime/capability-system.md` (`CAPABILITY_MAP` includes it and calls the mapping “authoritative”).
- **Problem:** The spec simultaneously says “reserved/NOT_IMPLEMENTED” and “authoritative mapping includes it”, which encourages divergent implementations.
- **Why it matters:** App portability across host implementations can fail if some hosts implement `contacts.get` while others (correctly) reject it as reserved.
- **Fix options (pick one):**
  1. Remove `contacts.get` from `CAPABILITY_MAP` (or mark it explicitly as reserved/always NOT_IMPLEMENTED in the map), **or**
  2. Promote `contacts.get` to v1: define its CBOR schema in `api-surface.md` and mark it v1 in `abi.md`.

### LOW — `progress.md` contains contradictory historical statements about mailbox routing
- **Where:** `spec/progress.md` “Issues Fixed (Iteration 107)” claims mailbox store/retrieve/delete keying is by “recipient_iid from PUSE header”, while RFC-0003 §7.4.1/§7.4.2/§7.4.3 are explicit that mailbox storage/routing is by **URL inbox owner IID** (and retrieval by `token.iid` inbox).
- **Problem:** Non-normative but misleading; can send implementers to the wrong routing model.
- **Fix:** Correct the wording in `progress.md` (or clearly mark it as potentially stale/non-normative historical notes).

### LOW — Version/iteration mismatch (user says iteration 123; repo says iteration 110)
- **Where:** user prompt vs `spec/progress.md` header.
- **Problem:** Spec version identification ambiguity (editorial).
- **Fix:** Ensure a single canonical spec version identifier and keep repo metadata aligned.
