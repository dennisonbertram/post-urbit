## BLOCKING (certain interop failure)

### B1) WASM Host API / ABI uses CBOR but does not normatively define the CBOR *wire* schemas
**Where:**  
- `spec/04-app-runtime/abi.md` (defines `host.call` args/result as CBOR, and `handle` input/result as CBOR)  
- `spec/04-app-runtime/api-surface.md` (defines request/response “interfaces” but not CBOR encoding)  
- `spec/04-app-runtime/wasm-sandbox.md` (references Host API usage)

**Problem:** These documents define TypeScript-shaped request/response structures, but do not specify the canonical CBOR representation that independent implementations must produce/accept, including at minimum:
- whether structs are encoded as CBOR maps with **text string keys** (and whether keys are snake_case as shown),
- whether keys must be present vs may be omitted vs may be `null`,
- how `Uint8Array` is encoded (CBOR byte string vs array of ints),
- how numeric bounds are handled (esp. 64-bit integers; CBOR supports them but many runtimes won’t round-trip through JS/JSON-like representations),
- whether deterministic/canonical CBOR is required (affects reproducibility and cross-runtime testing).

Two independent implementations (host runtime and app toolchain, or two runtimes) can easily choose different “obvious” CBOR encodings and fail immediately at the ABI boundary.

**Interop impact:** A `.wasm` app built for one runtime can fail on another because method arguments/results aren’t decodable.

**What to add (normative):** For each Host API method and for `HandleInput` / `HandleResult`, define an explicit CBOR schema (e.g., “CBOR map with text keys exactly matching snake_case field names; required keys MUST be present; optional keys MUST be omitted (or MUST be null)”, etc.), and specify integer handling (uint64 vs int64) and any canonical CBOR requirements.

### B2) DHT network/wire protocol is not specified (only an abstract API + “recommended” implementation)
**Where:**  
- `spec/00-shared/layer-integration.md` (“DHT Protocol Stack (Normative)” explicitly says routing/network protocol is out of scope; recommends Kademlia but not required)  
- `spec/06-rfcs/RFC-0002-transport.md` (explicitly puts discovery/DHT out of scope and points to `layer-integration.md`)  
- `spec/01-transport-connectivity/overview.md` (DHT is a core part of discovery integration)

**Problem:** The spec defines *what* keys/values look like in the DHT, but not *which DHT protocol/network* implementations must speak to participate in the same discovery plane:
- no required DHT wire protocol (e.g., “libp2p Kademlia over …”, protocol IDs, record validation rules at the transport level),
- no required node identity/transport for the DHT overlay (libp2p PeerID vs IID binding, etc.),
- bootstrap is “published separately” (not in-spec), so even two correct implementations can’t reliably join the same network.

Given two independent implementations, “use any DHT that meets these requirements” is not interoperable: they can both be compliant yet on different DHT overlays and never discover each other.

**Interop impact:** Peer discovery fails across implementations unless they coincidentally choose the same external DHT stack, protocol IDs, bootstrap set, and deployment.

**What to add (normative):** Either:
- standardize one concrete DHT stack and its wire protocol profile (recommended: libp2p Kademlia with exact protocol IDs, record validators, and bootstrap discovery rules), **or**
- define a Post-Urbit DHT wire protocol in-spec (even if based on Kademlia), including bootstrap discovery.

## HIGH (likely interop failure)

### H1) Hole-punch coordination signaling is underspecified (message transport/channel not defined)
**Where:**  
- `spec/01-transport-connectivity/nat-traversal.md` (defines JSON messages `hole_punch_request/offer/accept` and probe packet format, but not how/where those JSON messages are carried)  
- `spec/01-transport-connectivity/relay-protocol.md` (mentions relay-assisted hole punching with a JSON “coordination message”, but not integrated into RFC-0002 relay control plane)

**Problem:** The spec gives JSON shapes for coordination but omits the normative wire binding:
- which QUIC stream type carries these JSON coordination messages (Control 0x01? Identity 0x02? something else?),
- whether they require prior mutual authentication (handshake done or not),
- whether relay-assisted coordination uses PURL control packets, HTTPS, or a distinct protocol endpoint,
- framing/canonicalization requirements for these coordination messages (length-prefixed frames per RFC-0002?).

Independent implementations will guess different channels/handlers and hole punching will not interoperate.

**Interop impact:** Direct connectivity for NATs requiring coordination becomes unreliable or non-functional across implementations, especially if relays are not implemented/available (spec describes relays as “optional” in several places).

**What to add (normative):** Define a specific transport binding for hole-punch coordination:
- exact stream type (likely Control 0x01 JSON),
- message schemas + required fields,
- authentication/authorization requirements,
- relay coordination mechanism if relays are used (PURL control payload type vs HTTPS endpoint).

## MEDIUM (edge cases / likely divergence)

### M1) IDOC JCS-canonical verification + arbitrary `extensions` can become non-interoperable due to JSON number handling
**Where:**  
- `spec/02-identity-trust/identity-document-schema.md` (requires JCS; `extensions` is arbitrary JSON up to 4KB)  
- `spec/06-rfcs/RFC-0001-identity-document.md` (§6 JCS rules; signature over `JCS(doc_without_signatures)`)

**Problem:** JCS requires numeric canonicalization, but the spec does not constrain numeric ranges/representations inside `extensions` (or other free-form objects). Some implementations/languages parse JSON numbers as IEEE754 doubles (lossy for large integers), which can produce different canonical outputs and break signature verification even if the sender is “correct”.

**Interop impact:** Edge-case signature verification failures for documents that include large numeric values in extension fields.

**What to add (normative):** Constrain JSON number usage in any signed JSON fields that are unconstrained (`extensions`): e.g., “numbers MUST be in IEEE754 safe integer range” or “large integers MUST be encoded as strings”.

### M2) Endpoint host normalization language is partly advisory; could yield inconsistent connection behavior
**Where:**  
- `spec/02-identity-trust/identity-document-schema.md` (host normalization guidance, IPv6 bracket rules described but not consistently “MUST”)

**Problem:** Some normalization rules (lowercase hostnames, bracketed IPv6, trailing dots) are described, but not always with strict MUST-level enforcement. Implementations may accept/store/publish variants differently and then fail to connect to each other in edge cases (not a signature issue, but a connectivity parsing/interpretation issue).

**Interop impact:** Occasional endpoint parsing/connection failures (esp. IPv6 literal formatting).

**What to add:** Promote key normalization rules to explicit MUSTs for wire-encoded endpoints, or define exact accepted forms and required normalization on receipt.

## LOW (editorial / confusing but not normative interop break)

### L1) `spec/progress.md` contains statements inconsistent with current normative mailbox routing
**Where:**  
- `spec/progress.md` “Issues Fixed (Iteration 107): … Mailbox storage routing … store/retrieve/delete by recipient_iid from PUSE header”

**Problem:** Current normative specs (`RFC-0003` §7.4.1–7.4.3 and `layer-integration.md` Mailbox section) define mailbox storage keyed by the explicit `inbox_owner_iid` path parameter (and explicitly *not* by PUSE recipient for group messages). The progress log text contradicts that and can mislead implementers who treat it as guidance.

**Interop impact:** Documentation confusion; not normative if progress.md is non-authoritative, but still risky.

**Fix:** Update or clearly mark progress.md as non-normative and correct the mailbox note.
