## BLOCKING (certain interop failure)

### B1) DHT record key *wire key* format is contradictory (raw 32 bytes vs string `"/post-urbit/<hex>"`)
**Where**
- `spec/00-shared/layer-integration.md`
  - “Fixed-length keyspace: Keys are exactly 32 raw bytes…”
  - “DHT Key Output … 32 raw bytes, passed directly to the DHT API.”
  - **But also**: “Namespace Key Format: `DHT Key = "/post-urbit/" + hex(SHA256(prefix + identifier))`” and shows `dht_key` as a string.
- `spec/01-transport-connectivity/interfaces.md`: `dhtGet(key: Uint8Array)` / `dhtPut(key: Uint8Array, ...)` explicitly take **32 raw bytes**.
- `spec/06-rfcs/RFC-0001-identity-document.md` §12.1: `dht_key(...) -> bytes` returns **32 raw bytes** (SHA-256 digest), with no `"/post-urbit/"` namespace string.

**Why this breaks interop**
Two independent implementations will store and query under different Kademlia record keys:
- Impl A uses the 32-byte SHA-256 digest as the record key.
- Impl B uses the ASCII bytes of `"/post-urbit/" + hex(digest)` as the record key.
Those keys are not equal, so GETs won’t find PUTs across implementations.

**What must be specified**
Pick exactly one normative record-key encoding for the libp2p Kademlia DHT:
- Either **record key bytes = 32-byte digest**, and document how that maps onto libp2p record key APIs (string/bytes) without re-encoding, **or**
- **record key bytes = UTF-8 string** `"/post-urbit/" + hex(digest)` (77 bytes), and update every place that currently says “32 raw bytes” (interfaces + RFC-0001).

### B2) libp2p PeerID / DHT Node ID derivation is internally inconsistent (length mismatch) and underspecified for real libp2p interop
**Where**
- `spec/00-shared/layer-integration.md` → “DHT Node Identity” / “libp2p PeerID Derivation (Normative)”

**Problem**
The spec gives a “normative” PeerID byte construction:
- Text says: identity multihash `0x00` + length `0x24` + `0xed01` + pubkey.
- The provided code returns: `bytes([0x00, 0x24, 0xed, 0x01]) + ed25519_pubkey`.
  - That yields a multihash where the **declared digest length is 0x24 (=36)** but the digest bytes provided are **34 bytes** (`0xed 0x01` + 32-byte pubkey). This is inconsistent even within the document.

**Why this breaks interop**
- Any implementation that follows the code literally will produce an invalid multihash / invalid PeerID bytes (length field mismatch). Implementations using standard libp2p libraries will generate PeerIDs using libp2p’s actual key encoding rules, not this custom broken encoding. Result: nodes cannot agree on identity-to-PeerID mapping, and may fail to connect/bootstrap into the same overlay or compute consistent DHT node IDs where required.

**What must be specified**
For interoperability with existing libp2p stacks, the spec must normatively define one of:
1) **Use standard libp2p PeerID derivation** from Ed25519 keys as implemented by libp2p (including the exact protobuf/multicodec framing), and reference the canonical libp2p spec/source, OR  
2) Define a **fully custom PeerID format** with byte-accurate multihash/varint rules (and fix the length mismatch), and require implementations to use that (even if it requires nonstandard libp2p changes).

Right now it is contradictory and would cause implementations to diverge.

### B3) DHT security transport requirements contradict QUIC realities (Noise vs TLS 1.3 over QUIC)
**Where**
- `spec/00-shared/layer-integration.md` → “DHT Transport Layer”
  - Says: “libp2p Noise or TLS 1.3 … MUST support Noise; TLS 1.3 RECOMMENDED”
  - Also says DHT uses QUIC `/quic-v1` (RFC 9000/9001), which **mandates TLS 1.3** as part of QUIC.

**Why this breaks interop**
Two compliant implementations could choose different mutually-incompatible stacks:
- Impl A: libp2p over QUIC (TLS 1.3 only; typical libp2p-quic behavior).
- Impl B: tries to satisfy “MUST support Noise” by requiring Noise security negotiation (typical for TCP transports), which doesn’t apply to QUIC in the same way.
They may not negotiate a common security layer and fail to connect/participate in the same DHT overlay.

**What must be specified**
State a single interoperable requirement for DHT security on QUIC, e.g.:
- “For QUIC transport, the connection security is QUIC TLS 1.3; Noise is not used on QUIC.”  
and if TCP fallback is allowed:
- specify Noise (or TLS) **only for TCP fallback**, with explicit protocol IDs.

As written, the MUST/RECOMMENDED combination is contradictory.

## HIGH (likely interop failure)

### H1) Hole-punch coordination signatures are “SHOULD” in schema but treated as mandatory in verification text
**Where**
- `spec/01-transport-connectivity/nat-traversal.md`:
  - Message schemas list `"signature": "<...>"` as **SHOULD** for `hole_punch_request` / `hole_punch_accept`.
  - Later: “Verification: Recipients MUST verify signatures by fetching the signer’s identity document…”

**Why this breaks interop**
One implementation may omit signatures (allowed by “SHOULD”), while another treats them as required (per “MUST verify signatures”), rejecting coordination messages and causing hole punching to fail.

**What must be specified**
Choose one:
- Make `signature` **MUST** for relay-assisted coordination (and define behavior for direct coordination separately), or
- Keep it optional, but then explicitly specify receiver behavior when signature is absent (e.g., accept if authenticated channel, reject if relay-assisted, etc.).

## MEDIUM (edge-case interop problems)

### M1) DHT bootstrap node encoding is not fully pinned (PeerID string encoding/base)
**Where**
- `spec/00-shared/layer-integration.md` bootstrap config uses `"peer_id": "<libp2p-peer-id-base58>"`.

**Why this can break interop**
libp2p PeerID string representations can vary (base58btc, base36, CIDv1 forms). If one implementation expects base58btc and another emits CIDv1/base36, bootstrap lists may not be consumable.

**What must be specified**
Normatively require one textual representation for configuration exchange (e.g., “PeerID MUST be multibase base58btc string of the raw PeerID bytes”).
