## BLOCKING issues (certain interop failure)

### 1) IDOC required-field contradiction: `keys.signing.history` omitted in one “canonical” schema rendering
**Where:**
- `spec/02-identity-trust/identity-document-schema.md` → **“Document Structure”** JSON block shows `keys.signing` with `genesis/current/previous` but **omits `history`**.
- Same file later (“Nested Required Fields” + “Field Presence Rules”) says **`keys.signing.history` is wire-required** and must be present (possibly `[]`).
- `spec/06-rfcs/RFC-0001-identity-document.md` §4.1/§4.3/§6.6: `keys.signing.history` is present and **MUST be present** in wire encoding.
- `spec/00-shared/test-vectors.md` Test Vector 2 canonical document includes `"history":[]` (i.e., required on-wire).

**Why this breaks interop:**
A producer that follows the earlier “Document Structure” example will emit an IDOC lacking `keys.signing.history`. A verifier following RFC-0001 §6.6 (and/or the later “wire-required” rule) **must reject** such documents as missing a required field. Two independent implementations will therefore fail to interoperate.

**Fix (normative editorial repair):**
Update `identity-document-schema.md`’s “Document Structure” canonical JSON to include:
```json
"signing": { "genesis": "...", "current": "...", "previous": null, "history": [] }
```
and ensure every other “canonical structure” example across the repo matches RFC-0001 §6.6’s required-field set.

## HIGH issues (likely interop failure)

### 2) “Domain Separator Registry (Normative)” is incomplete vs transport/NAT signature specs
**Where:**
- `spec/00-shared/layer-integration.md` → “Domain Separator Registry (Normative)” claims to list **all** cryptographic domain separators and says implementations **MUST use these exact byte sequences**.
- `spec/01-transport-connectivity/nat-traversal.md` defines hole-punch coordination signatures using domain separator **`post-urbit-holepunch-v1`** (23 bytes) and hash-then-sign construction.
- That domain separator is **not present** in the “Domain Separator Registry (Normative)” table.
- Similarly, `spec/00-shared/layer-integration.md` “Signature Prehash Policy (Normative)” table specifies prehash rules for Transport contexts (handshake/relay alloc/rebind) but **does not mention hole-punch** (which is also a transport-layer signature context in `nat-traversal.md`).

**Why this breaks interop:**
Implementers who treat the registry as authoritative (as it states) will not implement the hole-punch domain separator and/or will guess the prehash rule. For relay-assisted hole punch, signatures are **MUST** (per `nat-traversal.md`). Any mismatch in domain separator or prehash policy causes deterministic signature verification failure, breaking NAT traversal interoperability.

**Fix:**
- Add `post-urbit-holepunch-v1` to the registry table in `layer-integration.md`.
- Add hole-punch to the Signature Prehash Policy table (it currently specifies `Ed25519_Sign(key, SHA256(x))` in `nat-traversal.md`; the shared table should explicitly match that).

## MEDIUM issues (edge-case / implementer-guesswork)

### 3) Sync “timestamp” type naming collision across docs can lead to wrong CBOR encoding choices
**Where:**
- `spec/03-messaging-sync/sync-protocol.md` defines a CBOR `Timestamp` **map** `{physical, logical, origin}` for sync ordering.
- Many other documents/types define `Timestamp` as an RFC3339 **string** (including shared `Timestamp` typedefs).
- `spec/03-messaging-sync/interfaces.md` tries to clarify the distinction, but the naming reuse (“Timestamp” for both concepts across the repo) remains easy to misapply.

**Why this can break interop:**
An implementation may accidentally encode sync timestamps as RFC3339 text strings (or decode expecting strings) rather than the required CBOR map form, causing CBOR parsing failures and signature/operation-id mismatches.

**Fix:**
Rename the sync HLC structure in the sync-protocol spec to a distinct term everywhere (e.g., `HLC` only), and avoid using the word `Timestamp` for both RFC3339 strings and HLC maps in the same repository.

## LOW issues (editorial / misleading but not wire-ambiguous by itself)

### 4) `spec/progress.md` contradicts the normative mailbox routing model
**Where:**
- `spec/progress.md` contains historical notes (e.g., Iteration 107/108/109 entries) that state mailbox routing keyed by recipient IID from the PUSE header.
- `spec/06-rfcs/RFC-0003-messaging.md` §7.4.1 is explicit that mailbox storage/routing is keyed by the **URL path parameter** `inbox_owner_iid` (and token’s IID), not by parsing the PUSE recipient field (which is group_id for group messages).

**Why this matters:**
`progress.md` is non-normative, but it is in the repo and written in a way that can be mistaken as current truth. An implementer using it as guidance can implement the wrong mailbox routing and break group mailbox fanout interop.

**Fix:**
Mark `progress.md` explicitly non-normative at the top and/or remove/correct the misleading mailbox routing bullets.
