## BLOCKING (certain / spec-internal contradiction → divergent implementations)

### B1. RFC-0002 §8.3 contradicts itself on whether *any* Post-Urbit bytes may be sent in QUIC 0‑RTT
- **Where:**
  - `spec/06-rfcs/RFC-0002-transport.md` §8.3 “0-RTT Resumption”
- **Contradictory statements:**
  1. “**MUST NOT send application-layer data** in QUIC 0-RTT early data.”
  2. “all **Post-Urbit protocol bytes MUST be sent in 1-RTT or later**.”
  3. Immediately after: “0‑RTT data can be replayed … **Safe operations: identity_request, ping, presence** … Implementations MUST NOT send replay-sensitive operations in 0‑RTT.”
- **Why this breaks interop:** One implementation can reasonably interpret the “safe operations” paragraph as permitting some Post‑Urbit frames in 0‑RTT (e.g., `identity_request`), while another will interpret the earlier MUST/MUST NOT as forbidding *all* Post‑Urbit bytes until 1‑RTT / handshake completion. That yields incompatible behavior (early-data sender vs receiver that treats it as protocol violation / ignores / closes).
- **What to fix (normative):**
  - Either delete the “safe operations” paragraph for v1, **or**
  - explicitly mark it “future versions only” and state **v1 MUST send zero Post‑Urbit bytes in 0‑RTT**, including no stream opens and no control frames, until TLS is confirmed and `tls_binding` is available.

## HIGH (likely interop failure / implementers must guess)

### H1. DHT bootstrap addressing format is inconsistent (multiaddr with `/p2p/...` vs separate `peer_id`)
- **Where:**
  - `spec/00-shared/layer-integration.md` “Bootstrap Node Configuration” JSON shows:
    - `"peer_id": "<libp2p-peer-id-base58>"` separate, and `"multiaddrs": ["/ip4/.../udp/4433/quic-v1", ...]` **without** `/p2p/<peerid>`.
  - Later in the same file, “Interoperability Test” vector shows a bootstrap multiaddr **with** `/p2p/12D3KooW...` appended:
    - `/dns4/test.bootstrap.post-urbit.net/udp/4433/quic-v1/p2p/12D3KooW...`
- **Why this breaks interop:** Implementations will diverge on what they must parse/emit/accept for bootstrap discovery:
  - Some will treat `/p2p/<peerid>` as required in each multiaddr (common libp2p convention),
  - others will rely on the separate `peer_id` field and reject `/p2p`-suffixed addrs or ignore it.
  Either divergence can prevent bootstrapping into the same DHT overlay.
- **What to fix (normative):**
  - Specify **one canonical bootstrap encoding**:
    - Option A: multiaddrs MUST include `/p2p/<peerid>` and `peer_id` field is optional/derived, **or**
    - Option B: `peer_id` field is REQUIRED and multiaddrs MUST NOT include `/p2p`, **or**
    - Option C: accept both, but define precedence and validation rules (e.g., if `/p2p` present it MUST match `peer_id`).

### H2. Multi-device messaging depends on “implementation-defined” ratchet state sync
- **Where:**
  - `spec/02-identity-trust/identity-document-schema.md` “Multi-Device Implications (v1: Identity-Level Sessions)” says: “Ratchet state is synced between devices … (implementation-defined)”.
  - `spec/03-messaging-sync/secure-envelope.md` “Multi-Device Model” states identity-level addressing and internal device fanout, but does not define a cross-device ratchet-state synchronization wire contract.
- **Why this breaks interop:** If a single identity uses multiple devices (a primary goal of having DIDs/device docs), then:
  - sending from different devices without a standardized ratchet-state sharing rule can cause chain index reuse, skipped-key divergence, or message loss/decrypt failure for peers.
  - Two independent implementations for two devices of the same identity will not reliably interoperate.
- **What to fix (normative):** Choose one:
  1. **Define a ratchet-state sync mechanism** (e.g., via Sync stream 0x04 with a specific CBOR message schema), or
  2. **Constrain behavior**: e.g., “For a given (sender IID, recipient IID) conversation, exactly one device may send; other devices MUST proxy via that device,” plus define how that proxying occurs, or
  3. Change the protocol model (e.g., per-(IID,DID) sessions) — larger change.

## MEDIUM (edge-case / ambiguity likely to cause divergent behavior)

### M1. “Connection reuse” between Post-Urbit QUIC and libp2p DHT is underspecified / likely infeasible as written
- **Where:** `spec/00-shared/layer-integration.md` “Connection Reuse: … reuse that connection for DHT operations”
- **Problem:** DHT is specified as **libp2p Kademlia** (multistream-select, libp2p peer identity), while Post‑Urbit transport is a custom QUIC protocol with ALPN `post-urbit/1` and its own stream-type framing. Reusing the same QUIC connection is not defined (and typical QUIC stacks cannot multiplex different ALPN protocols on one established connection).
- **Interop impact:** Some implementers may attempt reuse (and fail), others won’t. Not strictly required (“SHOULD”), but it’s a spec ambiguity that invites incompatible designs.
- **Fix:** Clarify “reuse” as **UDP socket/port reuse only**, or define a concrete multiplexing approach (e.g., a single QUIC server supporting multiple ALPNs, with separate connections per ALPN).

### M2. Relay allocation request nonce encoding is not consistently pinned outside RFC-0002
- **Where:**
  - RFC-0002 §7.8 requires `nonce` base64url no padding, 16 bytes (22 chars).
  - `spec/01-transport-connectivity/relay-protocol.md` uses `nonce: "<16-bytes-base64url>"` without explicitly stating **no padding** / fixed length.
- **Interop impact:** Minor but real: some clients may send padded base64url, some relays may reject.
- **Fix:** Mirror RFC-0002’s exact rule in relay-protocol.md (base64url, **no padding**, exactly 16 bytes → 22 chars).

### M3. Device doc / device index DHT value canonicalization is not consistently required across all docs
- **Where:**
  - RFC-0001 §12.4/§12.5 explicitly says DHT Value is **JCS-canonical JSON** for device index/device doc.
  - `spec/00-shared/layer-integration.md` “Device Document DHT Format” describes “Device document (JSON…)” but doesn’t explicitly state the stored bytes MUST be JCS-canonical (unlike IDOC).
- **Interop impact:** If some DHT nodes dedupe/compare by byte equality, non-canonical JSON encodings can create spurious “multiple distinct values” and inconsistent conflict handling.
- **Fix:** Add an explicit “DHT nodes MUST reject non-JCS-canonical device-doc/device-index JSON bytes” (or explicitly allow non-canonical bytes and require canonicalization-before-compare everywhere).
