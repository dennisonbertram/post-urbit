## BLOCKING

### 1) Multi-device connectivity model contradicts itself (device-discovery vs “single home node”)
**Why this breaks interop:** Two independent implementers can reasonably follow different “authoritative” passages and produce incompatible multi-device behavior (which endpoints to publish/look up; which device(s) accept inbound peer connections; whether peers should enumerate devices).

**Conflicting normative statements:**
- **Single Home Node Model (normative):** `spec/02-identity-trust/identity-document-schema.md` states (v1 normative) that all devices **MUST connect to a single “home node”** managing ratchet state, and “Devices do NOT directly communicate with remote peers for encrypted messaging; they proxy through their home node.”
- **Device discovery flow implies remote peers connect to each device:** `spec/00-shared/layer-integration.md` “Device Discovery Flow” instructs a peer to fetch a device index, fetch per-device docs, then “Connect to device endpoints … First successful connection wins.”
- **Transport API suggests per-device peer connections are a first-class feature:** `spec/01-transport-connectivity/interfaces.md` defines `PeerId { iid, did? }` and allows `connect(peerId: PeerId | IdentityIdentifier)` and describes connections as unique per `(local_iid, local_did, peer_iid, peer_did)`.

**Interop failure modes:**
- Implementation A (home-node-only) publishes only identity endpoints and expects peers to connect only to the home node; Implementation B follows device discovery and attempts per-device connects. B may connect to a non-home device that A never exposes for peer messaging/sync streams (or A never expects inbound), causing handshake/stream expectations to diverge.
- Device-specific relay endpoints are implied by per-device endpoint lists, but relay routing is explicitly IID-only in v1 (see `spec/01-transport-connectivity/relay-protocol.md` and RFC-0002), making “connect to a specific device via relay” impossible as described.

**What’s missing to resolve it:**
- A single normative statement answering: *Are device documents/device indexes meant for external peer selection, or only for internal (same-identity) device management?*
- If **home-node-only** is the v1 model, then the device discovery flow should be explicitly marked **non-normative** or scoped to **intra-identity** connectivity only, and Transport `connect()` should normatively resolve via **identity endpoints** (not device index) for peer messaging/sync.
- If **per-device external connectivity** is required, then v1 needs a ratchet-state synchronization protocol (or “ratchet sessions are per-(iid,did)”) to avoid guaranteed state divergence.

## HIGH

### 2) Identity endpoint wire format is contradicted by a “DHT interoperability test” example
**Why this is likely to break interop:** Endpoint encoding is fundamental to making a QUIC connection after discovery. A contradictory “test vector” encourages divergent encodings.

**Conflict:**
- **Canonical endpoint schema is host/port JSON object**: `spec/02-identity-trust/identity-document-schema.md` defines endpoints as objects `{type, host, port, transport, priority, ...}` and Transport `Endpoint` mirrors this (`spec/01-transport-connectivity/interfaces.md`).
- **But** `spec/00-shared/layer-integration.md` “Interoperability Test” describes “Node A publishes IDOC with endpoint: `/ip4/192.0.2.1/udp/4433/quic-v1`” (a multiaddr string), which does not match the endpoint schema.

**Needed normative fix:**
- Replace the multiaddr-style endpoint in that test with the actual endpoint object, or explicitly state that this is a *non-IDOC* “connection address” representation distinct from `IdentityDocument.endpoints`.

### 3) Bulk stream (0x05) is registered but lacks a complete normative wire protocol
**Why this is likely to break interop:** Two implementations cannot exchange bulk transfers without agreeing on message formats beyond “2-byte opcode + data”.

**Where:**
- `spec/00-shared/layer-integration.md` and `spec/01-transport-connectivity/quic-integration.md` / RFC-0002 define stream type 0x05 and mention opcodes.
- RFC-0002 §6.3 only lists opcodes (`0x0001=DATA_CHUNK`, etc.) but does not define:
  - chunk framing details (fields, ordering, offset vs streaming),
  - transfer identifiers,
  - integrity (hash/commit), retransmission/ack semantics,
  - end-of-transfer rules, error handling per opcode.

**Needed normative fix:**
- Define the Bulk payload format byte-for-byte for each opcode (at minimum: transfer_id, chunk_index/offset, total_size or final flag, optional hash), and define receiver behavior for out-of-order/duplicate chunks.

## MEDIUM

### 4) Admin API CSRF token delivery is underspecified/partially contradictory (cookie vs body)
**Why this can break interop:** A third-party admin UI client may implement only the documented `csrfToken` field in the login response body, while the daemon spec describes double-submit-cookie as the mechanism.

**Where:**
- `spec/05-ux-packaging/interfaces.md` `LoginResponse` includes `csrfToken` in JSON body.
- `spec/05-ux-packaging/node-daemon.md` CSRF section specifies “Server sets `csrf_token` cookie (NOT HttpOnly)” and client sends header matching cookie; it does not normatively state whether the token is also returned in the login JSON body, nor whether the cookie name is `postnode_csrf` vs something else in the UI docs.

**Needed normative fix:**
- Specify exactly: cookie name, whether the server MUST also echo the token in `LoginResponse.csrfToken`, and whether clients may rely solely on cookie reading vs response-body field.

### 5) Bootstrap `peer_id` string encoding is over-constrained (base58btc only)
**Why this can break interop:** Different libp2p stacks and tooling sometimes emit PeerIDs in different multibase encodings (base58btc vs base36 CIDv1 forms). If implementations strictly reject non-base58 in config exchange, they can fail to bootstrap even with identical underlying PeerID bytes.

**Where:**
- `spec/00-shared/layer-integration.md` “Bootstrap Encoding Rules (Normative)” requires Base58btc.

**Possible fix:**
- Allow any multibase string that decodes to the same PeerID bytes, while requiring canonicalization or validation checks.

Example: it claims a mailbox routing behavior that differs from RFC-0003’s explicit “store by inbox_owner_iid path parameter, not by PUSE recipient field.” This isn’t normative, but it can mislead implementers reading progress notes as guidance.
