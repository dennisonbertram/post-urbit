## BLOCKING (certain interop failure)

### B1. QUIC stream type `0x05` (Bulk) is **simultaneously specified as usable** and **forbidden in v1**
**Why this breaks interop:** One implementation following the non-RFC layer docs may open/use Bulk streams; another implementation following RFC-0002 v1 MUST reject them (`STREAM_TYPE_UNKNOWN` 0x102). Result: deterministic connection/stream failure.

**Conflicting specs:**
- **RFC-0002 §6.6**: Bulk (0x05) is **OUT OF SCOPE FOR V1**; v1 implementations **MUST NOT** open 0x05 and **MUST reject** incoming 0x05.
- **spec/00-shared/layer-integration.md**: Defines Bulk (0x05) payload as “Binary (2-byte opcode + data)” and stream initiation rules treat it as a normal stream type.
- **spec/01-transport-connectivity/quic-integration.md**: Lists Bulk as a stream type for “Large data transfers”.
- **spec/01-transport-connectivity/interfaces.md**: Exposes `StreamType = 'bulk'`, constants include `BULK: 0x05`, and API allows opening streams of that type.

**Needed normative fix:** Make all non-RFC docs explicitly match RFC-0002 v1:
- Mark `bulk` as **reserved/unusable in v1** everywhere it appears (interfaces, layer-integration, quic-integration).
- Or, if Bulk is intended in v1, RFC-0002 §6.6 must be reversed and the full Bulk wire protocol made normative in RFC-0002 (opcode registry, framing, resumption, etc.).

### B2. Handshake “abbreviated resumption” is **forbidden in RFC-0002 v1** but still described as a working feature elsewhere
**Why this breaks interop:** If an implementation sends `client_hello.resume` / expects `resume_accepted` based on `peer-handshake.md`, an implementation following RFC-0002 v1 will treat this as prohibited/unknown and fail or diverge in state machine behavior.

**Conflicting specs:**
- **RFC-0002 §8.4**: Abbreviated handshake is **OUT OF SCOPE FOR V1**; v1 implementations:
  - **MUST NOT** include `resume` in `client_hello`
  - **MUST NOT** send `resume_accepted`
  - **MUST** treat `resume_accepted` as unknown/error
- **spec/01-transport-connectivity/peer-handshake.md**: Contains “Connection Resumption” section with a concrete `resume` field in `client_hello` and “resume_accepted” behavior, presented as if usable.

**Needed normative fix:** Either:
- Mark the entire resumption subsection in `peer-handshake.md` as **reserved/out-of-scope for v1** (matching RFC-0002 §8.4), or
- Promote resumption back into RFC-0002 v1 with complete normative behavior (message schemas, downgrade behavior, transcript binding, error handling).

## HIGH (likely interop failure)

### H1. Admin API CSRF model is inconsistent: “token returned in response body” vs “double-submit cookie only”
**Why this breaks interop:** A UI/client implementation may rely on `LoginResponse.csrfToken` (body field) while a server implementation may only set a CSRF cookie (and not return a JSON field). That yields systematic 403s on state-changing requests.

**Conflicting/misaligned specs:**
- **spec/05-ux-packaging/interfaces.md**: `LoginResponse` includes `csrfToken: string`.
- **spec/05-ux-packaging/admin-ui.md**: API client stores CSRF token from response body and sends `X-CSRF-Token`.
- **spec/05-ux-packaging/node-daemon.md**: Describes **Double-Submit Cookie Pattern** and explicitly says session cookie is used; does not clearly require returning CSRF token in JSON (it focuses on cookie).

**Needed normative fix:** Specify one mandatory behavior:
- Either “server MUST return csrfToken in LoginResponse AND set csrf cookie to same value”, or
- “client MUST read CSRF token from cookie and LoginResponse MUST NOT include csrfToken”, and update the TS interfaces/admin-ui accordingly.

---

### H2. Multipart upload endpoints lack required field names / multipart structure
**Why this breaks interop:** Independent client/server implementations will choose different multipart field names (`file`, `package`, `backup`, etc.) and fail to interoperate.

**Missing normative details:**
- **node-daemon.md** defines:
  - `POST /admin/v1/apps/install/upload` (multipart/form-data)
  - `POST /admin/v1/backups/upload` (multipart/form-data)
…but does **not** specify:
- multipart form field name(s),
- filename requirements,
- whether additional fields are allowed/required (e.g., `type`, `password`),
- required `Content-Type` per part.

**Needed normative fix:** Define exact multipart schema, e.g.:
- field name `file` (single required part), content-type `application/zip` or `application/octet-stream`, max size, etc.

---

### H3. Admin API query parameter naming is inconsistent/undefined (camelCase vs snake_case)
**Why this breaks interop:** One client sends `sort_by`, another server expects `sortBy` (or vice versa). This is especially likely because the JSON naming rules are explicit (snake_case) but query string rules are not.

**Example inconsistency:**
- **node-daemon.md** contacts list endpoint: query includes `sortBy`, `sortOrder`.
- **spec/05-ux-packaging/interfaces.md** says on-wire JSON is snake_case, but is silent about query params; other places use snake_case names like `has_more`, etc.

**Needed normative fix:** State: “All query parameters MUST be snake_case” (or MUST be camelCase), and provide the canonical parameter names per endpoint.

---

### H4. PURL payload semantics are inconsistently described as “QUIC UDP payload” despite packet types that carry JSON
**Why this breaks interop:** Implementers may incorrectly feed non-DATA packet payloads (notably `COORDINATE` 0x09) into the QUIC stack, or reject them as “not QUIC”.

**Problem sources:**
- **RFC-0002 §7.4** describes PURL payload as “Payload (QUIC UDP payload)” (generic description).
- But **RFC-0002 §7.6** explicitly defines JSON payload for `REBIND` (0x08).
- **spec/01-transport-connectivity/nat-traversal.md** defines `COORDINATE` (0x09) payload as UTF-8 JSON and says the relay forwards it.

**Needed normative fix:** In RFC-0002 §7.4, redefine the PURL payload generically as “payload bytes; interpretation depends on Packet Type”, and add a short normative pointer/table entry for `COORDINATE` payload format (or explicitly reference nat-traversal.md from RFC-0002 in the PURL payload table).

---

### H5. Messaging “reserved” types vs exposed API methods are inconsistent (edit/delete/system)
**Why this breaks interop:** One implementation may emit `type: "edit"`/`"delete"` messages because the API exposes `editMessage`/`deleteMessage`; another implementation following RFC-0003 will treat them as unknown/unsupported (since they are not in RFC-0003’s v1 type registry).

**Conflicting specs:**
- **spec/03-messaging-sync/interfaces.md**:
  - `MessageType` includes `'edit' | 'delete' | 'system'` marked “Reserved for future”
  - but `MessagingService` exposes `editMessage()` / `deleteMessage()` as if supported
- **RFC-0003 §8.2** type registry does not include edit/delete/system as valid v1 wire types.

**Needed normative fix:** Either:
- Remove/mark `editMessage`/`deleteMessage` as reserved/not implemented in v1 APIs, or
- Add these types to RFC-0003 with full wire semantics and conflict rules.

## MEDIUM (edge-case interop failures / ambiguity)

### M1. `sync_op` encapsulation in PUSE: “CBOR bytes” phrasing can be misread as including the sync type byte
**Why this matters:** For mailbox-delivered sync, a sender might Base64-encode `(sync_type_byte || cbor_payload)` while receiver expects only `cbor_payload` because `sync_type` is separate. This would cause parse failures for mailbox sync fallback.

**Current text:**
- **RFC-0003 §8.2 (`sync_op`)**: includes `sync_type` and `cbor` fields, and says `cbor` is Base64 of “complete CBOR-encoded sync operation bytes”.

**Needed normative tweak:** Explicitly state: `cbor` contains **only** the CBOR payload bytes (the part that would appear after the 1-byte sync type on stream 0x04), i.e. it MUST NOT include the sync type byte.
