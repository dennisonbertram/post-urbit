## Interop issues (contradictions / missing normative details / ambiguous wire formats)

### BLOCKING — DHT-over-QUIC connection negotiation is underspecified vs Transport ALPN (likely split-brain DHT)
**Where**
- DHT stack specifies QUIC+TLS and libp2p multistream-select: `spec/00-shared/layer-integration.md` → “DHT Transport Layer”
- Post-Urbit QUIC requires ALPN `post-urbit/1` and “Implementations MUST reject connections with mismatched ALPN”: `spec/06-rfcs/RFC-0002-transport.md` §4.1
- The DHT wire protocol section mandates “libp2p Kademlia DHT” but does **not** normatively state which QUIC ALPN value is used for the libp2p QUIC transport, nor how a node listening on a single UDP port demuxes DHT vs Post-Urbit connections.

**Why this breaks interop**
Two independent implementations can reasonably do different things and still believe they are compliant:
- Implementation A: runs a single QUIC endpoint with ALPN `post-urbit/1` (per RFC-0002) on UDP/4433 and expects Post-Urbit stream-type framing on all streams; DHT is “over the same connection” (the spec even *recommends* connection reuse).
- Implementation B: runs a libp2p QUIC endpoint (which, in practice, uses libp2p’s own ALPN and multistream-select handshake) for `/post-urbit/kad/1.0.0`.

These two will fail to establish DHT connections at all if the ALPN differs, or will misparse streams if they attempt to share a single QUIC connection while using incompatible per-stream “first bytes” (Post-Urbit stream-type byte vs libp2p multistream-select protocol negotiation bytes).

**What’s missing (normative)**
You need a repo-internal, normative statement answering *at least*:
1. **ALPN for DHT QUIC connections** (exact byte string(s) to offer/accept for the libp2p QUIC transport).
2. Whether a node MUST run **two logical QUIC endpoints** (Post-Urbit vs libp2p) and how it demultiplexes them on a shared UDP socket (ALPN-based accept routing).
3. Whether “connection reuse” is actually permitted; if not, it should be removed or explicitly prohibited (because the stream-framing schemes are incompatible).

### HIGH — Bulk stream type (0x05) is “reserved for v2” in Transport, but presented as usable in Messaging overview
**Where**
- Reserved / MUST NOT be used in v1: `spec/06-rfcs/RFC-0002-transport.md` §6.6 (and elsewhere).
- Messaging layer overview lists Bulk as a stream used by this layer: `spec/03-messaging-sync/overview.md` → “Stream Types” table includes `Bulk | 0x05 | Large file transfers` with no v1 prohibition.

**Why this breaks interop**
One implementation can read the messaging overview and implement Bulk transfers in “v1”; another implementation correctly follows RFC-0002 and rejects incoming stream type 0x05 with `STREAM_TYPE_UNKNOWN` / closes. The two won’t interoperate for bulk transfers, and—worse—will disagree on what “v1 compliant” means.

**Fix**
Mark Bulk as **reserved for v2 / MUST NOT be used in v1** in `spec/03-messaging-sync/overview.md` (and any similar summaries), matching RFC-0002.

### HIGH — Relay COORDINATE packets: receiver-side allocation-token handling is underspecified (easy to implement wrong)
**Where**
- Relay-assisted hole-punching uses PURL `COORDINATE` (0x09) and says the relay forwards the *entire PURL packet* to the peer: `spec/01-transport-connectivity/nat-traversal.md` → “Relay-Assisted Coordination”
- Token handling is explicitly “recipient MUST NOT validate allocation token” for **DATA** packets: `spec/06-rfcs/RFC-0002-transport.md` §7.6 and `spec/01-transport-connectivity/relay-protocol.md` “Encapsulation Model (Normative)”
- But the spec does **not** explicitly extend the “recipient MUST NOT validate token” rule to forwarded `COORDINATE` packets.

**Why this breaks interop**
A receiver implementation might (reasonably) try to validate the `Allocation Token` field on *any* incoming PURL packet type, including COORDINATE. That will fail because the token belongs to the sender’s allocation and is not meaningful/verifiable by the destination peer. Result: relay-assisted coordination (and thus hole-punch attempts) fails between implementations.

**Fix**
Add a normative rule: for any **relay-forwarded** PURL packets (at least `DATA` and `COORDINATE`), the destination peer MUST ignore the allocation token (relay validates it), and only apply the message-level signature rules described for COORDINATE payloads.

### MEDIUM — Mailbox URL canonicalization rules conflict with Identity endpoint host constraints (IDN/punycode edge-case)
**Where**
- Mailbox token signing/verification requires mailbox URLs to be ASCII hostnames only; non-ASCII hosts rejected; punycode A-label expected: `spec/06-rfcs/RFC-0003-messaging.md` §7.3 “URL Canonicalization (Normative)”
- Identity endpoint host normalization in identity docs does not normatively require ASCII/punycode; it just says hostname lowercase, etc.: `spec/02-identity-trust/identity-document-schema.md` → “Host normalization”

**Why this breaks interop**
An identity could publish a mailbox endpoint with a Unicode hostname in `IdentityDocument.endpoints[].host`. One implementation may attempt to convert to punycode; another may follow RFC-0003 strictly (“reject non-ASCII”) and refuse to create/verify mailbox tokens, breaking mailbox delivery for that endpoint.

**Fix**
Add a normative constraint for `endpoints[].host` when `type=mailbox` (and possibly `type=relay` too): host MUST be ASCII (IDNA A-label / punycode), and/or define required IDNA processing.

### LOW — progress.md contains contradictory “fixed issues” summaries vs current RFC text (misleading, but non-normative)
**Where**
- `spec/progress.md` includes historical statements that contradict current protocol text (e.g., mailbox routing keyed by PUSE recipient vs keyed by inbox-owner IID path parameter; relay MTU inner payload size).

**Why it matters**
While not an authoritative wire spec, implementers may still read it and implement the wrong behavior.

**Fix**
Either: (a) explicitly declare `progress.md` non-normative and “may be stale”, or (b) update/remove incorrect historical bullets.
