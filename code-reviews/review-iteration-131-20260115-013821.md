## BLOCKING issues (certain interop failure)

### B1 — DHT PeerID derivation key is self-contradictory (identity key vs device key)
**Where**
- `spec/00-shared/layer-integration.md` → **“DHT Node Identity”**: step 1 says derive PeerID from **identity document signing key** `keys.signing.current`.
- Same file → **“Multi-Device Consideration”**: says each device’s DHT node uses the **device signing key** (not identity signing key) for its PeerID.

**Why this breaks interop**
Two independent implementations will derive different libp2p PeerIDs for the “same node/device” depending on which sentence they follow. That can prevent successful DHT overlay connections (PeerID mismatch at `/p2p/<peerid>`), and can break bootstrapping and routing table maintenance.

**What’s missing / needs to be made normative**
Choose **one** normative rule for v1:
- Either: “DHT PeerID MUST be derived from the device signing key (`device_signing_key`)”, or
- “DHT PeerID MUST be derived from identity signing key (`keys.signing.current`)”, plus how multi-device participates (single DHT peer vs multiple).

Also specify which key bootstrap nodes use (identity vs device) so published `peer_id` values are unambiguous.

### B2 — CSRF cookie name is contradictory (`csrf_token` vs `postnode_csrf`)
**Where**
- `spec/05-ux-packaging/node-daemon.md` → **CSRF Protection**:
  - Text says: server sets a `csrf_token` cookie (exact literal).
  - `CsrfConfig` immediately below says `cookieName: 'postnode_csrf'`.

**Why this breaks interop**
Cookie names are wire-visible. A client and server that implement different cookie names will fail CSRF validation (header-vs-cookie equality check) even if everything else is correct.

**What’s missing / needs to be made normative**
Pick exactly one cookie name (and path/domain/samesite/secure semantics) and use it consistently across:
- node-daemon spec
- UI/client expectations (even if the UI uses the body token, the server still validates the cookie value)

### B3 — Hole-punch coordination signatures: schema says MUST include, but later says MAY omit
**Where**
- `spec/01-transport-connectivity/nat-traversal.md` → **Message Schemas (Normative)**: “All coordination messages MUST include these fields” and includes `signature`.
- Same file → **Signature Requirements (Normative)**: for **Direct Peer (Control stream)** signatures “MAY be omitted”.

**Why this breaks interop**
One implementation will enforce presence of `signature` on control-stream hole-punch messages; another will omit it (allowed by the later section). That leads to immediate rejection and failed NAT traversal between compliant implementations.

**What’s missing / needs to be made normative**
Specify, per message type and per transport channel:
- whether `signature` field is **omitted** or present as **null** when not required (and whether receivers must accept both),
- the exact verification requirements when the field is present but optional.

This needs the same “absent == null” rule that RFC-0002 already provides for handshake messages, if that’s the intent.

## HIGH issues (likely interop failure)

### H1 — Admin API JSON field naming is underspecified at the wire level (snake_case vs camelCase)
**Where**
- `spec/05-ux-packaging/interfaces.md` says: on-wire JSON uses **snake_case**; TS uses **camelCase**; “When serializing to JSON, convert camelCase to snake_case.”
- `spec/05-ux-packaging/node-daemon.md` endpoint tables reference TS types but do not show the actual JSON keys.
- `spec/05-ux-packaging/admin-ui.md` example client uses `JSON.stringify(options.body)` without showing a required camel→snake transformation step.

**Why this breaks interop**
Independent client and server implementations may choose different field naming on the wire (e.g., `rememberDevice` vs `remember_device`, `createdAt` vs `created_at`). Without an explicit “server MUST accept both” rule (not present), this becomes a common request/response incompatibility.

**What’s missing / needs to be made normative**
For every Admin API request/response object, specify the **actual JSON field names** on the wire (snake_case), and explicitly state whether servers:
- MUST accept camelCase aliases, or
- MUST reject non-snake_case (preferred for canonicality).

### H2 — PURL “Payload is QUIC UDP payload” wording conflicts with non-DATA packet payloads (COORDINATE, REBIND, ERROR)
**Where**
- `spec/06-rfcs/RFC-0002-transport.md` §7.4 defines PURL payload as “Payload (QUIC UDP payload)”.
- Elsewhere (`RFC-0002` §7.11, §7.12; and `nat-traversal.md`) the payload for some packet types is **JSON** or structured error bytes, not QUIC.

**Why this breaks interop**
Implementations that treat all forwarded PURL payloads as QUIC packets can mis-handle COORDINATE packets (and potentially REBIND/ERROR) and fail NAT traversal coordination.

**What’s missing / needs to be made normative**
In RFC-0002 §7.4, make the payload definition explicitly **type-dependent**:
- DATA: inner payload is QUIC UDP payload (handed to QUIC stack)
- COORDINATE: payload is UTF-8 JSON (as per nat-traversal.md)
- ERROR: payload is the error struct
- REBIND: payload is UTF-8 JSON

Right now the normative interpretation is present but split; the wire-format section should not contradict it.

## MEDIUM issues (edge-case interop failures)

### M1 — Mailbox URL canonicalization can yield empty path in some inputs
**Where**
- `spec/06-rfcs/RFC-0003-messaging.md` §7.3 URL canonicalization rules:
  - “Normalize empty path to `/`”
  - then “if the path is not exactly `/`, remove all trailing `/` bytes”
- For inputs like `https://example.com///` the “remove all trailing `/`” rule can produce an empty string unless implementations re-normalize.

**Why this matters**
If different implementations normalize `https://example.com///` to `https://example.com/` vs `https://example.com` (or `https://example.com` with empty path), they will compute different signature inputs and reject each other’s mailbox tokens.

**Fix**
Add an explicit rule: after stripping trailing slashes, if the path becomes empty, it MUST be set to `/`.

### M2 — Domain-separator registry “Bytes” column contains at least one likely miscount
**Where**
- `spec/00-shared/layer-integration.md` Domain Separator Registry lists byte lengths, e.g. `/post-urbit/kad/1.0.0` shown as 22 bytes (appears to be 21 by direct count).

**Why this matters**
The bytes *value* is correct as a string, but implementers relying on the length column for assertions/tests may incorrectly reject correct inputs or embed incorrect expectations.

**Fix**
Treat the “Bytes” column as normative only if audited; otherwise remove or regenerate programmatically.
