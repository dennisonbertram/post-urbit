## BLOCKING (certain interop failure)

### B1 — CBOR optional-field encoding contradicts multiple API schemas (null vs omitted)
**Where**
- **Normative CBOR rule:** `spec/04-app-runtime/abi.md` → “CBOR Encoding” → **Struct Encoding Rules** → **Optional fields MUST be omitted entirely**; MUST NOT encode absent optionals as CBOR `null`.
- **Conflicting API schemas/examples:** `spec/04-app-runtime/api-surface.md`
  - `StorageListResponse.cursor?: string  // null if no more results`
  - Similar “cursor may be null” wording appears in other list/pagination responses (and in some UI-facing docs).

**Why this breaks interop**
Two independent implementations can both be “following the spec” but produce/expect different wire values:
- Impl A (following **abi.md**) omits `cursor` when absent.
- Impl B (following **api-surface.md** comment) encodes `cursor: null` (CBOR `null`).
A strict CBOR decoder expecting either “absent” or “text string” will fail on `null` with a type mismatch, causing hard failures in app↔host interoperability.

**What to change (normative fix)**
Pick one and make it consistent everywhere:
- Option 1 (recommended): keep `cursor` **optional** and define: “if no more results, **omit** `cursor`”; remove “null” wording.
- Option 2: make `cursor` explicitly **nullable** (`cursor: string | null`) and update **abi.md** to allow `null` for this specific field family (cursor-like sentinels), including decoding requirements.

## HIGH (likely interop failure)

### H1 — Admin API error-code registry is inconsistent across documents
**Where**
- `spec/05-ux-packaging/interfaces.md` defines `ApiErrorCode` including `CSRF_INVALID`, `FRESH_AUTH_REQUIRED`, `VALIDATION_ERROR`, etc.
- `spec/05-ux-packaging/node-daemon.md` “Error Responses” defines a **shorter/different** `ApiErrorCode` set (missing some that are used elsewhere), while other sections (CSRF) separately introduce `CSRF_INVALID`.

**Why this breaks interop**
Independent client/server implementations may:
- Treat the enumerated set as closed and reject/unwrap incorrectly on “unknown” codes.
- Diverge on which HTTP status/code combos are valid, breaking generic error handling and automated clients.

**Needed normative clarification**
- Declare a single authoritative error-code registry (preferably in `interfaces.md`), and add: **clients MUST accept unknown `error.code` strings** (forward compatibility), while servers MUST only emit codes from the registry for v1.

### H2 — App host API ↔ PUSE plaintext mapping is easy to miss (and not cross-linked from the Host API spec)
**Where**
- **Normative mapping exists:** `spec/06-rfcs/RFC-0003-messaging.md` §8.2 “Host API to PUSE Plaintext Mapping (Normative)” + CBOR↔JSON conversion rules.
- **But** `spec/04-app-runtime/api-surface.md` (`messaging.send`, `messaging.subscribe`) does not normatively point implementers to RFC-0003 for the required mapping between:
  - app-provided CBOR `content` and
  - on-wire PUSE plaintext JSON.

**Why this breaks interop**
Two host-runtime implementations could serialize app messages differently while still producing valid PUSE envelopes, causing the receiving node’s runtime/apps to misinterpret message types and payloads.

**Fix**
Add an explicit normative reference from `api-surface.md` messaging methods to RFC-0003 §8.2, stating the mapping is REQUIRED for interoperability.

## MEDIUM (edge-case / partial interop failure)

**Risk**

### M2 — WebSocket replay/resume parameters are underspecified
**Where**
- `spec/05-ux-packaging/node-daemon.md` WebSocket: `?lastEventId=<id>` and “server buffers last 1000 events”
- No normative definition for:
  - event ID type/format (numeric? lexicographic string?),
  - comparison rules,
  - behavior if `lastEventId` is unknown/too old.

**Risk**
Clients and servers may implement incompatible resume logic.

**Fix**
Specify event ID as either:
- monotonically increasing unsigned integer encoded as decimal string, or
- fixed-length opaque token with exact matching only,
and define server behavior on gaps.
