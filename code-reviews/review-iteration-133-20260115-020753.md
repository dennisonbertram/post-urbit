## HIGH (likely interop failure)

### HIGH-1: Ambiguous `sync_op` encapsulation bytes (CBOR payload vs full sync-wire message)
**Where**
- `spec/06-rfcs/RFC-0003-messaging.md` §8.2, “`sync_op` Plaintext Schema (Normative)”
- `spec/03-messaging-sync/sync-protocol.md` “Sync Wire Protocol” (type byte + CBOR)

**Problem**
RFC-0003 defines `sync_op` as:
```json
"content": { "sync_type": <uint8>, "cbor": "<base64>" }
```
and says `cbor` is “Base64 … of the **complete CBOR-encoded sync operation bytes**”.

However, the sync stream wire format in `sync-protocol.md` is:
- 1-byte `Message Type` **followed by CBOR Data** (and then outer QUIC frame length).

Two plausible interpretations for `content.cbor` exist:
1) **CBOR Data only** (the CBOR map corresponding to `sync_type`), since `sync_type` is already carried separately.
2) **The full sync payload** (`sync_type` byte + CBOR Data), because “complete … bytes” can be read that way.

Independent implementations choosing different interpretations will fail to decode mailbox-delivered sync payloads.

**What’s missing (normative)**
A single explicit statement such as:
- “`content.cbor` MUST contain **only** the CBOR Data portion (i.e., the bytes that follow the 1-byte sync Message Type on stream 0x04). It MUST NOT include the 1-byte `sync_type` prefix, and MUST NOT include the QUIC frame length prefix.”

(Alternatively, define it the other way—but pick one.)

### HIGH-2: Packaging signature Base64 canonical form is not restated where the field is introduced
**Where**
- `spec/05-ux-packaging/app-distribution.md` “SIGNATURE File Format (JSON)” and repository/update manifest signatures
- `spec/04-app-runtime/manifest-schema.md` signature verification example code
- Global rule exists in `spec/00-shared/layer-integration.md` “Encoding” table (keys/signatures Base64 std, no padding)

**Problem**
Some sections introduce JSON fields like:
- `SIGNATURE.signature`
- `repository.json.signature.sig`
- `updates.json.signature.sig`

…but do not explicitly repeat the global “Base64 standard **no padding**” rule at the field definition site. Many implementers treat Base64 in JSON as padded by default; others will enforce “no padding” strictly (as identity docs do). This is a likely divergence point.

**Why this matters**
If one implementation emits padded Base64 (`=`) in these JSON signature fields and another rejects padding (or computes signatures over canonicalized forms that require exact strings), installs/updates/repo verification will fail across implementations.

**Suggested fix**
Add a normative sentence in each signature-object schema section:
- “`signature`/`sig` MUST use RFC 4648 Base64 **standard alphabet**, **no padding**, and verifiers MUST reject padded input.”

(You already do this very explicitly for several other signature contexts; packaging should match that style.)

## MEDIUM (edge cases / confusion that can produce divergence)

### MEDIUM-1: Derived “max plaintext” limits in Host API doc don’t match RFC-0003 math
**Where**
- `spec/04-app-runtime/api-surface.md` under **“Message Size Limit (Normative)” → “Derived Plaintext Limits”**
- Compare to `spec/06-rfcs/RFC-0003-messaging.md` §3.2 (“Derived Maximum Plaintext Size”)

**Problem**
`api-surface.md` gives approximate plaintext maxima that appear to be off by ~20 bytes compared to RFC-0003’s derived formula/table.

**Interop impact**
If an implementation enforces these derived plaintext caps as hard limits (instead of enforcing the actual “final envelope ≤ 1,048,576” rule), it may reject messages that other implementations would accept (near the boundary).

**Suggested fix**
Either:
- Remove the derived plaintext numbers entirely (keep only the normative “envelope size after encryption/signing”), or
- Recompute and match RFC-0003’s derived values exactly and label them explicitly as “informative”.

### MEDIUM-2: `spec/progress.md` contains a contradictory historical claim about mailbox routing
**Where**
- `spec/progress.md` (historical “Issues Fixed” notes) claims mailbox routing keyed by PUSE recipient IID
- Contradicts the actual normative mailbox design in:
  - `spec/06-rfcs/RFC-0003-messaging.md` §7.4.1/7.4.2/7.4.3 (store/retrieve/delete by **inbox owner IID**, not envelope recipient)
  - `spec/00-shared/layer-integration.md` MailboxService docs (explicit `inboxOwnerIid` parameter)

**Problem**
Even though `progress.md` is meta, it lives alongside specs and is easy to misread as normative guidance. It directly contradicts the mailbox’s keying rules for group messages.

**Suggested fix**
Add an explicit banner at the top of `progress.md`:
- “Non-normative history; RFCs are authoritative”
and/or correct/remove the contradictory bullet to avoid implementers using it as a behavioral source.
