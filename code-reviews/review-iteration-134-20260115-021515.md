## BLOCKING

### 1) TLS certificate acceptance policy is not scoped by ALPN, contradicting libp2p QUIC requirements for the DHT
**Where**
- `spec/00-shared/layer-integration.md` → “QUIC TLS Certificate Policy” says **clients MUST accept ANY certificate**.
- `spec/06-rfcs/RFC-0002-transport.md` §4.3 / §10.1 similarly says certificates are not used for identity verification and **MUST accept ANY certificate**.
- But `spec/00-shared/layer-integration.md` → “DHT Wire Protocol (Normative)” requires **libp2p Kademlia DHT over QUIC** with ALPN `libp2p`.

**Why this breaks interop**
- libp2p QUIC uses TLS 1.3 *as part of libp2p’s secure transport identity*, and implementations typically **authenticate the peer’s PeerID via the presented certificate** (self-signed but bound to the PeerID).  
- If an implementation applies the “accept any certificate” rule to ALPN `libp2p` connections, it may:
  - accept peers that a standard libp2p stack will reject (or vice versa), and/or
  - fail to establish the libp2p security context needed for stream/protocol negotiation.
- Two independent implementations can therefore fail to join the same DHT overlay even if both “follow the spec” as written (because the cert rule is stated generally and the DHT section references libp2p without explicitly overriding the cert policy).

**What’s missing / ambiguous**
- A normative statement explicitly distinguishing TLS verification rules for:
  - ALPN `post-urbit/1` (Post-Urbit protocol), vs
  - ALPN `libp2p` (DHT/libp2p stack).

**Suggested normative fix**
- Add explicit scoping language in `layer-integration.md` (and/or RFC-0002) such as:
  - For ALPN `post-urbit/1`: clients MUST accept any TLS certificate (no PKI, no hostname checks).
  - For ALPN `libp2p`: implementations MUST follow the libp2p QUIC/TLS identity requirements (certificate MUST authenticate the libp2p PeerID as required by the libp2p spec / library).

## HIGH

### 2) PUSE initial (0x00) → ratchet (0x01) transition semantics are not consistently stated outside RFC-0003
**Where**
- RFC-0003 defines the transition rule (initial consumes the first chain step; subsequent ratchet messages start with `N=1` and reuse the same DH public until a DH ratchet).
- `spec/03-messaging-sync/secure-envelope.md` describes initial vs ratchet but does **not** clearly specify the required `N`/`PN` transition constraints for the first post-initial ratchet message.
- `spec/03-messaging-sync/double-ratchet.md` likewise does not clearly nail down the “initial counts as N=0” linkage to the first ratchet header values.

**Why this likely breaks interop**
- One implementer may reasonably send the first 0x01 message with `N=0` after a 0x00 message; another will expect `N=1` (per RFC-0003). That produces different message keys and guaranteed decrypt failure.

**Suggested fix**
- In `secure-envelope.md` and/or `double-ratchet.md`, either:
  - restate the RFC-0003 normative rule verbatim, or
  - add an explicit “MUST follow RFC-0003 §3.4.2 transition rule” note right at the initial/ratchet sections (not just a generic reference).

### 3) `sync_op` encapsulation is defined in RFC-0003, but other messaging docs still leave the wire bytes ambiguous
**Where**
- RFC-0003 §8.2 defines `sync_op.content.cbor` as **CBOR bytes only**, explicitly **excluding** the 1-byte `sync_type` prefix.
- `spec/03-messaging-sync/secure-envelope.md` mentions `sync_op` as a mailbox fallback but does not specify whether the embedded blob includes the sync type byte.

**Why this likely breaks interop**
- Independent implementations can choose different encodings (include vs exclude the 1-byte type), causing parse or signature/ID computation failures when recipients process mailbox-delivered sync.

**Suggested fix**
- Mirror the RFC-0003 `sync_op` encoding rule in `secure-envelope.md` (or add an explicit normative pointer to RFC-0003 §8.2 for `sync_op`).

### 4) App message (`type:"app"`) CBOR→JSON mapping is only fully specified in RFC-0003; other docs describe it too loosely
**Where**
- RFC-0003 §8.2 provides a **normative, reversible CBOR↔JSON mapping** using reserved `~`-prefixed strings for bytes and big integers.
- `spec/03-messaging-sync/interfaces.md` says app wire format is `{ "app_id": string, "data": CBOR-decoded }` but does not define how CBOR types that are not native JSON (bytes, big ints, non-string map keys, tags) are represented inside the PUSE plaintext JSON.

**Why this likely breaks interop**
- Two node implementations could encode the same app CBOR payload into *different* plaintext JSON representations (e.g., bytes as base64 vs array-of-ints vs RFC-0003 `~b...`), which breaks app-level interoperability across nodes.

**Suggested fix**
- Update `spec/03-messaging-sync/interfaces.md` to explicitly normatively reference RFC-0003 §8.2 for the CBOR→JSON mapping (or copy the mapping rules in abbreviated form).

## MEDIUM

### 5) Device document / device index DHT value canonicalization is inconsistent across documents
**Where**
- RFC-0001 §12.5 / §12.4: DHT Value is **JCS-canonical** JSON bytes for device doc/index.
- `spec/00-shared/layer-integration.md` describes device doc/index values as “JSON” and gives signature inputs based on JCS, but does not clearly require the *stored DHT value bytes* themselves to be JCS-canonical.

**Interop risk**
- Some implementations may store pretty-printed/non-canonical JSON bytes in the DHT; others might assume canonical bytes for deduplication, byte-equality refresh, or deterministic tie-breaking, resulting in unexpected multi-value returns or inconsistent “byte-identical refresh” behavior.

**Suggested fix**
- Add an explicit “DHT value bytes MUST be JCS-canonical UTF-8 JSON” requirement for device doc/index in `layer-integration.md` to match RFC-0001.

## LOW

### 6) `spec/progress.md` contradicts current mailbox routing semantics
**Where**
- `spec/progress.md` contains historical “Issues Fixed” notes claiming mailbox routing/store/delete keyed by PUSE header recipient IID, which conflicts with the now-normative RFC-0003 design (store/retrieve/delete keyed by inbox owner IID path / token identity, not envelope recipient).

**Interop risk**
- Mostly editorial (progress log), but it can mislead implementers skimming the repo.

**Suggested fix**
- Update/remove the outdated note or add a clear statement that RFC-0003 is authoritative and the earlier note is obsolete.
