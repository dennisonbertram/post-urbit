## BLOCKING (certain interop failure)

### B1. DHT TTL/expiration rules contradict revocation record TTL requirements
**Where:**
- `spec/00-shared/layer-integration.md` → **DHT Wire Protocol (Normative)** table: `Record expiration | 24 hours | TTL for stored records`
- `spec/06-rfcs/RFC-0001-identity-document.md` → §12.7: revocation DHT records **TTL = 31536000 seconds (365 days)**

**Why this breaks interop:**
Two compliant implementations cannot simultaneously:
- configure the DHT to expire “stored records” at 24h, and
- also store revocation records that must persist for 365 days.

Independent implementations will diverge on revocation discoverability: one will expire revocations after 24h (per layer-integration), another will retain them for a year (per RFC-0001). That leads to inconsistent verification outcomes (some nodes accepting identities/keys that others treat as revoked).

**What must be specified (normative fix):**
Clarify whether “record expiration” is:
- (a) a **per-record TTL** derived from the stored record (and thus MUST allow at least 365 days for `post-urbit:revocation:` and `post-urbit:device-revocation:`), or
- (b) a **global cap** (in which case RFC-0001’s 365-day TTL cannot be met and must change, or must specify mandatory periodic republishing by third parties—which is currently not defined).

### B2. Admin HTTP API query parameter naming is contradictory (snake_case vs camelCase)
**Where:**
- `spec/05-ux-packaging/interfaces.md` → “On-wire JSON uses snake_case”
- `spec/05-ux-packaging/node-daemon.md` → Contacts list endpoint shows query params: `sortBy`, `sortOrder` (camelCase)

**Why this breaks interop:**
An independent Admin UI client following `interfaces.md` will likely send `sort_by` / `sort_order` (snake_case), while an independent server following `node-daemon.md` will look for `sortBy` / `sortOrder` (camelCase). Sorting behavior will fail or differ.

**What must be specified (normative fix):**
For **query parameters**, specify one of:
- **MUST use snake_case** for all query keys (recommended for consistency), or
- **MUST use camelCase**, or
- **Servers MUST accept both** forms (and specify precedence if both provided).

Also specify the canonical names for the *values* of sort fields (`displayName` vs `display_name`, etc.), since `node-daemon.md` currently lists camelCase field names.

## HIGH (likely interop failure)

### H1. Sync protocol contradicts itself on whether non-canonical CBOR is rejectable vs mandatory
**Where:**
- `spec/03-messaging-sync/sync-protocol.md` → **CBOR Canonicalization (Normative)**: “All CBOR encoding in the sync protocol MUST follow deterministic encoding rules…”
- Same file → **Operation Signature** section: “Receivers MAY reject non-canonical CBOR but MUST hash the received bytes if verifying.”

**Why this breaks interop:**
One implementation may accept non-deterministic CBOR (because rejection is only MAY), while another rejects it (because deterministic encoding is MUST). That creates divergent behavior on the same wire bytes (accept vs reject), which is a classic interop failure mode.

**What must be specified (normative fix):**
Make this consistent by choosing one:
- **Strict conformance:** Receivers **MUST reject** any sync message whose CBOR payload (including embedded `operation` bstr bytes) is not deterministically encoded.
- **Permissive conformance:** Receivers **MUST accept** non-canonical CBOR but define canonicalization rules for operation-id computation to avoid divergence (this is much harder and currently contradicts the “exact bytes” hashing rule).

### H2. DHT JSON record canonical-bytes requirement is not consistently normed across docs
**Where:**
- `spec/06-rfcs/RFC-0001-identity-document.md`:
  - §12.4/§12.5/§12.7 state DHT values for device index/device doc/revocations are **JCS-canonical JSON**.
- `spec/00-shared/layer-integration.md`:
  - Defines these record formats and signature schemes, but does **not** clearly state whether DHT nodes/clients **MUST reject non-JCS-canonical JSON bytes** (or MUST canonicalize before storing) for these record types.

**Why this breaks interop:**
Conflict resolution and dedup rules sometimes rely on comparing “JCS-canonical bytes” lexicographically or checking byte-identical refresh. If one implementation stores and forwards non-canonical JSON bytes (but still signature-valid), while another expects canonical bytes for comparisons, they can:
- make different tie-break decisions,
- fail to treat refreshes as byte-identical,
- or present different “distinct values” sets to clients.

**What must be specified (normative fix):**
For each non-IDOC JSON DHT record type (device doc, device index, revocation, device revocation), specify one of:
- **MUST store only JCS-canonical JSON bytes** and **MUST reject** any put where the raw bytes are not JCS-canonical, OR
- **MUST canonicalize on ingestion** (store canonical bytes, forward canonical bytes), and specify whether signatures are computed over canonicalized JSON (they are) and whether the stored bytes are reserialized canonical bytes.

Right now RFC-0001 implies “JCS-canonical,” but the integration glue leaves implementers room to guess.

## MEDIUM (edge-case interop issues)

### M1. `progress.md` contains statements that contradict the RFCs and can mislead implementers
**Where:**
- `spec/progress.md` includes a historical note: “Mailbox storage routing … store/retrieve/delete by recipient_iid from PUSE header” (this contradicts RFC-0003 §7.4.*, which routes by explicit inbox owner IID from the URL path parameter and treats envelope recipient differently for groups).

**Why it matters:**
While not an authoritative wire spec, this repository file can cause implementers to implement the wrong mailbox routing semantics if they treat it as design guidance.

**Fix:**
Mark `progress.md` explicitly as non-normative and/or remove contradictory historical bullets, or add pointers: “RFCs are authoritative; progress notes may be stale.”
