## BLOCKING (certain interop failure)

### B1 — Admin WebSocket event wire format contradicts itself (wrapper vs bare event)
**Docs involved**
- `spec/05-ux-packaging/node-daemon.md` (WebSocket Events)
- `spec/05-ux-packaging/interfaces.md` (Event Types (WebSocket))
- `spec/05-ux-packaging/admin-ui.md` (Real-time Updates)

**What conflicts**
- `node-daemon.md` defines each WS message as:
  ```ts
  interface WebSocketMessage {
    id: string;
    type: AdminEventType;
    timestamp: Timestamp;
    data: unknown;
  }
  ```
  and describes `?lastEventId=<id>` replay semantics (which depend on `id` being present at top level).
- `interfaces.md` and `admin-ui.md` define/consume WS events as **bare** objects:
  ```ts
  { type: 'status_change', data: NodeStatus } | ...
  ```
  (no top-level `id` or `timestamp` wrapper).

**Interop impact**
- A UI/client implemented against `interfaces.md`/`admin-ui.md` will fail to parse a daemon that sends `WebSocketMessage` wrappers, and vice versa. Replay (`lastEventId`) cannot work without an agreed location/encoding for the event id.

**Fix**
- Choose one canonical WS message shape and make *all three* documents match.
  - If you keep the wrapper (recommended because `lastEventId` depends on it), then update `interfaces.md` and `admin-ui.md` to consume the wrapper and define the inner `data` schemas.
  - If you drop the wrapper, then remove/replace `lastEventId` replay semantics and define where the event id lives.

### B2 — Admin logs endpoint response shape is inconsistent across documents
**Docs involved**
- `spec/05-ux-packaging/node-daemon.md` (System endpoint `/admin/v1/logs`)
- `spec/05-ux-packaging/interfaces.md` (`AdminApiClient.getLogs`, `LogsResponse`)
- `spec/05-ux-packaging/admin-ui.md` (`SystemApi.getLogs`)

**What conflicts**
- `node-daemon.md` specifies `/admin/v1/logs` returns `LogsResponse`:
  ```ts
  interface LogsResponse { entries: LogEntry[]; cursor?: string; hasMore: boolean; }
  ```
- `interfaces.md` declares:
  ```ts
  getLogs(options?: LogOptions): Promise<LogEntry[]>;
  ```
  (array return, no cursor/hasMore at the method boundary), despite also defining a `LogsResponse` type elsewhere.
- `admin-ui.md` uses `getLogs(...): Promise<LogsResponse>`.

**Interop impact**
- Client/server generated from different documents will disagree on whether the endpoint returns an array or an object envelope → runtime failures (JSON decoding/type mismatch), and pagination is unusable if the client expects only an array.

**Fix**
- Make `interfaces.md` authoritative for Admin API and align it to `node-daemon.md`:
  - Change `AdminApiClient.getLogs` to return `LogsResponse`.
  - Ensure `LogOptions` includes the pagination input (`cursor`) if the endpoint supports it (see HIGH issue H2).

## HIGH (likely interop failure)

### H1 — DHT “single home node” vs “devices refresh DHT records” is contradictory / underspecified
**Docs involved**
- `spec/00-shared/layer-integration.md` (“Single Home Node Model (v1)” under DHT node identity)
- `spec/00-shared/layer-integration.md` (“Device Record TTL and Refresh”)
- `spec/02-identity-trust/identity-document-schema.md` (Single Home Node Model + device discovery implications)

**What conflicts / is missing**
- One section says: *devices do not participate in the DHT directly; home node handles DHT operations on behalf of the identity*.
- Another section says: *Devices should refresh their DHT records before TTL expiry* (implies devices are DHT participants capable of PUT/refresh).

**Interop impact**
- Independent implementations may choose incompatible operational models:
  - Impl A: only home node runs libp2p/Kad; devices never speak to DHT → device docs/index may never be published unless separately proxied.
  - Impl B: devices are DHT nodes and publish/refresh their own device docs/index.
- Result: multi-device discovery and device doc freshness behavior diverges; cross-implementation device management can fail even if external peer connectivity works.

**Fix**
- Add a normative rule clarifying **who performs DHT PUTs for device documents and device index** in v1:
  - Either: “Only the home node performs all DHT publishes/refreshes, including device docs/index; devices submit updates to the home node over an authenticated channel” (then specify that channel/message format).
  - Or: “Devices participate in the DHT overlay as first-class nodes” (then revise DHT node identity derivation/PeerID model accordingly, because current text implies one identity → one PeerID).

### H2 — Admin logs pagination request parameter is not consistently defined
**Docs involved**
- `spec/05-ux-packaging/node-daemon.md` (`/admin/v1/logs` query includes `cursor`)
- `spec/05-ux-packaging/interfaces.md` (`LogOptions` lacks `cursor`)
- `spec/05-ux-packaging/admin-ui.md` (LogOptions shown without cursor)

**What’s missing**
- The request-side pagination input (`cursor`) is documented for the endpoint but absent from the typed request options used by clients.

**Interop impact**
- Clients implemented from `interfaces.md`/`admin-ui.md` cannot perform pagination in a spec-conformant way (they can’t send `cursor` without out-of-band knowledge), leading to partial functionality and divergent client behavior.

**Fix**
- Add `cursor?: string` to `LogOptions` in `interfaces.md` and mirror in `admin-ui.md` examples/types.

### H3 — Backup creation request shape mismatch (typed API vs HTTP API)
**Docs involved**
- `spec/05-ux-packaging/node-daemon.md` (`POST /admin/v1/backups` body supports `{ type?: 'full'|'identity'|'data' }`)
- `spec/05-ux-packaging/interfaces.md` (`AdminApiClient.createBackup(): Promise<BackupResult>` takes no args)

**Interop impact**
- A client generated from `interfaces.md` cannot request non-default backup types as defined by the HTTP API; different implementations will expose incompatible capabilities.

**Fix**
- Add `createBackup(type?: 'full'|'identity'|'data')` (or a request object) to `interfaces.md` and align naming/serialization (snake_case on wire).

## MEDIUM (edge cases / ambiguity that can cause divergence)

### M1 — Base64 “no padding” is not uniformly repeated in non-RFC type aliases
**Docs involved**
- Various TS type aliases in `spec/*/interfaces.md` (e.g., `type PublicKey = string; // Base64`)
- Normative encoding rules in `spec/00-shared/layer-integration.md` + RFCs

**Problem**
- Some interface/type docs describe Base64 fields without repeating the “standard alphabet, no padding, reject `=`” rule, while other docs make it strict. Implementers building from the interface docs alone may accept/emit padded Base64.

**Interop impact**
- Edge-case failures in signature/key parsing if one side rejects padding and the other emits it.

**Fix**
- Either:
  - Add a single normative “Base64 is RFC4648 §4, no padding; receivers MUST reject padded input” reference next to each Base64-typed alias in interface docs, **or**
  - Make the interface docs explicitly defer to the global encoding rules section.
