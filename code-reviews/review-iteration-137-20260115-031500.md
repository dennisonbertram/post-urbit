## BLOCKING (certain interop failure)

### B1. WebSocket event wire format contradicts itself (wrapper vs unwrapped union)
**Where**
- **Wrapper specified (server → client):**
  - `spec/05-ux-packaging/interfaces.md` defines on-wire `WebSocketMessage { id, type, timestamp, data }`
  - `spec/05-ux-packaging/node-daemon.md` repeats the same wrapper format
- **Unwrapped events shown (server → client):**
  - `spec/05-ux-packaging/admin-ui.md` “Real-time Updates / WebSocket Connection” shows receiving `AdminEvent` objects shaped like `{ type: "..."; data: ... }` (no `id`, no `timestamp`, no `data` nesting vs wrapper)

**Why this breaks interop**
Two independent implementations that follow different documents will send/expect different JSON shapes for the same WebSocket endpoint (`/admin/v1/events`). Parsing will fail or silently mis-handle events.

**What to specify**
Pick **one authoritative server→client format** (the wrapper seems intended), then:
- Update `admin-ui.md` examples to parse the wrapper, e.g. `const msg: WebSocketMessage = JSON.parse(e.data);`
- Explicitly state that the unwrapped `AdminEvent` union is *internal/typed* and is carried inside `WebSocketMessage.data`.

## HIGH (likely interop failure)

### H1. Multipart upload endpoints are underspecified (no normative part names/structure)
**Where**
- `spec/05-ux-packaging/node-daemon.md`
  - `POST /admin/v1/apps/install/upload` uses `multipart/form-data` but **no part name** is specified.
  - `POST /admin/v1/backups/upload` uses `multipart/form-data` but **no part name** is specified.
- `spec/05-ux-packaging/admin-ui.md` references “installFromFile(file: File)” but doesn’t specify how it is encoded on the wire.

**Why this breaks interop**
Two independent clients/servers can legitimately choose different multipart field names (e.g., `file`, `package`, `upload`) and fail with 400/422. This is exactly the kind of “implementers must guess” gap that causes interoperability failures.

**What to specify**
For each multipart endpoint, define at least:
- Required part name (e.g., `file`)
- Accepted `Content-Type` (e.g., `application/octet-stream`)
- Whether filename matters (and encoding expectations)
- Whether additional form fields are allowed/ignored
- Error codes for missing/extra parts

### H2. Client→server WebSocket “subscribe” message is ambiguous (and conflicts with wrapper model)
**Where**
- `spec/05-ux-packaging/node-daemon.md` says client should send after connect: `{ type: 'subscribe', events: [...] }`
- `spec/05-ux-packaging/interfaces.md` defines a server→client wrapper but does **not** define client→server message schemas (subscribe/unsubscribe/ack/error), nor whether client messages are wrapped too.

**Why this breaks interop**
A client can’t know whether it should send:
- an unwrapped `{type:"subscribe", ...}` object,
- a wrapped `{id,type,timestamp,data}` object,
- or something else (and how the server responds/acks).
Independent implementations will diverge.

**What to specify**
Add a **normative client→server message schema**, including:
- exact JSON structure and allowed fields
- whether client messages are wrapped or not
- server response/ack behavior (or explicitly “no ack; best-effort”)

## MEDIUM (edge cases / partial feature interop break)

### M1. Admin API uninstall query parameter naming is internally inconsistent
**Where**
- `spec/05-ux-packaging/node-daemon.md`
  - App uninstall: `DELETE /admin/v1/apps/{app_id}` shows query `keepData?`
  - Same document states: “All query parameter names use snake_case”

**Why this matters**
Clients may send `keepData` while servers implement `keep_data` (or vice versa). This breaks the “keep data” option across independent implementations.

**What to specify**
Normatively define the parameter name and type, e.g.:
- `keep_data` as `true|false` (default false)
- Specify URL encoding rules and behavior if both are provided.

### M2. Mailbox HTTP response fields vs MailboxService interface are misaligned (risking divergent implementations)
**Where**
- **HTTP (authoritative)**: `spec/06-rfcs/RFC-0003-messaging.md` §7.4 defines:
  - Store response includes `message_id`, `stored_at`, `expires_at`
  - Retrieve response includes `messages[]` entries with `sender_iid`, `size`, `envelope` (Base64), plus cursor fields
- **Interface (non-HTTP)**: `spec/00-shared/layer-integration.md` defines `MailboxService.store()` returning `{ messageId, expiresAt }` and `MailboxMessage` with `{messageId,envelope,storedAt}` (different shape, missing fields)

**Why this matters**
Even if the RFC is “authoritative”, the repo also provides a “MailboxService interface” that implementers may treat as normative for HTTP payloads, leading to mailbox servers/clients that disagree on required response fields.

**What to specify**
- Explicitly state that mailbox HTTP JSON responses:
  - MAY include extra fields and clients **MUST ignore unknown fields**, OR
  - MUST include exactly the RFC fields (and then update the interface/mapping accordingly).
- Add an explicit mapping section “HTTP ↔ MailboxService interface”.
