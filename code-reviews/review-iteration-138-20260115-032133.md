## BLOCKING issues (certain interop failure)

### B1 — Mailbox base URL/path is not discoverable, but token binding requires exact URL match
**Where**
- Mailbox endpoint schema in identity docs: `spec/02-identity-trust/identity-document-schema.md` (Endpoint has `host`, `port`, `transport`, **no path/base_url**)
- Mailbox token includes `mailbox_url` and requires strict canonicalization + **server-side binding check**: `spec/06-rfcs/RFC-0003-messaging.md` §7.3 and §7.4.1 (“Mailbox URL Binding (Normative)”)

**Problem**
- The token signs (and the server verifies) an exact `mailbox_url` string including **path** semantics (trailing slash removal, preservation of internal `//`, etc.).
- But the identity document endpoint format provides no way for a client to learn a mailbox **base path** if the mailbox is hosted under e.g. `https://example.com/mailbox/…` instead of at `/`.
- The server is required to reject tokens whose `mailbox_url` does not exactly match its configured canonical URL, including base path.

**Interop impact**
Two correct implementations can’t interoperate if one mailbox deployment uses a non-root base path (or any base path other than what the client guesses). Clients will sign a different `mailbox_url` than the mailbox expects → **401/403 on all mailbox operations**.

**Fix (normative)**
Either:
1) **Constrain v1**: Require mailbox API base path to be `/` (root). Then define `mailbox_url` derivation strictly from the identity endpoint: `https://{host}:{port}/` (with `:443` omitted). Server binding check must also assume `/`.  
or
2) **Extend endpoint schema**: Add `base_url` or `path` to mailbox endpoints in the Identity Document schema, and define how to construct `mailbox_url` from it (and include it in DHT/identity exchange).

### B2 — Ratchet message counter `N` semantics conflict for the initial→ratchet transition
**Where**
- “Initial→Ratchet Transition (Normative)” says first 0x01 message MUST use `N=1`: `spec/03-messaging-sync/secure-envelope.md`
- Same requirement in RFC: `spec/06-rfcs/RFC-0003-messaging.md` §3.4.2 (Initial extension) and surrounding text
- But `spec/03-messaging-sync/double-ratchet.md` states: “first message in each sending chain has N=0” and provides send pseudocode that, if followed naively after an initial message, will likely emit `N=0` on the first 0x01 message.

**Problem**
There are two incompatible interpretations for the first ratchet-header (0x01) message after the initial (0x00) message:
- RFC/secure-envelope: initial consumes chain step `N=0`, so first ratchet-header message is `N=1`.
- double-ratchet.md can be read as “first ratchet message is `N=0`”.

**Interop impact**
If one implementation follows RFC-0003 and another follows `double-ratchet.md` literally, the receiver will derive a different message key for the same ciphertext → **AEAD decryption fails**, conversation breaks.

**Fix (normative)**
Update `double-ratchet.md` to explicitly match RFC-0003:
- State that the initial (0x00) message corresponds to `N=0` of the first sending chain, and the first subsequent 0x01 message MUST use `N=1` with the same DH public key as in the initial extension (until a DH ratchet occurs).
- Ensure pseudocode reflects this special-case transition.

## HIGH issues (likely interop failure)

### H1 — libp2p DHT record-level signing/validation requirements are not specified
**Where**
- DHT “wire protocol MUST be libp2p Kademlia”: `spec/00-shared/layer-integration.md` (DHT Wire Protocol)
- DHT validation rules focus on application value verification (“No separate DHT signature required”): `spec/00-shared/layer-integration.md` (DHT Record Format) and `spec/06-rfcs/RFC-0001-identity-document.md` §12.*

**Problem**
libp2p Kademlia implementations differ in how they handle record authenticity:
- Some deployments rely on record-level signatures / validators.
- This spec mandates value-level validation (IDOC signatures inside the value) but does not normatively specify:
  - whether libp2p record signatures MUST be present or MUST be absent,
  - what key signs them (PeerID key? identity signing key?),
  - what validator rules peers must enforce at the libp2p record layer.

**Interop impact**
Two implementations can join the same overlay but disagree on accepting/storing PUT_VALUE records (one rejects what the other publishes), causing **identity discovery failures**.

**Fix (normative)**
Specify one interoperable profile, e.g.:
- “Records MUST be unsigned at the libp2p record layer; validation is solely via the record value bytes (IDOC/JSON signature). Implementations MUST configure their libp2p validator accordingly.”
or
- “Records MUST be signed using the libp2p PeerID private key, and validators MUST verify signature matches the publisher PeerID.”

### H2 — Admin WebSocket event registry and casing rules are inconsistent across documents
**Where**
- WebSocket events list includes `log_entry` and subscription control messages: `spec/05-ux-packaging/node-daemon.md` (WebSocket Events)
- Admin UI doc also mentions `log_entry`: `spec/05-ux-packaging/admin-ui.md`
- But the canonical type union in `spec/05-ux-packaging/interfaces.md` omits `log_entry` in `AdminEventType`.

**Problem**
- Event type registry differs between “interfaces” (claimed API contract) and daemon/UI docs.
- Additionally, the repo-wide convention says on-wire JSON is snake_case, but WebSocket payload field casing is not explicitly reaffirmed for WS payloads, and examples/types mix conventions in a way that can cause one side to send `sender_iid` while the other reads `senderIid`.

**Interop impact**
Clients and servers implemented from different documents can:
- fail to subscribe/unsubscribe correctly for `log_entry`,
- fail to decode event payload fields consistently.

**Fix**
- Make `AdminEventType` authoritative and consistent across all three docs, including whether `log_entry` exists in v1.
- Add an explicit **normative** statement: “All WebSocket payload JSON uses snake_case on the wire” (or the opposite), and give one concrete example payload per event.

## MEDIUM issues (edge cases / likely confusion)

### M1 — Mailbox delete semantics differ between the “MailboxService” interface and RFC-0003 HTTP API
**Where**
- `spec/00-shared/layer-integration.md` defines `MailboxService.acknowledge(messageId: string): Promise<void>`
- `spec/06-rfcs/RFC-0003-messaging.md` §7.4.3 defines `DELETE /messages` with JSON body `{ "message_ids": [...] }`

**Problem**
The interface suggests a single-message “ack” operation, while the RFC specifies a batch delete with a request body. This is resolvable (batch of 1), but not stated.

**Interop impact**
Some implementations may incorrectly implement a different HTTP endpoint shape (e.g., `/messages/{id}`) based on the interface, causing mailbox deletion to fail.

**Fix**
State explicitly in `layer-integration.md` that `acknowledge(messageId)` maps to RFC-0003 `DELETE /messages` with `message_ids=[messageId]`.

**Where**

**Interop impact**
Implementers relying on `progress.md` may build incompatible behavior.

**Fix**
Add a clear banner to `progress.md` that it is **non-normative changelog only**, or remove/avoid protocol-mechanics assertions there.

**Where**

**Problem**
No normative format or ordering rules for `id` are given (numeric string? UUID? monotonic integer?).

Specify `id` as e.g. an unsigned decimal uint64 string (no leading zeros) or a UUID, and define replay comparison rules.
