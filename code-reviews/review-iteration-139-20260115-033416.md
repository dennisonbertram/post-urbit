## 1) Internal contradictions between documents

### B1 — Mailbox base URL construction contradicts RFC-0003 canonicalization (default port and path)
**Severity: BLOCKING** (will cause mailbox token verification failures across compliant implementations)

**What conflicts**
- `spec/00-shared/layer-integration.md` mandates mailbox base path is root and gives a **non-canonical URL construction** that always includes `:<port>` and always ends with `/`.
- `spec/06-rfcs/RFC-0003-messaging.md` requires strict mailbox URL canonicalization, including **omitting default port 443** and requiring tokens to already be canonical.

**Why this blocks interoperability**
Mailbox bearer tokens bind the signature input to `mailbox_url`. If one implementation follows layer-integration (“always include :443”) and another follows RFC-0003 (“omit :443”), signatures won’t verify → store/retrieve/delete fail with `401 Unauthorized` despite both being “spec compliant” from their perspective.

**Citations**
- `spec/00-shared/layer-integration.md` → section **“Mailbox Base Path (v1 Normative)”**, contains:
  - `"For v1, the mailbox API base path MUST be '/' (root)."`
  - `mailbox_url = "https://" + host + ":" + port + "/"`
- `spec/06-rfcs/RFC-0003-messaging.md` → section **“7.3 Authentication”**, subsection **“URL Canonicalization (Normative)”**, rules include:
  - `"Port: Omit default port (:443 for https...)"`
  - `"Verifiers MUST: Reject tokens where mailbox_url is not already in canonical form."`

**Fix required**
- Define **one** normative derivation of the mailbox base URL from the identity endpoint:
  - If `port == 443`: base URL MUST be `https://<host>/`
  - Else: `https://<host>:<port>/`
- Ensure `layer-integration.md` explicitly defers to RFC-0003’s canonicalization rules (or repeats them verbatim) and removes the always-include-port formula.

### B2 — v1 mailbox “root-only base path” contradicts RFC-0003 allowing non-root mailbox_url
**Severity: BLOCKING** (spec currently allows a deployment configuration that cannot be expressed in discovery)

**What conflicts**
- `spec/00-shared/layer-integration.md` says v1 mailbox API base path MUST be `/` and endpoint schema has no `path`.
- `spec/06-rfcs/RFC-0003-messaging.md` canonicalization explicitly supports and even gives examples of non-root paths (e.g., `/api`), implying non-root deployments are valid.

**Why this blocks**
If non-root mailbox deployments are valid (RFC-0003), peers need a way to discover/encode the base path. But v1 endpoint schema cannot express it, and layer-integration prohibits it. Implementers cannot know whether to support non-root in practice.

**Citations**
- `spec/00-shared/layer-integration.md` → **“Mailbox Base Path (v1 Normative)”**:
  - `"For v1, the mailbox API base path MUST be '/' (root). The endpoint schema does not include a path field"`
- `spec/06-rfcs/RFC-0003-messaging.md` → **“URL Canonicalization (Normative)”** examples:
  - `https://relay.net:8443/api/ → https://relay.net:8443/api`

**Fix required (choose one)**
- **Option A (simplest v1):** Make RFC-0003 explicitly **root-only** for v1 (remove non-root examples; state non-root paths are invalid in v1 and MUST be rejected).
- **Option B:** Extend endpoint schema to include `base_path` (or similar) and update all mailbox URL derivations + token rules accordingly.

### M1 — Encryption key history retention contradicts itself
**Severity: MEDIUM** (unclear but implementable; causes inconsistent retention behavior)

**What conflicts**
- `spec/02-identity-trust/identity-document-schema.md` defines encryption key history retention as **“at most 5 previous keys or 30 days”**.
- `spec/02-identity-trust/key-rotation.md` states **“Retain public key in keys.encryption.previous indefinitely”** (contradiction).

**Citations**
- `spec/02-identity-trust/identity-document-schema.md` → section **“Encryption Key History Entry”**:
  - `"Retention policy: Keep at most 5 previous keys or 30 days"`
- `spec/02-identity-trust/key-rotation.md` → section **“Handling Old Keys / Encryption Key (Old)”**:
  - `"Retain public key in keys.encryption.previous indefinitely"`

**Fix**
Pick one retention policy and apply it consistently; ideally align `key-rotation.md` to the schema (5 keys / 30 days), since that is already cross-referenced by other components.

## 2) Missing normative requirements

### H1 — 2DH initial-message decryption does not specify trying recipient’s own rotated private keys
**Severity: HIGH** (real interop break during/after recipient encryption key rotation; especially with mailbox-delayed first messages)

**Problem**
RFC-0003 describes the receiver (Bob) trying **sender (Alice)** encryption public keys (`keys.encryption.current` then `previous[]`) to account for sender rotation. But it does not normatively specify the symmetric required behavior when **Bob rotated his own encryption key** and the sender used a stale Bob key (common under caching + offline delivery).

Given other docs explicitly recommend retaining old encryption private keys for 30 days, the messaging RFC should specify *how to use them* for 2DH initial messages.

**Citations**
- `spec/06-rfcs/RFC-0003-messaging.md` → section **“5.3 Protocol / Bob receives initial message”**:
  - `"Bob tries Alice's encryption keys in order until decryption succeeds"`
  - No corresponding requirement to try Bob’s own retained private keys.
- `spec/02-identity-trust/key-rotation.md` → **“Handling Old Keys / Encryption Key (Old)”**:
  - `"Retain private key for 30 days to decrypt in-flight messages"`

**Fix**
Add a normative decryption trial order for initial (0x00) messages that accounts for both sides:
- Receiver MUST try `(recipient_private_key ∈ {current, retained_previous_privates}) × (sender_public_key ∈ {current, previous[] newest→oldest within expires_at})` in a specified deterministic order, stopping at first successful AEAD decrypt.
- Also specify which `expires_at` constraints apply (currently RFC-0003 says use `previous[]` whose `expires_at` has not passed; that should be made explicit for both sender-key trial and recipient-key trial).

### M2 — NAT discovery (PUDS) lacks a MUST for transaction-id matching and version handling
**Severity: MEDIUM** (interoperability and robustness issue; easy to fix)

**Problem**
The PUDS response echoes `Transaction ID`, but the spec doesn’t explicitly require clients to verify it matches the request, nor does it specify behavior for wrong magic/version.

**Citations**
- `spec/01-transport-connectivity/nat-traversal.md` → section **“Discovery Response”** shows `Transaction ID` field but no MUST about checking it.

**Fix**
Add normative requirements:
- Client MUST discard any response where `(magic, version, transaction_id)` does not match an outstanding request.
- Server MUST ignore requests with unknown version (or respond with an error format—if adding errors, specify them).

### M3 — PUHP probe text implies a response, but no response is specified
**Severity: MEDIUM** (ambiguous behavior)

**Problem**
The doc says “Don’t respond to probes without valid transaction ID”, but the probe format is defined as a one-way UDP packet and no response packet format exists.

**Citations**
- `spec/01-transport-connectivity/nat-traversal.md` → section **“Security Considerations”**:
  - `"Port scanning: Don't respond to probes without valid transaction ID"`
- Same file → section **“Probe Packet Format”** defines a one-way `PUHP` packet only.

**Fix**
Clarify normatively:
- Receivers MUST NOT send any response to `PUHP` probes (recommended), *or* define an explicit probe response format.

## 3) Ambiguous wire formats

### M4 — Direct-peer hole-punch coordination framing omits the required stream-type byte context
**Severity: MEDIUM** (confusing; implementable if RFC-0002 is followed, but this doc alone is ambiguous)

**Problem**
`nat-traversal.md` describes control-stream coordination framing as `[u32 length][json]` but does not restate that the control stream begins with a 1-byte stream type `0x01`, which matters for implementers reading only this file.

**Citations**
- `spec/01-transport-connectivity/nat-traversal.md` → section **“Direct Peer Coordination / Framing (per RFC-0002 §5.4)”** shows:
  - `Message Length (4 bytes) ... JSON Message`
- `spec/06-rfcs/RFC-0002-transport.md` → §5.2 / §5.4 requires:
  - `"Client writes stream type byte 0x01 (Control) as first byte"`

**Fix**
Add a single normative line in `nat-traversal.md`:
- “These messages are carried inside the RFC-0002 control stream, which includes the initial 1-byte stream type header.”

## 4) Security vulnerabilities

### H2 — DHT record validation requirements can create amplification/DoS (device docs / revocations)
**Severity: HIGH** (network-level DoS vector)

**Problem**
`layer-integration.md` and RFC-0001 require DHT nodes to verify and reject invalid records. For several record types (device documents, device index, revocations), verification requires fetching an identity document and potentially checking key history.

An attacker can spam many distinct device docs referencing many IIDs, forcing DHT nodes to perform follow-up DHT fetches (or heavy signature checks), amplifying resource usage.

**Citations**
- `spec/00-shared/layer-integration.md` → section **“Record Validation Rules”**:
  - `"Before storing ANY record, DHT nodes MUST ... Verify all required signatures"`
- `spec/00-shared/layer-integration.md` → section **“Device Document Verification”**:
  - `"1. Fetch identity document for iid"`
- `spec/06-rfcs/RFC-0001-identity-document.md` → §12.8:
  - `"Device Documents: Fetch parent identity document for iid, validate signature_by_identity..."`

**Fix**
Add explicit anti-DoS normative requirements for DHT validators, e.g.:
- Validators MUST NOT perform unbounded recursive fetches.
- Validators MUST apply per-source and per-key rate limits.
- Validators SHOULD cache identity docs used for validation for at least N minutes.
- If required parent identity is unavailable within a bounded budget (e.g., timeout), the node MUST treat the record as unverifiable and reject (or quarantine without re-gossiping).

### M5 — Unknown-sender PUSE verification can force DHT lookups (privacy + DoS)
**Severity: MEDIUM** (security/operational weakness; not a wire-format break)

**Problem**
RFC-0003 requires fetching the sender IDOC before verifying the PUSE signature. For unknown senders, this implies network activity (DHT/directory), allowing:
- resource-exhaustion attacks by sending many envelopes with random sender IIDs
- potential privacy leakage if lookups are observable

**Citations**
- `spec/06-rfcs/RFC-0003-messaging.md` → §3.8:
  - `"Fetch sender identity document ... Verify signature ..."`
- `spec/02-identity-trust/caching-policy.md` → discusses negative caching but does not define messaging-layer handling for adversarial unknown senders.

**Fix**
Add bounded-lookup and negative-caching requirements at the messaging ingress:
- Implementations SHOULD apply a per-remote-address and per-sender-IID budget for identity resolution triggered by inbound messages.
- Implementations MUST support negative caching for unknown/unverifiable sender IIDs (already suggested in caching-policy, but not bound to messaging ingress behavior).

## 5) Unspecified error handling

### H3 — WASM ABI says oversized results are “truncated”, producing invalid CBOR
**Severity: HIGH** (will break app interoperability; creates parser ambiguity)

**Problem**
`abi.md` states host truncates results > 1MB. Truncating a CBOR object generally makes it undecodable; different runtimes might truncate differently, and apps cannot distinguish truncation from corruption.

**Citations**
- `spec/04-app-runtime/abi.md` → section **“handle”**, bullet:
  - `"Maximum result size: 1 MB (1048576 bytes); larger results are truncated"`

**Fix**
Replace truncation with a normative error outcome, e.g.:
- Host MUST return a valid CBOR error envelope `{ok:false, error:{code:"RESULT_TOO_LARGE",...}}` (or a transport-level negative code) and MUST NOT truncate CBOR bytes.

### M6 — Sync “DEPENDENCY_MISSING” recovery is not fully specified on-wire
**Severity: MEDIUM** (unclear but workable; may cause divergent recovery strategies)

**Problem**
`sync-protocol.md` says queue and request dependency when missing, but does not specify a dedicated message for “request these missing dependency op IDs” beyond re-running offer/accept.

**Citations**
- `spec/03-messaging-sync/sync-protocol.md` → **“Error Handling”** table:
  - `DEPENDENCY_MISSING | Queue and request dependency`
- No corresponding normative “dependency request” message type beyond existing offer/accept.

**Fix**
Either:
- specify that the recovery mechanism is “send a new `SYNC_REQUEST` and rely on `SYNC_OFFER/ACCEPT` to include dependencies”, or
- add a `SYNC_WANT` / `SYNC_REQUEST_OPS` message type with an explicit CBOR schema.
