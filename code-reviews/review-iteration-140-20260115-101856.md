### 1) ABI error semantics contradict themselves (permission denied / method not found)  
**Severity:** **BLOCKING** (prevents interoperable app↔host implementations)  
**Category:** Internal contradiction, ambiguous wire format, unspecified error handling  
**Evidence:**
- `spec/04-app-runtime/abi.md`:
  - `host.call` return codes include transport-level `-4` for capability denial: **L62-L68** (“`-4`: Permission denied (missing capability)”).
  - Immediately after, `host.get_result` claims **permission denied** and **method not found** are *application-level* errors returned **inside the CBOR envelope**: **L87-L88**.
  - Later it reiterates “Application-level errors are always returned inside the CBOR envelope”: **L268-L274**.
- `spec/04-app-runtime/api-surface.md`:
  - States “Calls without required capability return `PERMISSION_DENIED`”: **L13-L16**.
  - Reserved methods return `{ ok: false, error: { code: "NOT_IMPLEMENTED" } }`: **L25-L30** (i.e., *envelope*, not negative `host.call`).

**Why this is a real contradiction / why it blocks implementation:**
- If a host returns `host.call = -4` for missing capability, the guest never receives a CBOR envelope (no call_id).  
- But other parts of the ABI and API surface tell app authors to expect permission denial as `{ ok:false, error:{code:"PERMISSION_DENIED"}}` via `get_result`.  
- Same ambiguity exists for unknown methods: is it `host.call = -1` (“Invalid method name”) or a `{ ok:false, error:{code:"METHOD_NOT_FOUND"}}` envelope?

**Required fix (normative, to unblock):**
1. **Pick exactly one model** for method/permission errors:
   - **Model A (recommended):** `host.call` returns a positive `call_id` for any syntactically valid method name + CBOR args; **ALL** method-level errors (permission denied, not found, not implemented, validation errors, quota) return as `{ok:false,...}` envelopes. Negative `host.call` only for ABI-level failures (bad UTF-8, invalid CBOR bytes, too many outstanding calls, internal host failure).
   - **Model B:** keep `-4` etc., but then **remove/replace** the statements in `abi.md` that say permission denied and method not found are application-level envelope errors, and update `api-surface.md` to match.
2. Clarify `-1`: does it mean “unknown method” or “method name bytes invalid UTF-8 / length > 64”? Right now it reads as “Invalid method name” (**abi.md L64-L67**) but is used elsewhere as “method not found”.

### 2) Handshake does not require pinning the expected peer IID  
**Severity:** **HIGH** (security vulnerability; enables wrong-peer acceptance if caller fails to enforce IID binding)  
**Category:** Security vulnerability, missing normative requirement  
**Evidence:**
- `spec/01-transport-connectivity/peer-handshake.md`:
  - ClientHello includes `expected_server_iid` but marks it optional: JSON schema **L94-L103**, field table **L106-L113** (`expected_server_iid` required = “No”).
  - No normative requirement is stated that “when connecting to a known IID, expected_server_iid MUST be provided and MUST be checked”.

**Impact:**
- The spec’s security model assumes identity is verified by the handshake, but if the client does not bind to the intended peer IID, a user can be induced to complete a valid handshake with **the wrong identity** (e.g., via UI confusion, malicious DNS naming, or misdirected endpoint hints).  
- In practice, `TransportService.connect(peerIID)` (in transport interfaces) strongly implies the caller *knows* the expected IID; the handshake should make that binding mandatory for that usage.

**Required fix (normative, for v1):**
- Add a clear requirement in RFC-0002 and/or `peer-handshake.md`:
  - **If the connection attempt is initiated for a specific IID (i.e., the caller has an intended peer IID), the client MUST send `expected_server_iid` and MUST abort the handshake if `server_iid` differs.**
  - (You can keep `expected_server_iid` optional only for cases where the client truly does not know who it is dialing, but then those cases should be explicitly enumerated and threat-modeled.)

### 3) WASI capability gating contradicts the virtual filesystem policy  
**Severity:** **MEDIUM** (unclear but implementable; likely causes inconsistent sandbox enforcement across implementations)  
**Category:** Internal contradiction / policy mismatch  
**Evidence:**
- `spec/04-app-runtime/wasm-sandbox.md`:
  - Enabled WASI capabilities table says filesystem read/write is “Gated by `storage:app`”: **L23-L29** (notably **L27**).
  - Storage mechanisms table later states `/cache/*` and `/tmp/*` are read-write and **“None (always allowed)”**: **L56-L61**.

**Impact:**
- If `fd_write` is globally gated by `storage:app`, then an app without `storage:app` cannot write even to `/tmp` or `/cache`, contradicting the “always allowed” claim.
- Different implementers may pick different interpretations (global gating vs path-based gating), producing behavior differences for apps.

**Recommended fix:**
- Clarify whether gating is:
  - **Per-path** (recommended): `/cache` and `/tmp` writable without `storage:app`, while Host Storage API requires `storage:app`.
  - Or **global**: any write requires `storage:app` (then update the storage mechanism table and rationale accordingly).

### 4) Handshake failure signaling is underspecified (wire-level close behavior)  
**Severity:** **MEDIUM** (interop risk; different peers may hang/wait or treat failures differently)  
**Category:** Unspecified error handling  
**Evidence:**
- `spec/01-transport-connectivity/peer-handshake.md`:
  - Defines `handshake_complete` success and error payloads: **L239-L260**.
  - Does **not** specify what happens on failure at the transport level: whether the sender MUST close the QUIC connection, what application close code to use, whether the control stream remains open, etc.

**Impact:**
- One implementation might send `handshake_complete {success:false}` and keep the connection alive; another might immediately close the connection with a QUIC application error; another might reset the stream. These choices affect retry logic and can create hangs or inconsistent UX.

**Recommended fix (normative):**
- Specify a required failure behavior, e.g.:
  - On handshake failure, the endpoint MUST send `handshake_complete` (best-effort), then MUST close the QUIC connection with a specific application error code (e.g., `HANDSHAKE_FAILED`), within a defined grace period, and MUST ignore any subsequent non-control streams.

### 5) Traceability framework requires stable IDs, but specs don’t include them  
**Severity:** **MEDIUM** (doesn’t block implementation, but fails the project’s own “completeness gate”)  
**Category:** Missing normative requirements (process-level), internal inconsistency with stated completion criteria  
**Evidence:**
- `spec/00-overview/traceability.md`:
  - Requires stable IDs for each success-criteria bullet: **L15-L24** (notably **L23**).
  - Requires stable IDs for each normative statement: **L25-L36** (notably **L36**).
- `spec/00-overview/success-criteria.md`:
  - Contains checklist bullets but **no SC-* IDs**: e.g. **L5-L27** show bullets without IDs.

**Impact:**
- Conformance/harness linkage is not mechanically possible as written, because the required identifiers don’t exist in the documents they’re supposed to index.

**Recommended fix:**
- Add SC-* IDs to each bullet in `success-criteria.md`, and add REQ-* IDs adjacent to each MUST/SHOULD statement across the component specs/RFCs (or provide a separate normative mapping file).
