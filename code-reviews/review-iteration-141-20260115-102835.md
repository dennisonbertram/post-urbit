## 1) Internal contradictions between documents

### C1 — `expected_server_iid`: RFC says SHOULD, layer doc says MUST (security + conformance mismatch)
**Severity: HIGH**

- **What conflicts**
  - The **transport RFC** treats `expected_server_iid` as **SHOULD** (and “MUST verify match if provided”), allowing clients to omit it.
  - The **transport layer doc** states a **Normative MUST**: when connecting to a specific known IID, the client must include `expected_server_iid` and abort on mismatch.

- **Why it matters**
  - This is a real security property (wrong-peer acceptance / endpoint-hint redirection). Divergent implementations will be “spec compliant” under different documents, producing inconsistent security posture.

- **References**
  - `spec/06-rfcs/RFC-0002-transport.md` §5.5 “ClientHello Message” (around **L220-L270**): field table says `expected_server_iid` **SHOULD**; text: “MUST verify match if provided”.
  - `spec/01-transport-connectivity/peer-handshake.md` § “IID Binding Requirement (Normative)” (around **L190-L230**): “client MUST include `expected_server_iid` … MUST abort …”

- **Fix**
  - Make RFC-0002 authoritative behavior match the layer spec:
    - **RFC-0002** should say: for any connection initiated to a known IID, the client **MUST** include `expected_server_iid` and fail if mismatch; omission allowed only for explicit “unknown-peer” scenarios.

### C2 — Encryption key retention policy contradicts itself (“indefinitely” vs “30 days / 5 keys”)
**Severity: MEDIUM**

- **What conflicts**
  - Identity schema says encryption key history is bounded (“at most 5 previous keys or 30 days”).
  - Key-rotation doc says “retain public key in `keys.encryption.previous` indefinitely”.

- **Why it matters**
  - It impacts document size bounds and implementer expectations. This can cascade into verification/decryption behavior for delayed messages and whether `keys.encryption.previous[]` is expected to contain long history.

- **References**
  - `spec/02-identity-trust/identity-document-schema.md` § “Encryption Key History Entry” / retention policy (around **L210-L240**): “Keep at most 5 previous keys or 30 days…”
  - `spec/02-identity-trust/key-rotation.md` § “Handling Old Keys → Encryption Key (Old)” (around **L170-L195**): “Retain public key in `keys.encryption.previous` indefinitely”

- **Fix**
  - Pick one normative retention policy and apply consistently. If the intent is bounded history, change key-rotation.md accordingly (and ensure it aligns with the 16KB IDOC limit).

### C3 — Relay allocation nonce encoding: padding requirement differs between component doc and RFC
**Severity: MEDIUM**

- **What conflicts**
  - Relay component doc uses `<16-bytes-base64url>` without explicitly stating “no padding”.
  - RFC-0002 is explicit: base64url **no padding**, and even validates **22 chars**.

- **References**
  - `spec/01-transport-connectivity/relay-protocol.md` “Allocation Request” (around **L35-L70**): `nonce`: `"<16-bytes-base64url>"`
  - `spec/06-rfcs/RFC-0002-transport.md` §7.8 “Allocation Protocol” (around **L470-L540**): `nonce`: `"<16-bytes-base64url-no-padding>"` and “exactly 22 characters”

- **Fix**
  - Update `relay-protocol.md` to explicitly require base64url **no padding**, 16 raw bytes → 22 chars, and reject `=`.

## 2) Missing normative requirements

### M1 — MUST specify retention of *private* encryption keys needed to decrypt delayed initial messages
**Severity: HIGH**

- **Problem**
  - The specs correctly describe that initial-message decryption may require trying historical encryption keys (recipient may have stale sender docs, or sender may use stale recipient key).
  - However, there is no explicit MUST/SHOULD about retaining the *private* keys corresponding to published `keys.encryption.previous[]`.

- **Why it matters**
  - This becomes an interoperability failure in practice: one implementation might discard old X25519 private keys immediately after rotation, making it impossible to decrypt initial messages encrypted to a previous key—especially relevant with mailbox/offline delivery.

- **References**
  - `spec/06-rfcs/RFC-0003-messaging.md` §5.3 “Protocol” (around **L520-L610**): receiver tries sender encryption keys (`current`, then `previous[]`).
  - `spec/02-identity-trust/identity-document-schema.md` § “Encryption Key History Entry” (around **L210-L240**): retention described for *public history entries*, not private-key retention requirement.

- **Fix**
  - Add a normative requirement (Identity layer):
    - If an encryption public key appears in `keys.encryption.previous[]`, the identity owner **MUST** retain the corresponding private key until at least `expires_at` (or for the stated retention window), specifically to support decryption of delayed initial messages and offline delivery.

### M2 — Mailbox token lifetime / skew acceptance is not normatively bounded
**Severity: HIGH**

- **Problem**
  - Tokens have `expires_at` and are signed; RFC-0003 rigorously defines URL canonicalization and token encoding, but does not normatively define:
    - maximum allowed token lifetime (server-side acceptance policy),
    - required clock-skew tolerance for mailbox token verification,
    - whether servers MUST reject “too-far-future” `expires_at`.

- **Why it matters**
  - Different mailbox implementations will accept/reject the same tokens depending on local policy → interop failures (401/403) across mailbox providers.

- **References**
  - `spec/06-rfcs/RFC-0003-messaging.md` §7.3 “Authentication” / token structure and signature (around **L300-L480**): defines `expires_at` but not a required acceptance window.

- **Fix**
  - Add normative constraints, e.g.:
    - `expires_at` MUST be within `[now - skew, now + max_lifetime]`
    - `max_lifetime` MUST be ≥ X and ≤ Y (e.g., 24h max), and skew MUST be at least ±5 minutes.

### M3 — PUSE replay protection policy is described but not made normative/consistent across docs
**Severity: MEDIUM**

- **Problem**
  - `secure-envelope.md` describes caching `{message_id, received_at}` TTL=7 days and a sequence window=100.
  - RFC-0003 defines that `message_id` is UUID and discusses replay protection conceptually, but does not normatively standardize cache TTL/window sizes (or explicitly declare them implementation-defined).

- **References**
  - `spec/03-messaging-sync/secure-envelope.md` § “Replay Protection” (around **L260-L290**): TTL and window described.
  - `spec/06-rfcs/RFC-0003-messaging.md` §10.3 “Replay Protection” (around **L980-L1010**): conceptual list.

- **Fix**
  - Either:
    - Make TTL/window normative in RFC-0003, **or**
    - Explicitly declare them “implementation-defined but MUST be ≥ X and ≤ Y” for interoperability expectations.

## 3) Ambiguous wire formats

### W1 — PUDS (STUN-like) has no normative length/trailing-bytes rules
**Severity: MEDIUM**

- **Problem**
  - PUDS packets have fixed layouts depending on IPv4 vs IPv6, but the spec does not state:
    - exact expected datagram sizes per Address Type,
    - whether trailing bytes MUST be rejected,
    - what to do if Address Type is unknown.

- **Interop impact**
  - Implementations may accept padded or malformed responses differently; some may parse extra bytes, others reject.

- **References**
  - `spec/01-transport-connectivity/nat-traversal.md` § “Discovery Protocol (STUN-like)” (around **L20-L70**): message formats shown; no “trailing bytes rule”.

- **Fix**
  - Add normative parsing rules similar to IDOC/PUSE/PURL:
    - expected lengths (IPv4 response = 4+1+16+1+4+2 = 28 bytes; IPv6 response = 40 bytes),
    - MUST reject if length mismatches,
    - MUST reject unknown Address Type.

### W2 — DHT “JCS-canonical JSON” validation requirement is underspecified on failure behavior
**Severity: MEDIUM**

- **Problem**
  - The DHT spec requires nodes to reject non-JCS JSON for some record types, but does not specify how this maps onto libp2p Kademlia behavior:
    - what error is returned to the PUT sender (if any),
    - whether the record is silently dropped,
    - whether peers penalize senders.

- **References**
  - `spec/00-shared/layer-integration.md` § “JCS Canonical JSON Requirement (Normative)” and § “Record Validation Rules” (around **L250-L340**).

- **Fix**
  - Specify normative behavior at the DHT RPC layer:
    - e.g., “MUST return a Kademlia error response for PUT_VALUE with code X” or “MUST silently drop” (pick one), plus rate-limit guidance.

## 4) Security vulnerabilities

### S1 — Wrong-peer acceptance risk if implementations follow RFC “SHOULD” and omit `expected_server_iid`
**Severity: HIGH**

- This is the security consequence of **C1**, but worth calling out explicitly: allowing omission of `expected_server_iid` in normal peer dialing makes endpoint-hint redirection (DNS poisoning / stale endpoint / UI confusion) much easier.

- **References**
  - Same as C1.

- **Fix**
  - Same as C1: make it a MUST for known-IID connections in RFC-0002.

---

### S2 — Mailbox retrieval response includes `sender_iid` without requiring it be derived from the envelope bytes
**Severity: MEDIUM**

- **Problem**
  - Mailbox is untrusted, but RFC-0003 retrieve response includes `sender_iid`. The spec does not explicitly require that the mailbox compute `sender_iid` by parsing the stored PUSE header (bytes 6–25), rather than storing separate metadata that could be corrupted/forged by mailbox operator.

- **Why it matters**
  - Clients should treat mailboxes as metadata-manipulable; if UIs trust `sender_iid` from mailbox response without checking the envelope header, they can be misled.

- **References**
  - `spec/06-rfcs/RFC-0003-messaging.md` §7.4.2 “Retrieve Messages” (around **L610-L690**): response schema includes `sender_iid`.

- **Fix**
  - Add: mailbox servers MUST derive `sender_iid` from the stored envelope header; clients MUST ignore/override `sender_iid` response field if it disagrees with the PUSE header.

## 5) Unspecified error handling

### E1 — No uniform rule for how to react on invalid PUSE received over QUIC (close stream vs close connection)
**Severity: HIGH**

- **Problem**
  - RFC-0003 defines detailed PUSE parsing errors and codes, but does not define transport reaction rules when receiving invalid envelopes on stream 0x03:
    - Is the correct behavior to reset only that stream?
    - Close the entire QUIC connection with an application error?
    - Rate-limit and continue?

- **Interop impact**
  - Implementations will diverge: some may tear down connections on a single malformed envelope; others will keep connections open. This affects reliability and abuse-resistance; also can produce surprising behavior differences.

- **References**
  - `spec/06-rfcs/RFC-0003-messaging.md` §9 “Error Handling” (around **L860-L950**): error code registry exists.
  - `spec/06-rfcs/RFC-0002-transport.md` §9.2 “Application Error Codes” (around **L760-L820**): transport errors exist, but no mapping for “invalid PUSE envelope on message stream”.

- **Fix**
  - Add normative handling guidance (RFC-0002 or RFC-0003):
    - e.g., “On invalid PUSE: MUST reset the message stream; MUST NOT close the connection unless N violations in T seconds; MAY close with 0x101/0x10x after threshold”.

---

### E2 — DHT same-sequence conflict state has no standardized external API/error surface
**Severity: MEDIUM**

- **Problem**
  - The client-side conflict rule is described (“enter conflict state”), but there’s no normative requirement for how this is surfaced across interfaces (e.g., `fetchIdentity()` returns what? an error code? partial data?).

- **References**
  - `spec/00-shared/layer-integration.md` § “Conflict Resolution (Normative)” (around **L140-L200**): same-sequence different content → conflict state.
  - `spec/01-transport-connectivity/interfaces.md` `DiscoveryService.fetchIdentity()` (around **L150-L220**) returns `IdentityDocument | null` only; no conflict channel.

- **Fix**
  - Add a normative error/return variant for identity fetch:
    - e.g., `fetchIdentity()` MUST be able to return `{status:"conflict", candidates:[...]}` or throw a specific error code.
