## Findings

### 1) Internal contradictions between documents

#### [HIGH] `expected_server_iid` requirement is contradictory (security + behavior)
- **Where**
  - `spec/06-rfcs/RFC-0002-transport.md` **§5.5** (`ClientHello Message`) — field table says:
    - `expected_server_iid` **“SHOULD”**
  - `spec/01-transport-connectivity/peer-handshake.md` — **“IID Binding Requirement (Normative)”** says:
    - “The client **MUST** include `expected_server_iid` … MUST abort …”
- **Why it matters**
  - This creates two plausible compliant behaviors:
    - RFC-led implementations omit `expected_server_iid` routinely (weaker wrong-peer protection).
    - Layer-doc-led implementations require it whenever connecting to a known IID.
  - This can cause **security posture divergence** and inconsistent telemetry/error paths, even if the handshake still “works”.
- **Fix**
  - Make RFC-0002 authoritative on the conditional requirement:
    - Keep field **optional** for discovery/unknown-peer cases.
    - Add an explicit MUST for “connect-to-known-IID APIs” (matching peer-handshake.md).

#### [LOW] Progress log contradicts mailbox routing rules (non-normative but misleading)
- **Where**
  - `spec/progress.md` — “Issues Fixed (Iteration 107) … **Mailbox storage routing … store/retrieve/delete by recipient_iid from PUSE header**”
  - Conflicts with RFC-0003’s current normative text:
    - `spec/06-rfcs/RFC-0003-messaging.md` **§7.4.1** “Storage Keying and Routing (Normative)”:
      - “Mailbox servers MUST route and store messages by the **explicit inbox owner IID from the URL path**…”
- **Why it matters**
  - Many implementers *do* read progress trackers as “what changed”; this could reintroduce a known-bad mailbox behavior (especially for group fanout where PUSE recipient is `group_id`).
- **Fix**
  - Update progress.md entry (or add an “obsolete note”) to avoid reintroducing the old rule.

### 2) Missing normative requirements

#### [HIGH] Revocation checking is not normatively required for message/token acceptance
- **Where**
  - `spec/03-messaging-sync/secure-envelope.md` — **“Signature Verification”** algorithm verifies against `current/previous/history` keys but does **not** require checking key/identity revocation.
  - `spec/06-rfcs/RFC-0003-messaging.md` — PUSE verification text (e.g., **§3.8**, **§9**) defines signature validity but does not clearly state: “MUST reject if sender identity/key is revoked”.
  - Similar gap for bearer tokens:
    - `spec/06-rfcs/RFC-0003-messaging.md` **§7.3** (Mailbox token signing/verification) describes signature verification but not a MUST-level revocation policy.
- **Why it matters**
  - Without a normative rule, compliant implementations may diverge:
    - Some will accept messages/tokens signed by **revoked** keys (security regression).
    - Others will reject them (potentially breaking offline-delivered items).
  - This is a classic **interop + security** split.
- **Fix**
  - Add a clear rule set, e.g.:
    - “Implementations MUST consult revocation state when verifying PUSE signatures / mailbox tokens.”
    - Define whether revocation is evaluated at **receipt time** vs **claimed send time** (send time is hard to trust pre-decryption).
    - Define behavior for mailbox-delayed messages (likely “reject once revocation is known” is simplest and safest).

---

#### [MEDIUM] DHT PUT failure semantics not specified (validation required, but what does a peer observe?)
- **Where**
  - `spec/00-shared/layer-integration.md` — **“Record Validation Rules”** and **“DHT Wire Protocol (Normative)”** require storage nodes to verify and “Reject records that fail validation”.
  - `spec/06-rfcs/RFC-0001-identity-document.md` **§12.8** similarly requires rejection on failed checks.
- **Why it matters**
  - Implementations building on libp2p Kademlia will face a practical question:
    - Does an invalid PUT return a protocol-level error? Is it silently dropped? Is it stored-but-not-republished?
  - Different libp2p stacks may expose different error surfaces; without a normative requirement, clients may interpret outcomes differently (e.g., “publish succeeded” vs “publish failed”).
- **Fix**
  - Add explicit guidance at the integration boundary, e.g.:
    - “If validation fails, the node MUST respond with a failed PUT outcome (application-visible error), and MUST NOT republish.”
    - If the underlying DHT cannot express this, specify client-side verification + “best-effort” semantics explicitly.

### 3) Ambiguous wire formats / parsing rules

#### [HIGH] Mailbox token example uses a non-canonical `mailbox_url` form
- **Where**
  - `spec/06-rfcs/RFC-0003-messaging.md` **§7.3** shows a token example:
    - `"mailbox_url": "https://mailbox.example.com"`
  - Same section’s **URL Canonicalization (Normative)** says:
    - “Normalize empty path to `/`”
  - And `spec/00-shared/layer-integration.md` — **Mailbox Base URL Derivation (v1 Normative)** constructs URLs ending with `/`.
- **Why it matters**
  - If an implementer follows the example literally, they will generate **non-canonical tokens** that verifiers “MUST reject” (since verifiers must reject non-canonical `mailbox_url` forms).
- **Fix**
  - Change the example to `"https://mailbox.example.com/"` and ensure all examples match the canonicalization rules.

---

#### [MEDIUM] Mailbox URL canonicalization has an underspecified corner case (path of only slashes)
- **Where**
  - `spec/06-rfcs/RFC-0003-messaging.md` **§7.3**, canonicalization rule #4:
    - “Normalize empty path to `/`. Then, if the path is not exactly `/`, remove all trailing `/`…”
  - The provided illustrative pseudocode in the same section can produce an **empty path** after stripping (e.g., input path `"///"`).
- **Why it matters**
  - Token signature inputs could differ across implementations for unusual-but-possible inputs (reverse proxies and misconfigured URLs do produce odd paths).
- **Fix**
  - Add a final normalization step:
    - “After removing trailing slashes, if the path becomes empty, set it to `/`.”

---

#### [MEDIUM] v1 behavior for unknown PUSE header extension types is implied but not made explicit in the non-RFC doc
- **Where**
  - `spec/03-messaging-sync/secure-envelope.md` — **“Header Extension Validation (Normative)”**:
    - Defines max sizes and fixed sizes for known types, and mentions “Unknown types…”
    - But does not explicitly say: **v1 MUST reject unknown extension types**.
  - `spec/06-rfcs/RFC-0003-messaging.md` **§9.1** includes `INVALID_EXTENSION`, implying rejection.
- **Why it matters**
  - A strict reading of secure-envelope.md could lead to “accept unknown extension type if ext_len ≤1024”, which is not workable (you cannot derive keys), and may create inconsistent logging/metrics and error signaling.
- **Fix**
  - Add an explicit v1 rule in secure-envelope.md:
    - “Receivers MUST reject extension types other than 0x00/0x01/0x02 in v1 (INVALID_EXTENSION 0x306).”

### 4) Security vulnerabilities

#### [HIGH] DHT validation requirements create a CPU/IO DoS surface without mandatory rate limits
- **Where**
  - `spec/00-shared/layer-integration.md` — **“Record Validation Rules”** and identity update authorization steps require parsing + JCS checks + Ed25519 verification before storing.
  - `spec/06-rfcs/RFC-0001-identity-document.md` **§12.8** similarly mandates verification.
- **Why it matters**
  - An attacker can flood a node with:
    - many invalid “records” that still force expensive parsing/canonicalization/signature checks.
  - The spec has some size limits (e.g., IDOC 16KB), but **does not require**:
    - per-peer/per-connection rate limiting,
    - concurrency caps,
    - early-drop policy before expensive steps.
- **Fix**
  - Add normative controls for DHT nodes (even if “implementation-defined defaults”):
    - Maximum PUTs per remote per minute
    - Max concurrent validations
    - Early size checks before JSON parse / JCS checks
    - Optional ban scoring for repeat invalid records

---

### 5) Unspecified error handling

#### [MEDIUM] Multiple protocols say “reject” without specifying the on-wire/error signaling mechanism
Examples:
- **PUSE parsing/validation**
  - `spec/06-rfcs/RFC-0003-messaging.md` **§9** defines error codes, but it’s not always explicit whether the receiver:
    - silently drops,
    - closes the stream,
    - closes the QUIC connection with an application error code,
    - sends an in-band error message (there is none defined for stream 0x03).
- **PUDS discovery**
  - `spec/01-transport-connectivity/nat-traversal.md` — discovery protocol defines request/response shapes but not explicit server behavior for invalid magic/version/length (drop vs reply). This matters for amplification resistance.
- **DHT PUT validation**
  - As noted above: rejection is required, but peer-visible failure semantics aren’t.

**Fix**
- For each wire protocol, add a short normative “On invalid X, do Y” section:
  - drop silently vs close with error code vs respond with ERROR frame (if defined)
  - and mandate consistent logging/metrics for diagnosability.
