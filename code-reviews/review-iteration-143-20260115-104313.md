## 1) Relay allocation: endpoint derivation + TLS policy are unspecified (and enable token-hijack)
**Severity: BLOCKING** (prevents interoperable implementation; also a concrete security break)

### Problem
Relay allocation is specified as an HTTPS request (`POST /allocate`), but the spec does not define **how a client derives the allocation URL (scheme/host/port/path)** from the relay endpoint it learns via identity documents/config, nor does it define **how TLS server authentication is performed** for that HTTPS request.

This is not just “missing detail”: if an implementation mistakenly applies the Post-Urbit QUIC policy (“accept ANY certificate”) to the relay’s HTTPS allocation call, a MITM can steal the allocation token and **race to bind** the allocation to the attacker’s IP:port (RFC-0002 “two-step UDP binding”). That enables hijacking inbound relayed traffic to the victim IID.

### Spec citations
- Allocation request is shown, but with no scheme/port binding:
  - `spec/01-transport-connectivity/relay-protocol.md` — “Allocation Request” (approx ~L40–L90)
  - `spec/06-rfcs/RFC-0002-transport.md` — §7.8 “Allocation Protocol” (approx ~L430–L520)
- Endpoint schema for relay endpoints has only QUIC fields (UDP), no HTTPS allocation API fields:
  - `spec/02-identity-trust/identity-document-schema.md` — “Endpoint Object (Normative…)” (approx ~L170–L240)
- Transport interface does not provide an allocation URL/port, only `RelayServer.address` + `RelayServer.port` (implicitly UDP/QUIC):
  - `spec/01-transport-connectivity/interfaces.md` — `interface RelayServer` (approx ~L250–L290)
- The “accept ANY certificate” rule is explicitly scoped to QUIC ALPN `post-urbit/1`, but HTTPS allocation is not covered:
  - `spec/00-shared/layer-integration.md` — “QUIC TLS Certificate Policy” (approx ~L520–L620)
  - `spec/06-rfcs/RFC-0002-transport.md` — §4.3 / §10.1 (approx ~L120–L190; ~L820–L870)

### Required fixes (normative)
You need all of the following specified:

1. **Allocation URL derivation (normative)**: define exactly how to derive the HTTPS URL from a relay endpoint:
   - e.g., `allocation_url = https://{relay.host}:{allocation_port}/allocate` with a default `allocation_port=443` (or explicitly reusing `relay.port` over TCP if intended), plus canonicalization rules.
2. **TLS authentication policy for relay HTTPS allocation (normative)**:
   - MUST use WebPKI validation (normal HTTPS rules), **OR**
   - MUST use an explicit relay identity pinning / signature scheme that cryptographically authenticates the allocation response and binds it to `relay_id` (and then you can allow self-signed TLS if you want).
3. **Token anti-hijack guidance (normative)**:
   - if you keep “first UDP packet binds”, then the HTTPS allocation channel MUST be authenticated to prevent MITM token theft.

Without this, two compliant implementations cannot reliably allocate relays or do so securely.

## 2) SyncOperation wire encoding is contradictory/ambiguous (bstr vs structured map)
**Severity: HIGH** (likely interop failure)

### Problem
`SyncOperation.operation` is described inconsistently:

- In the **sync protocol wire schema**, `operation` is a **CBOR bstr** containing deterministically-encoded CRDT-op bytes, and operation IDs/signatures depend on the **exact byte string** (“MUST NOT decode and re-encode”).
- In the **interfaces**, `operation` is modeled as a structured `CRDTOperation` union, which suggests direct CBOR encoding of that map into the enclosing `SyncOperation` structure (not as an embedded bstr).

If an implementation follows the TypeScript interfaces literally and encodes `operation` as a nested CBOR map rather than a CBOR byte string containing that map, it will compute different operation IDs and signatures and will not interoperate.

### Spec citations
- Wire schema says `operation` is **bstr**:
  - `spec/03-messaging-sync/sync-protocol.md` — “CBOR Schemas for Sync Messages: SyncOperation = { … operation: bstr … }” (approx ~L190–L260)
  - `spec/03-messaging-sync/sync-protocol.md` — “operation_bytes definition… EXACT byte string carried in the SyncOperation.operation CBOR bstr field” (approx ~L330–L380)
- Interfaces model `operation` as a structured union:
  - `spec/03-messaging-sync/interfaces.md` — `interface SyncOperation { … operation: CRDTOperation; … }` (approx ~L250–L330)

### Required fixes (normative)
- Make the wire representation unambiguous across all docs:
  - Either change the interface to reflect wire reality (e.g., `operationBytes: Uint8Array` for wire-level structs), or
  - Add an explicit normative note in `interfaces.md` that **wire encoding uses `bstr(operation_bytes)`**, and `CRDTOperation` is an app/internal representation that must be deterministically CBOR-encoded into those bytes.
- Ensure the “MUST NOT decode/re-encode” rule is repeated in the interface document, since that is the interop-critical constraint.

## 3) Handshake error code string mismatch: `IID_MISMATCH` vs `IDENTITY_MISMATCH`
**Severity: HIGH** (cross-doc contradiction; can break conformance/error handling expectations)

### Problem
The normative “IID binding requirement” in the handshake guidance uses an error code name that doesn’t match the rest of the transport error vocabulary:

- `peer-handshake.md` says abort with `IID_MISMATCH`
- Elsewhere (including RFC-0002 / QUIC app codes) the error is `IDENTITY_MISMATCH`

If implementations treat the JSON error `code` value as normative (and specs usually do once spelled out), this creates divergence.

### Spec citations
- Uses `IID_MISMATCH`:
  - `spec/01-transport-connectivity/peer-handshake.md` — “IID Binding Requirement (Normative)” (approx ~L170–L210)
- Transport-layer naming uses `IDENTITY_MISMATCH`:
  - `spec/01-transport-connectivity/quic-integration.md` — Application error codes table (`0x100 IDENTITY_MISMATCH`) (approx ~L150–L220)
  - `spec/06-rfcs/RFC-0002-transport.md` — §9.2 registry (`0x100 IDENTITY_MISMATCH`) (approx ~L760–L810)
  - `spec/01-transport-connectivity/peer-handshake.md` — error table also lists `IDENTITY_MISMATCH` (approx ~L300–L340)

### Required fixes
- Choose one canonical string code for the handshake JSON error payload and use it everywhere.
- If the JSON `error.code` field is not intended to be strict, explicitly say so (“code is informational; implementations MUST NOT branch on it”), but then provide a canonical list anyway for consistency.

## 4) Base64 “no padding” is inconsistent in transport handshake field definitions
**Severity: HIGH** (wire-format ambiguity → interop failure risk)

### Problem
Across the spec, “Base64 standard, no padding” is a global convention, but RFC-0002’s handshake fields are not uniformly explicit about padding for *all* base64 fields (especially signature fields). Some sections specify no padding for nonces/tls_binding, but signatures are sometimes described as “base64 standard” without reiterating “no padding”.

Given strict “no padding” requirements elsewhere (e.g., package signing and many other sections), this inconsistency can lead to one implementation accepting padded base64 while another rejects it.

### Spec citations
- “Keys/signatures: Base64 standard (no padding)” global rule:
  - `spec/00-shared/layer-integration.md` — “Encoding” table (approx ~L740–L820)
- Handshake fields explicitly say no padding for some fields but not consistently for all:
  - `spec/06-rfcs/RFC-0002-transport.md` — §5.5/§5.6 definitions (`client_nonce`, `tls_binding` say “no padding”; signature fields are less explicit) (approx ~L210–L330)

### Required fixes
- In RFC-0002, add a **single normative encoding subsection**: “All Base64 fields in handshake messages MUST use RFC4648 standard alphabet with NO padding (‘=’ MUST be rejected).”
- Apply that uniformly to:
  - `client_nonce`, `server_nonce`, `tls_binding`
  - `challenge_signature`, `device_signature`
  - relay allocation `signature`, rebind `signature`, etc.

## 5) Relay allocation HTTP error handling is underspecified
**Severity: HIGH** (interop failure risk between relay clients/servers)

### Problem
The UDP PURL error packet format is specified, but the **HTTPS allocation** path lacks a normative error model:
- required HTTP status codes
- required response body schema for failures
- retry semantics (e.g., rate-limit backoff)
- nonce replay failure response vs signature failure response, etc.

Without this, clients will vary widely in how they interpret failures and backoff/retry, which is a practical interop problem across relay providers.

### Spec citations
- Allocation over HTTPS specified, but no HTTP error/status model:
  - `spec/06-rfcs/RFC-0002-transport.md` — §7.8–§7.10 (approx ~L430–L590)
  - `spec/01-transport-connectivity/relay-protocol.md` — Allocation sections (approx ~L40–L160)
- UDP error packet exists but is unrelated to allocation request failures:
  - `spec/06-rfcs/RFC-0002-transport.md` — §7.12 “Relay Errors” (approx ~L650–L710)

### Required fixes
- Specify for `/allocate` at minimum:
  - status codes: 200/201 success, 400/401/403/429/5xx failure
  - a canonical JSON error response shape
  - required headers for rate limiting (`Retry-After`) if used
  - whether allocation responses are idempotent given same `(iid, nonce)` within replay window

## 6) PURL ERROR packet “Destination IID = 0” is implied but not explicit
**Severity: MEDIUM** (ambiguity; workable but risks divergent behavior)

### Problem
RFC-0002 says “Destination IID field is zero (20 null bytes) for relay control packets” but does not explicitly restate that for ERROR packets in §7.12, even though ERROR is a control-plane packet. Some implementations may (incorrectly) populate destination IID with the failing destination.

### Spec citations
- Control packets use Destination IID = 0:
  - `spec/06-rfcs/RFC-0002-transport.md` — §7.6 “Control Packets … Destination IID field is zero … for control packets” (approx ~L560–L640)
- ERROR payload format defined without stating destination IID rule:
  - `spec/06-rfcs/RFC-0002-transport.md` — §7.12 (approx ~L650–L710)

### Suggested fix
- Add one sentence in §7.12: “For ERROR packets, Destination IID MUST be 20 zero bytes.”

## 7) MailboxService interface in integration doc does not match RFC-0003 HTTP shapes (pagination, envelope encoding)
**Severity: MEDIUM** (doc mismatch; implementable if you ignore the interface)

### Problem
`MailboxService` in `layer-integration.md` presents a simplified interface (no pagination, envelope as bytes), while RFC-0003 specifies concrete HTTP responses including pagination (`cursor`, `has_more`) and Base64-encoded envelope in JSON.

Even though `layer-integration.md` says RFC-0003 is authoritative, the presence of a concrete interface risks implementers building to it and drifting from the actual HTTP wire format.

### Spec citations
- Simplified interface:
  - `spec/00-shared/layer-integration.md` — “MailboxService Interface” (approx ~L610–L720)
- Authoritative HTTP:
  - `spec/06-rfcs/RFC-0003-messaging.md` — §7.4.2 Retrieve / §7.4.3 Delete (approx ~L520–L640)

### Suggested fix
- Either:
  - Update `MailboxService` to reflect RFC-0003 features (cursor/pagination, Base64 envelope, etc.), or
  - Add a prominent note: “This interface is an internal abstraction; wire format is RFC-0003; implementations MUST map accordingly,” and include the mapping.

## 8) Mailbox token lifetime is not fully bounded/required
**Severity: MEDIUM** (security exposure; doesn’t block interop but affects deployment security)

### Problem
RFC-0003 includes `expires_at` and examples that imply 24h, but does not clearly require:
- maximum lifetime accepted by mailbox servers
- clock-skew policy for token expiry validation
- whether servers MUST reject tokens with very-long expiry

Without bounds, some clients might mint week-long tokens; some servers might accept them, increasing replay window and metadata exposure if tokens leak.

### Spec citations
- Token fields and signature scheme:
  - `spec/06-rfcs/RFC-0003-messaging.md` — §7.3 Authentication (approx ~L330–L520)

### Suggested fix
- Add normative constraints such as:
  - “Mailbox servers MUST reject tokens with `expires_at` more than X hours in the future” (and define skew tolerance).
  - “Clients SHOULD use max lifetime of Y hours.”

## 9) PUDS (STUN-like) discovery protocol: server behavior + retries + error handling are underspecified
**Severity: MEDIUM** (workable but inconsistent implementations likely)

### Problem
The PUDS wire format is defined, but not:
- server port discovery / default port conventions
- retransmission rules (UDP loss)
- response validation rules (what to do on wrong transaction ID)
- rate limiting guidance for reflection/amplification (briefly mentioned, but not normative)
- explicit error responses (or explicit statement “no errors; clients timeout”)

### Spec citations
- `spec/01-transport-connectivity/nat-traversal.md` — “Discovery Protocol (STUN-like)” (approx ~L20–L120)

### Suggested fix
- Add a normative subsection:
  - client retry schedule (e.g., 3 tries at 250/500/1000ms)
  - ignore responses with unknown transaction IDs
  - servers MUST be stateless echo, MUST rate limit per source IP, etc.

## 10) DHT `dhtGet` completeness requirement may be unrealistically strict without fallback semantics
**Severity: MEDIUM** (can cause “false noncompliance” and inconsistent behavior in real networks)

### Problem
`layer-integration.md` requires `dhtGet(key)` to query at least k=20 closest peers **or until a 2-second timeout**. In real-world DHT routing and NAT conditions, this may not be achievable reliably, and different libraries may not expose such control.

This is not a pure “style” issue: strict requirements here can produce interoperability claims disputes and inconsistent fetch behavior across implementations.

### Spec citations
- `spec/00-shared/layer-integration.md` — “DHT Query Completeness: dhtGet(key) MUST query at least k=20 closest peers (or until a 2-second timeout…)” (approx ~L170–L230)

### Suggested fix
- Rephrase as:
  - “Implementations MUST attempt to query up to k closest peers, subject to routing table availability and a timeout of at least 2 seconds” (or similar),
  - and define required minimum behavior when fewer peers are reachable.

## 11) PURL/relay path MTU: guidance exists but no normative fallback behavior
**Severity: MEDIUM** (availability risk; interop usually OK but deployments fail on some IPv6 paths)

### Problem
RFC-0002 correctly notes that 1244-byte relay datagrams can exceed the IPv6 minimum MTU safe payload and suggests PMTUD and “reduce inner payload if MTU issues detected,” but does not specify:
- what reduced size to use
- how to detect failure (loss threshold)
- whether endpoints should advertise a relay-safe max payload

### Spec citations
- `spec/06-rfcs/RFC-0002-transport.md` — §7.4 “MTU Considerations / PMTUD guidance” (approx ~L360–L430)
- Also reflected in constants:
  - `spec/01-transport-connectivity/interfaces.md` — `RELAY_PACKET_MAX_SIZE: 1244` comment (approx ~L340–L390)

### Suggested fix
- Add a normative fallback “relay_inner_payload_max_ipv6 = 1188” (or similar) and a simple detection heuristic (e.g., if no PONG within N seconds, reduce payload).
