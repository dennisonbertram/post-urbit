Below are the issues I found during a spec-level protocol review of the Post‑Urbit repository. Line numbers are **relative to each individual file** as rendered in this Repomix bundle.

---

## 1) Internal contradictions between documents

### C1 — Mailbox “MUST NOT selectively block” contradicts explicit rate limiting / validation requirements  
**Severity:** HIGH  
**Why it matters:** Implementers and mailbox operators will diverge on what behavior is allowed vs prohibited (policy + interop at the HTTP layer).  
**Where:**
- `spec/00-shared/layer-integration.md` **Mailbox Protocol → Trust Model**: says mailbox **MUST NOT** “selectively block messages” while also stating mailbox **MAY** rate limit / impose size limits. (Approx **L520–L545**)
- `spec/00-shared/layer-integration.md` **Mailbox Trust Model bullets** (same section) conflicts with validation expectations. (Approx **L540–L555**)  
- `spec/06-rfcs/RFC-0003-messaging.md` **§7.4.1 Store Message**: mailbox **MUST** enforce token validity and `token.iid == envelope.sender_iid` and other checks; these are, in practice, selective rejection. (Approx **L430–L520**)

**Fix:** Reword the prohibition to be precise, e.g. “Mailbox MUST NOT decrypt or modify envelopes, and MUST NOT selectively block based on *message content* (it may enforce auth, quotas, size, TTL, and rate limits).”

---

### C2 — “Connection resumption” terminology conflicts across transport docs (QUIC resumption vs handshake resumption)  
**Severity:** MEDIUM  
**Why it matters:** Implementers may disable QUIC session resumption entirely (hurting performance) or, conversely, incorrectly attempt “abbreviated handshake” behavior that v1 forbids.  
**Where:**
- `spec/01-transport-connectivity/peer-handshake.md` **Connection Resumption [OUT OF SCOPE FOR V1]**: “implementations MUST NOT use connection resumption” (ambiguous whether this includes QUIC TLS resumption). (Approx **L200–L235**)
- `spec/01-transport-connectivity/quic-integration.md` **0‑RTT Resumption**: allows QUIC resumption but forbids Post‑Urbit protocol bytes in 0‑RTT. (Approx **L90–L105**)  
- `spec/06-rfcs/RFC-0002-transport.md` **§8.3 0‑RTT Resumption** + **§8.4 Abbreviated Handshake**: distinguishes QUIC resumption from application/handshake resumption, and only forbids Post‑Urbit bytes in early data + forbids abbreviated handshake. (Approx **L470–L540**)

**Fix:** In `peer-handshake.md`, rename the section to “Abbreviated Handshake Resumption (OUT OF SCOPE FOR V1)” and explicitly state QUIC/TLS session resumption is allowed but early-data Post‑Urbit bytes are forbidden (matching RFC‑0002 §8.3/§8.4).

---

### C3 — PUSE plaintext size “derived limits” disagree across docs  
**Severity:** LOW (docs/UX), can become MEDIUM if implementations hard-code the smaller limits and reject valid messages  
**Where:**
- `spec/04-app-runtime/api-surface.md` **Messaging.send → “Derived Plaintext Limits”** gives plaintext maxima that are ~20 bytes smaller than RFC‑0003’s computed maxima. (Approx **L120–L145**)
- `spec/06-rfcs/RFC-0003-messaging.md` **§3.2 Size constraints → Derived Maximum Plaintext Size** provides the correct formula and table. (Approx **L85–L135**)

**Fix:** Align `api-surface.md` to RFC‑0003’s formula/table (or remove the derived numbers and reference RFC‑0003).

---

### C4 — App Host API method status vs method tables are internally inconsistent (reserved vs “documented methods”)  
**Severity:** MEDIUM  
**Why it matters:** App developers and runtime implementers may implement/assume different method availability, producing app portability failures.  
**Where:**
- `spec/04-app-runtime/api-surface.md` says **reserved methods are not specified** and lists `messaging.unsubscribe`, `messaging.list_groups`, etc as reserved. (Approx **L25–L35**)  
- Later in the same file, the **“Messaging API → Methods”** table still lists `messaging.unsubscribe` and `messaging.list_groups` as if they were part of the surface. (Approx **L95–L120**)  
- `spec/04-app-runtime/abi.md` method registry also marks these as reserved and defines reserved-method behavior (`NOT_IMPLEMENTED`). (Approx **L300–L345**)

**Fix:** Either (a) remove reserved methods from the per‑API “Methods” tables, or (b) annotate them explicitly as “reserved (returns NOT_IMPLEMENTED in v1)” in those tables.

## 2) Missing normative requirements (interop-impacting)

### M1 — No single canonical *string* representation for 32-byte DocumentId / OperationId in APIs  
**Severity:** HIGH  
**Why it matters:** Cross-implementation app portability and cross-node tooling can break if different nodes choose different display encodings for the same on-wire 32-byte IDs.  
**Where:**
- `spec/00-shared/layer-integration.md` **Encoding** table says DocumentId display is “64-char hex or UUID string (application-dependent)”. (Approx **L735–L770**)  
- `spec/03-messaging-sync/sync-protocol.md` defines DocumentId as **32 bytes on wire**, and separately mentions display forms are application-dependent. (Approx **L20–L60**)  
- `spec/03-messaging-sync/interfaces.md` similarly allows UUID string or 64-hex for `DocumentId` and hex for `OperationId`, but does not normatively define the conversion rule for “when to use which” (beyond examples). (Approx **L35–L75**)

**Fix (normative):** Standardize a canonical display mapping, e.g.:
- If `document_id[16:32] == 0x00…00`, render as RFC4122 UUID string of the first 16 bytes.
- Else render as 64-char lowercase hex of all 32 bytes.
Similarly define OperationId as 64-char lowercase hex always.

---

### M2 — Unknown JSON message handling on Control/Identity streams is not normatively defined  
**Severity:** HIGH  
**Why it matters:** Some implementations will ignore unknown message `type`s (forward compatibility), others will close connection/stream; this can cause avoidable disconnects and upgrade pain.  
**Where:**
- `spec/06-rfcs/RFC-0002-transport.md` defines framing and says JSON messages have a `type` field, but does not specify behavior for unknown `type` values on streams 0x01/0x02 (outside the resumption reservation case). (Approx **L300–L370**)  
- `spec/00-shared/layer-integration.md` defines identity stream message types (`identity_update`, etc.) but does not specify unknown-type behavior. (Approx **L410–L475**)  

**Fix:** Add a normative rule, e.g.:
- Control stream (0x01): unknown `type` **MUST** cause connection close with `HANDSHAKE_FAILED`/`PROTOCOL_VIOLATION` during handshake; after handshake, unknown control messages **SHOULD** be ignored (or vice versa).
- Identity stream (0x02): unknown `type` **MUST** be ignored (recommended for forward compatibility) unless it violates framing/size.

---

### M3 — Mailbox token lifetime / skew constraints are not normatively pinned  
**Severity:** MEDIUM  
**Why it matters:** Token acceptance windows affect usability and replay risk; inconsistent policies cause intermittent 401/403 across different mailbox servers.  
**Where:**
- `spec/06-rfcs/RFC-0003-messaging.md` defines `expires_at` and gives an example “now + 24h”, but does not specify max/min TTL or skew tolerance as MUST/SHOULD at the protocol level. (Approx **L300–L430**)

**Fix:** Add explicit requirements:
- Server MUST reject tokens where `expires_at` is in the past.
- Server MUST reject tokens where `expires_at` is more than (e.g.) 7 days in the future.
- Server MUST allow ±5 min clock skew (or explicitly not).

---

## 3) Ambiguous / under-specified wire formats

### W1 — PUDS (STUN-like) discovery protocol has no error response semantics and weak validation guidance  
**Severity:** MEDIUM  
**Why it matters:** Implementations will differ in retry/timeout/backoff and validation strictness; discovery interop can be flaky.  
**Where:**
- `spec/01-transport-connectivity/nat-traversal.md` defines PUDS request/response binary formats, but does not specify:
  - required response behavior when magic/version mismatch
  - whether servers should rate limit and how clients detect truncation
  - client timeout/retry parameters
  (Approx **L25–L90**, **L95–L135**)

**Fix:** Add normative client/server behavior: validation rules, timeouts, retry schedule, and whether malformed requests get no response vs explicit error.

---

### W2 — Test vectors for PUSE use non-JSON plaintext without explicitly stating “plaintext schema validation is out-of-scope for this vector”  
**Severity:** MEDIUM (developer confusion; can cause false “non-conformant” claims)  
**Where:**
- `spec/00-shared/test-vectors.md` **Test Vector 10 / 11**: plaintext is literal UTF‑8 `"hello"` / `"hello again"` (not a JSON object with `type/timestamp/sequence/content` as required by RFC‑0003 §8.1). (Approx **L520–L640**, **L650–L770**)  
- `spec/06-rfcs/RFC-0003-messaging.md` **§8.1 Plaintext Format** requires a JSON object schema. (Approx **L560–L610**)

**Fix:** In test vectors, add a normative note: “These vectors validate envelope framing/crypto/signature only; payload schema validation is not exercised here.” Or update the vectors to encrypt valid JSON message objects.

## 4) Security vulnerabilities / security-relevant gaps

### S1 — DHT spam/DoS mitigations are not normatively specified despite mandatory signature verification  
**Severity:** MEDIUM  
**Why it matters:** “Verify before store” prevents unauthorized overwrites but does not prevent high-volume garbage identities/records; without rate limiting/quotas, DHT nodes are DoS targets.  
**Where:**
- `spec/00-shared/layer-integration.md` DHT requirements: nodes MUST verify signatures before storing, but there is no normative rate limiting / quota / resource accounting for PUT_VALUE floods. (Approx **L110–L210**, **L350–L420**)  

**Fix:** Add at least SHOULD-level operational requirements (per-IP/per-peer rate limits, per-prefix quotas, max values per key, storage caps, and eviction strategy).

---

### S2 — Mailbox “MUST NOT selectively block” wording (see C1) can be interpreted to forbid necessary anti-abuse controls  
**Severity:** HIGH  
**Where:** same as C1.

**Fix:** clarify “content-based” vs “policy/abuse” blocking.

## 5) Unspecified error handling (behavioral interop risks)

### E1 — Messaging-layer error codes exist but transport signaling behavior is not defined (drop vs stream reset vs connection close)  
**Severity:** MEDIUM  
**Why it matters:** Different receivers may close connections on malformed envelopes while others drop-and-continue; this can cause persistent disconnect loops between implementations.  
**Where:**
- `spec/06-rfcs/RFC-0003-messaging.md` defines messaging error codes (0x301+), but does not normatively specify how these map onto QUIC actions (RESET_STREAM vs STOP_SENDING vs CONNECTION_CLOSE vs silent drop). (Approx **L690–L760**)  
- `spec/06-rfcs/RFC-0002-transport.md` defines transport-level application error codes (0x100–0x1FF) and stream-type errors, but does not define rules for application payload parse failures on stream 0x03. (Approx **L610–L660**, **L300–L420**)

**Fix:** Add a simple normative policy, e.g.:
- Invalid PUSE envelope: receiver MUST drop the frame and MAY reset that message stream with messaging error code; MUST NOT close the whole connection unless errors exceed a rate threshold.
- Malformed framing (length over limit): MUST reset stream and MAY close connection with `MESSAGE_TOO_LARGE` / `PROTOCOL_VIOLATION`.

---

### E2 — DHT validation “reject” behavior is not defined at the wire/API boundary  
**Severity:** LOW to MEDIUM (depending on whether implementers expose “put errors” to callers)  
**Where:**
- `spec/00-shared/layer-integration.md` says DHT nodes MUST reject invalid records but doesn’t specify how clients observe rejection (libp2p kad often doesn’t give strong write acknowledgements). (Approx **L250–L340**)

**Fix:** Specify observable semantics for `dhtPut`: best-effort vs quorum-ack; what errors are returned, and how callers should retry/backoff.

---

# Verdict

No issues rise to the level of **BLOCKING** (i.e., nothing I found prevents an implementation from being built in a reasonably interoperable way assuming implementers treat the RFCs as authoritative where noted). There are several **HIGH** and **MEDIUM** items that should be cleaned up to reduce interop risk and ambiguity, especially around mailbox policy wording, unknown-message handling, and DocumentId string canonicalization.
