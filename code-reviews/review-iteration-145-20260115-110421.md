### [BLOCKING] PU-DHT-PEERID-01 — libp2p PeerID derivation is internally inconsistent and likely incorrect
**Category:** Ambiguous wire format / Internal contradiction  
**Impact:** Prevents interoperable DHT overlay membership across implementations (Go/Rust/JS libp2p); bootstrap peer IDs and node IDs may not match.

**Location**
- `spec/00-shared/layer-integration.md` (approx. L140–L230), section **“DHT Node Identity”** / **“libp2p PeerID Derivation (Normative)”**  
  Anchor quotes:
  - “**Encode as libp2p PeerID** … *Multicodec-encode the public key: 0xed 0x01 …*”
  - “**Full PeerID bytes:** `0x00 0x22 0xed 0x01 <32-byte-pubkey>`”
- `spec/00-shared/layer-integration.md` (approx. L290–L330), section **“Bootstrap Encoding Rules (Normative)”**  
  Anchor quote: “**Base58btc-encoded PeerID multihash (36 bytes → starts with "12D3KooW" for Ed25519)**”

**Problem**
The spec simultaneously claims:
1) “MUST use standard libp2p PeerID derivation” (and links to libp2p peer-ids spec), and  
2) Defines a concrete byte layout that uses `multicodec(ed25519-pub)` (`0xed 0x01`) wrapped in an identity multihash.

In most libp2p stacks, “PeerID from public key” has historically been defined as an **identity multihash of a protobuf-marshaled public key**, not `multicodec(pubkey)`; even if newer variants exist, the spec must match the referenced normative libp2p spec precisely. As written, two independent implementers following different interpretations (actual libp2p implementation vs. this document’s byte recipe) will produce different PeerIDs, breaking:
- bootstrap connectivity
- DHT node ID computation (since it hashes PeerID bytes)
- routing table interoperability

**Required fix**
- In `spec/00-shared/layer-integration.md`, replace the bespoke byte recipe with **one authoritative derivation** that matches the linked libp2p peer-ids spec, and include:
  - exact bytes of the marshaled public key input (if protobuf-based) **or**
  - explicit citation + test vectors if multicodec-based is intended
- Add **a normative test vector**: given a 32-byte Ed25519 pubkey, specify the exact PeerID bytes and base58btc string.

### [HIGH] PU-BOOTSTRAP-TRUST-01 — Bootstrap list retrieval/authentication is not specified (eclipse/Sybil risk)
**Category:** Security vulnerability / Missing normative requirements  
**Impact:** Implementations may accept attacker-controlled bootstrap peers → DHT eclipse attack → identity discovery manipulation.

**Location**
- `spec/00-shared/layer-integration.md` (approx. L360–L470), section **“Bootstrap Requirements”**  
  Anchor quotes:
  - “**Well-known location** `https://bootstrap.post-urbit.net/nodes.json`”
  - “**DNS fallback** `_dnsaddr.bootstrap.post-urbit.net` TXT records”

**Problem**
The spec defines well-known bootstrap distribution points, but does not define:
- whether `nodes.json` is signed, by whom, using what key, and how clients pin/verify it
- whether DNS TXT answers must be DNSSEC-validated (dnsaddr records are otherwise trivially spoofable in many environments)
- client behavior on conflicting bootstrap sources (HTTPS vs DNS vs hardcoded)

**Suggested fix**
- Define a **signed bootstrap manifest** format (similar to repository/update manifests in `spec/05-ux-packaging/app-distribution.md`) with:
  - operator IID
  - timestamp
  - signature over JCS-canonical JSON
  - key pinning guidance (TOFU vs pinned vs shipped roots)
- Add explicit rules for DNSSEC-required vs best-effort.

### [HIGH] PU-IDSTREAM-ERRCODES-01 — `identity_ack.error_code` exists but no registry is defined
**Category:** Missing normative requirements / Unspecified error handling  
**Impact:** Interop failures in error recovery and debugging; implementations will invent incompatible codes.

**Location**
- `spec/00-shared/layer-integration.md` (approx. L560–L640), section **“Identity Message JSON Schemas (Normative)”**  
  Anchor quote:
  - `error_code?: number;  // Present if accepted=false`

- `spec/00-shared/layer-integration.md` (approx. L930–L980), section **“Error Code Registry”**  
  Anchor quote:
  - “0x200-0x2FF | Identity | INVALID_DOCUMENT, SIGNATURE_FAILED”

**Problem**
The spec introduces an error code field on the wire (`identity_ack.error_code`) but does not define:
- the concrete numeric codes and meanings
- whether they are QUIC application error codes, identity-layer error codes, or independent ack-specific codes
- whether senders should retry, refresh identity, or escalate

**Suggested fix**
- Define a small registry for identity stream ACK errors (e.g., reuse 0x200–0x2FF) and include required receiver behavior:
  - `0x201 INVALID_IDOC`
  - `0x202 SEQUENCE_REGRESSION`
  - `0x203 TOFU_VIOLATION`
  - etc.

### [HIGH] PU-MSG-ERRMAP-01 — RFC-0003 defines numeric error codes but not how they are surfaced on QUIC/streams
**Category:** Unspecified error handling  
**Impact:** Divergent behavior: some implementations close the QUIC connection, some close only a stream, some silently drop; leads to retry storms or dead connections.

**Location**
- `spec/06-rfcs/RFC-0003-messaging.md` (approx. L760–L860), section **“9. Error Handling”**  
  Anchor quote:
  - “Envelope Errors … Code 0x301 …”
- `spec/06-rfcs/RFC-0002-transport.md` (approx. L650–L740), section **“9. Error Handling”**

**Problem**
RFC-0003 assigns error codes (0x301… etc) but does not normatively specify:
- when to send a QUIC CONNECTION_CLOSE with those codes vs drop a message
- whether errors are signaled back to sender at all (and how)
- behavior on repeated malformed envelopes (rate limit? ban? close?)

**Suggested fix**
Add RFC-0003 normative rules such as:
- malformed PUSE on stream 0x03: **MUST close the message stream** (STOP_SENDING/RESET_STREAM) with messaging-layer code, but **MUST NOT** tear down the entire QUIC connection unless repeated N times in T seconds
- for signature failures: drop envelope + increment abuse counter; optionally send receipt/error message type (if defined)

### [MEDIUM] PU-TRANSPORT-RESUME-01 — “resumption” guidance contradicts across transport docs
**Category:** Internal contradiction (normative language conflict)  
**Impact:** Confusing implementers; may disable QUIC resumption unnecessarily.

**Location**
- `spec/01-transport-connectivity/peer-handshake.md` (approx. L250–L320), section **“Connection Resumption [OUT OF SCOPE FOR V1]”**  
  Anchor quote: “**For v1, implementations MUST NOT use connection resumption.**”
- `spec/01-transport-connectivity/quic-integration.md` (approx. L120–L150), section **“0-RTT Resumption”**  
  Anchor quote: “**QUIC 0-RTT MAY be used for transport-level connection resumption**…”

**Problem**
One document forbids “connection resumption” broadly, while another permits QUIC-level resumption but forbids Post-Urbit bytes in 0-RTT. RFC-0002 clarifies the latter. `peer-handshake.md` should align to RFC-0002 and clearly distinguish:
- QUIC/TLS session resumption (allowed)
- Post-Urbit abbreviated handshake / application 0-RTT (forbidden)

**Suggested fix**
Edit `peer-handshake.md` to: “MUST NOT use *abbreviated Post-Urbit handshake*; QUIC TLS resumption MAY be used but MUST NOT carry Post-Urbit bytes in 0-RTT.”

### [MEDIUM] PU-NAT-PUDS-01 — PUDS discovery protocol lacks normative error behavior and amplification controls
**Category:** Missing normative requirements / Unspecified error handling  
**Impact:** Interop ambiguity for discovery servers; security risk for reflection/amplification.

**Location**
- `spec/01-transport-connectivity/nat-traversal.md` (approx. L20–L95), section **“Discovery Protocol (STUN-like)”**  
  Anchor quote: packet diagrams for request/response.
- `spec/01-transport-connectivity/nat-traversal.md` (approx. L300–L340), section **“Security Considerations”**  
  Anchor quote: “Amplification attacks: Discovery servers should rate-limit responses”

**Problem**
The wire format is given, but server behavior is not:
- what response (if any) to send on invalid magic/version
- whether to ignore unknown versions vs respond with error
- minimum validation before responding (to limit spoofed-source reflection)
- rate limit requirements are only “should”, not MUST/SHOULD with parameters

**Suggested fix**
Add normative server behavior:
- invalid magic/version → silently drop
- max QPS per source IP
- optional cookie/nonce extension if needed later (version bump)

### [MEDIUM] PU-DHT-ERR-01 — DHT “reject” rules do not specify observable error signaling
**Category:** Unspecified error handling  
**Impact:** Harder to debug/operate; inconsistent behavior across DHT nodes.

**Location**
- `spec/00-shared/layer-integration.md` (approx. L250–L430), sections:
  - **“Record Validation Rules”**
  - **“DHT Record Format”**
  Anchor quotes:
  - “DHT nodes MUST reject records that fail validation (do not store, do not forward)”
  - Update authorization steps 1–6

**Problem**
For a concrete interoperability profile, you need to know whether a PUT failure:
- is signaled back to the PUT caller (and how, given libp2p kad’s message model)
- is silently ignored
- includes an error code (and where it’s encoded)

**Suggested fix**
Define at least:
- client-side behavior when PUT appears to succeed but record doesn’t propagate
- logging requirements and optional metrics counters
- if using libp2p kad: whether to rely on its native error semantics vs define an application-level acknowledgment scheme

### [MEDIUM] PU-MAILBOX-ROUTING-TEXT-01 — Minor contradictory phrasing about mailbox routing inputs
**Category:** Internal contradiction (documentation-level)  
**Impact:** Could mislead implementers, though RFC-0003 later clarifies.

**Location**
- `spec/00-shared/layer-integration.md` (approx. L820–L900), section **“Mailbox Protocol (Store-and-Forward)”**  
  Anchor quote: “The PUSE header contains sender/recipient IIDs for routing.”

**Problem**
For **group messages**, the PUSE recipient field is a **group_id**, not the inbox owner IID; mailbox routing is by URL path `POST /messages/{inbox_owner_iid}` (per RFC-0003 §7.4.1). The phrase “recipient IIDs for routing” is false in that case.

**Suggested fix**
Change to: “PUSE header contains sender IID and recipient *IID or group_id*; mailbox routing is keyed by inbox owner IID from the request path.”

### [LOW] PU-DOMSEP-LEN-01 — Domain separator byte-length table contains at least one likely miscount
**Category:** Cosmetic/style (but confusing)  
**Impact:** Confuses implementers who copy byte counts into tests.

**Location**
- `spec/00-shared/layer-integration.md` (approx. L900–L960), section **“Domain Separator Registry (Normative)”**  
  Anchor quote: `DHT protocol ID | "/post-urbit/kad/1.0.0" | 22`

**Problem**
`"/post-urbit/kad/1.0.0"` appears to be **21 bytes**, not 22. The *string itself* is what is normative; the count should match to prevent “false failures” in length-assertion tests.

**Suggested fix**
Recompute and correct the byte-length column everywhere, or explicitly label it “informative”.
