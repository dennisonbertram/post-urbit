### 1) Missing/weak “expected peer” binding in the **authoritative** handshake spec (wrong-peer acceptance risk)
**Severity:** HIGH  
**Category:** (1) Internal contradiction + (4) Security vulnerability + (2) Missing normative requirement

- **What’s wrong:** `peer-handshake.md` makes `expected_server_iid` effectively mandatory when you connect to a known IID, but **RFC-0002** only marks it **SHOULD** and does not make “known-IID connect MUST include it” a normative requirement. An implementation following the RFC strictly could omit it, enabling endpoint-hijack / wrong-peer acceptance (the attacker completes a valid handshake for *their* IID, and the victim accepts because no expected IID was pinned).
- **Where:**
  - Strong requirement in guidance doc:  
    - `spec/01-transport-connectivity/peer-handshake.md` **L150-L176** (“IID Binding Requirement (Normative): … client MUST include expected_server_iid … MUST abort …”)  
  - Weaker requirement in authoritative RFC:  
    - `spec/06-rfcs/RFC-0002-transport.md` **L205-L235** (§5.5 ClientHello table: `expected_server_iid` is **SHOULD**)  
    - `spec/06-rfcs/RFC-0002-transport.md` **L320-L360** (§5.11 verification: “If provided, verify it matches” but no MUST-to-provide rule)
- **Impact:** Security downgrade (accepting a valid handshake with the wrong identity) in common “connect by IID” flows; likely to be missed by implementers who treat RFC as sole authority.
- **Fix (normative):** In **RFC-0002**, add a requirement such as:  
  “When the initiating application has a specific target IID (e.g., `connect(peerIID)`), the client **MUST** include `expected_server_iid` and **MUST** fail the handshake if it differs.”

### 2) Relay allocation HTTPS **TLS validation** is normative in layer doc but absent in RFC-0002 (token theft / allocation hijack)
**Severity:** HIGH  
**Category:** (2) Missing normative requirement + (4) Security vulnerability + (1) Contradiction between “authoritative” documents

- **What’s wrong:** `relay-protocol.md` requires WebPKI validation for the HTTPS allocation endpoint (correctly), but **RFC-0002** (the authoritative transport RFC) does not state that requirement. A strict RFC implementation might accept self-signed / MITM’d HTTPS allocation responses, enabling allocation token theft and subsequent traffic hijacking via binding.
- **Where:**
  - TLS validation requirement present:  
    - `spec/01-transport-connectivity/relay-protocol.md` **L45-L78** (“HTTPS TLS Policy for Allocation (Normative) … MUST verify server cert … MUST reject self-signed …”)
  - Allocation protocol in RFC lacks TLS policy:  
    - `spec/06-rfcs/RFC-0002-transport.md` **L620-L710** (§7.8 Allocation Protocol: request/verification steps but no WebPKI/hostname validation requirements)
- **Impact:** Active network attacker can steal allocation token and race to bind allocation to attacker IP:port, intercepting inbound traffic (metadata and potentially enabling DoS / traffic correlation).
- **Fix (normative):** Add to **RFC-0002 §7.8** explicit requirements equivalent to the layer doc:
  - MUST perform WebPKI validation and hostname verification.
  - MUST reject self-signed certs.
  - Clarify that this policy is distinct from `post-urbit/1` QUIC “accept any cert” policy.

### 3) Contradictory/ambiguous PURL “Destination IID” length for relay control packets (“20 bytes or 0”)
**Severity:** HIGH  
**Category:** (1) Internal contradiction + (3) Ambiguous wire format

- **What’s wrong:** `relay-protocol.md` describes the PURL header field as “Destination IID … 20 bytes (or 0 for relay commands)”, which reads like the header length may vary. RFC-0002 defines the field as **always 20 bytes**, with **20 zero bytes** for control-plane packets.
- **Where:**
  - Ambiguous wording:  
    - `spec/01-transport-connectivity/relay-protocol.md` **L120-L150** (“Destination IID … 20 bytes (or 0 for relay commands)”)
  - Fixed-width requirement in RFC:  
    - `spec/06-rfcs/RFC-0002-transport.md` **L540-L590** (§7.6 Encapsulation Model: “Destination IID field is zero (20 null bytes) for control packets” and header format is fixed 44 bytes)
- **Impact:** Implementations that follow the non-RFC doc could build/parse variable-length headers → immediate interop failures with implementations following RFC-0002.
- **Fix:** Update `relay-protocol.md` to unambiguously match RFC:
  - “Destination IID (raw bytes) **20 bytes**; for control packets it MUST be **20×0x00**.”

### 4) Handshake failure behavior is underspecified (who sends `handshake_complete`, when to close, and what QUIC error code to use)
**Severity:** HIGH  
**Category:** (5) Unspecified error handling (with interop risk)

- **What’s wrong:** The handshake defines a `handshake_complete` message (server→client) and lists string error codes, and the transport defines QUIC application error codes. But the spec does not clearly require:
  - Whether the **server MUST send** `handshake_complete(success=false)` before closing on any failure.
  - What the **client does** when *it* rejects the server (send an error message? close immediately?).
  - Whether to close the **connection** or just the **stream**, and which **QUIC application error code** to use (e.g., 0x100/0x101) when terminating.
- **Where:**
  - HandshakeComplete schema but no close semantics:  
    - `spec/06-rfcs/RFC-0002-transport.md` **L285-L320** (§5.10 HandshakeComplete)  
    - `spec/06-rfcs/RFC-0002-transport.md` **L360-L420** (§5.12 Error Codes; §5.13 Timeouts)
  - Application error codes registry exists but not mapped to handshake termination actions:  
    - `spec/06-rfcs/RFC-0002-transport.md` **L900-L940** (§9.2 Application Error Codes)
- **Impact:** Interop failures and deadlocks: one side may wait for a final handshake message while the other just closes; inconsistent error codes complicate automated retry/backoff logic.
- **Fix (normative):**
  - Specify a deterministic failure procedure, e.g.:
    1) On server-side handshake failure, server MUST send `handshake_complete(success=false, error=...)`, then MUST close the QUIC connection with application error `HANDSHAKE_FAILED (0x101)` (or a more specific code if defined).  
    2) On client-side verification failure, client MUST close the QUIC connection with `IDENTITY_MISMATCH (0x100)` / `HANDSHAKE_FAILED (0x101)` as appropriate (and MUST NOT send further handshake frames).
  - Clarify stream-vs-connection closure rules.

### 5) Package signatures “MUST remain verifiable indefinitely” conflicts with signing-key history retention limits and non-versioned IDOC availability
**Severity:** HIGH  
**Category:** (1) Internal contradiction + (2) Missing normative mechanism

- **What’s wrong:** App distribution says package signatures are point-in-time assertions that **must remain verifiable indefinitely**, but identity documents limit signing key history retention to “10 entries or 2 years”. Additionally, the DHT model stores only “current” and “genesis” IDOCs (no full historical chain). Once a signing key drops out of `keys.signing.history`, an old package signature may become unverifiable without an external transparency log or archived IDOC history.
- **Where:**
  - “Must remain verifiable indefinitely” claim:  
    - `spec/05-ux-packaging/app-distribution.md` **L120-L155** (“Package signatures represent a point-in-time assertion that must remain verifiable indefinitely.”)
  - Signing key history retention limit:  
    - `spec/02-identity-trust/identity-document-schema.md` **L150-L190** (“Retention policy: Keep at most 10 previous signing keys or 2 years…”)
  - DHT storage model emphasizes current+genesis (no historical versions):  
    - `spec/00-shared/layer-integration.md` **L430-L520** (“Identity documents are stored under TWO DHT keys… current and genesis… updates replace previous…”)
- **Impact:** Users may be unable to verify/install archived packages (or repository history) after enough time/rotations, contradicting the stated security property.
- **Fix options (choose one, normatively):**
  1) **Relax/extend** signing history retention (e.g., “MUST retain signing keys used for package signing indefinitely” or much longer), **or**
  2) Specify a **verifiable historical-key mechanism**: e.g., append-only transparency log, or DHT storage of **key history records** keyed by `(iid, key_fingerprint)` with signatures, **or**
  3) Store **versioned IDOCs** (sequence-addressable) in the DHT so old keys can be verified against the chain.

### 6) Bootstrap node list integrity not specified (eclipse / routing-table poisoning risk)
**Severity:** MEDIUM  
**Category:** (4) Security vulnerability + (2) Missing normative requirement

- **What’s wrong:** The DHT bootstrap list is fetched from a well-known HTTPS URL and/or DNS TXT, but there is no mandatory signature/pinning scheme for that list itself. A compromised CA, DNS poisoning, or hosting compromise can redirect new nodes to attacker-controlled bootstrap peers, enabling eclipse attacks (especially relevant for TOFU first contact).
- **Where:**
  - `spec/00-shared/layer-integration.md` **L300-L380** (Bootstrap requirements; “Well-known location https://bootstrap.post-urbit.net/nodes.json”; DNS fallback)
- **Impact:** Weakens first-join security; increases risk of long-lived eclipse and identity resolution manipulation.
- **Fix (recommended):**
  - Define a signed bootstrap list format (e.g., JCS + Ed25519 signature under a pinned project key, or signature by a well-known IID whose genesis key is shipped/pinned).
  - Specify client behavior on signature failure (reject, or require explicit user override).

### 7) Relay ERROR payload framing constraints are incomplete (parsing ambiguity)
**Severity:** MEDIUM  
**Category:** (3) Ambiguous wire format + (5) Unspecified error handling

- **What’s wrong:** The ERROR payload structure is specified, but the relationship between:
  - PURL `Payload Length` (u16), and
  - ERROR payload’s internal `Message Length` (u16)
  
  is not made fully normative (e.g., MUST `payload_length == 1+4+2+msg_len`? what if mismatch?). Similar ambiguity exists for how receivers should react to malformed ERROR payloads.
- **Where:**
  - `spec/01-transport-connectivity/relay-protocol.md` **L210-L245** (ERROR Packet format)
  - `spec/06-rfcs/RFC-0002-transport.md` **L780-L820** (§7.12 Relay Errors: format given, but mismatch behavior not specified)
- **Impact:** Potential interop differences and parser differentials (some implementations accept truncated/extra bytes).
- **Fix:** Add explicit validation rules:
  - MUST reject ERROR packets where lengths are inconsistent.
  - MUST ignore/drop malformed ERROR packets (or respond with a specific action).

### 8) Behavior when sender identity document is unavailable during PUSE verification is underspecified
**Severity:** MEDIUM  
**Category:** (5) Unspecified error handling

- **What’s wrong:** PUSE parsing requires fetching sender IDOC prior to signature verification. The spec does not define what to do when:
  - sender IDOC cannot be resolved (DHT down, cache miss),
  - multiple conflicting IDOCs exist, or
  - IDOC is temporarily “pending recovery” state.
- **Where:**
  - `spec/06-rfcs/RFC-0003-messaging.md` **L150-L190** (§3.8 Parsing Order steps 7–8 require fetching identity doc)
  - Related caching policy guidance: `spec/02-identity-trust/caching-policy.md` **L85-L150** (offline operation policy), but not tied normatively to RFC-0003 delivery behavior.
- **Impact:** Implementations may diverge: drop messages, queue indefinitely, accept TOFU silently, or block UI—leading to user-visible inconsistencies and potentially exploitable behaviors.
- **Fix:** Add normative delivery handling guidance (at least for mailbox retrieval):
  - e.g., “If sender IDOC not available, client MUST retain envelope for up to X days and retry resolution; MUST NOT mark as verified; MAY show ‘unverified pending identity’ UI state.”

### 9) Cosmetic/consistency: v1 “resumption out of scope” vs exposed API knobs
**Severity:** LOW  
**Category:** (1) Minor internal inconsistency / clarity

- **What’s wrong:** Transport interfaces expose session ticket / 0-RTT knobs while multiple docs state v1 must not send Post-Urbit bytes in 0-RTT and handshake resumption is out-of-scope. This is workable, but could mislead implementers without reading the RFC sections carefully.
- **Where:**
  - Session ticket options/events in interface: `spec/01-transport-connectivity/interfaces.md` **L120-L210** (`sessionTicket`, `onSessionTicket`)
  - v1 prohibition: `spec/06-rfcs/RFC-0002-transport.md` **L840-L880** (§8.3 and §8.4)
- **Fix:** Mark these interface fields explicitly as “reserved for transport-layer TLS resumption only; MUST NOT carry Post-Urbit protocol bytes in early data; handshake resumption not supported in v1.”
