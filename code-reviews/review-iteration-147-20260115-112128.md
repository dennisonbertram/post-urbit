## Issues

### 1) PURL payload semantics contradict “QUIC payload” wording (COORDINATE is JSON, not QUIC)
**Severity: HIGH** (interop failure risk; implementations may feed COORDINATE payload into QUIC and fail coordination)

- **Where**
  - `spec/06-rfcs/RFC-0002-transport.md` (≈ L430-L520) — PURL format says: `│ Payload (QUIC UDP payload) │ <length> bytes`
  - `spec/01-transport-connectivity/nat-traversal.md` (≈ L70-L170) — defines **PURL COORDINATE** payload: `│ Payload (JSON, UTF-8) │ <length> bytes`
  - `spec/01-transport-connectivity/relay-protocol.md` (≈ L120-L210) — “Payload (QUIC packet)” in generic header diagram, but later references COORDINATE as JSON.

- **Why it’s a problem**
  - The PURL header is defined generically as carrying a QUIC UDP payload, but COORDINATE packets are defined as JSON blobs routed via relay forwarding.
  - A strict implementation following RFC-0002 §7.4 literally might decapsulate and pass the payload to QUIC for all forwarded packets, breaking hole-punch coordination.

- **What to fix**
  - In `RFC-0002` §7.4, change the payload field description to something like:
    - “Payload (opaque bytes; semantics depend on Packet Type)”
  - Add explicit normative handling:
    - DATA (0x01): payload MUST be a QUIC UDP payload and MUST be passed to QUIC after decapsulation.
    - COORDINATE (0x09): payload MUST be UTF-8 JSON (as per `nat-traversal.md`) and MUST NOT be passed to QUIC.
  - Ensure `relay-protocol.md` mirrors the same wording.

### 2) Hole-punch signatures do not bind the endpoint lists (tampering enables scanning/DoS)
**Severity: HIGH** (security vulnerability; signatures don’t protect the most sensitive fields)

- **Where**
  - `spec/01-transport-connectivity/nat-traversal.md` (≈ L170-L290) — signature construction:
    - Request signature input includes only `transaction_id`, `initiator`, `target`, `timestamp`
    - Does **not** include `initiator_endpoints`
  - Same for accept:
    - Accept signature input includes only `transaction_id`, `responder`, `timestamp`
    - Does **not** include `responder_endpoints`
  - Nearby snippet:  
    `signature_input = concat(DOMAIN, decode_base64url(transaction_id), encode_utf8(initiator), encode_utf8(target), encode_utf8(timestamp))`

- **Why it’s a problem**
  - Relay-assisted coordination requires signatures to prevent impersonation, but an untrusted relay (or on-path attacker) can modify the endpoint lists without invalidating signatures.
  - That can cause a victim node to send UDP probes to arbitrary third-party IP:port pairs (client-side scanning / reflected “poke” traffic), and can also derail connectivity attempts.

- **What to fix**
  - Bind endpoints into the signature input (normative), e.g.:
    - Add `JCS(canonical_endpoints_array)` (or a SHA-256 of canonical endpoints) into the signature transcript.
  - Define canonicalization rules for endpoint arrays:
    - Sorting (or explicit order preservation) and strict normalization for IPv6 formatting.
  - Apply the same rule to `hole_punch_offer` (if it reuses initiator signature) and `hole_punch_accept`.

### 3) Sync protocol has no interoperable wire-level error signaling / recovery behavior
**Severity: HIGH** (likely interop failures; implementations will diverge on “reject/close/ignore”)

- **Where**
  - `spec/03-messaging-sync/sync-protocol.md` (≈ L260-L520 and ≈ L760-L820) — defines message types `0x01..0x07`, and lists errors like `SIGNATURE_INVALID`, `PERMISSION_DENIED`, `DEPENDENCY_MISSING`, but **no message type** for errors and no required connection/stream actions.
  - `spec/00-shared/layer-integration.md` (≈ L560-L610) — reserves `0x400-0x4FF` for Sync error codes but does not define any concrete codes or when to use stream reset vs connection close.

- **Why it’s a problem**
  - When a peer receives an invalid CBOR payload, invalid op signature, or a permission violation, the spec says “Reject operation” but does not specify:
    - whether to send anything back (and in what format),
    - whether to close the sync stream, reset it, or close the connection,
    - how the sender should recover (retry? resync? drop peer?).
  - Different choices will cause deadlocks and divergent convergence behavior across implementations.

- **What to fix**
  - Add a normative `SYNC_ERROR` message type (e.g., `0x08`) **or** define mandatory QUIC application error-code behavior in the `0x400-0x4FF` range.
  - For each error class, specify:
    - **action** (ignore op / send error / close stream / close connection),
    - **retryability** and recommended backoff,
    - minimal error payload schema (CBOR map) including code + optional details (e.g., offending op id).
  - Clarify dependency recovery:
    - If `DEPENDENCY_MISSING`, MUST queue and MUST trigger a deterministic recovery action (e.g., send SYNC_REQUEST for the document_id, or a new “wanted_ids” request).

### 4) DHT “wire protocol” mandates libp2p Kad, but record-validation failure behavior is unspecified
**Severity: MEDIUM** (workable, but implementers will diverge; can affect robustness and debugging)

- **Where**
  - `spec/00-shared/layer-integration.md` (≈ L120-L260 and ≈ L300-L470) — “DHT Wire Protocol (Normative)” + “Record Validation Rules”
  - It normatively states DHT nodes MUST verify before storing and MUST reject invalid records, but does not specify how this maps onto libp2p Kademlia’s RPC responses/behavior.
  - Nearby snippet: `Reject records that fail validation (do not store, do not forward)`

- **Why it’s a problem**
  - In libp2p Kad, “PUT_VALUE” has defined request/response mechanics; whether validation failure is silent, returns an error response, penalizes the peer, etc., is not specified here.
  - Without a normative rule, interop at the “overlay behavior” level can vary (some nodes might gossip invalid records less, others might respond differently), which complicates network behavior and troubleshooting.

- **What to fix**
  - Define normative behavior on validation failure:
    - MUST NOT store; MUST NOT republish/forward.
    - SHOULD respond with a Kad error response / status (as supported by the implementation), and SHOULD apply peer scoring / rate limiting.
  - At minimum, specify required logging/metrics fields for invalid record events (record type, iid/did, failure reason).

### 5) PUDS (STUN-like) discovery protocol lacks explicit version/error handling and amplification guidance
**Severity: MEDIUM** (security/operational risk; interop is likely OK but servers will vary)

- **Where**
  - `spec/01-transport-connectivity/nat-traversal.md` (≈ L10-L80) — PUDS request/response format.
  - No normative behavior for:
    - unknown `Version`,
    - invalid `Transaction ID` length,
    - malformed packets,
    - response rate-limits / cookies.

- **Why it’s a problem**
  - Discovery servers are UDP and therefore easily abused (reflection/amplification).
  - Implementations may reply differently to malformed input; clients may mis-detect NAT types without consistent failure modes.

- **What to fix**
  - Add normative server rules:
    - Unknown version ⇒ MUST drop silently (or MUST reply with error code—pick one).
    - Malformed length ⇒ MUST drop.
    - Rate limit per source IP; optionally require a stateless cookie for repeat queries.
  - Add explicit max packet size and a recommendation to ensure response size ≤ request size (or close to it).

### 6) “Progress” document contradicts current normative MTU guidance (stale but confusing)
**Severity: LOW** (non-normative, but it is an internal contradiction and can mislead implementers)

- **Where**
  - `spec/progress.md` (≈ L230-L270) claims a past “fix”:
    - “Iteration 84: … relay path now limits inner payload to 1188 bytes (1232 total)”
  - Current normative text:
    - `spec/06-rfcs/RFC-0002-transport.md` §7.4 (≈ L460-L520) uses **1200 inner / 1244 outer**, and discusses IPv6 MTU risk.

- **Why it’s a problem**
  - A reader using `progress.md` as guidance might implement 1188 while RFC-0002 implements 1200; the repo itself contains contradictory statements (even if `progress.md` is not normative).

- **What to fix**
  - Update `spec/progress.md` to reflect the current decision (1200 inner payload) or clearly mark historical notes as superseded with a pointer to RFC-0002.

### 7) Sync CBOR schemas mix string-key maps (sync messages) and integer-key maps (CRDT ops) without an explicit “do not re-encode op bytes” enforcement point for relays/bridges
**Severity: MEDIUM** (subtle interop risk; already partially addressed but needs one more explicit “bridge” rule)

- **Where**
  - `spec/03-messaging-sync/sync-protocol.md`:
    - CRDT op bytes are CBOR with **integer keys** and must be deterministic.
    - Sync message CBOR schemas are **string-key** maps.
    - It does state: “Receivers MUST NOT decode and re-encode for hashing/signature… reject if not deterministically encoded.” (≈ L600-L700)
  - `spec/03-messaging-sync/secure-envelope.md` and `spec/06-rfcs/RFC-0003-messaging.md` introduce `sync_op` PUSE fallback with CBOR transported via Base64.

- **Why it’s a problem**
  - Any middleware layer that decodes CBOR and re-encodes (even deterministically) can break signature inputs if it does not preserve *exact* `operation_bytes` for `operation_id` calculation.
  - The spec says “MUST NOT re-encode”, but it would help to add a *normative bridge rule* specifically for `sync_op` PUSE fallback: the CBOR bytes are opaque and must be delivered unchanged.

- **What to fix**
  - In `RFC-0003` §8.2 (`sync_op`), add an explicit normative statement:
    - Recipients/forwarders MUST treat `content.cbor` bytes as opaque and MUST NOT decode/re-encode before verifying `operation_id` and signatures.
