## 1) Internal contradictions between documents

### Issue C1 — `expected_server_iid` requirement: MUST vs SHOULD (security + conformance mismatch)
**Severity: HIGH**

- **Where**
  - `spec/01-transport-connectivity/peer-handshake.md` (≈ lines 145–175), section **“IID Binding Requirement (Normative)”**:
    - States: client **MUST** include `expected_server_iid` when initiating for a known IID, and **MUST** abort on mismatch.
  - `spec/06-rfcs/RFC-0002-transport.md` (≈ lines 210–260), section **§5.5 ClientHello Message** table:
    - States `expected_server_iid` **SHOULD**.

- **Why this matters**
  - This is a *normative contradiction* between the “guidance” doc and the “authoritative” RFC.
  - Implementations that follow RFC-0002 literally may omit `expected_server_iid`, weakening the “wrong-peer acceptance” defense that peer-handshake.md treats as mandatory.

- **What to fix**
  - Align the RFC and the layer doc:
    - Either (preferred) update **RFC-0002 §5.5** to say `expected_server_iid` **MUST** be set when the caller has an intended IID (i.e., non-discovery connects), **OR**
    - downgrade peer-handshake.md language to match RFC and clearly mark it “RECOMMENDED security hardening” rather than “Normative”.
  - Add a conformance requirement/test: “connect-by-IID MUST populate expected_server_iid”.

### Issue C2 — Mailbox delete API shape vs TypeScript interface shape (single vs batch)
**Severity: MEDIUM**

- **Where**
  - `spec/00-shared/layer-integration.md` (≈ lines 640–730), section **“MailboxService Interface”**:
    - `acknowledge(messageId: string): Promise<void>`
  - `spec/06-rfcs/RFC-0003-messaging.md` (≈ lines 430–520), section **§7.4.3 Delete Messages**:
    - `DELETE /messages` with JSON body: `{ "message_ids": ["<uuid>", ...] }`
    - Response: `{"deleted": <count>}`

- **Why this matters**
  - Not a wire-format contradiction (you can send an array of length 1), but the spec never states that **`acknowledge()` maps to a one-element `message_ids` delete**.
  - Different implementations of the messaging layer could incorrectly implement DELETE semantics (e.g., expect a `/messages/{id}` endpoint).

- **What to fix**
  - Add a normative mapping statement (either in layer-integration.md or RFC-0003):
    - “`acknowledge(messageId)` MUST call DELETE /messages with `message_ids=[messageId]` and MUST treat missing/non-owned IDs as success.”
  - Or change the interface to `acknowledge(messageIds: string[]): Promise<{deleted: number}>`.

### Issue C3 — Repository progress log contradicts current mailbox routing model (non-normative but confusing)
**Severity: LOW**

- **Where**
  - `spec/progress.md` (≈ lines 260–310), entry **“Issues Fixed (Iteration 107): B2: Mailbox storage routing … store/retrieve/delete by recipient_iid from PUSE header”**
  - Current normative docs (RFC-0003 §7.4.1–7.4.3 + layer-integration mailbox section) specify **store/retrieve/delete by inbox owner IID from URL/token**, and explicitly **do not** key by PUSE recipient for group messages.

- **Why this matters**
  - `progress.md` is not normative, but teams use it as an index; this contradiction is likely to cause implementation churn.

- **What to fix**
  - Update `spec/progress.md` to reflect the current normative rule:
    - mailbox storage keying is by **`inbox_owner_iid` (path)** / **`token.iid` (retrieve/delete)**, not by PUSE recipient field.

## 2) Missing normative requirements

### Issue M1 — Mailbox token `expires_at` validation rules underspecified (skew, max lifetime)
**Severity: MEDIUM**

- **Where**
  - `spec/06-rfcs/RFC-0003-messaging.md` (≈ lines 250–430), section **§7.3 Authentication** and **Bearer Token Wire Format (Normative)**:
    - Defines token fields and canonicalization.
    - States 401 for “invalid or expired token”, but does not define:
      - allowed clock skew,
      - maximum acceptable `expires_at - now`,
      - whether `expires_at` equal to now is accepted,
      - whether servers must reject tokens too-far-in-the-future even if signature valid.

- **Why this matters**
  - Different mailbox servers will accept/reject the same token, causing intermittent auth failures and/or security issues (overlong token lifetimes).

- **What to fix**
  - Add explicit requirements in RFC-0003 §7.3 or §7.4:
    - e.g., `expires_at` MUST be ≤ `now + 24h + 5m`, MUST be > `now - 5m`, and max lifetime MUST be ≤ 24h (or whatever is intended).

### Issue M2 — Relay allocation lifetime bounds and “granted lifetime” semantics missing
**Severity: MEDIUM**

- **Where**
  - `spec/06-rfcs/RFC-0002-transport.md` (≈ lines 520–650), section **§7.8 Allocation Protocol**
    - Request includes `lifetime` and signature binds it.
    - No explicit server-side rule for:
      - allowed lifetime range (min/max),
      - whether the relay may clamp the requested lifetime,
      - how refresh extends expiry (requested vs granted).
  - `spec/01-transport-connectivity/relay-protocol.md` (≈ lines 80–160) uses “lifetime 3600” as a typical value, but not normative enforcement.

- **Why this matters**
  - A malicious client can request extremely large lifetime values unless relays clamp; this is a **resource exhaustion** vector and will diverge across relay implementations.

- **What to fix**
  - Make it normative in RFC-0002:
    - Relay MUST reject or clamp lifetimes outside `[min,max]`.
    - Allocation response MUST include the **effective granted lifetime** (or expiry derived from it).
    - REFRESH MUST extend by **granted lifetime**, not request lifetime (or specify the exact rule).

### Issue M3 — App/package signature verification mentions revocation checks but lacks a normative algorithm
**Severity: MEDIUM**

- **Where**
  - `spec/05-ux-packaging/app-distribution.md` (≈ lines 90–170), section **“Verification Process”**, step 9:
    - “Check no applicable revocation for that key before signature timestamp”
  - Related revocation records are specified elsewhere:
    - `spec/06-rfcs/RFC-0001-identity-document.md` §12.7 (revocation DHT key/value/TTL)
    - `spec/02-identity-trust/revocation.md`

- **Why this matters**
  - “Applicable revocation” can mean:
    - identity revocation,
    - signing key revocation,
    - key revocation document that rotates keys,
    - device revocation (probably irrelevant for app signing),
    - and can be evaluated fail-open vs fail-closed if revocation fetch fails.
  - Without a single normative algorithm, different nodes will accept/reject the same package.

- **What to fix**
  - Add a normative procedure (likely in app-distribution.md) that says:
    - which DHT keys to query (`post-urbit:revocation:` for the author IID),
    - how to compare `effective_at`,
    - what to do if revocation lookup fails (MUST fail-open? MUST fail-closed? SHOULD warn?),
    - which revocation types invalidate package signatures and from what timestamp boundary.

## 3) Ambiguous wire formats

### Issue W1 — PUDS (NAT discovery) framing lacks strict length/trailing-bytes rules
**Severity: MEDIUM**

- **Where**
  - `spec/01-transport-connectivity/nat-traversal.md` (≈ lines 20–65), section **“Discovery Protocol (STUN-like)”**
    - Request/response formats are described, but there is no explicit:
      - fixed-length rule for request (it’s implicitly 4+1+16 = 21 bytes),
      - exact-length rule for response (depends on address type),
      - trailing bytes rejection rule,
      - behavior for unknown version/address type.

- **Why this matters**
  - Without strict parsing rules, implementations can:
    - accept extra bytes (confusion attacks / parser differentials),
    - disagree on what constitutes a valid response.

- **What to fix**
  - Add explicit normative parsing rules similar to IDOC/PUSE/PURL:
    - Request MUST be exactly 21 bytes; otherwise ignore.
    - Response MUST be exactly 24 bytes (IPv4) or 36 bytes (IPv6); otherwise ignore.
    - Unknown version/address type => ignore (no response).
    - Optionally add an ERROR response type if desired, but ignoring is fine for UDP.

## 4) Security vulnerabilities

### Issue S1 — Hole-punch coordination signatures do not bind endpoint lists (relay can tamper)
**Severity: HIGH**

- **Where**
  - `spec/01-transport-connectivity/nat-traversal.md` (≈ lines 140–235), section **“Signature Construction”**
    - `signature_input` covers:
      - domain,
      - transaction_id,
      - initiator/target IIDs,
      - timestamp,
    - but **does not cover** `initiator_endpoints` / `responder_endpoints`.

- **Why this matters**
  - In relay-assisted coordination, the relay forwards JSON and the recipient “MUST verify signature”.
  - But because endpoints are not signed, a malicious relay (or on-path attacker) can:
    - replace endpoints with victim IP:port pairs, causing involuntary traffic / scanning,
    - downgrade connectivity by injecting unreachable endpoints (DoS),
    - bias NAT traversal toward attacker-controlled infrastructure.

- **What to fix**
  - Sign the **entire** coordination message (minus `signature`) using JCS canonicalization, consistent with other signed JSON objects:
    - `signature_input = DOMAIN || JCS(message_without_signature)` (and keep the hash-then-sign policy if desired).
  - Alternatively, explicitly include a canonical encoding of endpoints in the signature transcript (but JCS is simplest).
  - Add a normative requirement that implementations MUST ignore unsigned endpoint fields if you intentionally want them mutable (not recommended).

## 5) Unspecified error handling

### Issue E1 — Handshake parse/unknown-message handling not fully specified (close behavior + QUIC codes)
**Severity: MEDIUM**

- **Where**
  - `spec/06-rfcs/RFC-0002-transport.md`
    - §5.4 Stream Framing (≈ lines 170–210): framing defined
    - §5.12 Error Codes (≈ lines 330–380): codes listed as strings
    - §9.2 Application Error Codes (≈ lines 840–900): QUIC app codes registry
  - `spec/01-transport-connectivity/peer-handshake.md` (≈ lines 200–255), section **“Error Handling”** table and message schema.

- **What’s missing**
  - For malformed frames / invalid JSON / unknown `type`:
    - Should the peer send `handshake_complete {success:false}` first?
    - Should it immediately close the QUIC connection?
    - Which QUIC application error code should be used (0x101 HANDSHAKE_FAILED vs others)?
  - For a too-large handshake message (>64KB):
    - Should the peer close stream, close connection, or both?

- **Why this matters**
  - In practice, interop failures show up as “hangs” or mismatched close codes; deterministic behavior here significantly improves compatibility and debuggability.

- **What to fix**
  - Add explicit normative rules in RFC-0002 §5:
    - On framing/JSON parse error: MUST close connection with `HANDSHAKE_FAILED (0x101)`.
    - On unknown handshake `type`: MUST close with `HANDSHAKE_FAILED (0x101)` (or define an “UNKNOWN_MESSAGE_TYPE”).
    - If possible, MAY send `handshake_complete` before closing, but MUST NOT wait indefinitely to send it.
