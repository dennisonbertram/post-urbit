Below is a protocol-engineering review of the merged Post‑Urbit spec set, focusing on (1) internal contradictions, (2) missing normative requirements, (3) ambiguous wire formats, (4) security vulnerabilities, and (5) unspecified error handling.

> Line references: because this is a Repomix “packed” view without stable original line numbers, the `Lx–Ly` ranges below are *approximate* within each file as shown in this merged document. I also include section/heading anchors to make each cite unambiguous.

## Issues

### PU-01 — Mailbox API error response format is inconsistent / underspecified  
**Severity:** HIGH (interop failures likely for generic clients)  
**Category:** Unspecified error handling, ambiguous wire format

- **Where**
  - `spec/06-rfcs/RFC-0003-messaging.md` — Mailbox API:
    - Store: “HTTP Response Codes (Normative)” but **no error body schema** for 4xx/5xx responses (approx `§7.4.1`, L~430–L~520)
    - Retrieve: defines 200 response; **no normative error body** for 400/401 (approx `§7.4.2`, L~520–L~620)
    - Delete: **does** define an error response schema: `{"error": "<code>", "message": "<human-readable>"}` (approx `§7.4.3`, L~620–L~700)
- **Problem**
  - Only DELETE defines an error body schema; POST/GET list status codes but leave response body undefined. Clients can’t safely implement unified error parsing/diagnostics and will diverge.
- **Fix (spec)**
  - Make the mailbox error body schema **uniform across POST/GET/DELETE**, including:
    - required JSON fields (`error`, `message`, optional `details`)
    - content-type (`application/json`)
    - whether response bodies exist for each status code.
  - Alternatively define: “On error, mailbox server MAY return any body; clients MUST treat non-2xx as failure”, but then remove the one-off schema from DELETE to avoid misleading partial standardization.

### PU-02 — Relay HTTPS allocation endpoint lacks normative error model  
**Severity:** HIGH (interop friction; clients can’t reliably implement backoff/retry semantics)  
**Category:** Unspecified error handling

- **Where**
  - `spec/06-rfcs/RFC-0002-transport.md` — Allocation Protocol (approx `§7.8–§7.9`, L~340–L~470)
  - `spec/01-transport-connectivity/relay-protocol.md` — Allocation Request/Response and verification steps (approx “Allocation Protocol”, “Allocation Response”, L~40–L~160)
- **Problem**
  - The spec defines request/response bodies for success, plus many failure conditions in prose (timestamp window, nonce replay, cannot fetch identity doc, signature invalid), but does **not** define:
    - HTTP status codes for each failure class
    - whether error bodies are JSON and their schema
    - `Retry-After` usage for rate limiting / overload
    - whether allocation failures are distinguishable (auth vs transient).
- **Fix (spec)**
  - Add a normative table: failure condition → HTTP status → error JSON schema → retry guidance.
  - Reuse the Admin API style `{ error: { code, message, details } }` or the mailbox style—just pick one and apply consistently.

### PU-03 — No explicit maximum size constraints for Device Document / Device Index DHT values  
**Severity:** HIGH (DoS vector + inconsistent acceptance across implementations)  
**Category:** Missing normative requirements, security

- **Where**
  - `spec/00-shared/layer-integration.md` — “Device Document DHT Format” and “Device Index DHT Record” (approx “Device DHT Records”, L~520–L~740)
  - `spec/02-identity-trust/identity-document-schema.md` — Device Document schema (no size limits) (approx “Device Document”, L~240–L~330)
  - `spec/06-rfcs/RFC-0001-identity-document.md` — Device docs/index in DHT (approx `§13` and `§12.4–§12.5`, L~650–L~770)
- **Problem**
  - IDOC has a hard maximum (16KB), but device docs/index (JSON values stored in DHT) lack explicit max bytes. Because DHT nodes MUST validate and store these, an attacker can publish *validly-signed* but extremely large device docs/indexes to exhaust memory/bandwidth/CPU.
  - Different implementations will impose different implicit limits → interop divergence (some nodes store, others reject).
- **Fix (spec)**
  - Add normative max sizes (e.g., `MAX_DEVICE_DOC_SIZE_BYTES`, `MAX_DEVICE_INDEX_SIZE_BYTES`) and rejection behavior.
  - Also define per-record-type maximum endpoints and max device list length in the device index (currently only “max 10 devices” appears for trustees; not device list).

### PU-04 — DHT record “type detection” rule is underspecified and can be ambiguous / expensive  
**Severity:** MEDIUM (workable but risks divergent behavior + CPU DoS)  
**Category:** Ambiguous wire formats, security

- **Where**
  - `spec/00-shared/layer-integration.md` — “Record Validation Rules”: “type is determined by reconstructing expected DHT key from the record’s identifier field and comparing” (approx “DHT Record Types and Validation”, L~360–L~470)
- **Problem**
  - On a raw `(key, value)` PUT, the node needs to know which schema to parse to extract the identifier (`iid`, `did`, etc.) in order to reconstruct the expected key. But the spec doesn’t define a deterministic parse/dispatch algorithm, nor a hard cap on parse attempts.
  - A malicious peer can send values that are expensive to parse repeatedly (e.g., large JSON near limits), creating CPU DoS.
- **Fix (spec)**
  - Define an explicit decision procedure, e.g.:
    1. If value begins with `IDOC` magic → treat as identity/genesis doc candidate.
    2. Else parse JSON once (with size cap), then decide by presence of discriminator fields (`type`, `did`, `devices`, etc.).
    3. Reject if discriminator set is ambiguous (matches multiple types).
  - Add a strict “parse at most once” rule for JSON records.

### PU-05 — Sync `SYNC_ERROR` CBOR schema includes a `type: 8` field while other sync messages do not  
**Severity:** MEDIUM (confusing; potential encoding divergence)  
**Category:** Ambiguous wire format / schema consistency

- **Where**
  - `spec/03-messaging-sync/sync-protocol.md`:
    - “Sync Messages”: outer 1-byte message type (0x08 = SYNC_ERROR) (approx “Message Types”, L~120–L~170)
    - “Error Signaling (Normative)”: `SYNC_ERROR = { type: 8, error_code: ... }` (approx L~180–L~260)
    - “CBOR Schemas for Sync Messages”: again includes `"type": 8` only for SYNC_ERROR (approx L~260–L~360)
- **Problem**
  - The wire already has a 1-byte message type prefix. Having an additional `type` field inside the CBOR map only for errors is an inconsistency that implementers may “fix” differently:
    - some will omit the inner field (since redundant)
    - some will require it (since present in schema).
- **Fix (spec)**
  - Either:
    - remove the inner `type` field from SYNC_ERROR and define it like other messages, **or**
    - require all sync message CBOR bodies to include a `type` field consistently.
  - Add explicit MUST/MUST NOT language so implementations converge.

### PU-06 — PUSE flags reserved bits: the spec describes them but doesn’t consistently require rejection behavior  
**Severity:** MEDIUM (future-compat ambiguity; could cause divergent acceptance)  
**Category:** Missing normative requirements

- **Where**
  - `spec/06-rfcs/RFC-0003-messaging.md` — Flags byte diagram: reserved bits “must be 0” (approx `§3.3`, L~210–L~260)
  - `spec/03-messaging-sync/secure-envelope.md` — Flags byte diagram (approx “Flags Byte”, L~120–L~170)
- **Problem**
  - The docs state reserved bits “must be 0” but don’t clearly define receiver behavior:
    - MUST reject if any reserved bit set?
    - MUST ignore and continue?
  - This matters for forward compatibility: strict rejection breaks newer senders; permissive acceptance may create downgrade/feature-confusion risks.
- **Fix (spec)**
  - Add a single normative rule (typical approach):
    - receivers MUST reject if reserved bits are non-zero (strict v1), **or**
    - receivers MUST ignore reserved bits (future-compatible), but MUST NOT change semantics based on them unless version bumps.

### PU-07 — App Runtime messaging size guidance contradicts RFC‑0003’s computed maxima (even if “approximate”)  
**Severity:** LOW (implementation guidance inconsistency)  
**Category:** Internal contradiction (documentation)

- **Where**
  - `spec/04-app-runtime/api-surface.md` — `messaging.send` → “Derived Plaintext Limits” (approx L~110–L~135) states:
    - group: `~1,048,375`
    - ratchet: `~1,048,355`
  - `spec/06-rfcs/RFC-0003-messaging.md` — “Derived Maximum Plaintext Size” table (approx `§3.2`, L~140–L~210) states:
    - group (ext=21): `1,048,395`
    - ratchet (ext=41): `1,048,375`
- **Problem**
  - The app-runtime doc’s numbers are ~20 bytes lower than RFC‑0003. Even as “approximate”, this is a visible discrepancy that will cause implementer confusion.
- **Fix (spec)**
  - Update the app-runtime “Derived Plaintext Limits” to match RFC‑0003 math (or remove the numbers and refer to RFC‑0003 §3.2 formula).

### PU-08 — Fail-open revocation checking for app package signatures is a deliberate security downgrade without a REQUIRED UX/telemetry requirement  
**Severity:** MEDIUM (security posture gap; may cause unsafe installs by default)  
**Category:** Security vulnerability / missing normative requirements

- **Where**
  - `spec/05-ux-packaging/app-distribution.md` — “Revocation Check Algorithm (Normative)” includes:
    - “If DHT query fails… SHOULD warn… MAY proceed with installation (fail-open)” (approx L~120–L~175)
- **Problem**
  - “SHOULD warn” is not a strong enough requirement given the stated threat (installing software signed by a revoked key). Different implementations will implement anything from silent proceed to hard fail.
- **Fix (spec)**
  - Tighten to at least:
    - UI clients MUST present an explicit interstitial that requires affirmative user action, and
    - headless installs MUST require an explicit `--allow-revocation-check-failure` flag (or config).
  - Or define two conformance profiles (consumer vs high-security) with clear defaults.

### PU-09 — DHT implementation requirement text is internally inconsistent (“MUST use a DHT that provides…” vs “MUST use libp2p Kademlia DHT”)  
**Severity:** LOW (editorial/normative clarity)  
**Category:** Internal contradiction / normative clarity

- **Where**
  - `spec/00-shared/layer-integration.md`:
    - “Implementations MUST use a DHT that provides…” + “Recommended Implementation: Kademlia-based DHT” (approx “DHT Protocol Stack (Normative)”, L~90–L~140)
    - Later: “Implementations MUST use the libp2p Kademlia DHT protocol…” (approx “DHT Wire Protocol (Normative)”, L~140–L~190)
- **Problem**
  - The first phrasing reads like a generic requirement with a recommendation; later it becomes strictly libp2p‑kad. The end result is clear, but the earlier wording misleads.
- **Fix (spec)**
  - Collapse into a single statement: v1 DHT wire interoperability == libp2p‑kad on `/post-urbit/kad/1.0.0`. Keep the “abstract DHT interface” but make clear it is *implemented by libp2p‑kad* in v1.

## Summary: BLOCKING issues

None found in this pass.

The spec is generally implementation-directed: wire formats are mostly byte-level, canonicalization rules are mostly explicit, and cross-layer integration glue resolves many classic interop ambiguities. The remaining issues are primarily about (a) standardizing error response schemas for HTTP-facing components, (b) bounding DHT-stored JSON record sizes, and (c) a few consistency/documentation cleanups.
