**BLOCKING ISSUES:**

- **B1: Initial (0x00) header extension → message-key derivation is underspecified, enabling incompatible encrypt/decrypt** — **spec/06-rfcs/RFC-0003-messaging.md §3.4.2 + §5.3** — The RFC says the first message uses extension type **0x00** and is “encrypted with a key derived from `initial_chain_key`”, but does not normatively define *which bytes* become the AEAD key:
  - Implementer A may use `message_key = initial_chain_key` directly.
  - Implementer B may use `message_key = kdf_chain_step(initial_chain_key).message_key` (as implied by `secure-envelope.md`), advancing the chain.
  - Implementer C may avoid 0x00 entirely and send the first message as a ratchet message (0x01) with `N=0`.
  
  These produce non-interoperable ciphertexts because AEAD keys (and/or AAD) differ. The RFC MUST explicitly specify, for **extension 0x00**:
  1) exact message-key derivation (e.g., “apply `kdf_chain_step(initial_chain_key)` once; use returned `message_key`”),  
  2) whether/how sender stores the advanced chain key and what initial “N” becomes for subsequent messages,  
  3) whether 0x00 is allowed for more than one message per session (without an index it can’t be used safely for >1 message without trial-decrypt ambiguity/DoS).

- **B2: Mailbox bearer token serialization is ambiguous (JSON object vs encoded string)** — **spec/06-rfcs/RFC-0003-messaging.md §7.3** — The section presents the token as a JSON object (fields `iid`, `mailbox_url`, `expires_at`, `nonce`, `signature`) but never states, normatively, what the actual HTTP `Authorization: Bearer <token>` value *is* on the wire.
  - One implementer will send the literal JSON (or a compact JSON string) as the bearer value.
  - Another will send `base64url(JCS(token_json))` (as in the later pseudocode).
  - Another may implement a JWT/JWS.
  
  Mailbox servers and clients will not interoperate. The RFC MUST state the exact bearer token wire representation (including base64url alphabet + “no padding” rule), not only via pseudocode.

- **B3: Mailbox URL canonicalization is incomplete/underspecified for IPv6 + percent-encoding, causing signature mismatches** — **spec/06-rfcs/RFC-0003-messaging.md §7.3 “URL Canonicalization (Normative)”** — The rules + sample code omit/unclear handling that affects the bytes signed:
  - **IPv6 literals:** canonical form requires brackets (`https://[2001:db8::1]/`). The provided pseudocode reconstructs `netloc` from `hostname` without re-bracketing, yielding a different URL string (and often an invalid URL) → different signature input.
  - **Percent-encoding normalization:** the rules don’t say whether `%2F` vs `/`, or uppercase vs lowercase hex in escapes, must be preserved or normalized. Different choices change the signed UTF-8 bytes.
  - **Query/fragment:** rules say “MUST NOT contain”, but pseudocode silently drops them; some implementations will reject, others will accept-and-strip, producing different verification behavior.
  
  Because `mailbox_url` bytes are part of the signed `signature_input`, this will cause incompatible token verification across implementations.

- **B4: Mailbox “retrieve” envelope encoding is unspecified (Base64 vs Base64url, padding rules)** — **spec/06-rfcs/RFC-0003-messaging.md §7.4.2** — The response field `"envelope": "<base64-puse-envelope>"` does not specify:
  - Base64 **standard** vs **base64url**
  - padding permitted or forbidden
  - whether line breaks are permitted
  
  Clients will fail to decode envelopes depending on implementer choice. This MUST be pinned (preferably: Base64 standard alphabet, **no padding**, matching the global encoding rules used for keys/signatures).
