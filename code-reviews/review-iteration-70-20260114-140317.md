**BLOCKING ISSUES:**
- **B1: Group membership/state-update wire model is internally contradictory** — `spec/03-messaging-sync/group-messaging.md` vs `spec/06-rfcs/RFC-0003-messaging.md` (and `spec/03-messaging-sync/interfaces.md`) — `group-messaging.md` declares *“All membership changes are represented as Group State Updates”* with a specific `GroupStateUpdate.version` format (`"<logical_clock>.<first_8_chars_of_actor_iid>"`) and `previous_version` chaining + deterministic conflict rules, but the same file (and RFC-0003 §8.2) also uses a looser `group_event` message pattern (examples: `event: "member_left"`, `event: "member_removed"`) and a membership snapshot containing `"version": "42"` (no dot-suffix). Two implementers will ship incompatible group membership replication (one implementing CRDT-like GroupStateUpdate, another implementing ad-hoc `group_event`).  
  **What must be made normative:** either (a) define `group_event` as *exactly* `{ "type":"group_state_update", ...GroupStateUpdate... }` (and delete/forbid the ad-hoc event shapes), including the genesis `previous_version` value and snapshot `version` format; or (b) drop GroupStateUpdate entirely and fully specify the `group_event` schema + conflict resolution + versioning.

- **B2: Sync stream on-wire encoding conflicts with the “interfaces” types** — `spec/03-messaging-sync/sync-protocol.md` vs `spec/03-messaging-sync/interfaces.md` (plus framing references in `spec/00-shared/layer-integration.md` and `spec/06-rfcs/RFC-0002-transport.md`) — `sync-protocol.md` is explicit that stream 0x04 payloads are `1-byte type + CBOR`, with **byte-string** fields (`document_id: 32-byte bstr`, `origin: 20-byte bstr IID`, `id/signature/dependencies: bstr`). Meanwhile `interfaces.md` presents `DocumentId`, `Signature`, `OperationId` as **strings** (UUID/hex/base64) without a mandatory mapping section, which can be read as the wire contract for “Messaging & Sync Interfaces”. Two implementers can produce incompatible CBOR (bytes vs strings) on the sync stream.  
  **What must be added:** a normative “API↔wire mapping” stating that the TypeScript interfaces are *in-memory/app-facing only*, and specifying exact canonical conversions: DocumentId string ↔ 32-byte bstr (UUID bytes + 16x00 padding vs raw SHA256), Signature base64 ↔ 64-byte bstr, OperationId hex ↔ 32-byte bstr, etc.

- **B3: Historical signing key usage for verifying PUSE signatures is inconsistent across identity vs messaging specs** — `spec/06-rfcs/RFC-0001-identity-document.md` §7.5 vs `spec/03-messaging-sync/secure-envelope.md` (and `spec/02-identity-trust/identity-document-schema.md`) — RFC-0001 says verifiers should use `keys.signing.history[]` and “match by validity window”, but the history window fields are **sequence numbers** (`valid_from/valid_until`), while message verification must occur **before decryption** (so plaintext timestamps/sequence cannot be used to select the correct identity-doc sequence), and `secure-envelope.md` correctly notes `valid_from/valid_until` are not usable for time-filtering and instead suggests trial-verifying history keys gated only by `expires_at`. Two implementers will diverge: one may reject mailbox-delivered messages after rotations because it can’t “match the window”; another will accept by trial verification.  
  **What must be resolved normatively:** either (a) specify that PUSE signature verification MUST try `current`, then `previous`, then any `history[]` keys that are not past `expires_at` (and that `valid_from/valid_until` are advisory/audit-only), **or** (b) add a sender-idoc-sequence (or key-id) hint to the PUSE header so “validity window” matching is actually computable pre-decryption.
