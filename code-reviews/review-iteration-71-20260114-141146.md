**BLOCKING ISSUES:**

- **B1: Group membership message type registry contradicts the normative group spec** — **RFC-0003 §8.2 “Type Registry”** — RFC-0003 lists `"group_event"` as the group membership change message type, but the group layer spec mandates `"group_state_update"` and states `"group_event"` is deprecated and MUST be rejected (`spec/03-messaging-sync/group-messaging.md`, “Wire Format (Normative)”). Two implementers following different “authoritative” texts will send/accept different plaintext `type` values → incompatible group membership behavior.

- **B2: Double Ratchet PN (previous chain length) is encoded incorrectly for any message after the first in a new DH sending chain** — **RFC-0003 §4.4 “Sending a Message” (ratchet_encrypt pseudocode)** — `previous_chain_length` is initialized to `0` each call and only set when `state.sending_chain_key is None`. This means:
  - First message after a DH ratchet: PN is correct.
  - Second+ messages with the same `dh_public` (same sending chain): PN becomes `0`, which is wrong if the receiver missed the first message with that `dh_public`.
  
  This breaks out-of-order/loss tolerance: a receiver that first sees message N=1 (or later) for a new `dh_public` will ratchet using PN=0, derive the wrong skipped-key set, and can fail to decrypt or permanently desynchronize. This contradicts the intended semantics (and the earlier ratchet spec in `spec/03-messaging-sync/double-ratchet.md` which keeps PN as a persistent state value). PN must be a per-sending-chain constant carried in *every* header for that DH public until the next DH ratchet.

- **B3: UUID byte serialization for `message_id` is not specified or normatively referenced inside RFC-0003, but is required for mailbox interop** — **RFC-0003 §3.2 (PUSE `message_id` field) + §7.4 (Mailbox `message_id` semantics, “bytes 46–61”)** — RFC-0003 defines `message_id` as “UUID v4” and pins its byte offsets (46–61, 0-indexed) but does not state the required byte order for converting between:
  - the 16 raw bytes in the PUSE header, and
  - the RFC 4122 canonical string used by mailbox APIs.
  
  Platforms with mixed-endian UUID byte conventions (notably Windows/.NET GUID byte arrays) will produce different 16-byte sequences for the same UUID string unless the spec requires **RFC 4122 network byte order**. The repository *does* define this in `spec/00-shared/layer-integration.md` (“UUID Serialization (Normative)”), but RFC-0003 neither repeats nor normatively references it; two independent implementers reading RFC-0003 alone can diverge → incompatible mailbox `message_id` behavior and reply/receipt threading.
