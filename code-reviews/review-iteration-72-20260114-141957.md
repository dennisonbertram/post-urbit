**BLOCKING ISSUES:**

- **B1: Group membership operation schema is internally inconsistent (action type names + fields), so implementers will serialize/accept different JSON** — `spec/03-messaging-sync/group-messaging.md` (and referenced by `spec/06-rfcs/RFC-0003-messaging.md` §8.2) — `GroupAction` is defined as:
  - `member_added | member_removed | member_left | role_changed | settings_changed`
  
  but the later **examples** use different action types/fields:
  - “Leave” example uses `action.type: "leave"` (not `member_left`)
  - “Remove (Kick)” example uses `action.type: "remove"` + `target_iid` (not `member_removed` + `member_iid`)
  - examples include a `signature` field inside the state update content, while earlier text states authentication is via the PUSE envelope signature and **no separate group-state signature exists**.

- **B2: `previous_version` nullability is contradictory for genesis updates** — `spec/03-messaging-sync/group-messaging.md` — It normatively states: “The genesis version … MUST use `previous_version` set to `null`”, but the `GroupStateUpdate` interface declares `previous_version: string` (not `string | null`). This will cause some implementations to reject valid genesis updates or encode them differently.

- **B3: Version comparison/ordering for GroupStateUpdate is underspecified (numeric vs lexicographic), breaking deterministic convergence** — `spec/03-messaging-sync/group-messaging.md` — Conflict resolution says “Higher `version` wins”, but does not normatively define comparison as:
  - parse `logical_clock` as an integer (not string compare), then compare `actor_iid`/suffix.
  
  Two implementers can reasonably sort versions lexicographically (`"10.x" < "2.y"`) vs numerically (`10 > 2`), producing divergent membership state.

- **B4: Sync CBOR wire encoding contradicts the “API↔Wire Encoding Mapping (Normative)” for timestamps** — `spec/03-messaging-sync/interfaces.md` vs `spec/03-messaging-sync/sync-protocol.md` — The mapping table says:
  - `Timestamp` (RFC3339 string) → CBOR text string
  
  but the sync wire schema defines `timestamp` as a **Hybrid Logical Clock map**:
  - `{"physical": uint, "logical": uint, "origin": bstr(20)}`
  
  Because the mapping section is explicitly “Normative” and scoped to sync stream (0x04) CBOR payloads, this creates incompatible encoders/decoders.

- **B5: IDOC envelope JSON canonicalization requirement is inconsistent (JCS-required vs “canonical JSON” vague), enabling accept/reject divergence at the DHT boundary** — `spec/02-identity-trust/identity-document-schema.md` vs `spec/06-rfcs/RFC-0001-identity-document.md` §6.2 vs `spec/00-shared/layer-integration.md` (DHT record format) — RFC-0001 requires the JSON inside the IDOC envelope to be **JCS-canonicalized for the full document including signatures**, and `layer-integration.md` describes DHT values as “IDOC envelope … + **JCS-canonical JSON**”. But `identity-document-schema.md` wire format only says “Canonical JSON (UTF-8)” without a normative JCS requirement or accept/reject rule, so one implementer may emit/accept non-JCS JSON while another rejects it as non-conformant.
