**BLOCKING ISSUES:**

- **B1: Mailbox retrieval pagination is under-specified and contradicts the platform’s mailbox interface** — **RFC-0003 §7.4.2** — `GET /messages?since=<timestamp>&limit=100` returns `has_more` but **no cursor/next token**, and “since” semantics (inclusive/exclusive, tie-breaking when multiple messages share the same `stored_at`) are undefined. Meanwhile `spec/00-shared/layer-integration.md` models mailbox retrieval as `sinceCursor?: string` (opaque cursor). Two implementers will build incompatible mailbox clients/servers (timestamp-based vs cursor-based, and/or different boundary semantics).

- **B2: Initial (0x00) → Ratchet (0x01) transition leaves N/DH-public requirements ambiguous, enabling incompatible ratchet state evolution** — **RFC-0003 §3.4.2 + §3.4.3 + §4.4 + §5.5** — After the initial message, the spec says the sender stores `sendingChainIndex = 1`, but it does **not normatively state** that the next message (first with 0x01) MUST:
  - reuse the same DH public key as the 0x00 ephemeral public key, and
  - carry `N = 1` (because the implicit initial message is effectively “message 0” of that sending chain).
  
  A plausible alternate reading is that the first 0x01 message uses `N=0` and/or a fresh DH key, which will make receivers derive different message keys and fail decryption.

- **B3: No normative linkage between Flags.recipient_type and header-extension type (and ext_len)** — **RFC-0003 §3.3–§3.4** — The document defines both a recipient-type field (flags bits 0–1) and an extension-type registry (0x00/0x01/0x02) and requires exactly one extension, but it never states required combinations (e.g., recipient_type=group ⇔ extension_type=0x02, recipient_type=1:1 ⇔ extension_type∈{0x00,0x01}). Implementers will differ on accept/reject behavior for mismatches (and some will key routing/handling off flags while others key off extension type), producing interoperability differences and divergent security checks.

- **B4: Group Sender Key Iteration is effectively 1-indexed in algorithms but not specified as such in the wire header** — **RFC-0003 §3.4.4 + §6.6–§6.7** — The group extension carries `iteration` as a 4-byte big-endian uint32 (bytes 1..20 of the 21-byte extension), and the decryption pseudocode explicitly assumes **header.iteration is 1-indexed** (“first message has iteration=1”). The wire-format section does not state whether `iteration=0` is invalid. Two implementers can pick different conventions (0-indexed vs 1-indexed) and break group decrypt.

- **B5: Mailbox token URL canonicalization omits key validity constraints that affect signature reproduction** — **RFC-0003 §7.3** — Canonicalization rules mandate rejecting `?`/`#`, but do not define handling for **userinfo (`user@host`)**, require/forbid **non-https schemes**, or require host presence. Some implementations will reject these inputs; others will normalize by stripping components; that yields different `mailbox_url` strings and therefore different signature inputs, producing incompatible token verification behavior.
