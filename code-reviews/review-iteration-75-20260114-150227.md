**BLOCKING ISSUES:**

- **B1: PUSE signature verification key selection is underspecified in RFC-0003** — `spec/06-rfcs/RFC-0003-messaging.md` §3.7–§3.8 — RFC says `signature = Ed25519_Sign(sender_signing_key, signed_data)` and instructs “fetch identity document for sender IID”, but never normatively defines *which* signing key(s) from the identity document are valid for verifying a received PUSE envelope (current vs previous vs history). This is required for mailbox-delayed delivery across key rotations; RFC-0001 §7.5 provides a **normative** key-lookup order (current → previous → history where `expires_at` not passed), and `spec/03-messaging-sync/secure-envelope.md` repeats it. As written, two conforming implementers of RFC-0003 can diverge (current-only vs current+history), producing incompatible acceptance/rejection of the same envelopes.

- **B2: 2DH initial message decryption is ambiguous under sender encryption-key rotation** — `spec/06-rfcs/RFC-0003-messaging.md` §5.2–§5.3 and §3.4.2 — The initial (0x00) message key derivation uses `DH1 = X25519(IK_sender_private, IK_recipient_public)` and requires the receiver to choose the sender’s correct X25519 *public* key for DH1. The RFC’s receiver algorithm (§5.3) says “Bob extracts Alice’s identity key: `IK_A = alice.keys.encryption.current`”, but if Alice rotated `keys.encryption.current` between sending and Bob’s retrieval (common with mailbox delays), DH1 will be computed with the wrong key unless the receiver tries `keys.encryption.previous[]` (and/or older IDOC versions). The wire format carries no sender-key identifier to disambiguate. Different implementers will either (a) try only `current` and fail, or (b) try `current` + `previous[]` (and possibly cached historical IDOCs) until AEAD succeeds, yielding incompatible behavior. A normative “key trial order” (and constraints on which previous keys are eligible) is required, or the format must carry an explicit sender encryption key reference.

- **B3: PUSE plaintext type registry conflicts with non-RFC normative docs regarding `sync_op` over mailbox** — `spec/06-rfcs/RFC-0003-messaging.md` §1.2 and §8.2 vs `spec/03-messaging-sync/secure-envelope.md` (“Note on sync_op”) — RFC-0003 explicitly scopes sync “out of scope” and its message-type registry (§8.2) omits `sync_op`, while `secure-envelope.md` states that sync operations “may be encapsulated in PUSE with type `sync_op`” for mailbox fallback and imposes extra validation requirements. Two implementations following different documents will disagree on whether `sync_op` is valid/processable under RFC-0003, leading to incompatible behavior for offline sync delivery. This must be resolved by either (a) adding `sync_op` (and its verification rules) to RFC-0003, or (b) explicitly forbidding it everywhere outside the sync stream and removing the fallback claim from the other docs.
