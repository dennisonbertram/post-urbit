**BLOCKING ISSUES:**
- **B1: App-to-app message typing/encoding is underspecified and internally inconsistent** — `spec/04-app-runtime/api-surface.md` + `spec/04-app-runtime/abi.md` + `spec/04-app-runtime/manifest-schema.md` vs `spec/06-rfcs/RFC-0003-messaging.md` + `spec/03-messaging-sync/secure-envelope.md` + `spec/03-messaging-sync/interfaces.md` — Host API defines `messaging.send{ message_type: string, content: CBOR bytes }` and subscription filtering on `message_types` patterns (also `handlers.message_types` in manifests), but the PUSE plaintext schema/RFC message-type registry only defines a fixed `type` field (with `app` having `{app_id, data:any}`) and does not normatively define how `message_type` maps onto PUSE plaintext, nor how CBOR `content` is represented on the wire (e.g., base64 of CBOR inside JSON). Two implementers will choose different encodings and break cross-node app messaging/subscription dispatch.

- **B2: Glare/duplicate-connection resolution is not normatively specified in the Transport RFC** — `spec/01-transport-connectivity/interfaces.md` vs `spec/06-rfcs/RFC-0002-transport.md` — `interfaces.md` specifies deterministic connection uniqueness and glare resolution (lexicographic (iid,did) tuple initiator wins; close the other with `DUPLICATE_CONNECTION (0x105)`), but RFC-0002 only defines the error code registry (including 0x105) and does not define the required tie-break rule. Two independent implementations can make opposite choices and both close (or both keep) connections, producing intermittent incompatibility.
