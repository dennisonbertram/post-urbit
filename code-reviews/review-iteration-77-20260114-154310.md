### 1) **(B) Spec references “authoritative” documents that are not present / not in-repo**
**Problematic text (examples):**
- “For concrete test values, see `spec/00-shared/test-vectors.md`.”
- “// What Identity layer expects (from caching-policy.md)”
- “// What Transport layer provides (from interfaces.md)”
- “DHT Value: IDOC binary envelope (see identity-document-schema.md)”
- “If sequences match but content differs, see `identity-document-schema.md` "Concurrent Updates" section.”
- “OR verify `recovery_proof` is valid (see recovery-mechanisms.md)”
- “Perform identity handshake (see peer-handshake.md)”
- “See `sync-protocol.md` for message types.”
- “See `06-rfcs/RFC-0002-transport.md` §6 for the authoritative specification.”
- “**RFC-0003 §7 is the authoritative specification** for the Mailbox protocol.”

**Why ambiguous/inconsistent:**
This file declares itself normative for “cross-layer contracts,” but repeatedly defers essential wire-format and state-machine details to documents that are not included in the provided codebase. Two implementers using *only this repository* cannot converge on the same behavior.

**What two implementations might do differently:**
- Implementer A invents an IDOC envelope encoding, stream rules, mailbox token format, etc.
- Implementer B implements a different envelope, signature input, stream semantics, etc.
Both pass local tests but fail interoperability.

**Specific fix:**
- Either (a) vendor/include the referenced specs in-repo and mark exact versions/commit hashes, **or** (b) inline the required normative definitions here (IDOC envelope layout, identity handshake transcript, sync message types, mailbox token structure, concurrent update rules, recovery proof rules).
- Add a “Dependencies” section with a strict list of required documents and version identifiers.

### 2) **(B) Identity update stream defines framing and message “types” but not the actual JSON schemas**
**Problematic text:**
- “Identity updates use the `identity` stream type (0x02)”
- “Identity | UTF-8 JSON | Has `type` field for message kind”
- “Identity Update Message Types (JSON `type` field): `identity_update`, `identity_request`, `identity_response`, `identity_ack`”
- Flow diagrams show: “(new IdentityDocument)”, “(accepted: true, sequence: N)”, “(known_sequence: N-1)”, “(document or "no update")”

**Why ambiguous/inconsistent:**
The spec never defines:
- Field names, required/optional fields, field types (string vs number), and how the identity document is carried (inline JSON object vs base64 IDOC bytes vs something else).
- Whether `sequence` is a string (per global conventions) or a JSON number.
- How “no update” is represented.

**What two implementations might do differently:**
- Impl A sends `{type:"identity_update", document:{...}}` (inline JSON object).
- Impl B sends `{type:"identity_update", idoc:"<base64>"}` (binary envelope base64).
- Impl C uses `sequence: 12` (number) while Impl D uses `"12"` (string).
Result: immediate parse/validation failures.

**Specific fix:**
Define normative JSON schemas per message type, e.g.:

```jsonc
// identity_update
{
  "type": "identity_update",
  "idoc": "<base64-standard-no-padding of IDOC envelope bytes>",
  "sequence": "<decimal string uint64>",
  "sent_at": "<RFC3339 UTC canonical?>"
}

// identity_request
{
  "type": "identity_request",
  "known_sequence": "<decimal string uint64>"
}

// identity_response
{
  "type": "identity_response",
  "has_update": true,
  "idoc": "<base64...>",
  "sequence": "<decimal string uint64>"
}
// OR has_update:false and omit idoc/sequence

// identity_ack
{
  "type": "identity_ack",
  "accepted": true,
  "sequence": "<decimal string uint64>",
  "error_code": "<optional integer>",
  "error_message": "<optional string>"
}
```

Also specify whether timestamps in these JSON messages must be canonical (20-byte form) or any RFC3339.

### 3) **(B) QUIC stream usage is incomplete: unidirectional vs bidirectional, stream initiation rules, and multiplicity are unspecified**
**Problematic text:**
- “Stream Header (first byte of stream, written once)”
- “Each Message Frame (repeated)…”
- “This framing pattern … is consistent across all QUIC stream types.”
- No text defines who opens which streams, whether streams are uni/bidi, whether multiple streams of same type are allowed, and collision handling.

**Why ambiguous/inconsistent:**
In QUIC, interoperability depends on stream directionality and initiation conventions. Without rules, peers can deadlock or reject each other (e.g., both waiting for the other to open a control stream).

**What two implementations might do differently:**
- Impl A opens one **bidirectional** “identity” stream and expects request/response on it.
- Impl B opens separate **unidirectional** streams per direction and never reads from a bidi stream.
- Impl C opens a new stream per message, writing type byte each time.
- Impl D opens one long-lived stream per type.
These won’t interoperate.

**Specific fix:**
Add normative transport rules, e.g.:
- “All protocol streams are QUIC **unidirectional** streams.”
- “Each endpoint MUST open exactly one outgoing stream of each stream type it will send; the peer MUST accept at most one incoming stream per type; opening a second stream of the same type is a protocol error.”
- Or, if bidirectional is intended: define which side opens which stream(s), and whether messages can be sent by both sides on the same stream.

### 4) **(B) Sequence number format and comparison rules are underspecified (will fork conflict resolution)**
**Problematic text:**
- “type SequenceNumber = string;”
- “Monotonically increasing sequence number as decimal string (for uint64 safety)”
- “new sequence MUST be > existing sequence”
- Example sorts by `BigInt(a.sequence)`

**Why ambiguous/inconsistent:**
Not specified:
- Allowed range (uint64? arbitrary precision?)
- Whether leading zeros are permitted (`"01"` vs `"1"`)
- Whether `+` signs, whitespace are allowed
- Parsing/rejection rules for invalid strings

These details directly affect ordering and signature inputs (if sequence participates anywhere).

**What two implementations might do differently:**
- Impl A accepts `"001"` and treats it as 1; Impl B rejects it as non-canonical.
- Impl A caps at uint64; Impl B accepts arbitrarily large integers.
- Impl A compares lexicographically by mistake; Impl B compares numerically.

**Specific fix:**
Add a normative definition, e.g.:
- “`sequence` MUST be a base-10 unsigned integer in the range `[0, 2^64-1]` encoded as ASCII decimal with no leading zeros (except the single character `"0"`).”
- “Receivers MUST reject any non-canonical or out-of-range value.”

### 5) **(B) DHT conflict handling for same-sequence documents and genesis races is not specified (and refers out-of-repo)**
**Problematic text:**
- “If sequences match but content differs, see `identity-document-schema.md` "Concurrent Updates" section.”
- “Genesis Document… First-seen-wins applies if multiple genesis documents appear for the same IID (concurrent updates section).”

**Why ambiguous/inconsistent:**
You define a multi-source `getAll`, so same-sequence conflicts are expected. But you don’t define deterministic selection rules when `sequence` ties, nor how “first-seen-wins” is evaluated in a distributed DHT (first seen by which node? client? quorum?).

**What two implementations might do differently:**
- Impl A: on tie, chooses lexicographically smallest hash.
- Impl B: chooses newest `receivedAt`.
- Impl C: rejects and requires manual intervention.
For genesis collisions, node behaviors can diverge permanently.

**Specific fix:**
Define deterministic tie-breakers *in this document*, e.g.:
- “If multiple valid docs share the highest sequence: compute `h = SHA256(JCS(document_json))` and select the doc with the lexicographically greatest `h` (or least—pick one)”
- For genesis: clarify whether a separate “genesis key” is used (see Issue 6), or define a deterministic “genesis winner” rule using the same tie-breaker.

### 6) **(B) DHT “genesis key” prefix is defined but its semantics are unclear (two storage models possible)**
**Problematic text:**
- Key derivations include: `SHA256("post-urbit:genesis:" || iid)` → “genesis identity document lookup”
- But “DHT Record Format” states identity lookup uses: `SHA256("post-urbit:identity:" || iid)`
- “Genesis Document… For sequence 0 (genesis)… DHT nodes accept genesis documents…”

**Why ambiguous/inconsistent:**
It’s unclear whether genesis is:
- Stored only under the regular identity key as `sequence=0` then replaced by updates, **or**
- Stored immutably under a separate `genesis:` key in addition to the mutable `identity:` key.

Both are plausible and lead to different recovery / TOFU behaviors.

**What two implementations might do differently:**
- Impl A stores only under `post-urbit:identity:` and overwrites.
- Impl B stores sequence 0 under `post-urbit:genesis:` permanently and stores latest under `post-urbit:identity:`.
Clients that expect one model fail to find genesis or fail to validate update chains.

**Specific fix:**
Pick one model and specify it normatively, e.g.:
- **Option 1 (recommended for clarity):** “Genesis MUST be stored under `post-urbit:genesis:` and MUST be immutable (only sequence 0 allowed). Latest document MUST be stored under `post-urbit:identity:`.”
- Or remove the `genesis:` key derivation entirely if unused.

### 7) **(B) TLS certificate policy is contradictory (“accept any” vs restricted algorithms/validity)**
**Problematic text:**
- Certificate Requirements table: “Signature algorithm: ECDSA P-256 or Ed25519”, “Validity period: 1 hour to 30 days”
- Verification Strategy: “**Accept any valid TLS certificate** (self-signed OK)”

**Why ambiguous/inconsistent:**
“Accept any valid TLS certificate” conflicts with restricting signature algorithms and validity periods. Also unclear whether clients must check NotBefore/NotAfter at all if cert isn’t used for identity.

**What two implementations might do differently:**
- Impl A rejects RSA certificates (following table).
- Impl B accepts RSA (following “accept any”).
- Impl A rejects expired certs; Impl B ignores validity entirely.
This can prevent connections.

**Specific fix:**
Clarify client acceptance criteria separately from server generation recommendations, e.g.:
- “Servers SHOULD generate self-signed ECDSA P-256 certificates.”
- “Clients MUST accept any certificate chain that successfully completes the TLS 1.3 handshake in their TLS stack, and MUST NOT enforce Subject/Issuer/validity constraints for identity purposes.”
- If you truly require algorithm constraints for interoperability, then state: “Clients MUST reject non-(ECDSA P-256 or Ed25519).” (but then remove “accept any”).

### 8) **(H) DHT `getAll`/`dhtGet` “all available records” is not operationally defined**
**Problematic text:**
- “`getAll(key)`: Retrieve all values from reachable nodes”
- “returns all available records (`DhtResult[]`)”
- “Callers select the highest-sequence valid document from the results.”

**Why ambiguous/inconsistent:**
No minimum completeness requirements are defined (k-closest? quorum? timeouts? dedup rules?). Different “getAll” implementations will return different candidate sets, causing different “latest document” selection under churn.

**What two implementations might do differently:**
- Impl A queries 3 nodes and returns up to 3 values.
- Impl B queries k=20 closest nodes and returns up to 20 values.
Impl A can systematically miss the highest sequence and “stall” identity updates.

**Specific fix:**
Define baseline behavior, e.g.:
- “`dhtGet(key)` MUST query at least the k closest peers (k=20) or until a 2s deadline, whichever comes first, and return all distinct values discovered (dedup by exact byte equality).”
- Or define that `dhtGet` may be incomplete but then relax the MUST language around “select highest” (currently reads like correctness depends on completeness).

### 9) **(H) “Content-addressable storage” requirement contradicts described keying scheme**
**Problematic text:**
- “Implementations MUST use a DHT that provides: 1. **Content-addressable storage**: Keys are 32-byte SHA256 hashes”
- But keys are `SHA256(prefix || identifier)` (not hash of content)

**Why ambiguous/inconsistent:**
“Content-addressable” commonly means key = hash(content). Here key = hash(identifier namespace + identifier). The requirement wording can mislead implementers into designing a CAS layer (storing by value hash) instead of the required deterministic lookup by IID.

**What two implementations might do differently:**
- Impl A uses your namespace-derived key (correct for lookups).
- Impl B interprets “content-addressable” literally and stores under `SHA256(value)` and puts the IID inside the value.
Lookups fail across implementations.

**Specific fix:**
Replace with: “Fixed-length keyspace: DHT keys MUST be exactly 32 raw bytes (SHA-256 output). Keys for identity/device lookups are derived as specified in §DHT Key Encoding.”

### 10) **(H) Device index uses `name` but device document mandates `device_name` (schema divergence risk)**
**Problematic text:**
- Device doc note: “Field names MUST match exactly: `device_name` (not `name`)”
- Device index structure: `{ "did": "<did-1>", "name": "Phone", ... }`

**Why ambiguous/inconsistent:**
You explicitly warn against `name`, then immediately use `name` in another signed canonical structure. Implementers may “fix” it to `device_name` and break signature verification between implementations.

**What two implementations might do differently:**
- Impl A uses `name` in device index and signs it.
- Impl B uses `device_name` in device index and signs it.
They won’t verify each other’s device index signatures.

**Specific fix:**
Decide one field name and use it consistently. If you want `name` in the index, explicitly say:
- “Device index entries use the field `name` (string). This is distinct from device document field `device_name`.”

### 11) **(H) Device document signature verification allows “historical” signing keys but provides no mechanism to discover/identify them**
**Problematic text:**
- “Verify `signature_by_identity` field using identity's current (or historical) signing key (see signature scheme below)”

**Why ambiguous/inconsistent:**
There’s no key ID, no explicit list of historical keys, and no rule for how far back to try. This becomes critical after key rotation: existing device docs may become unverifiable depending on implementation choices.

**What two implementations might do differently:**
- Impl A verifies only against current signing key ⇒ device docs signed pre-rotation fail.
- Impl B tries to fetch older identity docs and iterates prior keys ⇒ accepts older device docs.
Divergent connectivity and device discovery.

**Specific fix:**
Pick a rule:
- **Simplest:** “Device docs and device index MUST always be signed by the identity’s *current* signing key; on key rotation, publisher MUST re-issue all device docs/index within N minutes. Verifiers MUST verify only against current key.”
- Or, if history is required: define an explicit `keys.signing.history[]` structure and key IDs.

### 12) **(M) Crockford Base32 canonicalization rule is internally ambiguous (reject vs normalize)**
**Problematic text:**
- “Case: Lowercase only (reject uppercase or normalize to lowercase)”

**Why ambiguous/inconsistent:**
This presents two incompatible behaviors as equivalent. Canonicalization affects DHT key derivation input and on-wire validation.

**What two implementations might do differently:**
- Impl A rejects uppercase IIDs/DIDs.
- Impl B lowercases and accepts them.
Users/peers may succeed in one and fail in the other; DHT keys could differ if one hashes the raw presented string.

**Specific fix:**
Make it a single MUST:
- “Identifiers MUST be transmitted in lowercase. Receivers MUST reject any identifier containing characters outside `[0-9a-hjkmnp-tv-z]` and MUST NOT accept uppercase.”

(Or explicitly allow normalization, but then also specify that DHT key derivation MUST use the normalized lowercase string.)
