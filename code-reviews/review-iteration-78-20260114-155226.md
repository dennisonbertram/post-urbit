## 1) Same-sequence IDOC conflict resolution: deterministic hash tiebreaker vs TOFU/manual  
**Severity: BLOCKING (B)** — different nodes will converge on different “current” identity docs under conflict.

**Conflicting text A (deterministic hash tiebreaker):**  
From `spec/00-shared/layer-integration.md` (Conflict Resolution, Normative):
> “**Same sequence, different content:** This indicates a bug or attack. Resolution:  
>  - Compute `h = SHA256(JCS(document_json))` for each document  
>  - Select the document with the **lexicographically smallest** hash (lowercase hex)  
>  - … This is a deterministic tie-breaker; all implementations will select the same document”

**Conflicting text B (explicitly forbids hash tiebreaker):**  
From `spec/02-identity-trust/identity-document-schema.md` (Conflict Resolution):
> “# Real conflict - **DO NOT auto-resolve with hash comparison**  
> (hash tiebreaker is gameable by attackers who control keys)…  
> Option 1: Prefer document you saw first (TOFU)…  
> … require manual resolution”

**What two implementations might do differently**
- Impl A (follows `layer-integration.md`) will auto-select the smallest-hash doc at the same sequence.
- Impl B (follows `identity-document-schema.md`) will keep first-seen or halt/flag conflict for manual resolution.
Result: different peers accept different “current” identity docs for the same IID+sequence → incompatible routing/endpoints, verification chains, device auth decisions.

**Proposed fix**
- Make **one** rule normative everywhere. Recommendation: align to the **security posture in `identity-document-schema.md`**.
  - In `layer-integration.md`, replace the “same sequence, different content → smallest hash wins” rule with:
    - “MUST NOT auto-resolve via hash tiebreaker; MUST enter conflict state; MAY apply first-seen TOFU locally; SHOULD notify operator/user; SHOULD attempt to fetch genesis + additional sources.”
  - If deterministic convergence is desired, explicitly scope it to **DHT storage nodes only** (not clients) and explain why clients still MUST treat as a conflict. Right now it reads like a client selection rule.

## 2) Device Index field name mismatch: `name` vs `device_name`  
**Severity: BLOCKING (B)** — signatures and parsing break because JCS depends on exact field names.

**Conflicting text A (`device_name`):**  
From `spec/00-shared/layer-integration.md` (Device Index Structure):
```json
{
  "devices": [
    { "did": "<did-1>", "device_name": "Phone", "last_seen": "<RFC3339>" }
  ],
  "signature": "<base64-signature-by-identity-signing-key>"
}
```
and:
> “**Note:** Device index entries use `device_name` (matching the device document field name).”

**Conflicting text B (`name`):**  
From `spec/06-rfcs/RFC-0001-identity-document.md` (§13.4 Device Index):
```json
{
  "devices": [
    {"did": "<did-1>", "name": "Phone", "last_seen": "<RFC3339>"}
  ]
}
```

**What two implementations might do differently**
- Impl A signs/verifies a device index containing `device_name`.
- Impl B signs/verifies a device index containing `name`.
Result: device index signature verification fails across implementations; device discovery becomes unreliable/interoperability breaks.

**Proposed fix**
- Choose one canonical schema (recommend `device_name` because it matches the device document and `layer-integration.md` already declares it canonical).
  - Update RFC-0001 §13.4 to use `device_name` (and add an explicit “MUST” field name requirement).
  - Optionally allow a **non-normative migration**: receivers MAY accept `name` as an alias for display only, but signature verification MUST be over the canonical `device_name` form (which implies producers must canonicalize before signing).

## 3) Identity update message schema mismatch: `document` vs `idoc` (base64 IDOC envelope)  
**Severity: BLOCKING (B)** — direct identity update propagation will fail between implementations.

**Conflicting text A (base64 IDOC envelope):**  
From `spec/00-shared/layer-integration.md` (IdentityUpdateMessage, Normative):
```ts
interface IdentityUpdateMessage {
  type: "identity_update";
  idoc: string;           // Base64 ... of IDOC envelope bytes
  sequence: string;
  sent_at: string;
}
```

**Conflicting text B (inline JSON document):**  
From `spec/02-identity-trust/key-rotation.md` (Propagation Message):
```json
{
  "type": "identity_update",
  "document": { <full identity document> },
  "urgency": "normal|urgent",
  "reason": "routine|suspected_compromise|device_migration"
}
```

**What two implementations might do differently**
- Impl A expects/sends `idoc` (base64 of **binary IDOC envelope**).
- Impl B expects/sends `document` (a JSON object).
Result: peers can’t parse each other’s identity update messages; identity rotation propagation breaks, leading to stale keys/endpoints and handshake failures.

**Proposed fix**
- Standardize on a single wire representation for identity updates.
  - Recommendation: keep `layer-integration.md`’s `idoc` (base64 IDOC envelope) and update `key-rotation.md` to match:
    - Replace `document` with `idoc` + optional `urgency`/`reason`.
    - If you want to keep human-readable JSON, explicitly add a new message type or a versioned union, e.g.:
      - v1: `idoc` only (normative)
      - v2: optional `document` for debugging, MUST be ignored for verification.
- Also update any TypeScript interfaces elsewhere that reference `document` to avoid drift.

## 4) “Identity document wire format” scope: IDOC envelope “for network transmission” vs handshake carrying JSON object  
**Severity: BLOCKING (B)** — an implementer can reasonably conclude the handshake must embed IDOC envelope bytes, conflicting with RFC-0002.

**Conflicting text A (implies IDOC envelope for all network transmission):**  
From `spec/02-identity-trust/identity-document-schema.md` (Wire Format):
> “**For network transmission**, Identity Documents are encoded as:  
> `Magic "IDOC" … Length … JCS-Canonical JSON …`”

**Conflicting text B (handshake carries JSON object):**  
From `spec/06-rfcs/RFC-0002-transport.md` (§5.6 ServerHello):
```json
{
  "identity_document": { /* IDOC per RFC-0001 */ },
  ...
}
```
(and similarly in `spec/01-transport-connectivity/peer-handshake.md`)

**What two implementations might do differently**
- Impl A reads identity-document-schema and sends identity docs as IDOC envelopes everywhere (including handshake), likely as base64 or binary.
- Impl B follows RFC-0002 and sends a JSON object in `identity_document`.
Result: handshake parsing fails (type mismatch), preventing connections.

**Proposed fix**
- Tighten wording in `identity-document-schema.md` to avoid overbroad “for network transmission”.
  - Replace with something like:
    - “**For DHT storage and binary transports**, identity documents MUST be encoded as the IDOC envelope…”
    - “**For JSON control-plane messages** (e.g., RFC-0002 handshake), identity documents are transmitted as JSON objects; signature verification operates on JCS(doc_without_signatures) derived from the parsed object.”
- Alternatively (larger change): update RFC-0002 to carry `identity_document_idoc` as base64 envelope bytes. But RFC-0002 is currently “authoritative”, so simplest is to narrow the schema doc language.

## 5) QUIC stream directionality contradiction: “all bidirectional” vs Bulk unidirectional  
**Severity: BLOCKING (B)** — stream opening rules differ; some stacks will reject peers.

**Conflicting text A (claims all streams are bidirectional):**  
From `spec/00-shared/layer-integration.md` (QUIC Stream Initiation Rules):
> “**All protocol streams are QUIC bidirectional streams.**”

**Conflicting text B (Bulk explicitly unidirectional):**  
From `spec/00-shared/layer-integration.md` (same table):
> “| Bulk (0x05) | … | Per-transfer (**unidirectional**) |”

Also consistent with:
- `spec/01-transport-connectivity/quic-integration.md`:
> “| **Bulk** | **Unidirectional** | Large data transfers … |”
- `spec/06-rfcs/RFC-0002-transport.md` (§6.1):
> “0x05 Bulk — **Unidirectional**”

**What two implementations might do differently**
- Impl A follows “all bidirectional” and opens Bulk as bidi.
- Impl B opens Bulk as uni and may reject bidi Bulk or never accept reads on it.
Result: Bulk transfers fail and may cause application errors/stream limits issues.

**Proposed fix**
- Edit `layer-integration.md` to say:
  - “Control/Identity/Message/Sync streams are bidirectional. Bulk streams are unidirectional.”
- Ensure “Multiplicity/Lifecycle” statements reflect uni streams (e.g., “each bulk transfer uses one unidirectional stream opened by the sender”).

## 6) Group sender key iteration indexing: explicit 1-indexed in RFC-0003 vs unspecified/ambiguous elsewhere  
**Severity: BLOCKING (B)** — a 0-index vs 1-index choice breaks group decryption.

**Conflicting/ambiguous text A (1-indexed, reject 0):**  
From `spec/06-rfcs/RFC-0003-messaging.md` (§3.4.4 Group Extension):
> “**Iteration Counter (Normative):**  
> - Sender Key Iteration is **1-indexed** …  
> - Value **0 is invalid; implementations MUST reject** group envelopes with `iteration = 0`”

**Conflicting/ambiguous text B (iteration=0 appears as a normal value; no explicit envelope rule):**  
From `spec/03-messaging-sync/group-messaging.md` (sender_key_share):
```json
{
  "type": "sender_key_share",
  "content": {
    ...
    "iteration": 0
  }
}
```
From `spec/03-messaging-sync/secure-envelope.md` (Group Header Extension):
> “│ Sender Key Iteration │ 4 bytes (big-endian) │”  
(no indexing rule given)

**What two implementations might do differently**
- Impl A (RFC-0003) treats iteration in the **PUSE group header extension** as starting at 1 and rejects 0.
- Impl B (reading group-messaging/secure-envelope only) may treat it as 0-indexed and emit `iteration=0` for the first group message.
Result: group messages fail to decrypt across implementations.

**Proposed fix**
- Add an explicit, normative statement to both:
  - `spec/03-messaging-sync/group-messaging.md`
  - `spec/03-messaging-sync/secure-envelope.md`
  stating:
  - “PUSE group header extension `iteration` is 1-indexed; first encrypted group message uses 1; receivers MUST reject 0.”
- Also clarify that `sender_key_share.content.iteration = 0` is a **state hint** (pre-first-message), not a value that ever appears in the PUSE header extension.

## 7) Genesis DHT record semantics: MUST+immutable vs SHOULD+long TTL  
**Severity: HIGH (H)** — likely divergence in bootstrap/TOFU behavior; interoperability impact is real but has fallbacks.

**Conflicting text A (MUST store, immutable, reject overwrites):**  
From `spec/00-shared/layer-integration.md` (Genesis Key Semantics, Normative):
> “Identity documents are stored under TWO DHT keys…  
> … `post-urbit:genesis:` … **Immutable**; once written, the genesis document MUST NOT be replaced…  
> DHT nodes MUST reject writes … if a document already exists…”

**Conflicting text B (only SHOULD store genesis; TTL “forever or 365 days”):**  
From `spec/06-rfcs/RFC-0001-identity-document.md` (§12.3):
> “For chain verification support, implementations **SHOULD** also store genesis documents…  
> TTL: **Forever (or very long, e.g., 365 days)**”

**What two implementations might do differently**
- Impl A requires genesis publication and enforces write-once semantics.
- Impl B may not publish genesis at all, or may accept genesis “refresh” writes, or treat TTL differently.
Result: genesis fetch-based bootstrap varies widely; some nodes may rely on genesis immutability guarantees that aren’t met.

**Proposed fix**
- Align RFC-0001 with the integration glue:
  - Change RFC-0001 §12.3 from SHOULD to MUST (publish genesis record).
  - Add explicit “write-once” behavior and rejection rules for `post-urbit:genesis:` overwrites.
  - Define TTL more precisely: e.g., “TTL SHOULD be >= 365 days; DHT nodes MUST treat existing genesis value as immutable regardless of TTL refresh attempts.”

## 8) Base32 canonicalization: “reject uppercase” vs “reject or normalize”  
**Severity: MEDIUM (M)** — should not happen on-wire, but inconsistent validators cause edge-case divergence.

**Conflicting text A (permits normalization):**  
From `spec/00-shared/layer-integration.md` (Crockford Base32, Normative):
> “Case: Lowercase only (**reject uppercase or normalize to lowercase**)”

**Conflicting text B (reject non-lowercase):**  
From `spec/06-rfcs/RFC-0002-transport.md` (§2.1):
> “**Decoding:** Accept lowercase only. Reject any character not in alphabet.”

Also consistent with `spec/02-identity-trust/identity-document-schema.md`:
> “Normalization: Always lowercase; **reject non-canonical forms**”

**What two implementations might do differently**
- Impl A accepts uppercase IIDs/DIDs on the wire by normalizing, while Impl B rejects.
This can lead to inconsistent acceptance of malformed peers, and signature inputs that include encoded identifiers could become inconsistent if the encoded form is ever used directly.

**Proposed fix**
- Clarify in `layer-integration.md`:
  - “On-wire MUST be lowercase and receivers MUST reject uppercase. UI/input layers MAY normalize prior to producing on-wire values.”
  - Remove “or normalize” from the normative on-wire rules.
