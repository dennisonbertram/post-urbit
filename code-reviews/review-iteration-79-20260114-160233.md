## Issues found in `spec/03-messaging-sync/sync-protocol.md` (Iteration 79 — DEEP DIVE)

### 1) (B) `DocumentId` is sometimes a string, sometimes *exactly 32 raw bytes*
**Problematic text**
> ```ts
> type DocumentId = string;
> ```
>  
> **CBOR Schemas for Sync Messages:**
> ```
> "document_id": bstr,      // 32 bytes
> ```
>  
> **Document ID Format:**
> > “Document IDs are always 32 bytes.”

**Ambiguity / inconsistency**  
The spec simultaneously defines `DocumentId` as a `string` and as an on-wire `bstr` of length 32. This will directly affect encoding, signature verification, Merkle hashing, and message parsing.

**How two implementations diverge**
- Impl A sends `document_id` as CBOR `text` (a UUID string or hex string).
- Impl B sends `document_id` as CBOR `bstr`(32) per schema. They won’t interoperate.

**Specific fix**
- Make `DocumentId` **bytes-first** and define textual forms only for logs/JSON:
  - Replace `type DocumentId = string;` with:
    ```ts
    type DocumentIdBytes = Uint8Array; // MUST be length 32
    type DocumentIdString = string; // hex for display/JSON only
    ```
- Add a normative rule: **All wire messages MUST use `bstr` length 32 for `document_id`**. If a JSON form exists, it MUST be hex (64 chars) or base64url (explicitly pick one).

### 2) (B) `IdentityIdentifier` / `origin` representation is inconsistent (string vs 20-byte raw IID)
**Problematic text**
> ```ts
> origin: IdentityIdentifier;  // Who created this operation
> ```
>  
> **CBOR schema**
> ```
> "origin": bstr,           // 20 bytes (raw IID)
> ```
>  
> **HLC**
> ```ts
> origin: IdentityIdentifier;
> ...
> return a.origin.localeCompare(b.origin);
> ```

**Ambiguity / inconsistency**  
On-wire `origin` is specified as 20 raw bytes, but other parts treat it as a string (and compare it with `localeCompare`, which is not a bytewise canonical ordering and depends on encoding/normalization assumptions).

**How two implementations diverge**
- Impl A stores `origin` internally as Crockford Base32 string and uses Unicode collation rules for tie-breaks.
- Impl B stores `origin` as 20 raw bytes and compares lexicographically by bytes. Their LWW and HLC ordering decisions can differ, causing permanent state divergence.

**Specific fix**
- Define `IdentityIdentifier` normatively:
  - Wire form: **`iid_raw` = 20-byte `bstr`**
  - Display/JSON form: **Crockford Base32 string** (or whatever you choose, but specify one)
- Replace `localeCompare` tie-breakers with **bytewise lexicographic compare of the 20 raw bytes**:
  ```ts
  // compare iid_raw bytes, not strings
  ```

### 3) (B) `OperationId` format conflicts: “string”, “SHA256(...)”, CBOR requires 32-byte `bstr`, and later “hex string”
**Problematic text**
> ```ts
> type OperationId = string;  // SHA256(origin || timestamp || operation_bytes)
> ```
>  
> **CBOR schema**
> ```
> "id": bstr,               // 32 bytes
> ```
>  
> **Operation ID Calculation**
> ```
> operation_id_bytes = SHA256(...)
> operation_id_string = hex(operation_id_bytes)
> ```

**Ambiguity / inconsistency**  
You define `OperationId` as a string, but the wire schema uses 32 raw bytes. Later you define both raw bytes and hex string. Without a single normative “on-wire vs API vs JSON” rule, implementations will mismatch.

**How two implementations diverge**
- Impl A uses hex string everywhere (including CBOR `text`).
- Impl B uses raw 32-byte `bstr` on wire and only hex for logs.

**Specific fix**
- Define:
  - `operation_id` on wire: **`bstr` length 32**
  - JSON/display: **hex string length 64**
- Update all earlier type aliases and comments to match:
  ```ts
  type OperationIdBytes = Uint8Array; // 32
  type OperationIdHex = string; // 64 hex chars
  ```

### 4) (B) `dependencies` exist in the wire schema but are NOT included in operation-id hashing or signatures
**Problematic text**
> **CBOR schema**
> ```
> "dependencies": [bstr],   // array of operation IDs
> ```
>  
> **Operation ID Calculation**
> ```
> SHA256(origin || timestamp_bytes || operation_bytes)
> ```
>  
> **Signature Construction**
> ```
> signature_input = concat(..., operation_bytes)
> ```
> (no dependencies included)

**Ambiguity / inconsistency**  
Dependencies affect causal application (“Operations are applied only after dependencies are satisfied.”), but they are not authenticated. That means a relay/peer can rewrite dependencies without breaking signature validation, causing different replicas to queue/apply in different orders or deadlock.

**How two implementations diverge**
- Impl A treats `dependencies` as untrusted metadata and ignores it, relying on CRDT commutativity.
- Impl B enforces dependencies strictly and may stall/queue based on them. A malicious or buggy peer can cause impl B to behave differently than impl A.

**Specific fix**
- Make dependencies part of the signed payload and operation-id:
  - Define `dependencies_bytes` as canonical encoding of the dependency set:
    - either: sorted lexicographically by 32-byte value, then concatenated
    - or: deterministic CBOR array of `bstr` sorted ascending
  - Update:
    ```
    operation_id_bytes = SHA256(origin || timestamp_bytes || operation_bytes || dependencies_bytes)
    signature_input = concat(domain_sep, operation_id_bytes, document_id, timestamp_bytes, operation_bytes, dependencies_bytes)
    ```
- Also specify whether `dependencies` is a **set** (recommended) and mandate sorting.

### 5) (B) What exactly is `operation_bytes`? “Use the encoded bytes” vs “CBOR-encoded CRDT operation”
**Problematic text**
> ```
> "operation": bstr,        // CBOR-encoded CRDT operation
> ```
>  
> **CRDT Operation CBOR**
> > “The encoded bytes are used in `operation_bytes` for signatures.”

**Ambiguity / inconsistency**  
When verifying signatures, should a receiver:
- Use the `bstr` bytes as-is (treat it as opaque), or
- Decode then re-encode deterministically and use the re-encoded bytes?

These two choices yield different `operation_id`/signature inputs.

**How two implementations diverge**
- Impl A signs/verifies the **exact bytes** carried in the `operation` bstr.
- Impl B decodes and re-encodes to canonical CBOR before hashing/signing. It will reject operations that impl A accepts (or vice versa).

**Specific fix**
Add a normative rule:
- **`operation_bytes` is exactly the byte string carried in `SyncOperation.operation` (no re-encoding permitted for hashing/signature).**
- Additionally require: sender MUST canonical-encode it initially (per deterministic CBOR rules), and receivers MAY reject if it is not canonical (but must still hash the original bytes if verifying?—pick one consistent approach; simplest is “reject if not canonical, and hash the received bytes”).

### 6) (B) Merkle “efficient sync” protocol is described but not actually specified on the wire (no subtree exchange messages)
**Problematic text**
> Sync process:
> 1. Exchange root hashes
> 2. If different: exchange subtree hashes recursively
> 3. Identify missing operations efficiently
>
> **Wire Format for SYNC_REQUEST:**
> ```
> "depth": <tree depth for subtree exchange>
> ```
>  
> Message types list includes no “subtree hash exchange” message type.

**Ambiguity / inconsistency**  
The spec claims recursive subtree-hash exchange, but provides only:
- `SYNC_REQUEST` with root+depth
- `SYNC_OFFER` with a list of `operation_ids`

There is no defined message to carry subtree hashes, leaf ranges, or proofs. A peer cannot derive “what ops the requester is missing” from only a remote Merkle root.

**How two implementations diverge**
- Impl A ignores Merkle recursion and sends **all** op IDs in `SYNC_OFFER` when roots differ (inefficient but functional).
- Impl B attempts recursive subtree comparison (as text suggests) and waits for undefined messages, failing to sync.

**Specific fix**
Choose one of:
1) **Define the missing wire messages** (recommended):
   - Add message type(s), e.g. `SYNC_MERKLE` / `SYNC_MERKLE_REPLY` that exchange `(level, index, hash)` tuples or range-hash vectors, and specify the recursion algorithm precisely.
2) Or **delete recursion wording** and redefine `SYNC_OFFER`:
   - e.g., `SYNC_REQUEST` includes a compact “have” summary (Bloom filter / interval vector / prefix tree), making it possible to compute missing ops without subtree exchange.

Until one is done, independent implementations will not converge on behavior.

### 7) (B) Merkle tree construction is underspecified (padding, “complete” meaning, leaf count, depth meaning)
**Problematic text**
> “The tree is a complete binary tree, padded with empty hashes (...) if needed.”
>
> “Operations are ordered by HLC timestamp.”

**Ambiguity / inconsistency**  
Key missing details needed for deterministic Merkle roots:
- Is the tree padded to **next power of two** leaves? Or to a fixed depth? Or to exactly `2^depth`?
- What is `depth` precisely: max depth, actual depth, or request recursion limit?
- Leaf ordering: HLC ties resolved how? (bytewise origin? operation_id tie-breaker?)

**How two implementations diverge**
- Impl A pads to next power-of-two and computes depth = ceil(log2(n)).
- Impl B pads to a fixed depth agreed per document (e.g., 32), yielding different roots for same op set.

**Specific fix**
Add a normative algorithm section:
- Define leaf ordering key: `(timestamp.physical, timestamp.logical, origin_raw_bytes, operation_id_bytes)` ascending.
- Define leaf count `N`, tree size `M = next_power_of_two(N)` (or fixed `M`; pick one).
- Define padding: append `M-N` empty leaves, each hash = `SHA256("post-urbit:merkle-empty:")`.
- Define depth as `log2(M)` and specify whether `depth` field is:
  - MUST equal the computed depth, or
  - MUST be omitted, or
  - is a request limit (and how peers respond).

### 8) (B) Transport framing is not interoperably specified for QUIC streams (4-byte length vs QUIC reality)
**Problematic text**
> “On QUIC sync stream (type 0x04)… **Transport Frame:** Length (big-endian) 4 bytes”
>
> “using standard transport framing (see RFC-0002 §6.3)”

**Ambiguity / inconsistency**  
QUIC streams are byte streams; QUIC does not impose “4-byte big-endian length” by default. Since RFC-0002 is not included here, implementers won’t know whether:
- framing is required
- length is uint32 BE or QUIC varint
- messages may be coalesced, fragmented, etc.

**How two implementations diverge**
- Impl A writes `type_byte || cbor` without a length prefix (treating QUIC stream boundaries as message boundaries).
- Impl B expects a 4-byte big-endian length prefix and blocks/parses incorrectly.

**Specific fix**
Make this document self-contained and normative:
- State explicitly: “Within QUIC stream 0x04, each sync message MUST be framed as: `u32be length` + `payload`.”
- Or choose QUIC varint: “`varint length` + payload” and specify exactly.
- Define maximum length, handling of partial reads, and whether multiple frames can be concatenated.

### 9) (B) Encrypted sync is defined but has no interoperable on-wire signaling / schema integration
**Problematic text**
> “Operations (the `operation` field) encrypted with document key using ChaCha20-Poly1305”
>
> ```ts
> interface EncryptedOperation { ... encrypted_operation ... nonce ... }
> ```
>  
> But **CBOR schema for SYNC_OPERATIONS** is:
> ```
> "operations": [SyncOperation]
> ```

**Ambiguity / inconsistency**  
It’s unclear whether encrypted documents:
- still use `SyncOperation.operation` but with ciphertext bytes inside, or
- switch to an `EncryptedOperation` object, and how a receiver knows which to parse.

Also `EncryptedOperation` signature text:
> “signature: Over id || document_id || timestamp || encrypted_operation”
does not mention nonce or domain separator, and conflicts with earlier signature scheme.

**How two implementations diverge**
- Impl A encrypts `operation` bytes in-place (still a `SyncOperation`) and signs using the plaintext scheme.
- Impl B sends a different CBOR map shape (`EncryptedOperation`) and signs a different input. They won’t parse/verify each other.

**Specific fix**
Pick one unified approach and specify it on wire:
- Option A (simpler): **Keep `SyncOperation` shape** and define:
  - `operation` contains either canonical CBOR plaintext OR AEAD ciphertext
  - add fields: `"enc": true`, `"nonce": bstr(12)`, `"key_version": uint`
  - update operation-id/signature input to include `enc flag`, `nonce`, and ciphertext bytes
- Option B: add a new message type `SYNC_ENCRYPTED_OPERATIONS` with a distinct schema, and specify negotiation/detection.

### 10) (B) CBOR “major types 0–5 only” forbids booleans, but application examples include booleans
**Problematic text**
> “Type constraints: Use CBOR major types 0-5 only (no tags, no special values except null)”
>
> Example:
> ```ts
> interface TodoItem { ... completed: boolean; }
> ```

**Ambiguity / inconsistency**  
CBOR booleans are major type 7 (simple values). Your normative constraint forbids them, implying apps must encode booleans as integers/strings—yet the spec never defines that mapping.

**How two implementations diverge**
- Impl A encodes booleans as CBOR `true/false` (major type 7).
- Impl B encodes booleans as `0/1` integers to comply. Their operation_bytes differ → operation_id/signatures differ.

**Specific fix**
- Either relax the rule: allow major type 7 for `true`, `false` (and maybe float disallowed still).
- Or define a normative mapping for application scalar types (but that’s more complex). The common fix is: **permit booleans**.

### 11) (B) “CRDT Operation CBOR schema” is referenced but not present; implementers can’t encode the same operations
**Problematic text**
> “Each CRDT type defines its own CBOR schema (see individual CRDT type definitions).”

**Ambiguity / inconsistency**  
This repository (as provided) contains only this file; there are no “individual CRDT type definitions.” Without normative schemas, independent implementations will produce different `operation_bytes`, breaking operation_id/signatures and merge semantics.

**How two implementations diverge**
- Impl A encodes OR-Set add as `{ "op":"add","e":<...>,"tag":<...> }`.
- Impl B encodes it as `[0, <e>, <tag>]`. Different bytes → different hashes → no interoperability.

**Specific fix**
- Add a section in this document (or referenced files that actually exist) defining **normative CBOR schemas** for each supported CRDT operation, including:
  - field names/types
  - canonical ordering requirements
  - how to encode element values (esp. strings/bytes/ints/bools)
  - how to encode deletions/tombstones

### 12) (H) `SYNC_SUBSCRIBE.from_hlc` resume semantics (inclusive/exclusive) are unspecified
**Problematic text**
> ```
> "from_hlc": Timestamp     // resume from this timestamp
> ```

**Ambiguity / inconsistency**  
“Resume from” can mean:
- include ops with timestamp == from_hlc (inclusive), or
- start strictly after it (exclusive).
This impacts duplicates/missed ops.

**How two implementations diverge**
- Impl A sends ops with `ts >= from_hlc`.
- Impl B sends ops with `ts > from_hlc`. A subscriber may miss the boundary op or receive duplicates.

**Specific fix**
- Define it normatively, e.g.:
  - “Server MUST send operations with `(hlc_compare(op.ts, from_hlc) > 0)`” (exclusive)
  - and define how clients de-dup (by op id).

### 13) (H) “Total ordering” rule is not implementable as written; topological tie-break is underspecified
**Problematic text**
> ```
> apply_order = causal_order || hlc_order
> ```
> “This ensures all replicas apply operations in the same order.”

**Ambiguity / inconsistency**  
To get identical order across replicas you must specify:
- how to compute a deterministic topological order when multiple ops are concurrently ready
- what tie-breaker to use (HLC? op id?) and exact comparison

**How two implementations diverge**
- Impl A uses “process ready queue sorted by HLC”.
- Impl B uses “FIFO arrival order among ready ops” (still causally valid). Results can diverge if CRDT semantics aren’t fully commutative for all operations.

**Specific fix**
Specify:
- Maintain a set of “ready ops” (deps satisfied).
- Always pick next op by sorting ready ops by `(timestamp.physical, timestamp.logical, origin_raw_bytes, operation_id_bytes)` ascending.

### 14) (M) OR-Set `UniqueTag` format is informal and can lead to incompatible tags
**Problematic text**
> `type UniqueTag = string;  // origin_iid + lamport_counter`

**Ambiguity / inconsistency**  
“origin_iid + lamport_counter” doesn’t specify encoding, separator, width, or whether lamport is decimal/string/binary.

**How two implementations diverge**
- Impl A uses `"IID:counter"` string.
- Impl B uses raw bytes concatenation and then base64. Tags won’t match → removes won’t work.

**Specific fix**
Define tag as bytes, not string:
- `UniqueTag = bstr(24)` where it is `origin_raw(20) || lamport_u32be(4)`.
- Or if it must be string, specify exact format (e.g., base32(iid_raw) + ":" + decimal counter) and require canonical form.
