## Cross-document consistency review (Iteration 80) — focus on Iterations 77–79 fixes

### 1) Type representations (DocumentId, OperationId, IdentityIdentifier) — **bytes on wire; hex/base32 for display**

**B1 — “on wire” IID/DID encoding contradicts the RFC wire formats**
- **Docs:** `spec/00-shared/layer-integration.md` (“Global Conventions / Encoding” table) vs `spec/06-rfcs/RFC-0002-transport.md` (PURL), `spec/06-rfcs/RFC-0003-messaging.md` (PUSE), `spec/03-messaging-sync/sync-protocol.md` (CBOR)
- **Problem:** `layer-integration.md` says **“IID/DID on wire = 32-char Base32”**, but the actual binary wire formats use **raw bytes**:
  - PUSE: sender/recipient IID are **20 raw bytes**
  - PURL: destination IID is **20 raw bytes**
  - Sync CBOR: `origin` is **20-byte bstr**
- **Why BLOCKING:** “on wire” is used normatively in the glue doc; an implementer could incorrectly encode identifiers as Base32 strings inside binary protocols.
- **Fix:** In `layer-integration.md`, replace the table row with an unambiguous split:
  - **Binary wire formats:** IID/DID = **20-byte raw**
  - **Text/JSON protocols & display:** IID/DID = **32-char Crockford Base32**
  - Avoid the overloaded phrase “on wire” unless qualified as “on-wire JSON” vs “on-wire binary”.

**B2 — Messaging/Sync interfaces mix string IDs with a “normative wire mapping” that expects bytes**
- **Docs:** `spec/03-messaging-sync/interfaces.md` vs `spec/03-messaging-sync/sync-protocol.md`
- **Problem:** `interfaces.md` declares:
  - `type DocumentId = string;`
  - `interface SyncOperation { id: string; ... dependencies: string[]; ... }`
  - Yet it also includes an **“API↔Wire Encoding Mapping (Normative)”** stating DocumentId/OperationId are **CBOR bstr** of fixed lengths.
- **Why BLOCKING:** This file is positioned as the layer’s “complete API surface” and also claims normative wire mapping; two implementers can legitimately diverge (string CBOR vs bstr CBOR) when implementing sync stream payloads.
- **Fix (minimal, keeps API ergonomics):**
  1. Add explicit display types and use them in the interfaces:
     - `type DocumentId = string /* UUID canonical string OR 64-hex */`
     - `type OperationId = string /* 64-char hex */`
     - `dependencies: OperationId[]`
  2. Add explicit wire-only types:
     - `type DocumentIdBytes = Uint8Array /* len=32 */`
     - `type OperationIdBytes = Uint8Array /* len=32 */`
     - `type IdentityIdentifierBytes = Uint8Array /* len=20 */`
  3. State clearly: **Network sync stream (0x04) uses the wire types**; the TS interfaces are app/in-memory only.

**H1 — Host API (WASM↔host CBOR) uses string IDs without pinning the string encoding**
- **Docs:** `spec/04-app-runtime/api-surface.md` (`sync.create_document`, `sync.apply_operation`) vs `spec/03-messaging-sync/interfaces.md` mapping
- **Problem:** Host API defines `document_id: string` / `operation_id: string` but does not normatively say whether these strings are UUID, 64-hex, etc. Meanwhile the sync layer mapping implies UUID-string conventions for DocumentId and 64-hex for OperationId.
- **Impact:** App authors and host implementers may choose different encodings → ecosystem friction and interop bugs at the app boundary (even if network sync is correct).
- **Fix:** In `api-surface.md`, specify:
  - `document_id` string format (e.g., **UUID canonical string** for UUID-backed docs, or allow `sha256:<hex>` explicitly)
  - `operation_id` string format (**64 lowercase hex**)
  - Reference the `03-messaging-sync/interfaces.md` mapping section as authoritative for display formats.

### 2) Signature and hash inputs — must include dependencies consistently

**M1 — Sync “operation_bytes” handling is correctly specified in sync-protocol, but not mirrored in the TS interfaces**
- **Docs:** `spec/03-messaging-sync/sync-protocol.md` vs `spec/03-messaging-sync/interfaces.md`
- **What’s good:** `sync-protocol.md` includes `dependencies_bytes` in both `operation_id` and signature input; it also mandates dependency sorting.
- **Gap:** The TS `SyncOperation.operation: CRDTOperation` shape doesn’t warn that the *hashed/signed bytes are the exact CBOR bstr carried on wire*, and MUST NOT be “decode + re-encode” at verification time.
- **Impact:** Confusion more than divergence (because `sync-protocol.md` is clear), so **Medium**.
- **Fix:** Add a short normative note in `interfaces.md` SyncOperation: when producing/verifying network operations, hashing/signing uses the **exact encoded CBOR bytes** and **sorted dependencies**.

### 3) Stream directionality — Bulk unidirectional; others bidirectional

**M2 — Transport API surface doesn’t enforce Bulk unidirectionality**
- **Docs:** `spec/00-shared/layer-integration.md`, `spec/06-rfcs/RFC-0002-transport.md` (clear) vs `spec/01-transport-connectivity/interfaces.md`
- **Problem:** `TransportService.openStream(connectionId, type)` doesn’t constrain direction; `Stream.direction` even allows `'bidirectional'` for any type.
- **Impact:** Likely implementers still follow RFC-0002, but this is a foot-gun.
- **Fix:** Add normative constraint in `interfaces.md`:
  - If `type === 'bulk'`, `openStream` MUST open a **unidirectional outbound** stream; inbound bulk streams are receive-only.
  - Optionally expose `openBulkStreamUnidirectional()` or add `openStream(connectionId, type, directionHint)` with constraints.
