Below are the remaining spec issues in **spec/06-rfcs/RFC-0001-identity-document.md** that are likely to cause **incompatible implementations**. I’m focusing on wire formats, signature inputs, canonicalization, key/field encodings, and cross-reference consistency.

---

## Issue 1 (B): IID allowed-character rule is self-contradictory and the regex/range is wrong

**Problematic text (quotes)**

- §3.2:
  > Alphabet | Crockford Base32: `0123456789abcdefghjkmnpqrstvwxyz`  
  > Excluded chars | `i`, `l`, `o`, `u`

- §3.3:
  > Reject IIDs containing characters outside `0-9a-hj-km-np-tv-z`

**Ambiguity / inconsistency**

The character-class/range `0-9a-hj-km-np-tv-z` **includes forbidden letters**:
- `n-p` includes `o`
- `t-v` includes `u`

So §3.3 contradicts §3.2’s “excluded chars”. This will directly change which IIDs are considered valid.

**What two implementations might do differently**

- Impl A follows §3.2 alphabet strictly and rejects `o` and `u`.
- Impl B follows §3.3 range and accepts IIDs containing `o` and/or `u`.

**Specific fix**

Replace the range with an explicit, correct canonical regex and make it normative:

> Implementations MUST reject IIDs that do not match:  
> `^[0-9a-hjkmnpqrstvwxyz]{32}$`

(And delete the misleading `0-9a-hj-km-np-tv-z` text entirely.)

## Issue 2 (B): IID case normalization contradicts “reject uppercase” and will split validators

**Problematic text (quotes)**

§3.3:
> Normalize to lowercase before comparison  
> Reject non-canonical forms (e.g., uppercase)

**Ambiguity**

“Normalize to lowercase before comparison” implies you might accept uppercase input (by normalizing), but “Reject … uppercase” implies you must not accept it.

**What two implementations might do differently**

- Impl A lowercases first and accepts uppercase IIDs in received documents (treats it as equivalent).
- Impl B rejects any IID containing uppercase characters in received documents.

**Specific fix**

Decide one policy and state it unambiguously. For wire/doc validity, the safest is strict:

> In IDOC JSON, `iid` MUST be lowercase and MUST match `^[0-9a-hjkmnpqrstvwxyz]{32}$`.  
> Verifiers MUST reject documents with non-lowercase IIDs.  
> (User-interface input MAY be normalized, but that is outside this wire spec.)

## Issue 3 (B): Updated-document “authorization” rule is ambiguous when the signing key did NOT change

**Problematic text (quote)**

§7.2 step 6:
> **Authorization** (one of the following):  
> - **Key continuity**: `signatures.previous` valid with previous known signing key  
> - **Recovery**: `recovery_proof` validates per Section 9

**Ambiguity**

For routine updates where the signing key remains the same, there may be **no meaningful `signatures.previous`**, and recovery is not involved. The spec doesn’t explicitly say that “no key change” requires no extra authorization beyond `signatures.current`.

§8.2 *implies* this (“If signing key changed, previous signature required”), but §7.2 reads as if **every** update must satisfy either `signatures.previous` or recovery.

**What two implementations might do differently**

- Impl A: accepts updates with unchanged signing key using only `signatures.current`.
- Impl B: rejects such updates because `signatures.previous` is missing/null and recovery_proof absent.

**Specific fix**

Amend §7.2 to explicitly branch on whether the signing key changed compared to the prior accepted document:

> Authorization rules for `sequence > 0`:
> - If `keys.signing.current` is byte-identical to the prior accepted document’s `keys.signing.current`, then authorization is satisfied by a valid `signatures.current` alone.
> - If `keys.signing.current` differs, then the update MUST contain either:
>   - `signatures.previous` verifiable by the prior accepted signing key, OR
>   - a valid `recovery_proof` per §9.  
>   In this case `signatures.previous` MUST be `null`/absent when recovery is used (pick one encoding and require it).

(Also specify whether “absent” vs explicit `null` is permitted; see Issue 5.)

## Issue 4 (B): Key rotation signing input contradicts the canonical signing algorithm

**Problematic text (quote)**

§8.1 step 5:
> Sign with BOTH keys:  
> - `signatures.current = Sign(K_new_private, JCS(doc))`  
> - `signatures.previous = Sign(K_old_private, JCS(doc))`

But §6.1 says:
> 1. Remove the `signatures` field entirely  
> 2. Apply JCS canonicalization …

And §8.2 verify_rotation uses:
> `canonical_json = jcs(without_signatures(new_doc))`

**Ambiguity**

Is the signature over `JCS(doc)` (including signatures) or `JCS(doc_without_signatures)`? Those are different bytes and will not verify each other.

**What two implementations might do differently**

- Impl A signs the document *including* signatures (or with an empty `signatures` placeholder).
- Impl B signs the document with the `signatures` field removed (per §6.1 / §8.2).

**Specific fix**

Change §8.1 to explicitly reference the §6.1 algorithm and define `signature_input` identically everywhere:

> Let `payload = ASCII("post-urbit:idoc:v1:") || JCS(idoc_without_signatures)` where `idoc_without_signatures` is the JSON object with the top-level member `"signatures"` removed.  
> Then:
> - `signatures.current = Ed25519_Sign(K_new_private, payload)`
> - `signatures.previous = Ed25519_Sign(K_old_private, payload)`

(And remove the ambiguous `JCS(doc)` wording.)

## Issue 5 (B): History entry field types/encodings are underspecified (string vs number), which changes JCS bytes

**Problematic text (quotes)**

§4.4 Signing Key History Entry:
```json
{
  "key": "<base64-ed25519-pubkey>",
  "valid_from": "<sequence-number>",
  "valid_until": "<sequence-number>",
  "expires_at": "<RFC3339-timestamp>"
}
```

§4.2 defines top-level `sequence` as:
> `sequence` | string | Decimal uint64 …

But `valid_from` / `valid_until` do not state whether they are JSON strings or JSON numbers.

**Ambiguity**

If one encoder uses `"valid_from": "12"` (string) and another uses `"valid_from": 12` (number), JCS output differs, therefore signatures differ. Verifiers that enforce schema may disagree on validity.

**What two implementations might do differently**

- Impl A treats `valid_from` as a JSON string matching the same regex as `sequence`.
- Impl B treats `valid_from` as a JSON number.

**Specific fix**

Explicitly specify the JSON types and constraints (recommend aligning with `sequence` as string to avoid 64-bit portability issues):

> `valid_from` and `valid_until` MUST be JSON strings matching the `sequence` regex in §6.4 and representing uint64 decimal values.

Also add a table for history entry fields (like §4.2) and state verifiers MUST reject incorrect JSON types.

## Issue 6 (B): DHT/bootstrapping chain verification is internally inconsistent (fetch-by-sequence is used but not specified/storable)

**Problematic text (quotes)**

§7.3 pseudocode:
```python
genesis = dht_fetch_sequence(iid, sequence=0)
...
latest = dht_fetch_latest(iid)
...
verify_chain(genesis, latest)
```

But §12 only defines storage keys for:
- latest:
  > DHT Key: SHA256("post-urbit:identity:" || iid)
- genesis:
  > DHT Key: SHA256("post-urbit:genesis:" || iid)

There is **no** specified DHT keyspace for `sequence=N` for N>0.

Also §7.3 says:
> If sequence gap exists:  
> - The latest document's `keys.signing.previous` MUST match a key in the chain  
> - The `signatures.previous` MUST be valid with that key

…but “the chain” is not concretely defined in a way that can be reconstructed given only {genesis, latest}.

**Ambiguity**

Two independent implementers cannot know whether:
- The DHT is required to store every sequence document,
- Or chain verification is intended to work with only latest+genesis (which generally cannot prove multi-rotation continuity without additional proofs),
- Or “chain” means “whatever keys are in `history[]`” (which is self-asserted and not cryptographically linked unless intermediate documents exist).

**What two implementations might do differently**

- Impl A implements additional per-sequence DHT records to make `dht_fetch_sequence` work and verifies full sequence-by-sequence signature continuity.
- Impl B only stores latest+genesis (per §12) and either:
  - cannot implement `verify_chain` as intended, or
  - invents a “chain” meaning (e.g., trusting `history[]`), leading to different acceptance/rejection.

**Specific fix**

Pick one interoperable design and specify it normatively. Two viable options:

### Option A (recommended): define per-sequence DHT keys
Add to §12:

- **Per-sequence record**
  - DHT Key: `SHA256("post-urbit:identity-seq:" || iid || ":" || sequence)`
  - DHT Value: IDOC envelope for that exact `sequence`
  - TTL: long (e.g., 365 days) or policy-defined minimum retention window

Then update §7.3 “Validate chain” to be concrete:

> To validate an update from genesis to sequence S, fetch documents for sequences `0..S` (or until missing), verify each document per §7.1/§7.2, and ensure each step either maintains the same signing key or provides a valid `signatures.previous` (or recovery) linking to the immediately prior accepted doc.

### Option B: remove chain verification and make TOFU explicit
If you truly only store latest+genesis, then remove/replace the “verify_chain” language and state:

> Bootstrap verification can only prove binding of IID↔genesis and validity of the latest document’s self-signature. Continuity across key rotations cannot be proven without intermediate documents; implementations MAY apply TOFU for continuity.

Right now the spec sits between these and will fork implementations.

## Issue 7 (B): Recovery attestation verification key selection is underspecified (current vs historical trustee keys)

**Problematic text (quotes)**

§9.3:
> Sign with trustee's current signing key

§9.5 pseudocode:
> Verify trustee signature … using `trustee_doc['keys']['signing']['current']`

**Ambiguity**

If a trustee rotates their signing key after issuing an attestation, verifying only against the trustee’s *current* key will fail. Other implementations may try previous/history keys (like §7.5 describes for PUSE messages), leading to different recovery outcomes.

**What two implementations might do differently**

- Impl A verifies attestations only with trustee’s current signing key at verification time → recovery may fail spuriously.
- Impl B verifies attestations against trustee current + previous + non-expired history keys → recovery succeeds.

**Specific fix**

Make attestation verification follow a specified key search order (reuse §7.5 logic) and specify which trustee IDOC to fetch:

> To verify a recovery attestation, the verifier MUST fetch the trustee’s latest IDOC (or otherwise trusted highest-sequence IDOC) and MUST attempt verification using:
> 1) `keys.signing.current`, then  
> 2) `keys.signing.previous` (if present), then  
> 3) each `keys.signing.history[].key` whose `expires_at` has not passed.  
> The attestation is valid if any of these keys verifies the signature.

(Optionally: require that the trustee IDOC used is itself verified to its genesis unless the implementation is explicitly operating in TOFU mode.)

## Issue 8 (B): Duplicate JSON object keys are not explicitly forbidden/rejected (parser differences cause divergent verification/security issues)

**Problematic text (quote)**

No explicit prohibition exists; §6.3 lists JCS rules but does not say what to do with duplicate member names.

**Ambiguity**

Different JSON parsers handle duplicate keys differently (“first wins”, “last wins”, “error”). JCS (RFC 8785) assumes a deterministic JSON data model; duplicates break determinism and can enable signature confusion.

**What two implementations might do differently**

Given:
```json
{"iid":"good...","iid":"evil...", ...}
```
- Impl A keeps the first `iid` and verifies against it.
- Impl B keeps the last `iid` and verifies against that.
- Impl C rejects as malformed.

**Specific fix**

Add a normative rule near §6.1/§6.3:

> IDOC JSON MUST NOT contain duplicate object member names at any level.  
> Implementations MUST reject documents containing duplicate keys before signature verification.

(Also consider stating “MUST be strict RFC 8259 JSON; no NaN/Infinity”.)

## Issue 9 (H): “Signature is over the literal JSON as received” contradicts JCS signing and can mislead implementers

**Problematic text (quote)**

§6.6:
> The signature is over the literal JSON as received

**Ambiguity**

Elsewhere, the spec clearly defines signing over `JCS(doc_without_signatures)`, which is *not* the “literal JSON bytes received” (whitespace/key order/etc are normalized).

**What two implementations might do differently**

- Impl A signs/verifies using raw received bytes (or a non-JCS normalization).
- Impl B signs/verifies using RFC 8785 JCS output (as intended).

**Specific fix**

Replace that sentence with:

> The signature is over the JCS-canonicalized JSON data model **containing exactly the members present in the received document** (minus the removed signature field), i.e., defaults MUST NOT be inserted prior to canonicalization.

## Issue 10 (H): Envelope JSON canonicalization requirement is not paired with a receiver rule (accept/reject), causing ecosystem splits

**Problematic text (quote)**

§6.2:
> The JSON inside IDOC envelopes (Section 11) MUST also be JCS-canonicalized for the **full document including signatures**.

**Ambiguity**

This reads like a hard validity requirement, but the spec never says whether receivers:
- MUST reject non-canonical envelope JSON, or
- MAY accept and re-canonicalize.

Since signature verification doesn’t require the envelope body itself to already be canonical (verifiers canonicalize internally), different nodes may enforce differently.

**What two implementations might do differently**

- Impl A (strict): rejects any envelope whose body bytes are not exactly JCS canonical.
- Impl B (lenient): accepts any valid JSON and proceeds.

**Specific fix**

Add a clear accept/reject rule, e.g.:

> Producers MUST encode the envelope JSON body as JCS canonical (full document including signatures).  
> Receivers SHOULD accept any valid JSON body, but MUST re-emit/store using JCS canonical form.  
> DHT nodes MUST store the JCS-canonical form (i.e., they may canonicalize before storage, or reject non-canonical inputs—pick one and specify).

## Issue 11 (H): Relationship between envelope version and JSON `version` is not defined

**Problematic text (quotes)**

- §11.1:
  > Version: 0x01 | 1 byte
- §4.2:
  > `version` … MUST be `1`

**Ambiguity**

If these ever differ (malformed or future extensions), behavior is undefined. Some will gate on envelope version only; others on JSON version only; others require equality.

**What two implementations might do differently**

- Impl A accepts envelope version=1 and ignores JSON `version`.
- Impl B requires JSON `version==1` and ignores envelope version.
- Impl C requires both to be 1 and equal.

**Specific fix**

State explicitly:

> For this RFC, envelope version MUST be `0x01` and JSON `version` MUST be `1`. Receivers MUST reject if either check fails. (Optionally: receivers MUST also reject if they do not match.)

## Issue 12 (H): External cross-references are declared “authoritative” but not present; Endpoint schema is undefined in this RFC

**Problematic text (quotes)**

- §3.2:
  > See RFC-0002 §2.1 for the authoritative Base32 specification.
- §13.2:
  > See `00-shared/layer-integration.md` for Endpoint schema definition.
- §12.6:
  > see recovery-mechanisms.md

**Ambiguity**

Independent implementers using *this* RFC alone will invent details:
- Crockford Base32 has multiple commonly-implemented “decode leniencies”
- Endpoint schema constraints (host formatting, IPv6 bracket rules, etc.) are underspecified here
- Recovery proof validation reference points to a non-existent/unspecified doc

**What two implementations might do differently**

- Impl A follows Crockford’s permissive decoding or a different bit-packing interpretation.
- Impl B follows only the provided alphabet/test vectors.
- Endpoint parsing differs (accept `[IPv6]` vs raw IPv6, normalize hostnames, etc.).
- Recovery validation may be partially implemented or incompatible.

**Specific fix**

Make RFC-0001 self-contained for all wire-relevant pieces it normatively depends on:
- Inline a concise normative Crockford Base32 *encoding* definition (bit order) and keep the test vector.
- Inline the Endpoint schema (at least the exact JSON field types and allowed values).
- Replace “recovery-mechanisms.md” with “Section 9” (or add the missing normative text here).
