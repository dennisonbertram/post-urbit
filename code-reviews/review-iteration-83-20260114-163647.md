## Holistic Review (Iteration 82) — Cross-layer consistency, RFC alignment, implementability

Overall the spec-set is unusually cohesive: identifiers (IID/DID), canonicalization (JCS), stream framing (type byte once + u32 length frames), and the “internal IDOC signature only” DHT model are consistently carried through most documents. The RFCs (0001–0003) largely match the layer specs (01–05), and the integration glue (`00-shared/layer-integration.md`) resolves many previous ambiguities.

That said, there are **2 BLOCKING cross-document conflicts** that can produce interoperable divergence or make deployment brittle.

---

# BLOCKING Issues

## B1 — Genesis DHT record: **immutability rules conflict with TTL/refresh requirements**
**Where**
- `spec/00-shared/layer-integration.md` → **“Genesis Key Semantics (Normative)”** and **Storage rules**
  - “genesis … immutable; once written MUST NOT be replaced”
  - “DHT nodes MUST reject writes … if a document already exists”
- `spec/00-shared/layer-integration.md` → **“DHT Protocol Stack (Normative)”**
  - “TTL enforcement: Nodes MUST expire records after TTL seconds”
- `spec/06-rfcs/RFC-0001-identity-document.md` → **§12.3 Genesis Document Storage**
  - “TTL: Forever (or very long, e.g., 365 days)”
  - “Implementations SHOULD also store genesis documents”

**Why this is BLOCKING**
- If *TTL applies* to genesis records, they will expire.
- If *rewrites are forbidden* once a record exists, the genesis record cannot be refreshed before expiry.
- If genesis is required for TOFU anchoring/chain auditing, network behavior becomes non-deterministic over time (genesis may vanish), breaking bootstrap verification for late joiners.

**Concrete interoperability failure mode**
- Client A publishes genesis; DHT node stores it with TTL 365d.
- At day 366, record expires.
- Publishing the same genesis again is rejected (“already exists”) if the DHT node retains any “already exists” state; or, if it doesn’t, a malicious alternate genesis could be inserted post-expiry and appear “first” to new clients. Either way, the “immutable genesis” property is not well-defined.

**Required fix (normative, choose one)**
1. **Idempotent refresh allowed**  
   Amend the “reject if exists” rule to:
   - DHT nodes MUST reject writes to `post-urbit:genesis:` **unless** the incoming value is **byte-identical** to the stored value (exact IDOC envelope bytes).  
   - If identical, treat as a TTL refresh (extend expiry).  
   This preserves immutability while permitting liveness.
2. **Genesis TTL exemption**  
   Define that `post-urbit:genesis:` records are stored with a special TTL policy (e.g., “infinite” / never expired) and adjust the DHT requirements to explicitly exempt genesis from TTL enforcement.
3. **Genesis as multi-value immutable set**  
   Allow multiple values at the genesis key but require clients to treat conflicts as fatal/manual. (Least desirable operationally.)

You should also align RFC-0001 wording to match the chosen policy (right now it implies “forever” but doesn’t define refresh semantics).

## B2 — Sync message maximum frame size conflicts across layers/RFCs
**Where**
- `spec/03-messaging-sync/sync-protocol.md` → **“Transport Framing (Normative)”**
  - “Length … max value **16 MB (0x01000000)**”
- `spec/06-rfcs/RFC-0002-transport.md` → **§6.4 Stream-Specific Limits**
  - Sync max message size **1 MB**
- `spec/01-transport-connectivity/quic-integration.md` and `spec/01-transport-connectivity/interfaces.md`
  - transport constants and sizing assumptions generally center around ~1 MB limits for non-bulk streams

**Why this is BLOCKING**
Two independent implementers can legitimately enforce different limits:
- Implementation X (following RFC-0002) rejects >1 MB sync frames.
- Implementation Y (following sync-protocol.md) sends/accepts up to 16 MB sync frames.
This produces hard interop failures on large operation batches.

**Required fix**
- Pick **one** normative limit for sync frames:
  - If you want >1 MB: update RFC-0002 §6.4 (and any constants) accordingly.
  - If you want 1 MB: update `sync-protocol.md` to state max 1 MB (and preferably specify an explicit error/close behavior when exceeded).
- Ensure Bulk stream semantics cover the “large sync payload” case if you keep sync at 1 MB.

# HIGH Issues

## H1 — Domain separator registry claims “all” but omits packaging/update/repo signature domains
**Where**
- `spec/00-shared/layer-integration.md` → **“Domain Separator Registry (Normative)”** says “All cryptographic domain separators used across the Post-Urbit protocol.”
- `spec/05-ux-packaging/app-distribution.md`:
  - `postapp-signature-v1:` (package SIGNATURE)
  - `postnode-repo-v1:` (repository.json)
  - `postnode-update-v1:` (updates.json)

**Impact**
- Implementers treating the registry as exhaustive may miss these strings or accidentally vary them, breaking signature verification.

**Fix**
- Either:
  - Extend the registry to include these packaging-related domain separators (recommended), **or**
  - Narrow the claim: “registry covers layers 01–03 + sync cryptography” and explicitly exclude packaging/admin signatures.

## H2 — Crockford Base32 “normalize vs reject” is inconsistent in normative text
**Where**
- `spec/06-rfcs/RFC-0001-identity-document.md` → **§3.3 Validation**
  - “Reject uppercase characters (no normalization on wire)”
- `spec/06-rfcs/RFC-0002-transport.md` → **§2.1 Base32 Encoding (Normative)**
  - “Lowercase only (**MUST normalize**)”
  - also “Decoding: Accept lowercase only. Reject … not in alphabet.” (internally inconsistent)
- `spec/00-shared/layer-integration.md` → **Global Conventions / Crockford Base32**
  - “reject uppercase or normalize to lowercase” (ambiguous)

**Impact**
- In handshake JSON fields, one implementation may accept uppercase and normalize, another may reject, causing connection failures in real-world UIs/QR encoders.

**Fix**
- Make a single normative rule per *wire context*:
  - **On-wire / signed contexts (IDOC, device docs, tokens):** MUST be lowercase; receivers MUST reject non-lowercase.
  - **User input / UI:** MAY normalize before creating signed/wire artifacts.
- Update RFC-0002 §2.1 accordingly (remove “MUST normalize” or scope it to UI).

---

## H3 — PURL receiver decapsulation: token handling is underspecified relative to “forward unchanged”
**Where**
- `spec/06-rfcs/RFC-0002-transport.md` → **§7.6 Encapsulation Model**
  - “Relay forwards the entire PURL packet unchanged”
- `spec/01-transport-connectivity/relay-protocol.md` and `interfaces.md` imply stable-port + token usage but do not clearly state receiver behavior.

**Impact**
- A receiver implementation might incorrectly assume the token in inbound PURL is “my allocation token” and reject packets, breaking relayed connectivity.

**Fix**
Add an explicit normative statement (preferably in RFC-0002 §7.6 or §7.7):
- **Recipients MUST NOT validate the allocation token on received (forwarded) PURL DATA packets** and MUST ignore it for decapsulation; only relays validate tokens.
Optionally:
- Recipients MAY sanity-check `Destination IID == my IID` and drop otherwise.

## H4 — Test vectors are strong, but **some “test vectors” are still algorithm-only (missing concrete outputs)**
**Where**
- `spec/00-shared/test-vectors.md`:
  - **Test Vector 8: Device Identifier (DID) Derivation** provides method but **no expected DID output**
  - No concrete vectors for:
    - Sync operation signature / operation_id derivation (complex, easy to get wrong)
    - PUSE full-envelope encryption/decryption round-trip bytes (at least one minimal vector)

**Impact**
- Crypto interoperability frequently fails on “small encoding choices”; missing concrete vectors increases integration risk.

**Fix**
- Add:
  1. A DID test vector with actual derived pubkey + DID string.
  2. At least one **SyncOperation** test vector covering:
     - deterministic CBOR encoding bytes for `operation`
     - `timestamp_bytes`
     - `operation_id_bytes` and signature
  3. One minimal PUSE vector (initial 0x00) and one ratchet 0x01 vector:
     - full envelope bytes (hex or base64) + expected plaintext.

**Where**
- `spec/02-identity-trust/revocation.md` → **DHT Storage (Normative)**:
  - “Multiple revocations … keep highest effective_at”
  - no rule for ties (same effective_at, different content)

**Impact**
- Potential non-deterministic client behavior; storage nodes may diverge.

**Fix**
- Add tie-handling consistent with IDOC same-sequence conflict policy (e.g., treat as conflict state; do not auto-resolve via hash).

**Fix**

# RFC Alignment Check (summary)

- **RFC-0001 ↔ identity layer (02):** Largely aligned (IID derivation, JCS signing, history keys, recovery semantics). Main divergence is the **genesis DHT policy** (B1).
- **RFC-0002 ↔ transport layer (01) + shared glue (00):** Stream framing, handshake transcript, relay stable-port model align well. Need clarification on **Base32 normalization** (H2) and **PURL receiver token handling** (H3).
- **RFC-0003 ↔ messaging layer (03) + shared glue (00):** PUSE format, extension constraints, signature key lookup, mailbox token canonicalization align well. Missing more complete **PUSE and sync test vectors** (H4).
