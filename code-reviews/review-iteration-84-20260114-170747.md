## Remaining issues

## **BLOCKING**

### 1) Relay (PURL) packet sizing vs QUIC minimum datagram size / IPv6 minimum MTU
**Where**
- `spec/06-rfcs/RFC-0002-transport.md` §7.4 (PURL header = 44 bytes; payload “MUST NOT exceed 1200”)
- `spec/01-transport-connectivity/interfaces.md` constants (`MAX_UDP_PAYLOAD=1200`, `RELAY_PACKET_MAX_SIZE=1244`)
- `spec/01-transport-connectivity/quic-integration.md` (`max_udp_payload=1200`)

**Problem**
- If inner QUIC UDP payload is 1200 bytes and you add a 44-byte PURL header, the outer UDP payload becomes **1244**. Over IPv6 minimum MTU (1280), the max UDP payload is **1232** (1280 − 40 IPv6 − 8 UDP). So 1244 exceeds the IPv6 minimum-MTU safe envelope.
- If you reduce inner payload to fit (≤1232−44=1188), many QUIC stacks enforce the QUIC requirement that client Initial datagrams be padded to **at least 1200 bytes** (implementation behavior varies, but a large portion of real QUIC stacks enforce this). That risks relay-path handshake failure.

**Why this is blocking**
The relay path is explicitly the fallback for “hard NAT / hostile networks”; it cannot depend on “path MTU > IPv6 minimum” or on QUIC stacks tolerating undersized Initials without a normative workaround.

**What to fix (normative choice required)**
Pick one implementable design and specify it end-to-end, e.g.:
- **Option A (recommended if you keep PURL):** define a *relay-path QUIC max_datagram_size* such that `PURL_header + QUIC_datagram <= 1232` (IPv6 min), and explicitly specify how the QUIC “Initial 1200” requirement is satisfied (e.g., by treating the outer datagram size for amplification padding purposes, which may require QUIC stack adaptation, or by defining a relay-specific padding shim that produces a 1200-byte QUIC packet after decapsulation—hard with 44-byte overhead).
- **Option B:** redesign PURL header so it’s ≤32 bytes overhead (so 1200 inner fits in 1232 outer). With current fields (16 token + 20 dest IID) this is not possible without changing routing/auth semantics.
- **Option C:** change relay encapsulation model (e.g., relay is a stateful forwarder that does *not* require per-packet destination IID, or uses connection-local short IDs negotiated after allocation) to cut header size.

Right now the text claims “payload ≤1200 ensures no fragmentation”, which is false for the full datagram, and leaves implementers no interoperable rule.

### 2) Sync Operation test vector contradicts normative UUID/document-id encoding
**Where**
- `spec/00-shared/test-vectors.md` Test Vector 9 (Document ID “32-byte padded” shown as ASCII bytes of the UUID string)
- Normative mapping elsewhere:
  - `spec/00-shared/layer-integration.md` UUID bytes mapping (RFC 4122 network byte order)
  - `spec/03-messaging-sync/interfaces.md` “DocumentId padding rule: UUID bytes (16) + 16 zero bytes”
  - `spec/03-messaging-sync/sync-protocol.md` “Document IDs are always 32 bytes… UUID bytes + 16 zero bytes”

**Problem**
Test Vector 9 shows the padded Document ID as ASCII for `"550e8400-e29b-..."` (`35 35 30 65 ...`), not the 16-byte UUID value. This conflicts with the normative encoding rules repeated elsewhere.

**Why this is blocking**
This is the only “worked” sync-signature example, and it is currently misleading. Implementers following it will produce non-interoperable operation IDs/signatures.

**Fix**
Regenerate Test Vector 9 using the normative UUID-bytes+zero-padding rule, and publish the actual computed `operation_id` and signature (no placeholders).

### 4) Mailbox protocol: missing normative binding check between bearer token IID and envelope sender IID
**Where**
- `spec/06-rfcs/RFC-0003-messaging.md` §7 (Mailbox)
- `spec/00-shared/layer-integration.md` Mailbox Trust Model / Message Format

**Problem**
The mailbox returns `sender_iid` in retrieval responses but there is no normative requirement that:
- the mailbox verifies `token.iid` (authenticated) matches the envelope header’s `sender_iid` (unauthenticated), or
- the mailbox uses `token.iid` as the authoritative “sender” metadata in responses.

**Impact**
Even if recipients ultimately verify the PUSE signature, UIs/apps might trust mailbox-provided `sender_iid` metadata for previews/routing/anti-spam decisions prior to verification.

**Fix**
Add a normative rule: mailbox servers **MUST** parse the PUSE header and reject store requests where `PUSE.sender_iid != token.iid` (and should set response `sender_iid` from the token, not the envelope).

### 5) Signature-input conventions (sign raw vs sign SHA256(input)) are inconsistent across the protocol without a single summary table
**Where**
- Identity docs: sign raw `domain || JCS(...)` (RFC-0001)
- Handshake/relay/mailbox: sign `Ed25519(SHA256(input))` (RFC-0002/RFC-0003)
- Device docs/index: sign raw `domain || JCS(...)` (RFC-0001 + layer-integration)

**Impact**
This is specified per subsystem, but it is a frequent real-world interop footgun. Given the spec’s emphasis on uniform domain separation, a single “signature prehash policy” table would materially reduce implementation errors.

**Fix**
Add a normative registry/table: for each signature context, state explicitly whether Ed25519 signs:
- raw bytes, or
- SHA256(preimage)

## **MEDIUM**

### 6) DHT “storage node MUST verify update authorization” may be unrealistic for common Kademlia deployments
**Where**
- `spec/00-shared/layer-integration.md` DHT Record Verification / Update Authorization

**Issue**
Requiring DHT storage nodes to validate `signatures.previous` against the currently stored doc, and/or recovery proofs, makes the DHT behave like an application-aware authoritative registry. Many “real” DHT deployments won’t (or can’t) do this at the storage layer; they do validation client-side.

**Fix**
Clarify a two-tier model:
- **Clients MUST verify** all docs and apply conflict/sequence rules.
- **DHT nodes SHOULD verify** basic validity (parse, `iid` binding, `signatures.current`) and MAY enforce monotonic sequence if they keep state—otherwise store-and-return, leaving full correctness to clients.

### 7) PUSE plaintext `sequence` field semantics remain under-specified (esp. groups + multi-device)
**Where**
- `spec/03-messaging-sync/secure-envelope.md` replay protection references sequence
- `spec/06-rfcs/RFC-0003-messaging.md` plaintext format

**Issue**
The spec says “per-conversation monotonic sequence” but doesn’t pin down:
- whether the sequence is per-(sender, recipient) or per-conversation shared counter,
- how it behaves across multiple devices for the same IID,
- whether receivers MUST enforce it, and what the windowing rules are for group messages.

This is implementable but will diverge across implementations unless made normative (or explicitly made “advisory only”).
