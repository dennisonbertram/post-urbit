## Remaining BLOCKING issues

### BLOCKING 1 — Signature input / prehash policy is internally inconsistent (and currently ambiguous)
**Conflict**
- `spec/00-shared/layer-integration.md` **claims (normatively)**:
  - “All Post-Urbit signatures use single-pass Ed25519 on raw bytes (not Ed25519ph prehash).”
  - Handshake challenge signs `domain || challenge_data` as raw bytes.
- But the authoritative per-layer specs do something else:
  - `spec/06-rfcs/RFC-0002-transport.md` §5.7:
    - `challenge_signature = Ed25519_Sign(signing_key, SHA256(challenge_data))`
  - `spec/01-transport-connectivity/peer-handshake.md` also uses `Ed25519_Sign(..., SHA256(challenge_data))`
  - `spec/06-rfcs/RFC-0002-transport.md` §7.8 (relay allocation) signs `SHA256(signature_input)`
  - `spec/06-rfcs/RFC-0003-messaging.md` mailbox token signing signs `sha256(signature_input)`
- Additionally, the prehash policy table references a “PUSE envelope signature domain separator”, but:
  - `spec/06-rfcs/RFC-0003-messaging.md` §3.7 defines the PUSE signature as Ed25519 over **raw envelope bytes**, **with no extra domain separator** (the `PUSE` magic provides context separation implicitly).

**Why this is BLOCKING**
Two conforming implementations could reasonably follow:
- the shared glue document’s “single-pass raw bytes” rule, or
- the RFCs’ “hash-then-sign” constructions,
…and they will fail to interoperate.

**Required resolution**
Pick one of these strategies and apply it consistently everywhere:

**Option A (recommended for simplicity): “No application-level prehash anywhere.”**
- Change RFC-0002 and RFC-0003 transport/mailbox/relay signatures to sign raw bytes:
  - Handshake: `Ed25519_Sign(sk, challenge_data)` (where `challenge_data` already includes the domain separator)
  - Relay alloc/rebind: `Ed25519_Sign(sk, signature_input)` (domain already included)
  - Mailbox token: `Ed25519_Sign(sk, signature_input)`
- Update Test Vector 7 (handshake) and any other vectors/examples that imply hash-then-sign.
- Update docs that currently compute/display “challenge_hash” as part of the signature process (keep it as diagnostic only, not part of signing).

**Option B: “Context-specific: some signatures hash-then-sign; some do not.”**
- Keep RFC behavior, but then **fix the shared prehash policy table** to explicitly list:
  - which contexts sign raw bytes
  - which contexts sign `SHA256(preimage)`
- Also update the “Summary: all signatures use single-pass Ed25519” sentence accordingly (it is false under this option).
- Add the missing “PUSE signature uses no domain separator” rule to the table.

Either option is fine, but the current mix (“table says raw; RFCs say hash”) is not.

### BLOCKING 2 — PURL “1188 inner payload” conflicts with QUIC Initial minimum datagram size in practice
**What the spec currently mandates**
- `spec/06-rfcs/RFC-0002-transport.md` §7.4:
  - Relay-path inner QUIC payload MUST NOT exceed **1188** bytes
  - Receivers MUST drop PURL packets with Payload Length > 1188

**Why this is BLOCKING**
QUIC (RFC 9000) requires that **UDP datagrams carrying Initial packets be at least 1200 bytes** (anti-amplification). In most real QUIC stacks, this is enforced at the QUIC endpoint based on the size of the datagram delivered to the QUIC stack.

With your relay model:
- the OS receives a UDP payload of ~1232 bytes (PURL header + inner QUIC payload),
- **but the QUIC stack is fed only the decapsulated inner bytes** (≤1188).
- If the QUIC implementation enforces the “Initial datagram ≥1200” rule on the bytes it receives, it will discard Initial packets and the handshake can fail.

Your RFC attempts to justify this with:
- “outer datagram is 1232 so amplification protection is equivalent”
…but typical QUIC libraries do not have a mechanism to treat “decapsulated payload length” differently from “received UDP payload length”.

**Required resolution**
You need a normative, implementable story that works with commodity QUIC libraries:

**Option A (most practical): allow/require inner QUIC datagrams to be 1200 bytes and accept that the *outer* datagram may exceed IPv6 minimum MTU.**
- Set relay inner max to 1200 (or “QUIC stack default”) for Initial compatibility.
- Update the MTU guidance: relay path may fragment on strict-1280 IPv6 links; recommend PLPMTUD / fallback behavior / operational guidance.
- Remove “MUST drop >1188” (or restrict it only after handshake completion, though that still doesn’t solve Initial).

**Option B: redesign PURL header to shrink enough that `header + 1200 <= 1232`.**
- This requires cutting the header from 44 to **32** bytes, which is not achievable without changing core fields (token length, destination IID size, etc.). As specified (dest IID 20 + token 16 already 36), this is not feasible without security/functionality tradeoffs.

**Option C: explicitly require QUIC implementations that do not enforce the 1200-byte Initial minimum on the decapsulated datagram length.**
- This is effectively “you must use a QUIC stack or mode that allows undersized Initials”, which is a major portability/interoperability hazard and should be avoided.

As written, the “1188 inner” rule is very likely to break interoperability across mainstream QUIC stacks, so it is BLOCKING.
