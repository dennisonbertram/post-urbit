## Remaining **BLOCKING** issues

### B1 — Sync protocol lacks a canonical on-wire schema for CRDT operations
**Where:** `spec/03-messaging-sync/sync-protocol.md` (“CRDT Operation CBOR… each CRDT type defines its own CBOR schema”) plus `spec/03-messaging-sync/interfaces.md` lists `CRDTOperation` variants, but neither document normatively defines the CBOR map layout (keys, types, nesting) for each operation type.

**Why this blocks interoperability:**
- `operation_id_bytes` and `SyncOperation.signature` are computed over `operation_bytes` (CBOR bstr).  
- Deterministic CBOR alone does **not** fix schema ambiguity (different key names/encodings can still be deterministic).
- Two correct implementations can produce different `operation_id`s for the “same” semantic operation, causing:
  - duplicate application of operations (divergence), or
  - failure of dedupe-by-id assumptions, or
  - inconsistent Merkle ordering and sync diffs.

**Minimal fix:** Add a normative CBOR schema registry for each `CRDTOperation` variant (e.g., `{"t":"lww_set","k":<text>,"v":<cbor-any>,"ts":<hlc-map>}` or integer-keyed maps), and state whether `operation_bytes` is the canonical encoding of that schema.

## HIGH (non-blocking but should be resolved)

### H1 — Stream multiplicity rules live in glue doc, not Transport RFC
**Where:** `spec/00-shared/layer-integration.md` defines “At most 1 per direction” for Identity/Sync streams and error handling for duplicates, but `spec/06-rfcs/RFC-0002-transport.md` does not normatively specify these limits.

**Risk:** Implementers following RFC-0002 alone may open/accept multiple long-lived streams, while others enforce the glue constraints, producing avoidable interop failures.

**Fix:** Move/duplicate these rules into RFC-0002 §6 (or explicitly state RFC-0002 defers to layer-integration.md for stream lifecycle/multiplicity).
