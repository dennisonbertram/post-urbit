## CBOR schema fix (Iteration 86) — verified

The change in `spec/03-messaging-sync/sync-protocol.md` **does** address the previously-missing canonical operation encoding:

- **CRDT operations are now normatively encoded as deterministic CBOR** (RFC 8949 §4.2) using **integer map keys** with a **type registry (0–7)**.
- The example encoding for `lww_set` is consistent with CBOR major types and key ordering.
- The spec correctly distinguishes:
  - **Sync message payload CBOR** (maps with text keys like `"document_id"`, allowed as long as deterministic CBOR rules are followed), vs
  - **CRDT operation bytes** (`operation_bytes`) which must follow the new integer-key schema.

So the “canonical CBOR schema for CRDT operations” fix is correct *in isolation*.

## Remaining **BLOCKING** issues (must be resolved)

### B1 — Sync operation signature construction is inconsistent across documents
There is a **normative mismatch** between:

- `spec/00-shared/layer-integration.md` → **Signature Prehash Policy (Normative)** table:
  - **Sync operation signature input** is specified as  
    `domain || timestamp || operation_id`
- `spec/03-messaging-sync/sync-protocol.md` → **Operation Signature** (normative):
  - Signature input is specified as  
    `domain || operation_id_bytes || document_id || timestamp_bytes || operation_bytes || dependencies_bytes`

These cannot both be correct; implementations will not interoperate if they follow different sources.

**Required fix:** Pick one authoritative construction (strongly recommend: treat `sync-protocol.md` as authoritative for sync) and update `layer-integration.md` accordingly.

---

### B2 — Test Vector 9 (“Sync Operation Signature”) contradicts the sync-protocol’s normative encoding
In `spec/00-shared/test-vectors.md`, Test Vector 9 states (even if “illustrative”):

- `timestamp_bytes` is **8 bytes**, and payload is `domain || timestamp_bytes || operation_id`

But `sync-protocol.md` defines `timestamp_bytes` as **20 bytes** (`8 + 4 + 8`) and a different signature input.

Because `test-vectors.md` is explicitly positioned as implementer guidance, this is a **practical interoperability blocker**: many implementers will copy it.

**Required fix:** Rewrite Test Vector 9 to match the final normative sync signature + timestamp_bytes definition (or clearly mark the conflicting parts as non-normative and remove “Normative encoding rules” from that section).

---

### B3 — Messaging/Sync TS interfaces define CRDT operations that do not match the wire CRDT schema
`spec/03-messaging-sync/interfaces.md` defines app-facing `CRDTOperation` variants like:

- `lww_set` with `{ key, value, timestamp }`
- `counter_inc/dec` with `delta`
- `list_insert` with `{ index, element, id }`

But `spec/03-messaging-sync/sync-protocol.md` defines wire-level CRDT ops as:

- `lww_set` with only a **value** (no key)
- `pncounter_inc/dec` with `amount`
- `rga_insert` with **(id, parent, value)** (no index)

This can be fine **only if** the spec explicitly defines a translation layer (“API op” → “wire op bytes”) and declares which is normative for interoperability. Today it reads like both are “the” CRDT operation model.

**Required fix:** Either:
1) Align the TS `CRDTOperation` model with the wire schema (preferred), **or**
2) Explicitly define and normatively specify the translation mapping and state which layer owns that translation (sync engine vs apps).
