## Remaining **BLOCKING** issues

### B1 — Device document signature verification key selection is inconsistent across layers (breaks interoperability under key rotation)

**Where it conflicts:**
- `spec/02-identity-trust/identity-document-schema.md` (Device Document Verification) says to verify `signature_by_identity` using identity **current or historical** signing keys (current → previous → history, subject to `expires_at`).
- `spec/00-shared/layer-integration.md` (Device Document Verification) also allows **current (or historical)** signing key verification.
- `spec/06-rfcs/RFC-0001-identity-document.md` §12.6 “Device Documents” states DHT nodes validate device docs using identity **current or historical** signing keys.
- But `spec/06-rfcs/RFC-0002-transport.md` §5.8 “Device Verification” says:  
  > “Verify `device_document.signature_by_identity` using identity’s **current** signing key”
- And `spec/01-transport-connectivity/peer-handshake.md` repeats the “current signing key” rule.

**Why this is BLOCKING:**
- If an identity rotates signing keys, existing device docs and/or device index records may still be signed with the *previous* key until they are re-issued and republished everywhere.
- Under RFC-0002’s “current-only” rule, a valid device doc signed by a still-valid previous/history key would be rejected during handshake → **device-authenticated transport sessions can fail spuriously** after key rotation.
- This is a real interoperability/liveness failure for multi-device nodes.

**Required resolution (one clear rule, applied everywhere):**
- Update RFC-0002 §5.8 and `peer-handshake.md` to:  
  **Verify `signature_by_identity` against identity signing keys using RFC-0001 key lookup order (current → previous → history entries not expired)**.  
  (And optionally require that producers *should* resign device docs promptly after rotation, but verification must remain backward-compatible.)
