- **Normative definition** in `spec/03-messaging-sync/sync-protocol.md`:
  - `timestamp_bytes = physical_ms_u64be || logical_u32be || SHA256(origin_raw_iid)[0:8]`
- **Conflicting/ambiguous “normative encoding rules”** appear in `spec/00-shared/test-vectors.md` Test Vector 9:
  - It states `timestamp_bytes` includes “8 origin prefix” without specifying that this is **SHA256(origin_raw_iid)[0:8]**.
  - This can be (reasonably) misread as “first 8 bytes of origin IID raw bytes”, which would produce different `operation_id` and signatures, breaking sync interop.

**Why this is BLOCKING:** `timestamp_bytes` feeds both `operation_id` and the signature input. If two implementations choose different 8-byte origin components, they will compute different operation IDs and reject each other’s signed ops.

- Update **Test Vector 9** to explicitly say: `origin_hash8 = SHA256(origin_raw_iid)[0:8]` and replace “origin prefix” with “origin_hash_prefix”.
- Audit any other mention of “20 bytes: 8 physical + 4 logical + 8 origin …” to ensure it matches sync-protocol.md exactly.
