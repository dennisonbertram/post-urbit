## Summary
Most cross-layer wire formats (IDOC, QUIC stream framing, PURL, PUSE) are internally consistent between the layer docs and RFCs, but there are a few **normative cross-document contradictions** that would cause implementers to produce incompatible signatures / repository metadata.

## Issues Found

### BLOCKING

**B1 — Repository manifest signature field format is inconsistent (string vs object):**  
- `spec/05-ux-packaging/app-distribution.md` in **“Repository Manifest (repository.json)”** example shows:
  - `"signature": "<repository-operator-signature>"` (a string)
- The same file in **“Repository Manifest Signing”** specifies adding:
  - `"signature": { "operator_iid": "...", "timestamp": "...", "sig": "..." }` (an object)

This is a format-level incompatibility: clients cannot reliably parse/verify repository manifests if the signature field is sometimes a string and sometimes an object.  
**Interop impact:** repository discovery + update workflows break across implementations.

---

**B2 — “Signature Prehash Policy (Normative)” contradicts the authoritative RFC signature constructions (double-domain / missing delimiters risk):**  
- `spec/00-shared/layer-integration.md` **“Signature Prehash Policy (Normative)”** states (examples):
  - Handshake challenge: `SHA256(domain || challenge_data)`
  - Relay allocation: `SHA256(domain || allocation_data)`
  - Mailbox token: `SHA256(domain || token_data)`
- But RFCs define the hashed inputs as already **domain-prefixed**:
  - `spec/06-rfcs/RFC-0002-transport.md` §5.7: `challenge_data = DOMAIN || ...` then sign `SHA256(challenge_data)`
  - `spec/06-rfcs/RFC-0002-transport.md` §7.8: `signature_input = DOMAIN || ...` then sign `SHA256(signature_input)`
  - `spec/06-rfcs/RFC-0003-messaging.md` §7.3: `signature_input = domain || ...` then sign `sha256(signature_input)`

As written, the **normative** table can be interpreted as “prepend domain again”, yielding `SHA256(DOMAIN || (DOMAIN || ...))`, which will not verify.  
**Interop impact:** handshake / relay allocation / mailbox auth signatures can fail if an implementer follows the glue doc’s “normative” table literally.

### HIGH

**H1 — App-defined PUSE plaintext schema is inconsistent between RFC-0003 and Messaging layer interfaces:**  
- `spec/06-rfcs/RFC-0003-messaging.md` §8.2 **“Host API to PUSE Plaintext Mapping (Normative)”** requires for app-defined types:
  - PUSE plaintext: `{ "type": "app", "content": { "app_id": "<message_type>", "data": <CBOR-decoded> } }`
- `spec/03-messaging-sync/interfaces.md` defines:
  - `AppContent { appId: string; appVersion: string; payload: unknown }`

Unless explicitly declared as a *post-parse in-memory projection*, this reads like a different on-wire schema (`app_id/app_version/payload` vs `app_id/data`).  
**Interop impact:** cross-node app messaging (filters + payload decoding) is likely to diverge between implementations.

---

**H2 — PUSE “illustrative” test vectors contradict the current PUSE wire format and extension placement (misleading implementers):**  
- `spec/00-shared/test-vectors.md` **Test Vector 10 / 11** show an older envelope layout with a separate “Message Type” byte and imply extensions are inside ciphertext.
- Authoritative spec now is:
  - `spec/06-rfcs/RFC-0003-messaging.md` §3 (flags byte + header extension) and
  - `spec/03-messaging-sync/secure-envelope.md` (exact header fields, extension is AAD, not encrypted)

Even labeled “illustrative”, these are structurally wrong relative to the normative wire format and are likely to cause early interop bugs.  
**Interop impact:** high risk of incorrect encoder/decoder implementations.

---

**H3 — CSRF token distribution is specified inconsistently (cookie vs response body):**  
- `spec/05-ux-packaging/node-daemon.md` **“CSRF Protection”** describes double-submit cookies (`postnode_csrf` cookie + `X-CSRF-Token` header), implying JS can read the cookie and echo it.
- `spec/05-ux-packaging/interfaces.md` defines `LoginResponse.csrfToken` returned in the response body.
- `spec/05-ux-packaging/admin-ui.md` `ApiClient` assumes CSRF token is obtained from the login response body and stored in JS.

Not fatal if implementations “do both”, but the spec should pick one normative mechanism (or explicitly specify both and precedence).  
**Interop impact:** Admin UI clients may fail against servers that implement only the cookie-readable variant (or only body-return).

---

**H4 — RFC-0001 “DHT Storage” omits revocation DHT record format that is normative elsewhere:**  
- `spec/02-identity-trust/revocation.md` defines revocation DHT storage under `SHA256("post-urbit:revocation:" || iid)` with TTL 365 days.
- `spec/00-shared/layer-integration.md` includes the revocation DHT prefix in the registry and key derivations.
- `spec/06-rfcs/RFC-0001-identity-document.md` §12 covers identity/genesis/device records, but does **not** specify revocation DHT records despite having §10 “Revocation”.

Because RFCs are positioned as authoritative, this is a spec authority gap: implementers using RFC-only guidance may not publish/resolve revocations correctly.  
**Interop impact:** revocation discovery inconsistencies across implementations.

### MEDIUM

**M1 — Progress log contains stale technical claims that contradict current normative values:**  
- `spec/progress.md` still references an older relay MTU fix (“inner payload 1188 bytes”) while current specs use **1200 inner / 1244 outer** (`spec/06-rfcs/RFC-0002-transport.md` §7.4; `spec/01-transport-connectivity/interfaces.md` constants).  
This is non-normative, but confusing.

---

**M2 — Packaging docs have a few outdated phrases around where signatures live:**  
- `spec/04-app-runtime/manifest-schema.md` package directory snippet says `manifest.json # ... with signature` even though the same document correctly says signatures are in `SIGNATURE`.  
Documentation-only, but it increases audit/implementation errors.

---

**M3 — Domain separator registry does not include TLS exporter label (arguably cryptographic context material):**  
- `spec/06-rfcs/RFC-0002-transport.md` §4.4 uses exporter label `"post-urbit handshake binding"`.  
Not strictly a “domain separator”, but it is protocol-critical context and could be registered alongside other fixed cryptographic context strings to avoid drift.
