## Summary
The spec set is broadly coherent and the RFCs largely align with the layer docs, but there is a **signature-construction inconsistency** that will cause packaging signature verification failures across implementations, plus several smaller cross-doc ambiguities.

## Issues Found

### BLOCKING

B1 — Packaging signature payload concatenation mismatch (missing delimiters in prehash table):  
The **Signature Prehash Policy** table specifies packaging signature inputs as `domain || manifest_hash_hex || timestamp` (and similar), but the packaging specs (and verification pseudocode) define payloads that include **explicit `:` separators** between fields. Implementers following the table will generate different signatures than implementers following the packaging docs.

- **Spec with incorrect/ambiguous construction**:  
  - `spec/00-shared/layer-integration.md` → **“Signature Prehash Policy (Normative)”** table:  
    - App package SIGNATURE: `domain || manifest_hash_hex || timestamp`  
    - Repository signature: `domain || manifest_hash_hex || timestamp`  
    - Update manifest: `domain || app_id || manifest_hash_hex || timestamp`
- **Specs with explicit delimiter requirements** (the ones that will actually be implemented):  
  - `spec/04-app-runtime/manifest-schema.md` → **“Signature Verification”** example:  
    - `payload = "postapp-signature-v1:${manifestHashHex}:${timestamp}"`
  - `spec/05-ux-packaging/app-distribution.md` → **“Signing Process”**, **“Repository Manifest Signing”**, **“Update Manifest Signing”**:  
    - `postapp-signature-v1:` + `<hash>` + `:` + `<timestamp>`  
    - `postnode-repo-v1:` + `<hash>` + `:` + `<timestamp>`  
    - `postnode-update-v1:` + `<app_id>` + `:` + `<hash>` + `:` + `<timestamp>`

**Interop impact:** Signature bytes differ → packages/repos/update manifests fail verification between implementations.  
**Fix:** Update `layer-integration.md` prehash table rows to match exact payload bytes, including separators (e.g., `domain || manifest_hash_hex || ":" || timestamp`, etc.), or reference the authoritative payload formats in `app-distribution.md`/`manifest-schema.md` directly.

### HIGH

H1 — QUIC/TLS certificate algorithm policy is inconsistent across docs (may cause avoidable interop failures):  
One doc says clients MUST accept **any** certificate; another implies a restricted signature algorithm for TLS.

- `spec/00-shared/layer-integration.md` → **“QUIC TLS Certificate Policy”**:  
  - “Clients MUST accept ANY certificate… MUST NOT reject based on signature algorithm (RSA, ECDSA, Ed25519, etc.)”
- `spec/01-transport-connectivity/quic-integration.md` → **“TLS Configuration”** table:  
  - “Signature: Ed25519 (for identity binding)”

**Risk:** An implementer could read `quic-integration.md` as “only accept Ed25519 certs”, contradicting the integration policy and breaking interop.  
**Fix:** In `quic-integration.md`, reword “Signature: Ed25519” to clearly mean **handshake proof signatures** are Ed25519, and/or explicitly state **TLS certificate signature algorithm is unrestricted** per the TLS policy.

H2 — Handshake nonce/base64 encoding underspecified in peer-handshake.md vs RFC-0002:  
`peer-handshake.md` uses placeholders like `<32-bytes-base64>` without specifying **standard Base64 vs Base64url** and padding rules, while RFC-0002 is explicit (Base64 standard, no padding).

- `spec/01-transport-connectivity/peer-handshake.md` → **ClientHello/ServerHello**: `client_nonce`, `server_nonce`, `tls_binding` are described as “base64” but not alphabet/padding.
- `spec/06-rfcs/RFC-0002-transport.md` → **§5.5/§5.6**: explicitly “Base64 standard, no padding”.

**Risk:** Cross-implementation decoding/validation differences.  
**Fix:** Add the same encoding constraint text from RFC-0002 into `peer-handshake.md` (or explicitly reference RFC-0002’s encoding rules at the field level).

H3 — DocumentId display/JSON encoding rules conflict (hex-only vs “UUID or hex”):  
The shared conventions explicitly allow UUID string form for DocumentId display/JSON, while `sync-protocol.md` claims hex-only for JSON/display.

- `spec/00-shared/layer-integration.md` → **“Global Conventions → Encoding”**:  
  - `DocumentId | JSON/display | 64-char hex or UUID string | Application-dependent`
- `spec/03-messaging-sync/sync-protocol.md` → **“Documents”** section type comments:  
  - “For display/JSON: hex string (64 chars)” and `type DocumentIdHex = string; // 64 hex chars for JSON/display only`

**Risk:** App/runtime APIs and debugging tooling disagree on canonical textual forms; some implementations may reject UUID-form DocumentIds in JSON where others accept them.  
**Fix:** Align `sync-protocol.md` with the repository-wide convention (allow UUID string OR 64-hex for display/JSON), while keeping the **wire rule** (32-byte bstr) unchanged.

H4 — DHT node verification steps in layer-integration omit the RFC-0001 “JSON-in-envelope MUST be JCS-canonical” enforcement:  
RFC-0001/identity schema require the **envelope JSON bytes** be JCS-canonical, which is especially important for genesis “byte-identical refresh” semantics. `layer-integration.md` describes DHT node verification but doesn’t explicitly include the canonical-bytes check.

- `spec/06-rfcs/RFC-0001-identity-document.md` → **§6.2**: envelope JSON MUST be JCS-canonical (full doc incl signatures).  
- `spec/02-identity-trust/identity-document-schema.md` → **“Wire Format → JSON Canonicalization (Normative)”**: reject non-JCS-canonical envelope JSON.  
- `spec/00-shared/layer-integration.md` → **“DHT Record Format → Verification (New Records)”**: lists checks but does not explicitly say “verify envelope JSON bytes are already JCS-canonical”.

**Risk:** Some DHT nodes may accept and store non-canonical encodings, breaking byte-identical refresh and dedup-by-byte equality expectations.  
**Fix:** Add an explicit step in `layer-integration.md` DHT verification: recompute JCS from parsed JSON and require **exact byte equality** with envelope JSON bytes.

### MEDIUM

M1 — progress.md contains stale statements that contradict current normative docs (MTU + prehash policy history):  
`spec/progress.md` still references earlier iterations’ decisions (e.g., relay inner payload = 1188; “all signatures single-pass”) that no longer match the current RFCs and integration doc (inner payload 1200; transport/mailbox are hash-then-sign).

**Risk:** Reader confusion; not normative, but it’s the first place many implementers will look.  
**Fix:** Update the “Issues Fixed” historical notes or add a prominent disclaimer that progress.md is non-normative and may contain historical superseded statements.

M2 — Some “See RFC-XXXX §Y” references are one-way only (no reciprocal anchor/backlink):  
Not strictly required, but several layer docs reference RFC sections without RFCs pointing back to the layer docs (even when the layer docs provide integration semantics). This is fine structurally but makes audits harder.

**Fix:** Optional: add “Integration notes” backlinks in RFC appendices.
