## Summary
The spec set is generally well-aligned across layers and the three RFCs, but there are two cross-document inconsistencies that can realistically lead to incompatible implementations (PUSE test vectors vs RFC-0003 wire format, and DocumentId string representation across Sync/App APIs).

## Issues Found

### BLOCKING

**B1 — PUSE “test vectors” show an obsolete wire format (would cause wrong encoders/decoders):**  
- **Doc A:** `spec/00-shared/test-vectors.md` §“Test Vector 10: PUSE Envelope (Initial 0x00) (Illustrative)” and §“Test Vector 11: PUSE Envelope (Ratchet 0x01) (Illustrative)” describe a header containing a “Message Type” byte and omit required fields (flags, recipient IID/group_id, message_id UUID, header_extension_length, nonce, signature).  
- **Doc B:** `spec/06-rfcs/RFC-0003-messaging.md` §3.2 and `spec/03-messaging-sync/secure-envelope.md` §“Wire Format” define the authoritative PUSE envelope with:
  - flags byte (not “message type” byte),
  - 20B recipient field,
  - 16B message_id UUID,
  - 2B header extension length + extension bytes,
  - 12B nonce,
  - 64B Ed25519 signature trailer.
- **Why BLOCKING:** Implementers commonly treat “test-vectors.md” as implementation guidance; even marked “illustrative”, the *structure* being wrong is enough to ship incompatible wire code.  
- **Fix:** Update vectors 10/11 to match RFC-0003 §3.2 byte layout and the “exactly one header extension” rule; or remove them entirely and replace with “PUSE frame layout sanity checks” that explicitly mirror the RFC fields.

**B2 — DocumentId string format is inconsistent across Sync spec vs shared conventions vs App APIs (breaks portability / interop at API boundaries):**  
- **Doc A (Sync):** `spec/03-messaging-sync/sync-protocol.md` defines `DocumentIdHex` for “JSON/display only” as **64 hex chars** and sets `type DocumentId = DocumentIdBytes` (wire).  
- **Doc B (Shared conventions):** `spec/00-shared/layer-integration.md` §“Encoding” allows **“64-char hex or UUID string (application-dependent)”** for `DocumentId` in JSON/display.  
- **Doc C (Messaging & Sync interfaces):** `spec/03-messaging-sync/interfaces.md` defines `DocumentId = string` and explicitly allows **UUID string or 64-char hex**.  
- **Doc D (App Host API):** `spec/04-app-runtime/api-surface.md` uses `document_id: string` (e.g., `SyncCreateDocumentResponse`) but does **not** normatively pin the string format.  
- **Why BLOCKING:** Two node implementations can be wire-compatible (CBOR) but still break app portability and admin/app APIs if one emits UUID strings and the other emits 64-hex (or prefixes like `sha256:`).  
- **Fix:** Choose and standardize one canonical `DocumentId` string form across **all** JSON-facing surfaces (Admin API, Host API, app-level TS types), e.g.:
  - Option A: canonical = UUID string for UUID-based docs; canonical = `sha256:<64hex>` for content-addressed docs.
  - Option B: canonical = always 64 hex (UUID padded to 32 bytes then hex-encoded), and UUID string only for UI presentation (non-normative).
  Then update `layer-integration.md`, `sync-protocol.md`, `03-messaging-sync/interfaces.md`, and `04-app-runtime/api-surface.md` to match.

### HIGH

**H1 — Domain separator registry is missing the TLS exporter label (“post-urbit handshake binding”):**  
- **Doc A:** `spec/06-rfcs/RFC-0002-transport.md` §4.4 defines TLS exporter label `"post-urbit handshake binding"`.  
- **Doc B:** `spec/00-shared/layer-integration.md` §“Domain Separator Registry (Normative)” aims to list *all* cryptographic domain separation strings but does **not** include this exporter label.  
- **Impact:** Risk of divergent implementations if someone “implements from the registry” and misses the exporter label constant.  
- **Fix:** Add a registry entry for the TLS exporter label (and explicitly state it is used with TLS Exporter, not Ed25519/HKDF).

**H2 — Device revocation DHT record: prefix exists, but publication/lookup rules are not bidirectionally specified:**  
- **Doc A:** `spec/00-shared/layer-integration.md` includes DHT prefix `post-urbit:device-revocation:` and lists it in key derivation formulas.  
- **Doc B:** `spec/02-identity-trust/identity-document-schema.md` §“Device Revocation” defines the device revocation document but does **not** normatively specify DHT key/TTL/storage rules for device revocation lookups (unlike identity/key revocation in `spec/02-identity-trust/revocation.md`).  
- **Impact:** Implementations may disagree on *where* device revocations live (DHT vs only pushed), leading to inconsistent acceptance of revoked devices.  
- **Fix:** Add a “Device Revocation DHT Storage (Normative)” subsection (key = `SHA256("post-urbit:device-revocation:" || did)`, value = JCS JSON, TTL policy, conflict rules) and ensure RFC-0001 references it (or duplicates it) for completeness.

**H3 — RFC-0003 parsing order text is internally inconsistent about when the sender key is available for signature verification:**  
- **Doc A:** `spec/06-rfcs/RFC-0003-messaging.md` §3.8 lists “Verify signature” before “fetch identity document for sender IID”, but signature verification needs the sender’s public key from IDOC.  
- **Doc B:** `spec/03-messaging-sync/secure-envelope.md` §“Signature Verification” correctly assumes sender_doc is available before verify.  
- **Impact:** Not a wire mismatch, but enough to cause implementation ambiguity and wasted cycles.  
- **Fix:** Reorder RFC-0003 §3.8 steps to: parse header → fetch/resolve sender IDOC → verify signature → derive key → decrypt.

**H4 — Handshake nonce encoding is underspecified in the non-RFC handshake doc (could cause “helpful” but incompatible encoders):**  
- **Doc A:** `spec/01-transport-connectivity/peer-handshake.md` ClientHello/ServerHello show `client_nonce: "<32-bytes-base64>"` (alphabet unspecified).  
- **Doc B:** `spec/06-rfcs/RFC-0002-transport.md` §5.5/§5.6 normatively require **Base64 standard, no padding**.  
- **Impact:** Guidance doc could lead to Base64url usage by mistake.  
- **Fix:** Update `peer-handshake.md` to explicitly say “Base64 standard alphabet (RFC 4648 §4), no padding” for both nonces and `tls_binding`.

**H5 — Sync operation “raw bytes” requirement is stronger than what the TS interface suggests (risk of re-encoding bugs):**  
- **Doc A:** `spec/03-messaging-sync/sync-protocol.md` §“operation_bytes definition” says receivers **MUST NOT decode and re-encode** for hashing/signature; they must hash the exact bstr bytes received.  
- **Doc B:** `spec/03-messaging-sync/interfaces.md` models `SyncOperation.operation` as a structured `CRDTOperation` union (no explicit `operationBytes` field), which nudges implementations toward re-encoding.  
- **Impact:** Likely okay if deterministic CBOR is perfectly implemented everywhere, but the spec explicitly disallows re-encoding—so the interface should support the normative requirement.  
- **Fix:** Add a field like `operationBytes: Uint8Array` (and similarly `dependenciesBytes` optional) in the wire-facing representation, or clearly split “wire struct” vs “decoded struct” types.

### MEDIUM

**M1 — `spec/progress.md` contains stale historical notes that contradict current normative MTU rules:**  
- `spec/progress.md` (Iteration 84 notes) mentions relay inner payload “1188 bytes (1232 total)”, while `spec/06-rfcs/RFC-0002-transport.md` §7.4 and `spec/01-transport-connectivity/interfaces.md` constants use **1200 inner / 1244 outer**.  
- Fix: update the progress log or annotate it as “historical (superseded)” to avoid confusion.

**M2 — Some “see RFC section” pointers are slightly imprecise (exist but not the best anchor):**  
- Example: `spec/00-shared/layer-integration.md` references “RFC-0002 §5.5” for timestamp canonicalization; the requirement is spread across §5.5 and repeated in other handshake sections.  
- Fix: point at a single dedicated RFC subsection (or add one) to make references tighter.

**M3 — `spec/01-transport-connectivity/relay-protocol.md` includes a simplified signature comment that doesn’t match the normative construction:**  
- It shows `signature: Ed25519(signing_key, iid + timestamp + nonce)` in an interface snippet, while the normative scheme is domain-separated and includes lifetime and SHA256 prehash (RFC-0002 §7.8).  
- Fix: mark as illustrative or update the interface comment to match RFC-0002 precisely.
