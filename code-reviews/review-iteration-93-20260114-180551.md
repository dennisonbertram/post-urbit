## Summary
Several cross-document mismatches remain in handshake signature construction and relay encapsulation semantics that would cause authentication/relay interop failures if different implementers follow different documents. There are also a few high-impact ambiguities (error-code selection, encoding rules, and “placeholder” vectors) that should be tightened.

## Issues Found

### BLOCKING

B1 — Handshake signature input uses **raw IID/DID bytes** in RFC, but `peer-handshake.md` is ambiguous and can be read as using **Base32 string bytes**:  
- **Where:** `spec/01-transport-connectivity/peer-handshake.md` → “Challenge Signature” and “ClientAuth” sections (the `concat(..., client_iid, server_iid)` description), and “Device Signature” sections.  
- **Expected (authoritative):** `spec/06-rfcs/RFC-0002-transport.md` §5.7 and §5.8 explicitly require `decode_base32(iid)` / `decode_base32(did)` to 20 raw bytes before concatenation; `spec/00-shared/test-vectors.md` “Test Vector 7: Peer Handshake Challenge” also uses `client_iid_raw`/`server_iid_raw` (20 bytes each) in the transcript.  
- **Why it breaks interop:** If one implementation concatenates UTF-8 bytes of the 32-char Base32 string while another uses decoded 20-byte values, the SHA256 digest and Ed25519 signature will never match → handshake fails.  
- **Fix:** In `peer-handshake.md`, replace `client_iid`/`server_iid` (and DID fields) in the signature transcript with explicit `DecodeBase32(client_iid)` / `DecodeBase32(server_iid)` (20 bytes), matching RFC-0002 + test vector language.

B2 — Handshake JSON field encoding rules for `client_nonce`, `server_nonce`, `tls_binding`, and signatures are inconsistent/underspecified (Base64 alphabet + no-padding):  
- **Where:** `spec/01-transport-connectivity/peer-handshake.md` → ClientHello/ServerHello schemas use placeholders like `<32-bytes-base64>` and `<Ed25519-signature-base64>` without stating **Base64 standard alphabet** vs **Base64url**, and without stating **no padding**.  
- **Expected (authoritative):** `spec/06-rfcs/RFC-0002-transport.md` §5.5/§5.6/§5.7 require “Base64 standard, no padding” for nonces, tls_binding, and signatures; `spec/00-shared/layer-integration.md` → “Global Conventions / Encoding” mandates “Base64 standard (no padding)” for keys/signatures and distinguishes Base64url for tokens.  
- **Why it breaks interop:** An implementer following `peer-handshake.md` could emit padded Base64 (`=`) or Base64url (`-_`). A strict RFC-0002 implementation will reject or compute a different transcript.  
- **Fix:** Update `peer-handshake.md` to explicitly match RFC-0002: Base64 **standard alphabet** and **no padding** for these fields.

B3 — Relay encapsulation/forwarding semantics are **authoritative in RFC-0002** but ambiguous in `relay-protocol.md` (PURL forwarded unchanged vs stripped):  
- **Where:**  
  - Ambiguous layer doc: `spec/01-transport-connectivity/relay-protocol.md` → “Relay Wire Protocol” / “Relay Data Flow” describes PURL framing but does not explicitly state whether the relay forwards the **entire PURL packet unchanged** to the destination, and does not state receiver decapsulation rules.  
  - Authoritative: `spec/06-rfcs/RFC-0002-transport.md` §7.6 “Encapsulation Model” explicitly says relay forwards **the entire PURL packet unchanged** for DATA packets and recipients decapsulate; it also states recipients MUST NOT validate tokens on forwarded DATA packets. `spec/00-shared/layer-integration.md` also states “Recipients MUST NOT validate the allocation token…”.  
- **Why it breaks interop:** If a relay implementation strips the PURL header and forwards only the inner QUIC payload, a receiver following RFC-0002 decapsulation will drop packets (expects PURL). Conversely, if receiver expects raw QUIC but gets PURL, it may feed garbage into QUIC.  
- **Fix:** Make `relay-protocol.md` explicitly mirror RFC-0002 §7.6: (1) DATA packets forwarded unchanged including PURL header, (2) receiver decapsulates before passing to QUIC, (3) receiver ignores token (may only sanity-check destination IID).

### HIGH

H1 — Wrong/overloaded error code suggested for “duplicate long-lived streams” (STREAM_TYPE_UNKNOWN used for “stream already open”):  
- **Where:** `spec/00-shared/layer-integration.md` → “QUIC Stream Initiation Rules” says opening a second stream of same type is a protocol error “close with STREAM_TYPE_UNKNOWN”.  
- **Conflicts with:** `spec/06-rfcs/RFC-0002-transport.md` §9.2 defines `0x102 STREAM_TYPE_UNKNOWN` as “Unknown stream type byte” (not “duplicate stream type”).  
- **Impact:** Different implementations will close with different codes or interpret 0x102 differently, complicating debugging and possibly automation.  
- **Fix:** Either (a) define a new transport error code (e.g., `STREAM_ALREADY_OPEN`) in RFC-0002 §9.2 and use it everywhere, or (b) specify using QUIC `PROTOCOL_VIOLATION` (0x0A) or `HANDSHAKE_FAILED`/`APPLICATION_ERROR` consistently—pick one and align all docs.

H2 — `.postapp` manifest signature wording inconsistency (“manifest.json with signature”):  
- **Where:** `spec/04-app-runtime/manifest-schema.md` → Package directory listing comments “manifest.json … with signature” while the same document repeatedly says signature is **only** in `SIGNATURE` file; also echoed in some packaging prose.  
- **Impact:** Confusing but not wire-breaking; implementers might mistakenly add/expect `manifest.signature`.  
- **Fix:** Remove “with signature” phrasing; consistently say “manifest.json (unsigned; signature in SIGNATURE file)”.

H3 — “Placeholder” PUSE test vector layout is materially inconsistent with RFC-0003 and risks copy/paste errors:  
- **Where:** `spec/00-shared/test-vectors.md` → “Test Vector 10: PUSE Envelope (Placeholder)” omits fields that exist in RFC-0003 (e.g., sender IID, ciphertext length) and shows a different layout.  
- **Impact:** Even labeled placeholder, it’s structurally misleading.  
- **Fix:** Replace with an exact byte layout excerpt that matches RFC-0003 §3.2 (or delete entirely and only reference RFC-0003).

H4 — App-defined message payload conversion (CBOR↔JSON) is underspecified and not clearly tied back to App Runtime CBOR constraints:  
- **Where:** `spec/06-rfcs/RFC-0003-messaging.md` §8.2 “Host API to PUSE Plaintext Mapping (Normative)” defines CBOR→JSON mappings for byte strings and tags, but doesn’t specify how to map CBOR maps with non-text keys, floats, or other CBOR types; `spec/04-app-runtime/abi.md` defines CBOR constraints but doesn’t cross-reference RFC-0003’s conversion rules.  
- **Impact:** Cross-implementation app payload ambiguity (not crypto failure, but app-level interop divergence).  
- **Fix:** Either (a) constrain Host API message `content` CBOR to a JSON-compatible subset, or (b) fully specify a total CBOR→JSON mapping (including integer keys, arrays/maps, floats) and the reverse JSON→CBOR re-encoding rule for delivery to apps.

### MEDIUM

M1 — Relay payload size limits are not consistently restated in the non-RFC relay doc:  
- **Where:** RFC-0002 §7.4 mandates “Receivers MUST silently drop PURL packets with Payload Length > 1200”; `spec/01-transport-connectivity/relay-protocol.md` defines u16 length but doesn’t repeat the strict 1200 rule in the wire-format section.  
- **Impact:** Doc drift risk; could become interop-relevant if someone relies on u16 capacity.  
- **Fix:** Add the same normative 1200-byte inner payload cap (and drop behavior) to `relay-protocol.md`’s wire format section, pointing to RFC-0002 §7.4.
