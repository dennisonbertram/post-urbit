## Summary
The spec set is close to internally consistent, but there is at least one normative cross-document contradiction (MUST vs SHOULD) around **genesis IDOC DHT storage**, plus several high-risk documentation mismatches that can mislead implementers about **PUSE wire format** and **verification order**.

## Issues Found

### BLOCKING

**B1 — Genesis IDOC DHT storage requirement is contradictory (MUST vs SHOULD):**  
`spec/00-shared/layer-integration.md` makes genesis-record storage a **MUST** and defines strict immutability/refresh semantics as a mandatory part of DHT integration, but `spec/06-rfcs/RFC-0001-identity-document.md` only makes genesis storage a **SHOULD**.

- **Layer-integration (normative):** “Identity documents are stored under TWO DHT keys” and “When publishing a genesis document (sequence=0), write to BOTH keys” (File: `spec/00-shared/layer-integration.md`, section **“Genesis Key Semantics (Normative)”**).
- **RFC-0001:** “implementations SHOULD also store genesis documents” (File: `spec/06-rfcs/RFC-0001-identity-document.md`, §**12.3 Genesis Document Storage**).

**Why this is BLOCKING:** DHT behavior/security assumptions diverge by conformance target. A network with mixed implementations will not have a clear interoperability baseline for genesis anchoring (some will not publish/serve the genesis key at all, others will rely on it for TOFU/continuity auditing). This needs a single normative stance across RFC-0001 and the integration spec.

**Fix:** Choose one:
- Make RFC-0001 §12.3 **MUST** (and keep layer-integration as-is), or
- Downgrade layer-integration’s “stored under TWO keys” requirement to **SHOULD**, and explicitly define required client behavior when genesis key is missing.

### HIGH

**H1 — RFC-0003 PUSE parsing/verification order is internally inconsistent:**  
RFC-0003 §3.8 lists “Verify signature” before “fetch identity document for sender IID”, but signature verification requires the sender’s signing key (from the identity document).

- File: `spec/06-rfcs/RFC-0003-messaging.md`, §**3.8 Parsing Order** (steps 7–8).

**Impact:** Implementers following the literal order may hit an impossible step ordering, leading to ad-hoc behavior and inconsistent implementations.

**Fix:** Reorder/clarify §3.8 to: parse → fetch sender IDOC (or cached keys) → verify signature → derive key → decrypt.

---

**H2 — `test-vectors.md` PUSE placeholder layouts contradict RFC-0003 and can mislead implementers:**  
Even though marked “placeholder” and “implement from RFC-0003”, the byte layout and flags described are **wrong** relative to RFC-0003.

- **Missing `ciphertext_length` field:** Placeholder “PUSE Envelope Layout” omits the 4-byte ciphertext length that RFC-0003 §3.2 requires.  
  File: `spec/00-shared/test-vectors.md`, **Test Vector 10: PUSE Envelope (Placeholder)** vs File: `spec/06-rfcs/RFC-0003-messaging.md`, §**3.2 Wire Format**.
- **Incorrect flags bit allocation:** Placeholder defines bits 0–2 as “message type” etc., but RFC-0003 defines bits 0–1 recipient type, bit2 ack, bit3 priority, bit4 forwardable.  
  File: `spec/00-shared/test-vectors.md`, **Test Vector 10** vs File: `spec/06-rfcs/RFC-0003-messaging.md`, §**3.3 Flags Byte**.
- **Ratchet header field order mismatch:** Placeholder shows `DH || N || PN`, but RFC-0003 uses `DH || PN || N`.  
  File: `spec/00-shared/test-vectors.md`, **Test Vector 11** vs File: `spec/06-rfcs/RFC-0003-messaging.md`, §**3.4.3 Ratchet Extension**.

**Impact:** High chance of interop-breaking implementations if someone copies the placeholder.

**Fix:** Either delete the byte-layout drawings in TV10/TV11 entirely (leave only RFC references), or update them to exactly match RFC-0003.

---

**H3 — `secure-envelope.md` under-specifies `ext_len` fixed-size enforcement compared to RFC-0003:**  
RFC-0003 §3.4 mandates that `Header Extension Length` must match the fixed expected size for the extension type and that mismatches MUST be rejected. `secure-envelope.md` strongly implies fixed sizes but does not clearly restate the “reject ext_len mismatch” rule in its own normative text.

- File: `spec/03-messaging-sync/secure-envelope.md`, sections **“Envelope Structure / Wire Format”** and **“Header Extension (AAD)”**  
- File: `spec/06-rfcs/RFC-0003-messaging.md`, §**3.4 Header Extensions** (fixed-size enforcement)

**Impact:** Some implementations may accept non-canonical extensions; others will reject, creating avoidable incompatibility.

**Fix:** Add explicit language in `secure-envelope.md`: “`ext_len` MUST equal the expected fixed size for the decoded extension type; otherwise reject.”

---

**H4 — Domain separator/constant registry is missing the TLS exporter label used for `tls_binding`:**  
The “Domain Separator Registry (Normative)” centralizes protocol-critical strings, but does not include the TLS exporter label:

- File: `spec/06-rfcs/RFC-0002-transport.md`, §**4.4 TLS Binding** uses label `"post-urbit handshake binding"`.
- File: `spec/00-shared/layer-integration.md`, **Domain Separator Registry (Normative)** does not list it.

**Impact:** This label is effectively a domain-separation constant for keying material export. Missing it from the central registry risks divergent implementations.

**Fix:** Add a “TLS exporter labels” subsection (or a row) to the registry, explicitly listing `"post-urbit handshake binding"` and its byte length.

---

### MEDIUM

**M1 — Device “transport key” presence is inconsistently described across docs:**  
Layer-integration/device docs state `device_transport_key` is removed in v1, but node-daemon key hierarchy still depicts a “Device transport key (X25519)”.

- File: `spec/00-shared/layer-integration.md`, **Device Document Structure note** (“`device_transport_key` removed in v1”).
- File: `spec/05-ux-packaging/node-daemon.md`, **Key Hierarchy** diagram includes “Device transport key (X25519)”.

**Impact:** Not a wire-interop issue, but can create implementation churn/confusion.

**Fix:** Align wording: either mark it clearly “reserved / not published / not used in v1”, or remove it from the hierarchy diagram.

---

**M2 — `progress.md` contains outdated relay MTU guidance (1188 vs 1200) relative to current RFCs:**  
`progress.md` claims an older decision (“inner payload 1188”), while RFC-0002 and transport constants specify 1200.

- File: `spec/progress.md`, **Iteration 84** bullet “PURL … limits inner payload to 1188 bytes”
- File: `spec/06-rfcs/RFC-0002-transport.md`, §**7.4 PURL Wire Format** (inner payload MUST NOT exceed 1200)
- File: `spec/01-transport-connectivity/interfaces.md`, `TRANSPORT_CONSTANTS.RELAY_MAX_INNER_PAYLOAD = 1200`

**Fix:** Update or annotate `progress.md` as historical (non-normative) to avoid confusion.
