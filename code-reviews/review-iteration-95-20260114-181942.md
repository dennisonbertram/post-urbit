## Summary
Most cross-layer values (stream framing, key derivations, signature inputs, encodings) are consistent across the layer specs and RFCs. One security/interop-critical gap remains: **device revocation discovery is specified as required but lacks a complete, aligned DHT publication/lookup definition across documents**.

## Issues Found

### BLOCKING

B1 — Device revocation discovery is REQUIRED but DHT record format/lookup is underspecified and not bidirectionally consistent  
**Why this breaks interop:** `peer-handshake.md` requires device authentication when a DID is presented, and `identity-document-schema.md` states “Peers MUST check for revocation before accepting connections from a device.” Without a normative “where/how to fetch device revocations” (key, value encoding, TTL, conflict rules), two conforming implementations will diverge (some won’t check; others will check different locations/formats), leading to inconsistent acceptance/rejection of device connections.

**Where the inconsistency shows up:**
- **Spec defines a DHT namespace but not the record semantics:**  
  - `spec/00-shared/layer-integration.md` — **DHT Key Encoding (Normative)** includes:  
    - `SHA256("post-urbit:device-revocation:" || did)` → device revocation lookup  
  - `spec/00-shared/layer-integration.md` — **Domain Separator Registry** includes:  
    - Device revocation signature: `post-urbit:device-revocation:v1:`  
    - DHT device revocation key prefix: `post-urbit:device-revocation:`
- **Device revocation document exists but DHT storage/lookup is not defined in the authoritative identity RFC DHT section:**  
  - `spec/06-rfcs/RFC-0001-identity-document.md` — **§13.5 Device Revocation** defines the document + signature scheme  
  - `spec/06-rfcs/RFC-0001-identity-document.md` — **§12 DHT Storage** defines identity/genesis/device index/device doc records, **but does NOT define a device-revocation DHT record** (key, value encoding, TTL, multi-record behavior)
- **“MUST check revocation” without a canonical retrieval mechanism:**  
  - `spec/02-identity-trust/identity-document-schema.md` — **Device Revocation**: “Peers MUST check for revocation before accepting connections from a device.” (but no normative DHT key/value/TTL reference here either)

**Required fix (normative alignment):**
1. Add a **Device Revocation DHT Record** section to **RFC-0001 §12** (authoritative place), matching `layer-integration.md`:
   - Key: `SHA256("post-urbit:device-revocation:" || did_base32)` (confirm `did` input is 32-char crockford base32 lowercase, UTF-8/ASCII)
   - Value: **JCS-canonical JSON** of the device revocation document from RFC-0001 §13.5 (or define an envelope if desired; today everything else uses raw JCS JSON for non-IDOC docs)
   - TTL: specify (likely align with revocations: 365 days, or explicitly justify if shorter)
   - Multiple records: define selection (e.g., highest `revoked_at`, or first-seen-wins if equal)
   - Verification rules for DHT nodes before storing (which identity signing keys are acceptable; likely current/previous/history per RFC-0001 §7.5)
2. Add a cross-reference in `identity-document-schema.md` Device Revocation section: “Device revocations are discovered via DHT key … (RFC-0001 §12.x / layer-integration.md …)”.

### HIGH

H1 — Test vector placeholders for PUSE contradict RFC-0003 wire format and could mislead implementers  
Even though marked “placeholder”, the content includes **structural inaccuracies** that conflict with the authoritative PUSE spec (RFC-0003 + `secure-envelope.md`), risking divergent implementations.

- `spec/00-shared/test-vectors.md` — **Test Vector 10: PUSE Envelope (Placeholder)**  
  Problems vs RFC-0003:
  - Missing **Sender IID** field (RFC-0003 §3.2 includes Sender IID 20 bytes)
  - Missing **Ciphertext Length** field (RFC-0003 §3.2 includes 4-byte ct_len)
  - Flags bit layout described there does not match RFC-0003 §3.3 (placeholder mentions “message type bits 0-2”, etc.)
- `spec/00-shared/test-vectors.md` — **Test Vector 11: PUSE Ratchet Message (Placeholder)**  
  Mentions ratchet header “inside ciphertext”; current spec requires ratchet parameters in the **header extension (AAD)** (RFC-0003 §3.4.3 + `spec/03-messaging-sync/secure-envelope.md`).

**Fix:** Replace the placeholder layouts with an exact copy of RFC-0003 §3.2/§3.4 summaries (or delete all byte-layout claims and only point to RFC-0003).

H2 — IDOC envelope canonicalization: receiver strictness differs between schema doc and RFC  
- `spec/02-identity-trust/identity-document-schema.md` — **Wire Format / JSON Canonicalization (Normative)** says:  
  “Implementations MUST reject IDOC envelopes where the JSON is not JCS-canonical”
- `spec/06-rfcs/RFC-0001-identity-document.md` — **§6.2 / §11.4 parsing algorithm** does not explicitly require receiver-side rejection of non-JCS JSON (it normatively requires canonicalization but the parsing/validation text doesn’t clearly impose a MUST-reject rule on receivers).

**Fix:** Add explicit receiver validation text in RFC-0001 (best: in §11 Wire Format / parsing) to match `identity-document-schema.md`, or downgrade the schema doc requirement to SHOULD (not recommended; canonical-bytes enforcement is important to avoid “same JSON different bytes” ambiguity).

H3 — Domain separator / crypto-context registry is missing the TLS exporter label  
The repository has a “Domain Separator Registry (Normative)” intended to be complete for cryptographic contexts. The TLS exporter label is security-critical and protocol-visible:

- Used in:
  - `spec/06-rfcs/RFC-0002-transport.md` — **§4.4 TLS Binding** label `"post-urbit handshake binding"`
  - `spec/01-transport-connectivity/peer-handshake.md` — **TLS Binding** section

- Not listed in:
  - `spec/00-shared/layer-integration.md` — **Domain Separator Registry (Normative)**

**Fix:** Add an entry (or a separate “Crypto Context Strings Registry”) for the TLS exporter label, including exact bytes/length.

### MEDIUM

M1 — App manifest docs still contain a misleading “manifest has signature” note  
- `spec/04-app-runtime/manifest-schema.md` — **Package Format / Directory Structure** shows:  
  `manifest.json # Required: App manifest with signature`  
This contradicts:
- `spec/05-ux-packaging/app-distribution.md` — signature is in separate `SIGNATURE` file
- `spec/04-app-runtime/manifest-schema.md` elsewhere (correctly) says signature is not in manifest.json

**Fix:** Change that directory comment to “App manifest (unsigned; signature in SIGNATURE file)”.

M2 — Reserved Host API methods are listed without clear per-method status markers in method tables  
- `spec/04-app-runtime/api-surface.md` lists reserved methods in tables (e.g., `messaging.list_groups`) but the “reserved” status isn’t consistently annotated inline, which can cause implementers to treat them as v1-complete.

**Fix:** Add a `Status` column to each method table (v1 vs reserved), matching `abi.md`’s authoritative registry.
