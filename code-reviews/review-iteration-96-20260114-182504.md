## Summary
The spec set is very close to internally consistent, but there are still a few cross-document mismatches/ambiguities that can lead implementers to produce incompatible wire behaviors (notably QUIC stream framing) or to accidentally break signature verification when mapping between “wire JSON” and TypeScript structs.

## Issues Found

### BLOCKING

B1 — QUIC stream framing is contradictory (length-prefix vs “payload immediately after type”):  
If an implementer follows `quic-integration.md` literally, they can omit the 4‑byte frame length prefixes and become non-interoperable with implementations following the RFC/shared glue.

- **Source A (implies no 4-byte framing):** `spec/01-transport-connectivity/quic-integration.md` — section **“Stream Opening”** shows:
  - `Stream Type (1 byte)` then `Payload...` (no 4-byte length framing shown; reads like “payload starts immediately”).
- **Source B (requires framing):** `spec/06-rfcs/RFC-0002-transport.md` — **§6.3 Message Frame Format** requires:
  - `Length (4 bytes big-endian)` + `Payload`
- **Source C (requires framing):** `spec/00-shared/layer-integration.md` — **“QUIC Stream Framing (Normative, All Stream Types)”** requires:
  - stream type once, then repeated `u32be length + payload`

**Why this is BLOCKING:** a peer expecting length-prefixed frames cannot parse a peer that writes raw payload bytes after the type byte (and vice versa).  
**Fix:** Update `quic-integration.md` to explicitly include the `u32be length` framing and/or normatively defer to RFC-0002 §6.3 in the “Stream Opening” example.

### HIGH

H1 — TLS certificate algorithm guidance is ambiguous vs “accept any certificate” policy:  
There’s a risk implementers read “Signature: Ed25519” under TLS config as a *requirement for certificate algorithms*, which contradicts the explicit “accept any cert” rule.

- `spec/01-transport-connectivity/quic-integration.md` — **“TLS Configuration”** table includes `Signature | Ed25519 (for identity binding)` (ambiguous whether TLS cert signature alg is restricted).
- `spec/00-shared/layer-integration.md` — **“QUIC TLS Certificate Policy”** says clients **MUST accept ANY certificate**, including RSA/ECDSA/Ed25519, expired, self-signed, etc.
- `spec/06-rfcs/RFC-0002-transport.md` — **§4.3** aligns with “certs not used for identity”.

**Impact:** interop failure if any implementation rejects non-Ed25519 TLS certificates.  
**Fix:** In `quic-integration.md`, rewrite the TLS table to separate:
- “Handshake identity signature algorithm: Ed25519” (post-TLS), and
- “TLS certificate signature algorithm: any (recommend ECDSA P-256 or Ed25519), clients accept any”.

---

H2 — IDOC wire optionality vs TypeScript interface “required fields” can break signature verification:  
Wire documents may omit optional fields; if a TS model forces them present and the implementation materializes defaults before JCS, signature verification can fail.

- `spec/06-rfcs/RFC-0001-identity-document.md` — **§4.3 Optional Fields** marks several fields optional; **§6.6** says defaults are semantic only and **MUST NOT** be materialized before verification.
- `spec/02-identity-trust/identity-document-schema.md` — required fields table does **not** require `keys.signing.previous`; optional fields may be absent.
- `spec/02-identity-trust/interfaces.md` — `KeySet.signing.previous: PublicKey | null` (non-optional property) and `SignatureSet.previous: Signature | null` (non-optional) encourages “always present”.

**Impact:** implementers can accidentally canonicalize a *different JSON object* than the signer signed.  
**Fix:** Make these TS fields optional (`previous?: PublicKey | null`, etc.) *or* add a very explicit rule in `interfaces.md` that:
- signature verification must operate on the raw parsed snake_case JSON object (no default insertion), and
- the typed struct is only for post-verification normalized representation.

H3 — Stream multiplicity rules exist in glue spec but not in RFC-0002 (and error code choice is off):  
`layer-integration.md` defines “at most one Identity/Sync stream per direction” and says opening a second is a protocol error closed with `STREAM_TYPE_UNKNOWN`, but RFC-0002 does not specify this constraint nor that error code.

- `spec/00-shared/layer-integration.md` — **“QUIC Stream Initiation Rules (Normative)”**:
  - “Identity/Sync: at most 1 per direction”
  - “Opening a second is a protocol error (close with STREAM_TYPE_UNKNOWN)”
- `spec/06-rfcs/RFC-0002-transport.md` — stream type codes and framing exist, but **no matching multiplicity rule** and `0x102 STREAM_TYPE_UNKNOWN` is defined as “unknown stream type byte”, not “duplicate stream”.

**Impact:** one implementation may allow multiple identity streams; another may close the connection, causing interoperability issues in multi-stream scenarios.  
**Fix:** Either:
- add the multiplicity rule + a dedicated error code to RFC-0002, or
- relax/remove the rule from `layer-integration.md`, and
- do not use `STREAM_TYPE_UNKNOWN` for “duplicate stream”; use a more appropriate existing code (e.g., `PROTOCOL_VIOLATION` / `APPLICATION_ERROR`) or define a new one.

---

H4 — Transport `AddressCandidate` shape is inconsistent across docs (relay token + relayServer type):  
- `spec/01-transport-connectivity/interfaces.md` — `AddressCandidate` has `relayServer?: string` and no `allocationToken`.
- `spec/01-transport-connectivity/nat-traversal.md` — candidate collection example uses:
  - `relayServer: relay` (object) and `allocationToken: allocation.token`

**Impact:** implementers won’t know whether tokens are part of candidate objects (needed for relay connectivity) and what type `relayServer` should be.  
**Fix:** Align `AddressCandidate` in `interfaces.md` with `nat-traversal.md` (likely `relayServer?: RelayServer` and `allocationToken?: string`).

---

H5 — “Placeholder” PUSE test vector sections contain incorrect layouts/orderings that conflict with RFC-0003:  
Even with warnings, the placeholder snippets are internally inconsistent and can mislead implementers.

- `spec/00-shared/test-vectors.md` — **Test Vector 10** placeholder omits fields that RFC-0003 requires (e.g., sender IID, ciphertext_length) and presents a different layout.
- `spec/00-shared/test-vectors.md` — **Test Vector 11** placeholder “Ratchet Header” order (`N` then `PN`) conflicts with RFC-0003 and `secure-envelope.md` (`PN` then `N`).

**Impact:** high risk of incorrect implementations by copy/paste.  
**Fix:** Replace placeholder layouts with a minimal “see RFC-0003 §3.2/§3.4” plus a byte-offset table (matching RFC-0003), or delete the misleading layouts entirely.

### MEDIUM

M1 — `spec/progress.md` contains stale historical statements that contradict current normative text (MTU sizing note):  
Example: progress log mentions an earlier “inner payload 1188 bytes” MTU fix, but the current RFC/specs define inner payload max 1200 and accept 1244 outer datagrams. This is likely just a stale changelog note, but it can confuse reviewers.

M2 — Naming inconsistency: “X3DH” terminology persists in some places even though v1 is specified as “2DH”:  
E.g., `spec/00-shared/test-vectors.md` calls it “X3DH Key Agreement” while `spec/06-rfcs/RFC-0003-messaging.md` frames it as 2DH (but keeps the `post-urbit-x3dh-v1` info string). Not a wire break, but it increases cognitive load.
