## Summary
The spec set is generally well-aligned (wire framing, encodings, signature prehash policy, and domain separators are mostly consistent), but there are **two cross-document mismatches that can plausibly produce incompatible implementations** (messaging plaintext/type registry, and genesis/DHT validation rules).

## Issues Found

### BLOCKING

B1 — Messaging plaintext/type registry is inconsistent across RFC-0003 vs layer docs/interfaces  
**Why it breaks interop:** Implementers following different documents will serialize different plaintext JSON for the same “message type”, and app runtimes won’t agree on how `messaging.send` maps onto PUSE plaintext for app-defined messages.

**Where:**
- `spec/06-rfcs/RFC-0003-messaging.md` §8.1–§8.2 (“Plaintext Format”, “Type Registry”, plus “Host API to PUSE Plaintext Mapping (Normative)”)
- `spec/03-messaging-sync/secure-envelope.md` (“Plaintext Format” + “Message Types” table)
- `spec/03-messaging-sync/interfaces.md` (“MessageType” union + `TypingContent`, `AppContent`, `EditContent`, `DeleteContent`, `SystemContent`)

**Conflicts (examples):**
1. **Typing message schema**
   - RFC-0003: `typing` → content only `{ "is_typing": boolean }` (no `expires_at` inside content); expiry is not defined as required in content.
   - Interfaces: `TypingContent` includes `expiresAt: Timestamp` (required) inside content, while the base message structure already has `expiresAt?: Timestamp` at the top level. This creates ambiguity and divergent wire encodings.

2. **App message schema**
   - RFC-0003 (normative mapping): app-defined Host API `message_type` becomes PUSE plaintext `"type":"app"` with content `{ "app_id": "<message_type>", "data": <CBOR-decoded> }`.
   - Interfaces: `AppContent` uses `{ appId, appVersion, payload }` (different field names and extra `appVersion`), and the interface set does not define the normative `{app_id,data}` mapping.

3. **Extra message types present in interfaces but not specified/registered in RFC-0003**
   - Interfaces include `edit`, `delete`, `system` in `MessageType` and define payload schemas.
   - RFC-0003 §8.2 does not define these types (nor mark them as reserved), so a strict RFC implementation could reject or ignore them.

**Fix direction (normative):**
- Either:
  - **(Preferred)** Update `spec/03-messaging-sync/interfaces.md` to match RFC-0003’s §8 registry and schemas; explicitly mark extra message types as *reserved/future* with rejection semantics; and define a clear wire↔API mapping for `typing.expires_at` and for `app` messages; or
  - Update RFC-0003 §8 to explicitly include `edit/delete/system` and reconcile `typing` expiration semantics and `app` message content fields.

B2 — Genesis/DHT validation rules are not fully aligned (genesis immutability + “sequence=0” enforcement + genesis invariants)  
**Why it breaks interop:** A DHT node/client implementing only one document’s rules can accept/store genesis-key records that other implementations will reject, breaking bootstrap/genesis anchoring and (in the worst case) producing persistent same-IID disagreements.

**Where:**
- `spec/00-shared/layer-integration.md` (“Genesis Key Semantics (Normative)” + “Storage rules” + DHT verification steps)
- `spec/06-rfcs/RFC-0001-identity-document.md`
  - §7.1 (Genesis document requirements include `keys.signing.genesis == keys.signing.current`)
  - §12.3 (Genesis DHT key/value semantics)
  - §12.7 (DHT verification rules)

**Inconsistencies / missing normative checks:**
1. **Genesis key write acceptance must enforce `sequence == 0`**
   - Layer integration: “DHT nodes MUST reject writes to `post-urbit:genesis:` with sequence > 0.”
   - RFC-0001 §12.3: states the genesis key stores “sequence=0 document”, but does **not** explicitly state a MUST-level *rejection rule* for seq>0 writes (especially when no prior record exists).

2. **Genesis-document invariant enforcement in DHT-node verification**
   - RFC-0001 §7.1 requires `keys.signing.genesis == keys.signing.current` for sequence 0.
   - RFC-0001 §12.7 “Verification (New Identity Records)” lists checks (iid binding + `signatures.current`), but does not explicitly include the §7.1 genesis invariant when a DHT node is validating a genesis doc for storage.
   - Layer-integration’s DHT-node “Verification (New Records)” likewise omits this explicit genesis-only invariant check.

**Fix direction (normative):**
- In **RFC-0001 §12.3 and/or §12.7**, add explicit MUST-level checks:
  - When storing under `post-urbit:genesis:`: the document **MUST** have `sequence == "0"` and **MUST** satisfy genesis invariants (including `keys.signing.genesis == keys.signing.current`).
  - When validating for storage generally: DHT nodes MUST apply the same structural invariants as RFC-0001 §7 (with branch on `sequence`).
- In `layer-integration.md`, either:
  - reference RFC-0001 §7/§12.7 as the complete verification rule set, or
  - explicitly list the genesis-only invariant check in the “Verification (New Records)” step list.

### HIGH

H1 — Media content encoding is ambiguous between messaging interfaces and RFC wire format  
**Where:**
- `spec/03-messaging-sync/interfaces.md` (`MediaContent.key: Uint8Array`, `MediaContent.nonce: Uint8Array`)
- `spec/06-rfcs/RFC-0003-messaging.md` §8.4 (media plaintext example uses Base64 strings for `key` and `nonce`)
- `spec/03-messaging-sync/secure-envelope.md` (media plaintext example doesn’t specify encoding)

**Problem:** The wire plaintext is UTF-8 JSON; raw bytes must be encoded. RFC-0003 implies Base64 strings, while the TS interfaces present bytes with no explicit mapping rule. Different implementations could emit different JSON (base64 vs array-of-ints vs something else).

**Fix:** Add a normative mapping section (in `interfaces.md` and/or `secure-envelope.md`) stating:
- On-wire PUSE plaintext JSON uses **Base64 standard (no padding)** strings for binary fields like media `key` and `nonce`.
- In-memory APIs may use `Uint8Array`, but serializers MUST convert to/from Base64 standard no padding.

H2 — Relay receiver “destination sanity check” mentions DIDs even though PURL destination is IID-only  
**Where:**
- `spec/01-transport-connectivity/relay-protocol.md` (“Destination IID sanity check … matches their own IID (or one of their DIDs)”)
- `spec/06-rfcs/RFC-0002-transport.md` §7.4 (Destination IID field is explicitly “Destination IID (raw bytes) 20 bytes”)

**Problem:** This suggests the destination field might sometimes be a DID, which is not specified anywhere else for PURL routing and could cause acceptance of misrouted traffic.

**Fix:** Change the sanity check to “MUST match my IID” (or explicitly define an extension if DIDs are intended as routable destinations, and update RFC-0002 accordingly).

H3 — Bulk stream opcode registry is referenced but not actually specified as a complete registry  
**Where:**
- `spec/00-shared/layer-integration.md` (stream type table: “Bulk … See RFC-0002 §6.3 for opcodes”)
- `spec/06-rfcs/RFC-0002-transport.md` §6.3 (mentions “first 2 bytes = opcode” and gives examples, but no normative opcode registry section or semantics beyond the brief list)

**Problem:** Implementers cannot build interoperable bulk transfers without a stable opcode registry, framing, and end-of-transfer/error semantics.

**Fix:** Add a short normative “Bulk opcode registry” subsection (either in RFC-0002 §6 or a new §6.5), defining:
- opcodes, payload formats, termination, error handling, max chunk sizes, and whether bulk frames are additionally length-prefixed (they are via the common 4-byte frame length).

H4 — NAT hole-punch probe “Sender IID truncated” is underspecified  
**Where:** `spec/01-transport-connectivity/nat-traversal.md` (“Sender IID (truncated, first 8 bytes)”)

**Problem:** It does not explicitly say “first 8 bytes of the 20-byte raw IID” vs some other representation. Ambiguity here risks probe format mismatch.

**Fix:** Specify: “Sender IID = first 8 bytes of `decode_base32(iid)` (raw IID bytes).”

### MEDIUM

M1 — App manifest schema text contradicts itself about embedded signatures  
**Where:** `spec/04-app-runtime/manifest-schema.md` (“Package Format” directory listing says `manifest.json # Required: App manifest with signature`) while the same file and `spec/05-ux-packaging/app-distribution.md` are clear that signatures live only in `SIGNATURE`.

**Fix:** Update the directory listing comment to “manifest.json (no embedded signature)”.

M2 — Node daemon key hierarchy still lists a “device transport key” while v1 explicitly doesn’t use it  
**Where:** `spec/05-ux-packaging/node-daemon.md` (“Device transport key (X25519)”) vs `spec/00-shared/layer-integration.md` (“device_transport_key removed in v1”) and multiple transport/handshake docs stating device auth uses device signing key.

**Fix:** Either mark the device transport key as “future-only, not generated in v1” or explicitly state it MAY exist internally but MUST NOT affect any v1 wire protocol.

M3 — PUSE placeholders in test vectors include non-authoritative layouts that conflict with RFC-0003  
**Where:** `spec/00-shared/test-vectors.md` Test Vector 10/11 placeholders.

They are labeled as placeholders and point to RFC-0003, so not fatal, but the placeholder layouts differ (e.g., missing `ciphertext_length`, header field omissions). This can still mislead implementers skimming.

**Fix:** Replace the placeholder diagrams with a direct excerpt pointer to RFC-0003 §3.2 (or reproduce the exact RFC layout verbatim).
