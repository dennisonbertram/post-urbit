## Summary
The spec set is close to internally consistent, but there is a **relay allocation binding semantic contradiction** inside RFC-0002 (and echoed by the Transport API), which can lead to incompatible relay implementations. A few other cross-document mismatches (MailboxService fields, AddressCandidate shape, and a wrong section reference) should be corrected to avoid implementer divergence.

## Issues Found

### BLOCKING

B1 — Relay allocation binding semantics are contradictory (would break relay connectivity):  
- **What conflicts**
  - `spec/06-rfcs/RFC-0002-transport.md` **§7.8 “UDP Binding Establishment (Two-Step Model)”** states binding is **pending** after HTTPS allocation and is established by the **first UDP PURL** packet.  
  - `spec/06-rfcs/RFC-0002-transport.md` **§7.10 “Allocation Binding”** states: “Allocations are bound to the source IP:port at creation time”, which implies binding is known/locked at HTTPS allocation time (impossible / different behavior).  
  - `spec/01-transport-connectivity/interfaces.md` **RelayAllocation** returns `boundAddress` and `boundPort` as if known at allocation time, reinforcing the conflicting interpretation.
- **Why this is interop-breaking**
  - A relay that “binds at creation time” may attempt to bind to the HTTPS TCP source port (wrong) or reject the first UDP packet if it comes from a different 5-tuple. A relay that follows the two-step model will accept the first UDP packet to establish binding. These behaviors are incompatible, and clients behind NAT will fail against one of them.
- **Concrete places**
  - `spec/06-rfcs/RFC-0002-transport.md` §7.8 vs §7.10  
  - `spec/01-transport-connectivity/interfaces.md` under `interface RelayAllocation { boundAddress; boundPort; ... }`
- **Fix**
  - In RFC-0002 §7.10, change wording to “Allocations are bound to the source IP:port **when the first valid UDP PURL packet is received** (initial bind)” and explicitly state the HTTPS request does **not** establish UDP binding.  
  - In Transport interfaces, make `boundAddress`/`boundPort` **optional** and add an explicit `bindingState: 'pending'|'bound'` (or an event like `onRelayAllocationBound`) so the API cannot imply the UDP mapping is known at HTTPS allocation time.

### HIGH

H1 — MailboxService interface in glue doc does not match RFC-0003 mailbox wire/API semantics:  
- **Mismatch**
  - `spec/00-shared/layer-integration.md` “MailboxService Interface” omits fields required/defined by RFC-0003 retrieval semantics:
    - RFC-0003 retrieval includes `sender_iid` and `size` and returns `stored_at`, whereas the interface provides only `{ messageId, envelope, storedAt }`.
    - RFC-0003 store response includes `stored_at` (and `expires_at`), while the interface’s `store()` return type omits `storedAt`.
- **Why it matters**
  - Even though RFC-0003 is declared authoritative, the glue doc is explicitly positioned as integration guidance; mismatched fields are a common source of “implementation by interface” mistakes.
- **Concrete places**
  - `spec/00-shared/layer-integration.md` “MailboxService Interface”  
  - `spec/06-rfcs/RFC-0003-messaging.md` §7.4.1 / §7.4.2
- **Fix**
  - Update the TypeScript interface to include (at least) `senderIid` and `size` on retrieved messages and include `storedAt` in the store response, or explicitly label the interface as a **local internal abstraction** and provide a separate “HTTP wire JSON schema” mapping table aligned to RFC-0003.

H2 — AddressCandidate type shape is inconsistent between NAT traversal doc and Transport interfaces:  
- **Mismatch**
  - `spec/01-transport-connectivity/nat-traversal.md` defines `AddressCandidate` with `allocationToken?: string` when `type == 'relay'`.
  - `spec/01-transport-connectivity/interfaces.md` defines `AddressCandidate` without `allocationToken` (it has `relayServer?: string` only).
- **Why it matters**
  - This is an intra-layer inconsistency that will cause different components (or different implementers) to model candidates differently, especially in ICE-like pairing logic.
- **Fix**
  - Either (a) add `allocationToken?: string` to the canonical Transport interface type, or (b) remove it from nat-traversal.md and instead reference the relay allocation token as coming from `RelayAllocation.token`, not as an AddressCandidate field.

H3 — Incorrect cross-reference in RFC-0002 handshake verification steps:  
- **Issue**
  - `spec/06-rfcs/RFC-0002-transport.md` **§5.11 “Server Verifies Client”** step 6 says: “If `client_did` provided, verify device signature per §5.7”. Device signature is specified in **§5.8**, while §5.7 is challenge signature.
- **Fix**
  - Update the reference to §5.8 (and check for any other “§5.7/§5.8” swaps).

### MEDIUM

M1 — PUSE placeholder test vector text can mislead about signature coverage:  
- **Issue**
  - `spec/00-shared/test-vectors.md` “Test Vector 10: PUSE Envelope (Placeholder)” says `Signature: Ed25519 over header` (ambiguous / implies not covering nonce+ciphertext), while RFC-0003 requires signing **all bytes before the signature field**.
- **Fix**
  - Change placeholder wording to “Ed25519 over entire envelope except signature field” (or remove the signature line entirely in the placeholder).

M2 — Terminology drift: “X3DH” naming persists where the RFC calls it “2DH”:  
- **Issue**
  - `spec/03-messaging-sync/double-ratchet.md` still uses “X3DH” terminology in places, while `spec/06-rfcs/RFC-0003-messaging.md` is explicit that v1 is **2DH** (no prekeys).
- **Fix**
  - Rename references in the layer doc to “2DH” (keeping the domain string `post-urbit-x3dh-v1` unchanged unless you intentionally want a breaking change).
