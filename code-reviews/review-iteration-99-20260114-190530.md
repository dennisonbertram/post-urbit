## Summary
The RFCs are generally coherent and most layer documents align. However, there is at least one protocol-level contradiction around DHT TTL refresh semantics that will cause divergent behavior (and thus unreliable discovery) across conforming implementations.

## Issues Found

### BLOCKING

- **DHT identity record TTL requires refresh, but update rules forbid byte-identical refresh (forces sequence bumps or expiration)**
  - **What conflicts (quotes)**
    - RFC-0001 defines short-lived DHT records:  
      > “TTL: 86400 seconds (24 hours)”  
      — `spec/06-rfcs/RFC-0001-identity-document.md` §12.2
    - RFC-0001 update authorization forbids non-increasing sequence writes:  
      > “Compare `sequence` numbers: new sequence MUST be > existing sequence”  
      — `spec/06-rfcs/RFC-0001-identity-document.md` §12.7
    - The operational layer assumes periodic refresh without implying sequence bumps:  
      > “Identity publish | 24 hours | Refresh DHT record”  
      — `spec/05-ux-packaging/node-daemon.md` §Background Services → Scheduled Tasks
    - The shared integration doc explicitly adds “byte-identical refresh” semantics for **genesis** but not for the **current** identity record:  
      > “DHT nodes MUST accept byte-identical refreshes (idempotent writes) … This preserves immutability … while ensuring liveness”  
      — `spec/00-shared/layer-integration.md` §Genesis TTL and Refresh (Normative)
  - **Why this breaks interop**
    - With a 24h TTL, identities must either (a) republish the same document bytes to refresh TTL, or (b) increment `sequence` (and often `timestamp`) purely to keep the record alive.
    - Today, a DHT node that implements RFC-0001 §12.7 strictly will **reject byte-identical refresh** for the mutable `post-urbit:identity:` key because `sequence` is not greater—causing records to expire even though the owner is “refreshing”.
    - Other implementations will inevitably choose different behavior (accept identical refresh; bump sequence daily; store multi-values), yielding incompatible expectations about liveness and producing “works on my network” discovery failures.
  - **Concrete file paths and section numbers**
    - `spec/06-rfcs/RFC-0001-identity-document.md` §12.2, §12.7
    - `spec/00-shared/layer-integration.md` §Genesis TTL and Refresh (Normative), §DHT Record Format → Update Authorization (Existing Records)
    - `spec/05-ux-packaging/node-daemon.md` §Background Services → Scheduled Tasks
  - **Suggested fix**
    - In **RFC-0001 (authoritative)**, add explicit TTL refresh rules for the **current identity record** (not just genesis), mirroring genesis behavior:
      - If a DHT node already has a value for `SHA256("post-urbit:identity:" || iid)` and receives a **byte-identical** IDOC envelope, it **MUST** treat it as an idempotent refresh and extend TTL (even if `sequence` is equal).
      - If the incoming value is not byte-identical, then enforce the existing rule: `new.sequence MUST be > existing.sequence` plus key continuity / recovery proof checks.
    - Also add a sentence in RFC-0001 §12.2 stating identity owners **SHOULD** refresh the current identity record before TTL expiry (same as genesis).
    - Apply the same “byte-identical refresh extends TTL” rule to device docs and device index records if they are intended to be refreshed without semantic updates.

### HIGH

- **Terminology “prehash policy” can be misread as Ed25519ph (interop-breaking)**
  - **What conflicts (quotes)**
    - Shared doc introduces “prehash” framing:  
      > “Ed25519 signing can operate on raw bytes directly … or on a prehashed digest.”  
      — `spec/00-shared/layer-integration.md` §Signature Prehash Policy (Normative)
    - Transport RFC defines signatures as signing the 32-byte SHA-256 output as the Ed25519 *message*:  
      > `challenge_signature = Ed25519_Sign(server_signing_key, SHA256(challenge_data))`  
      — `spec/06-rfcs/RFC-0002-transport.md` §5.7  
  - **Why this breaks interop**
    - Many crypto stacks expose both “Ed25519” and “Ed25519ph”. A reader could interpret “prehash” as requiring **Ed25519ph**, which produces different signatures than “Ed25519(sign(sha256(...)))”.
    - Two implementations could both claim conformance yet generate incompatible signatures.
  - **Concrete file paths and section numbers**
    - `spec/00-shared/layer-integration.md` §Signature Prehash Policy (Normative)
    - `spec/06-rfcs/RFC-0002-transport.md` §5.7, §7.8, §7.11
    - `spec/06-rfcs/RFC-0003-messaging.md` §7.3 (mailbox token signing)
  - **Suggested fix**
    - Add a normative clarification in the shared doc (and ideally in RFC-0002 and RFC-0003):  
      “All signatures use **standard Ed25519** (RFC 8032). When this specification says `Ed25519_Sign(key, SHA256(x))`, the 32-byte SHA-256 digest is the **message input** to standard Ed25519. **Ed25519ph MUST NOT be used**.”

- **Layer docs still contain misleading (though labeled “placeholder”) PUSE wire details that contradict RFC-0003**
  - **What conflicts (quotes)**
    - Placeholder vector describes a different flags layout and omits `ciphertext_length`:  
      > “Flags byte structure: Bits 0-2: Message type …”  
      > “… Ciphertext: <variable> … Signature …” (no ciphertext length field)  
      — `spec/00-shared/test-vectors.md` Test Vector 10 (Placeholder)
    - RFC-0003 defines flags bits 0-1 as recipient type and includes a 4-byte ciphertext length:  
      > “Flags … Recipient type: 00=1:1, 01=group …”  
      > “Ciphertext Length … 4 bytes (big-endian)”  
      — `spec/06-rfcs/RFC-0003-messaging.md` §3.2–§3.3
  - **Why this breaks interop**
    - Even with a “placeholder” warning, implementers frequently copy test-vector layouts into code. This specific mismatch would produce incompatible bytes and parsing.
  - **Concrete file paths and section numbers**
    - `spec/00-shared/test-vectors.md` Test Vector 10
    - `spec/06-rfcs/RFC-0003-messaging.md` §3.2–§3.3
  - **Suggested fix**
    - Replace the placeholder layout with either:
      1) a minimal, correct byte layout excerpt copied from RFC-0003 §3.2, or  
      2) remove the incorrect field breakdown entirely and only reference RFC-0003.

- **Duplicate-stream error handling uses an unrelated error code (confusing implementers)**
  - **What conflicts (quotes)**
    - Layer integration says duplicate stream type should close with STREAM_TYPE_UNKNOWN:  
      > “Opening a second stream of the same type is a protocol error (close with STREAM_TYPE_UNKNOWN).”  
      — `spec/00-shared/layer-integration.md` §QUIC Stream Initiation Rules (Normative)
    - Transport RFC defines STREAM_TYPE_UNKNOWN specifically as:  
      > “0x102 | STREAM_TYPE_UNKNOWN | Unknown stream type byte”  
      — `spec/06-rfcs/RFC-0002-transport.md` §9.2
  - **Why this breaks interop**
    - Peers may key recovery/telemetry off error codes. Overloading “unknown type” to mean “duplicate type” leads to inconsistent retry logic and confusing diagnostics.
  - **Concrete file paths and section numbers**
    - `spec/00-shared/layer-integration.md` §QUIC Stream Initiation Rules (Normative)
    - `spec/06-rfcs/RFC-0002-transport.md` §9.2
  - **Suggested fix**
    - Either (a) specify PROTOCOL_VIOLATION / APPLICATION_ERROR with a new transport code (e.g., `0x109 DUPLICATE_STREAM_TYPE`), or (b) define duplicate-stream behavior in RFC-0002’s error registry.

### MEDIUM

- **Non-RFC transport NAT traversal wire formats lack explicit cross-reference to “big-endian by default”**
  - **What conflicts (quote)**
    - NAT discovery response includes multi-byte integers but does not reiterate endianness locally:  
      > “Observed Port | 2 bytes”  
      — `spec/01-transport-connectivity/nat-traversal.md` §Discovery Protocol (STUN-like)
    - Endianness default is defined elsewhere:  
      > “All multi-byte integers in binary wire formats are big-endian … unless explicitly stated otherwise.”  
      — `spec/00-shared/layer-integration.md` §Global Conventions → Endianness
  - **Why this matters**
    - Not an interop break if implementers follow the shared convention, but this is a common “miss” when implementing isolated documents.
  - **Concrete file paths and section numbers**
    - `spec/01-transport-connectivity/nat-traversal.md` §Discovery Protocol (STUN-like)
    - `spec/00-shared/layer-integration.md` §Global Conventions → Endianness
  - **Suggested fix**
    - Add a single sentence in `nat-traversal.md` explicitly: “All multi-byte integers in PUDS/PUHP messages are big-endian (network byte order) per layer-integration.md.”

- **Secure-envelope layer doc omits UUID byte-order reminder (RFC already defines it)**
  - **What conflicts (quote)**
    - Secure-envelope says “Message ID … 16 bytes (UUID)” without stating RFC4122 byte order.  
      — `spec/03-messaging-sync/secure-envelope.md` §Envelope Structure
    - RFC-0003 defines UUID network byte order and points to shared section.  
      — `spec/06-rfcs/RFC-0003-messaging.md` §3.2
  - **Why this matters**
    - Not interop-breaking if RFC-0003 is followed, but it’s a common implementation pitfall.
  - **Suggested fix**
    - Add a one-line reference in `secure-envelope.md` pointing to RFC-0003 §3.2 / `layer-integration.md` UUID section.
