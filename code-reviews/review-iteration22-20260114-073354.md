STATUS: NOT-COMPLETE  
B1: RFC-0003 §3.2 states PUSE permits an “empty extension” (ext_len=0) and a variable header extension up to 1024 bytes, while RFC-0003 §3.4 and `03-messaging-sync/secure-envelope.md` require **exactly one** header extension with a **fixed** size and explicitly reject `ext_len == 0`; this is a direct wire-format rule contradiction that prevents interoperable implementation.  
B2: RFC-0003 §5.5 “Initial Ratchet State Setup (Normative)” is internally inconsistent with the 2DH flow: the initiator sets `dhSendingKey = None` (discarding the initial ephemeral private key) which makes it impossible to derive the root/receiving chain needed to decrypt the responder’s first ratchet message; the specified initiator/responder DH key assignments do not enable the first reply to be decrypted, so independent implementations will not interoperate.  
B3: DHT key derivation for device discovery is contradictory: `02-identity-trust/identity-document-schema.md` states device records use keys like `"device:" + did` and `"devices-for:" + iid`, while `00-shared/layer-integration.md` (and RFC-0001/§12) mandate `SHA256("post-urbit:device:"||did)` / `SHA256("post-urbit:devices-for:"||iid)` (UTF-8 Base32 identifiers). Implementations will compute different DHT keys.  
B4: The DHT/discovery layer is not implementable for interoperability: the spec defines record key/value formats and verification rules but does not define the actual DHT protocol/network behavior (bootstrap, routing, replication rules, TTL enforcement semantics, conflict handling across multiple writers, “getAll” semantics, etc.), so two implementations cannot interoperate without guessing a specific DHT stack and conventions.  
B5: Relay allocation request schema is inconsistent across spec documents: `01-transport-connectivity/relay-protocol.md` uses `identity_doc_sequence: 42` (JSON number) while RFC-0002 §7.8 requires `identity_doc_sequence: "42"` (decimal string). This mismatch is wire-visible and can cause client/server rejection.
