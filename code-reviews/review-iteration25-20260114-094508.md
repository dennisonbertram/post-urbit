B1: Device Document schema is inconsistent across specs: `00-shared/layer-integration.md` and `01-transport-connectivity/interfaces.md` require `endpoints` in the Device Document for device discovery/connection, but `02-identity-trust/identity-document-schema.md` and `06-rfcs/RFC-0001-identity-document.md` define Device Documents without `endpoints`. This blocks interoperable device discovery and handshake routing.

B2: Revocation DHT record format is contradictory: `02-identity-trust/revocation.md` states the DHT `post-urbit:revocation:` value for `key_revocation` is the *replacement identity document* (revocation “implicit”), while `06-rfcs/RFC-0001-identity-document.md` defines an explicit `key_revocation` document with its own signature scheme and semantics. Implementers cannot know what exact bytes to store/fetch/verify/select for revocation records, preventing interoperable revocation checks.

B3: DHT key representation is not consistently specified at the API boundary: `00-shared/layer-integration.md` normatively defines DHT keys as 32 raw bytes (`SHA256(...)` output) passed to the DHT API, but identity/transport interfaces include `dhtPut(key: string, ...)`/similar string-typed keys. Without a single mandated encoding for these “string” keys (hex/base64/base64url) or a uniform `Uint8Array` type, implementations will not interoperate.
