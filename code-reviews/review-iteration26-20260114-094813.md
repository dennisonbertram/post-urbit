STATUS: NOT-COMPLETE  
B1: **Identity document `sequence` max bound is inconsistent**: `identity-document-schema.md` caps at `"18446744073709551614"` while RFC-0001 §6.4 allows up to `18446744073709551615` (2^64−1). Implementations cannot deterministically validate/encode the allowed range.  
B2: **Device revocation discovery/storage is not specified**: `identity-document-schema.md` requires peers to check device revocation before accepting device connections, but there is no normative DHT key derivation / record format / lookup procedure for `device_revocation` (only IID-based `post-urbit:revocation:` is defined).  
B3: **Genesis IDOC DHT record is inconsistent/missing from shared DHT key registry**: RFC-0001 defines `post-urbit:genesis:` storage/lookup, but `00-shared/layer-integration.md` omits any genesis key derivation/prefix; other documents reference “fetch genesis” behavior. Implementers cannot know whether/how genesis documents are published and retrieved.  
B4: **Recovery mechanisms are not implementable as written due to schema mismatches/incompleteness**: `recovery-mechanisms.md` and the Admin/API schemas define conflicting `device-escrow` configuration fields, and several recovery methods (device-escrow / threshold) lack fully specified cryptographic encoding/signature construction and verification rules sufficient to implement interoperably; the spec also does not state which recovery methods are mandatory for v1 conformance.
