STATUS: NOT-COMPLETE  
B1: DHT storage “verification” is specified as validating only `signatures.current` using the **embedded** `keys.signing.current`, and claims this “ensures only identity owners can update their records”; this is false/insecure because an attacker can publish an updated IDOC for an existing IID by keeping the public genesis key (which is public) but choosing a new `keys.signing.current` they control and signing with it. The spec does not define a workable DHT-side update authorization rule (e.g., continuity check against the previously stored document, recovery-proof verification, replacement policy), which is required for correct discovery semantics.  
B2: Sync protocol wire format is not implementable interoperably: it relies on “CBOR-encoded, deterministic, sorted keys” for `operation_bytes` and message payloads but does not specify a normative CBOR canonicalization profile (RFC 8949 canonical rules, key ordering, type constraints) nor complete CBOR schemas for each sync message type (SYNC_REQUEST/OFFER/ACCEPT/OPERATIONS/ACK/SUBSCRIBE/UNSUBSCRIBE). Because operation IDs and signatures depend on exact byte encoding, different implementations will not agree without this.
