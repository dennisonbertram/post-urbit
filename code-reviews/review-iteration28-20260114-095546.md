B1: [spec/02-identity-trust/recovery-mechanisms.md:Recovery Protocol / Recovery Document Format] Recovery identity document examples omit required `keys.signing.genesis` (and sometimes `iid`-binding invariants) and use `keys.encryption.previous: null`, contradicting the canonical schema where `keys.signing.genesis` is REQUIRED and `keys.encryption.previous` is an array; this makes recovery-document construction/verification ambiguous and can cause invalid documents or unsafe acceptance.

B2: [spec/01-transport-connectivity/interfaces.md:Endpoint] `priority` is optional with a default, but [spec/02-identity-trust/identity-document-schema.md:Endpoint Object (Normative)] defines `priority` as required (0–255) and signatures are over literal JSON (no default materialization); this mismatch can lead to signature verification failures or divergent on-wire encoding.

B3: [spec/00-shared/layer-integration.md:Domain Separator Registry (Normative)] The registry claims to enumerate “all cryptographic domain separators used across the Post-Urbit protocol,” but it omits the recovery attestation separator required by [spec/06-rfcs/RFC-0001-identity-document.md:§9.3 Recovery Attestation Format]; implementers following the registry will produce unverifiable attestations (or choose inconsistent separators), creating an interop/security failure.

B4: [spec/01-transport-connectivity/interfaces.md:DiscoveryService vs spec/00-shared/layer-integration.md:Discovery Contract/Resolution vs spec/02-identity-trust/caching-policy.md:IdentityTransport] Cross-layer contract requires Transport to support fetching/storing full identity documents via DHT (`fetchIdentity` / `dhtGet`/`getAll` semantics), but Transport’s public interfaces only expose `registerIdentity` and `lookupPeer` returning endpoints; the identity layer cannot be implemented against the transport interface as written without inventing missing methods or changing the contract.
