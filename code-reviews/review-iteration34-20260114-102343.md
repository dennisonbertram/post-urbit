B1: RecoveryConfig schema is inconsistent between Identity layer and Admin/UX layer
- File(s): 
  - `spec/02-identity-trust/interfaces.md`
  - `spec/02-identity-trust/recovery-mechanisms.md`
  - `spec/05-ux-packaging/interfaces.md`
  - `spec/05-ux-packaging/node-daemon.md`
- Issue: The Admin API (`/admin/v1/identity/recovery`) relies on `RecoveryConfig`, but the UX/Packaging layer defines recovery method configs that do not match the canonical Identity schema (field names and semantics differ). This prevents interoperable implementation of recovery configuration over the Admin API and risks producing invalid IDOCs.
- Evidence:
  - Canonical (Identity) device-escrow config:
    - `spec/02-identity-trust/interfaces.md`:
      > `interface DeviceEscrowConfig { escrowKeyHash: string; deviceLabel: string; }`
    - `spec/02-identity-trust/recovery-mechanisms.md`:
      > `"config": { "escrow_key_hash": "<SHA256-of-escrow-public-key>", "device_label": "Backup phone in safe" }`
  - Admin/UX “mirrors canonical schema” but actually differs:
    - `spec/05-ux-packaging/interfaces.md`:
      > `interface DeviceEscrowRecoveryConfig { escrowDeviceDid: DeviceIdentifier; escrowDeviceName: string; }`
      >
      > `interface ProviderRecoveryConfig { providerName: string; providerEndpoint: string; providerPublicKey: string; }`
      >
      > `interface ThresholdRecoveryConfig { threshold: number; totalShares: number; shareHolders: ShareHolderConfig[]; }`
- Fix: Make `spec/05-ux-packaging/interfaces.md`’s `RecoveryConfig` exactly match the canonical Identity layer schema (and wire names via snake_case mapping), or explicitly define it as an Admin-only “view model” with a mandatory mapping section to/from the canonical Identity schema used in IDOCs. Concretely:
  - Replace `DeviceEscrowRecoveryConfig` with canonical `{ escrowKeyHash, deviceLabel }` (and wire `escrow_key_hash`, `device_label`).
  - Replace `ProviderRecoveryConfig` with canonical `{ providerIid, providerEndpoint, policy, cooldownHours }` (wire `provider_iid`, `provider_endpoint`, `policy`, `cooldown_hours`).
  - Replace `ThresholdRecoveryConfig` with canonical `{ threshold, totalShares, shareCommitments, recoveryKeyHash }` (wire `share_commitments`, `recovery_key_hash`).
  - Update `node-daemon.md` endpoint docs to reference the canonical `RecoveryConfig`.

B2: Relay allocation request nonce encoding contradicts RFC-0002 and global encoding conventions
- File(s):
  - `spec/01-transport-connectivity/relay-protocol.md`
  - `spec/06-rfcs/RFC-0002-transport.md`
  - `spec/00-shared/layer-integration.md`
- Issue: The relay allocation HTTP request’s `nonce` encoding is specified as Base64 in `relay-protocol.md`, but RFC-0002 (authoritative) specifies Base64url. Since the relay computes signatures over `nonce` raw bytes, inconsistent decoding rules will cause signature verification failures across implementations.
- Evidence:
  - `spec/01-transport-connectivity/relay-protocol.md`:
    > `"nonce": "<16-bytes-base64-random>",`
  - `spec/06-rfcs/RFC-0002-transport.md`:
    > `"nonce": "<16-bytes-base64url>",`
  - `spec/00-shared/layer-integration.md` (Global Conventions):
    > `Tokens (relay, auth) | Base64url (no padding)`
- Fix: Standardize relay allocation `nonce` encoding to **Base64url (no padding)** everywhere:
  - Update `relay-protocol.md` allocation request schema to `"<16-bytes-base64url>"`.
  - Add/confirm an explicit rule: `nonce` MUST be decoded with Base64url alphabet `A-Za-z0-9-_` (no padding), and signature construction uses the decoded 16 raw bytes.

B3: Domain-separator byte-length annotations conflict with the centralized registry (risk of truncated/modified separators)
- File(s):
  - `spec/00-shared/layer-integration.md`
  - `spec/06-rfcs/RFC-0001-identity-document.md`
- Issue: The spec centrally defines a “Domain Separator Registry (Normative)” with exact strings and byte lengths, but RFC-0001 contains multiple different byte-length claims for the same domain-separator strings. Implementers who treat the stated byte length as normative (e.g., fixed-size buffers or truncation to match length) can silently produce incompatible signatures.
- Evidence:
  - Registry (normative):
    - `spec/00-shared/layer-integration.md`:
      > `Key revocation signature | post-urbit:key-revocation:v1: | 29`
      >
      > `Identity revocation signature | post-urbit:identity-revocation:v1: | 34`
      >
      > `Device revocation signature | post-urbit:device-revocation:v1: | 32`
  - Conflicting byte-length annotations in RFC-0001:
    - `spec/06-rfcs/RFC-0001-identity-document.md`:
      > `"post-urbit:key-revocation:v1:",   // domain separator (28 bytes)`
      >
      > `"post-urbit:identity-revocation:v1:",   // domain separator (33 bytes)`
      >
      > `"post-urbit:device-revocation:v1:",   // domain separator (31 bytes)`
- Fix: Make RFC-0001 fully consistent with the centralized registry:
  - Correct the byte-length annotations in RFC-0001 to 29 / 34 / 32 respectively, OR remove byte-length claims outside the centralized registry and state: “Lengths are authoritative in `00-shared/layer-integration.md` registry; compute as `len(utf8(domain_separator))`.”
  - Ensure all domain separators are always specified as exact UTF-8 byte strings, not “N bytes” buffers.
