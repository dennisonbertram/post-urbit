B1: Sender-key KDF domain separator length is inconsistent (24 vs 25 bytes)
- File(s): 
  - `spec/06-rfcs/RFC-0003-messaging.md`
  - `spec/00-shared/layer-integration.md`
- Issue: The domain separator `post-urbit-sender-key-v1:` is specified with conflicting byte lengths across documents. This is cryptographically binding; implementers will derive different keys if they follow different documents.
- Evidence:
  - RFC-0003 Appendix A: `| Sender key KDF | post-urbit-sender-key-v1: | 24 bytes + binding |`
  - 00-shared registry: `| Sender key KDF | post-urbit-sender-key-v1: | 25+ | HMAC domain prefix + binding data |`
- Fix: Normalize everywhere to the correct length for the literal ASCII string `post-urbit-sender-key-v1:` which is **25 bytes** (and then “+ binding data”). Update RFC-0003 Appendix A and any other mention that claims 24 bytes.

B2: Multiple domain-separator / prefix byte-length annotations are wrong (must be corrected everywhere)
- File(s):
  - `spec/00-shared/layer-integration.md`
  - `spec/02-identity-trust/recovery-mechanisms.md`
- Issue: The spec includes explicit byte counts for domain separators / prefixes, and some of those counts are incorrect. Since the registry claims byte counts are derived by `len(string.encode('utf-8'))`, incorrect counts create implementation divergence and fail the registry’s “exact bytes” intent.
- Evidence:
  - In `layer-integration.md` (Device Document Signature Scheme):
    - ` "post-urbit:device-doc:v1:",   // domain separator (24 bytes)`
    - but the registry in the same file lists `post-urbit:device-doc:v1:` as **25** bytes.
  - In `recovery-mechanisms.md` (Contest DHT Publication):
    - `DHT Key: SHA256("post-urbit:contest:" || iid) (22-byte prefix + IID)`
    - but `post-urbit:contest:` is **19** bytes (as also listed in the central registry in `layer-integration.md`).
- Fix:
  - Update the incorrect inline byte-count comments to match actual UTF-8 lengths:
    - `post-urbit:device-doc:v1:` → **25 bytes**
    - `post-urbit:contest:` → **19 bytes**
  - Audit all other “(N bytes)” annotations to ensure they match `len(utf8)`.

B3: Recovery method enum is inconsistent (“provider” missing) in the Identity Document schema
- File(s): `spec/02-identity-trust/identity-document-schema.md`
- Issue: The allowed `recovery.method` values are inconsistent across the spec. `provider` appears elsewhere (e.g., `02-identity-trust/interfaces.md`, `recovery-mechanisms.md`, and the embedded `recovery_proof.method` list), but the identity document schema omits it in at least one normative snippet. This blocks interoperable validation.
- Evidence:
  - `identity-document-schema.md` “Recovery Configuration” example:
    - `"method": "social|device-escrow|threshold|none"`
  - Same file later allows provider in recovery proof:
    - `"method": "social|device-escrow|threshold|provider"`
  - `02-identity-trust/interfaces.md`:
    - `method: 'none' | 'social' | 'device-escrow' | 'threshold' | 'provider';`
- Fix: Update `identity-document-schema.md` to include `provider` everywhere `recovery.method` is specified, i.e.:
  - `"method": "social|device-escrow|threshold|provider|none"`

B5: Event type is used across multiple interface specs without a shared definition (cross-layer type reference ambiguity)
- File(s):
  - `spec/01-transport-connectivity/interfaces.md`
  - `spec/02-identity-trust/interfaces.md`
  - `spec/03-messaging-sync/interfaces.md`
- Issue: These interface documents use `Event<...>` but do not define `Event` (nor reference a shared “common types” file). The only visible `Event` definition is in `spec/04-app-runtime/interfaces.md`, where it is explicitly described as “host-side events for the Node.js/TypeScript runtime implementation”, creating an unclear cross-layer dependency and leaving implementers without an authoritative shared event type.
- Evidence:
  - Transport interfaces: `onConnectionEstablished: Event<{ connection: Connection }>;` (no `Event` definition in file)
  - Identity interfaces: `onSelfIdentityUpdated: Event<{ ... }>;` (no `Event` definition in file)
  - Messaging interfaces: `onMessageReceived: Event<{ message: Message }>;` (no `Event` definition in file)
  - App runtime interfaces is the only place that defines:
    - `type Event<T> = { subscribe(callback: (data: T) => void): Unsubscribe; };`
- Fix:
  - Add a shared `Event<T>` and `Unsubscribe` definition in a neutral shared location (e.g., `spec/00-shared/interfaces.md` or `spec/00-shared/types.md`) and reference it from all layers, **or**
  - Inline the same `Event<T>` definition in each interface document that uses it, and ensure the definition is identical across files.
