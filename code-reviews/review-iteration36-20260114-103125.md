B2: DHT “get vs getAll” operation naming is inconsistent between the normative stack, the Transport interface, and the integration code sample
- File(s):
  - `spec/00-shared/layer-integration.md`
  - `spec/01-transport-connectivity/interfaces.md`
- Issue: The spec defines a normative DHT API with both `get(key)` (single) and `getAll(key)` (multi), but the Transport layer’s exposed interface only has `dhtGet(key): Promise<DhtResult[]>` (multi) and no single-get, while the integration code sample calls `dht.getAll(key)` (a method not present in the Transport interface). This is a blocking ambiguity for implementers wiring Identity↔Transport: which exact method name and semantics are required?
- Evidence:
  - Normative stack in `spec/00-shared/layer-integration.md`:
    > `get(key)` | Retrieve single value (any valid copy)  
    > `getAll(key)` | Retrieve all values from reachable nodes (for conflict detection)
  - Transport interface in `spec/01-transport-connectivity/interfaces.md`:
    > `dhtGet(key: Uint8Array): Promise<DhtResult[]>;`  
    (returns multiple; no `dhtGetOne` / `get` / `getAll` method is defined)
  - Integration code sample in `spec/00-shared/layer-integration.md`:
    > `const results = await dht.getAll(key);`
- Fix: Normalize the API surface and naming in one of these consistent ways (pick one and apply everywhere):
  1) **Expose both operations** in Transport: `dhtGetOne(key): Promise<DhtResult | null>` and `dhtGetAll(key): Promise<DhtResult[]>`, and update all prose/samples accordingly; OR
  2) Define that `DiscoveryService.dhtGet` is *the* normative “getAll”, rename it to `dhtGetAll`, and update the normative stack table to use `dhtGetAll` (or update the sample code to call `dhtGet` and explicitly state it is “getAll” semantics); optionally add a separate `dhtGetOne` if needed.
  
  Additionally, ensure the Identity↔Transport contract references the same names as `01-transport-connectivity/interfaces.md` and that samples compile against that interface.
