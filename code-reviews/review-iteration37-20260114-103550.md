B1: RFC-0001 includes non-reproducible / placeholder test-vector bytes that conflict with the shared authoritative test vectors
- File(s): `spec/06-rfcs/RFC-0001-identity-document.md`, `spec/00-shared/test-vectors.md`
- Issue: RFC-0001’s test vectors claim concrete “full” SHA-256 outputs and DHT key hashes, but the values shown are clearly placeholders (made-up suffixes / made-up DHT key hex). This prevents implementers from validating against a single consistent set of cryptographic vectors across documents.
- Evidence: 
  - RFC-0001 §15.1:
    - `SHA-256 hash (full 32 bytes, hex):`
      `586a763f2c82b31a0c5de9dcaef01e0261e0785bb0a3c4d5e6f708192a3b4c5d`
  - RFC-0001 §15.5:
    - `Identity DHT key (SHA-256, hex):`
      `9f4a8b2c1d3e5f6071829a0b4c5d6e7f8091a2b3c4d5e6f7081929a0b1c2d3e4`
  - Meanwhile `spec/00-shared/test-vectors.md` provides the real deterministic seed-based derivations but does not include these “full hash” values, and the RFC’s values are not derived from the shared generator.
- Fix: Replace RFC-0001 §15.1/§15.5/§15.6 with either:
  1) computed, generator-derived values that match `spec/00-shared/test-vectors.md` exactly (include the real full SHA-256(pubkey) and the real SHA-256("post-urbit:identity:"||iid) as 32-byte hex), OR
  2) remove the fabricated hex outputs entirely and normatively reference `spec/00-shared/test-vectors.md` as the single source of truth for these vectors (preferred to avoid duplication drift).

B2: `identity-document-schema.md` contains conflicting/incomplete “Test Vectors” that contradict the “no TBDs / raw keys not DER” rules
- File(s): `spec/02-identity-trust/identity-document-schema.md`
- Issue: The file includes a “Test Vectors” section with placeholder/truncated values and an explicit “to be generated during implementation” note. It also shows a DER/SPKI-looking base64 prefix (`MCowBQYDK2Vw...`) in the example list, which conflicts with the normative requirement elsewhere in the spec that keys are raw 32-byte Ed25519/X25519 bytes encoded as Base64 (not DER/SPKI). This creates ambiguity about the correct encoding and which test vectors are authoritative.
- Evidence:
  - `identity-document-schema.md`:
    - `### Test Vector 1: Genesis Document`
      `Signing Private Key (hex): e8f3...2a1b`
      `Signing Public Key (base64): MCowBQYDK2VwAyEAb7YH...`
      `(Full test vectors to be generated during implementation)`
- Fix: Delete this placeholder “Test Vectors” section entirely and replace it with a pointer to the authoritative vectors:
  - “See `spec/00-shared/test-vectors.md` and RFC-0001 §15 for authoritative test vectors.”
  Or, if you want vectors in this file, fully replace them with the real values from `spec/00-shared/test-vectors.md` (and ensure they use raw-key Base64, not DER/SPKI-looking encodings). Remove the “to be generated” language.

B3: `DhtResult` is referenced by the Identity layer contract without a defined cross-layer type
- File(s): `spec/02-identity-trust/caching-policy.md`, `spec/00-shared/layer-integration.md`, `spec/01-transport-connectivity/interfaces.md`
- Issue: `caching-policy.md` defines a “Minimal Transport Interface for Identity” that returns `Promise<DhtResult[]>`, but `DhtResult` is not defined in that document nor in the shared common types section. Implementers reading the Identity layer in isolation (as intended for layering) cannot implement/compile the interface or know what metadata is required.
- Evidence:
  - `caching-policy.md`:
    - `dhtGet(key: Uint8Array): Promise<DhtResult[]>;  // May return multiple values`
  - `layer-integration.md` defines `dhtGet`/`dhtPut` but does not define `DhtResult`.
  - `01-transport-connectivity/interfaces.md` defines `interface DhtResult { value: Uint8Array; source: string; receivedAt: number; }`, but this is not referenced/aliased in the shared layer contract.
- Fix: Define `DhtResult` in `spec/00-shared/layer-integration.md` (preferred, as the glue contract) and have both Identity and Transport reference that canonical definition; OR explicitly reference/import the Transport definition in `caching-policy.md` (e.g., “`DhtResult` as defined in `01-transport-connectivity/interfaces.md`”) and restate the fields required by Identity.
