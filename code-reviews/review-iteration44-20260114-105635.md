- Problem: Minimum-size calculation uses `21` as “minimum header extension, Ephemeral type”, but the **Initial/Ephemeral** extension is **33 bytes** (type `0x00`), while **21 bytes** is the **Group** extension (type `0x02`). This contradicts the extension registry in the same file and RFC-0003.
- Exact fix:
  - Replace the “Minimum size” lines with correct minimums and correct labeling, e.g.:
    - Change:
      - `Minimum size: ... + 21 + ... = 181 bytes (21 = minimum header extension, Ephemeral type)`
    - To:
      - `Minimum size (group ext, 21 bytes): 4 + 1 + 1 + 20 + 20 + 16 + 2 + 21 + 12 + 4 + 16 + 64 = 181 bytes`
      - `Minimum size (initial ext, 33 bytes): 4 + 1 + 1 + 20 + 20 + 16 + 2 + 33 + 12 + 4 + 16 + 64 = 193 bytes`
      - `Minimum size (ratchet ext, 41 bytes): ... = 201 bytes`
  - Also change the note label from “Ephemeral type” → “Group type” for the 21-byte case.

B2: `spec/06-rfcs/RFC-0003-messaging.md` — **Contradictory Group header-extension definition**
- Problem: RFC-0003 §3.2 states: `Group extension (21 bytes): 1 + 20 group_id`, but §3.4.4 correctly defines Group extension as `1 + 16 + 4` (sender_key_id + iteration). This also contradicts `spec/03-messaging-sync/group-messaging.md` and `spec/03-messaging-sync/secure-envelope.md`.
- Exact fix:
  - In RFC-0003 §3.2 “Header extension sizes by type”, replace:
    - `Group extension (21 bytes): 1 + 20 group_id`
  - With:
    - `Group extension (0x02, 21 bytes): 1 (type) + 16 (sender_key_id) + 4 (iteration)`
  - Ensure any later references to group_id-in-extension are removed (group_id is in the 20-byte recipient field when flags recipient type = group).

B3: `spec/06-rfcs/RFC-0002-transport.md` vs `spec/01-transport-connectivity/peer-handshake.md` and `spec/01-transport-connectivity/relay-protocol.md` — **Timestamp canonicalization requirement inconsistent across Transport docs**
- Problem: RFC-0002 requires handshake timestamps be **canonical** (`YYYY-MM-DDTHH:MM:SSZ`, no fractional seconds) and says implementations MUST reject non-canonical forms (RFC-0002 §5.5). The layer spec (`peer-handshake.md`) and relay spec (`relay-protocol.md`) only say “RFC3339”, implying fractional seconds and other RFC3339 forms are acceptable. This is a cross-document normative contradiction for what implementations must accept.
- Exact fixes (align layer docs to RFC-0002, since RFC-0002 is stated authoritative for transport):
  1) In `spec/01-transport-connectivity/peer-handshake.md`, under ClientHello/ServerHello field tables (timestamp rows) and/or “TLS Binding / Verification Steps”, add:
     - `timestamp` **MUST** be canonical RFC3339 UTC: `YYYY-MM-DDTHH:MM:SSZ` (no fractional seconds) and implementations **MUST reject** non-canonical forms.
  2) In `spec/01-transport-connectivity/relay-protocol.md`, in Allocation Request schema and signature construction, add the same canonical timestamp requirement (and ensure any stated byte-length calculations or examples assume 20-byte timestamps).
  3) In `spec/00-shared/layer-integration.md` (Global Conventions → Timestamps), add a scoped clarification:
     - General timestamps: RFC3339 UTC
     - **Transport handshake + relay allocation/rebind signature inputs**: MUST use canonical `YYYY-MM-DDTHH:MM:SSZ` (no fractional seconds), matching RFC-0002.
