- **Problem 2:** Session cookie settings claim `secure: true` “always (even localhost uses TLS)”, but `node-daemon.md` defines **local mode HTTP** with `Secure=false` and production mode HTTPS with `Secure=true`.
- **Problem 3:** WebSocket example uses `wss://localhost:8080/...` which conflicts with `node-daemon.md` local mode `ws://localhost:8080/...`.

+    this.csrfToken = null;
   }

-  setAuthToken(token: string): void {
-    this.authToken = token;
-  }
+  setCsrfToken(token: string): void {
+    this.csrfToken = token;
+  }

-        ...(this.authToken && { 'Authorization': `Bearer ${this.authToken}` }),

+          ? { 'X-CSRF-Token': this.csrfToken }
+          : {}),

       ...

B2: `spec/04-app-runtime/interfaces.md` — `AppManifest` TypeScript interface field names contradict the normative manifest wire format in `spec/04-app-runtime/manifest-schema.md` and `spec/05-ux-packaging/app-distribution.md`.
- `interfaces.md` defines `AppManifest.manifestVersion`, `runtime.memory.initialPages`, etc. (camelCase).
- `manifest-schema.md` defines on-disk `manifest.json` as `manifest_version`, `initial_pages`, etc. (snake_case) and treats that as the package-verified format.
- Unlike Identity layer interfaces, App Runtime interfaces do **not** state a wire-vs-TS mapping rule, so this is an interop-breaking ambiguity.

**Exact fix (choose one):**
- **Option A (recommended):** Add a “Wire Format vs TypeScript Convention” section to `spec/04-app-runtime/interfaces.md` (mirroring `spec/02-identity-trust/interfaces.md`) stating that `manifest.json` is snake_case on disk and TS interfaces are camelCase with explicit mapping; and provide a complete mapping list for all manifest fields used in signatures/hashes.
- **Option B:** Rename fields in `spec/04-app-runtime/interfaces.md` to snake_case to match the canonical manifest (`manifest_version`, `initial_pages`, etc.), and if you still want camelCase internally, introduce a separate `AppManifestInternal` type.
