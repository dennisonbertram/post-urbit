B1: `spec/00-shared/layer-integration.md` + `spec/02-identity-trust/caching-policy.md` + `spec/02-identity-trust/identity-document-schema.md` — IID/DID derivation/verification inconsistently (and sometimes incorrectly) hashes **Base64 strings** instead of **raw key bytes**.
- Problem examples:
  - `caching-policy.md` “Verify `iid == Base32Lower(SHA256(keys.signing.genesis))`” (genesis is Base64 text, but IID is defined as hash of raw 32-byte key).
  - `layer-integration.md` DHT verification step uses `derive_iid(keys.signing.genesis)` without stating Base64 decode.
  - `layer-integration.md` device verification uses `SHA256(device_signing_key)` without stating Base64 decode.
  - `identity-document-schema.md` device verification step `SHA256(device_signing_key)` has the same ambiguity.
- Exact fixes (make all of these explicit and consistent with Test Vector 1 / IID definition):
  1) In `spec/02-identity-trust/caching-policy.md` under **TOFU → Genesis Binding**, replace:
     - `Verify iid == Base32Lower(SHA256(keys.signing.genesis))`
     with:
     - `Verify iid == derive_iid(Base64Decode(keys.signing.genesis))`
     (or equivalently `iid == Base32Lower(SHA256(Base64Decode(keys.signing.genesis))[0:20])`).
  2) In `spec/00-shared/layer-integration.md` under **DHT Record Format → Verification (New Records)**, replace:
     - `Verify iid == derive_iid(keys.signing.genesis)`
     with:
     - `Verify iid == derive_iid(Base64Decode(keys.signing.genesis))`
  3) In `spec/00-shared/layer-integration.md` under **Device Document Verification**, replace:
     - `Verify did == Base32Lower(SHA256(device_signing_key)[0:20])`
     with:
     - `Verify did == Base32Lower(SHA256(Base64Decode(device_signing_key))[0:20])`
  4) In `spec/02-identity-trust/identity-document-schema.md` under **Device Document Verification**, replace step 1:
     - `Verify did == Base32Lower(SHA256(device_signing_key)[0:20])`
     with:
     - `Verify did == Base32Lower(SHA256(Base64Decode(device_signing_key))[0:20])`

B2: `spec/06-rfcs/RFC-0003-messaging.md` vs `spec/03-messaging-sync/secure-envelope.md` vs `spec/03-messaging-sync/interfaces.md` — plaintext message schemas + identifier encodings contradict each other (wire incompatibility).
- Concrete contradictions:
  1) `RFC-0003` §6.4 `sender_key_share` uses Base64-encoded **raw 20-byte** values for `group_id` and `sender_iid` (`"<20-bytes-base64>"`), but everywhere else group IDs/IIDs are specified as **32-char Crockford Base32 strings** in JSON contexts (and raw 20 bytes only in binary headers).
  2) `RFC-0003` §8.2 message type schemas don’t match the messaging layer API model:
     - `typing`: RFC uses `{ "typing": boolean }` while `interfaces.md` defines `TypingContent { isTyping: boolean; expiresAt: Timestamp; }`.
     - `reaction`: RFC uses `{ "emoji": string, "message_id": string }` while `interfaces.md` defines `{ targetMessageId, emoji, action }`.
     - `rich`: RFC uses `{ "markdown": string }` while `interfaces.md` defines `{ format, text }`.
- Exact fixes (pick one wire model; recommended: snake_case-on-wire + Base32 IDs, consistent with other layers):
  1) In `spec/06-rfcs/RFC-0003-messaging.md` §6.4, change `sender_key_share` content fields to use Base32 strings for IDs:
     - Replace:
       ```json
       "group_id": "<20-bytes-base64>",
       "sender_iid": "<20-bytes-base64>",
       ```
       with:
       ```json
       "group_id": "<32-char-base32-group-id>",
       "sender_iid": "<32-char-base32-iid>",
       ```
       Keep `key_id` as Base64 (16 bytes) and `chain_key` as Base64 (32 bytes).
  2) In `spec/06-rfcs/RFC-0003-messaging.md` §8.2 **Type Registry**, update schemas to match the existing messaging layer model (wire uses snake_case):
     - `typing` → `{ "is_typing": boolean }` (and use top-level `expires_at` for expiry as already defined in §8.1).
     - `reaction` → `{ "target_message_id": "<uuid>", "emoji": string, "action": "add|remove" }`
     - `rich` → `{ "format": "markdown|html", "text": string, "mentions": [...] }`
  3) Add an explicit wire/TS field-mapping rule to `spec/03-messaging-sync/interfaces.md` (currently missing, unlike Identity/Runtime layers). Insert near the top:
     - “On-wire plaintext JSON inside PUSE uses snake_case; TypeScript interfaces use camelCase; implementations MUST map between them.”
     - Include at least these mappings: `thread_id↔threadId`, `reply_to↔replyTo`, `expires_at↔expiresAt`, `receipt_type↔receiptType`, `message_ids↔messageIds`, `target_message_id↔targetMessageId`, `is_typing↔isTyping`, `media_type↔mediaType`.
