B1: `spec/03-messaging-sync/secure-envelope.md` — **Signature verification pseudocode uses non-existent field names / inconsistent access style vs the normative IDOC JSON schema (snake_case)**
- **Problem:** The Python snippet references `hist_entry.expires_at` even though the schema defines `expires_at` (snake_case), and uses mixed dot/dict access (`sender_doc.keys.signing.get(...)`) which is incompatible with the JSON object model described elsewhere in the spec. This can lead implementers to check the wrong field or fail to check key expiry at all.
- **Exact fix:** Replace the verification snippet with consistent dict access and snake_case field names.
  - Change (representative lines):
    - `for hist_entry in sender_doc.keys.signing.get('history', []):`
    - `if parse_time(hist_entry.expires_at) > now():`
  - To:
    ```python
    signing = sender_doc["keys"]["signing"]

    # 1. Try current signing key
    if ed25519_verify(signing["current"], signed_data, signature):
        return True

    # 2. Try previous signing key
    if signing.get("previous"):
        if ed25519_verify(signing["previous"], signed_data, signature):
            return True

    # 3. Try historical signing keys (snake_case: expires_at)
    for hist_entry in signing.get("history", []):
        if parse_time(hist_entry["expires_at"]) > now():
            if ed25519_verify(hist_entry["key"], signed_data, signature):
                return True
    ```
  - (If you prefer dot-access pseudocode, then the schema in this file must explicitly define camelCase equivalents; currently it does not.)

B2: `spec/06-rfcs/RFC-0003-messaging.md` — **AEAD AAD input in Double Ratchet / Group algorithms is ambiguous and can contradict the PUSE wire format**
- **Problem:** In §4.4 and §4.5 (and similarly in §6.6/§6.7), the algorithms use `aad=header.encode()`, but the PUSE spec in §3 requires the AEAD AAD to be the **full header extension bytes** (which include the 1-byte extension type). If `header.encode()` is implemented as “fields only” (common), senders/receivers will authenticate different AAD and decryption will fail. This is a spec/code mismatch risk.
- **Exact fix:** Make AAD definition explicit and normatively bind `encode()` to the on-wire extension bytes (including the extension type), or rename to avoid ambiguity.
  - In `RFC-0003`:
    - In §4.4 “Sending a Message”, replace:
      - `aad=header.encode()`
    - With:
      - `aad=ratchet_extension_bytes`
    - And add a normative definition immediately above:
      ```text
      ratchet_extension_bytes MUST be the exact 41-byte PUSE header extension:
        0x01 || dh_public(32) || PN(u32-be) || N(u32-be)
      This byte string is used verbatim as ChaCha20-Poly1305 AAD.
      ```
  - Apply the same pattern in §4.5 “Receiving a Message” (AAD must be the same `ratchet_extension_bytes` parsed from the envelope), and in §6 (group) with:
    ```text
    group_extension_bytes MUST be:
      0x02 || sender_key_id(16) || iteration(u32-be)
    ```
