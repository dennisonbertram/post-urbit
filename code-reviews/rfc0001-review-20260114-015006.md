## Overall assessment

The core IDOC idea is coherent (self-certifying IID from genesis key, JCS signing, dual-sign rotation), but several parts are underspecified in ways that will cause divergent implementations—especially around **bootstrapping verification across rotations**, **what exact bytes are on the wire / in the DHT**, and **recovery proof validation**.

Below are concrete issues, prioritized and written to be actionable.

---

## BLOCKING issues (will prevent interoperable implementations)

### B1. Bootstrapping / chain-of-trust across key rotations is undefined
**Where:** §7.2, §8, §12, §14.6  
**Problem:** Verification of `signatures.previous` requires a “previous known signing key” / “previous_known_sequence”. But the RFC never defines how a node that learns an IID for the first time obtains trustworthy prior state. With only the latest IDOC in hand:
- `signatures.current` is trivially self-signed by the included `keys.signing.current`
- `signatures.previous` is also trivially satisfiable if the verifier accepts `keys.signing.previous` supplied by the new doc (attacker can set both keys and sign with both private keys)

**Why it blocks:** Two implementations can make opposite choices (TOFU vs. fetch chain vs. require genesis doc), breaking interop and/or security.

**Actionable fix options (pick one and specify normatively):**
1. **Chain-required:** Define a canonical “update chain” rule: a verifier MUST obtain (and validate) a chain from sequence 0 (genesis) to the target sequence, with each update authorized by `signatures.previous`. Then specify retrieval strategy (DHT stores last *K* docs, or updates are stored under `iid + sequence`, etc.).  
2. **Hash-linked:** Add `prev_doc_hash` (hash of canonical JSON including signatures, or envelope bytes) to each doc and require continuity; still requires fetching at least one prior doc, but allows unambiguous linking.  
3. **Genesis-anchored authorization:** Require every update to include a signature by a long-lived “root/identity key” (could be genesis or a dedicated recovery/root key). This avoids requiring prior docs but changes the rotation model.

At minimum, define a **bootstrap verification procedure**: what a node does when it has IID but no prior doc/key cached.

---

### B2. “Canonical JSON” on the wire is ambiguous (envelope bytes are not deterministic)
**Where:** §6, §11.1  
**Problem:** §11.1 says the envelope contains “Canonical JSON (UTF-8)”, but §6 only defines canonicalization *for signing* after removing `signatures`. It never defines whether the **transmitted JSON**:
- must be JCS-canonicalized (including the `signatures` field), or
- may be any JSON serialization

**Why it blocks:** If any external signature (e.g., DHT record signature in §12.1) is computed over envelope bytes, different JSON serializations yield different bytes and signatures.

**Actionable fix:**
- Specify: **The JSON inside the IDOC envelope MUST be JCS-canonicalized for the full document (including `signatures`)**.  
- Keep §6’s “remove signatures for signing” rule, but add a second rule: “wire encoding canonicalization”.

(Alternatively: remove all signatures-over-envelope notions and treat the envelope strictly as a length-prefixed container, but then don’t call it “Canonical JSON”.)

---

### B3. DHT record signature is underspecified/redundant and not parseable as written
**Where:** §12.1–§12.3  
**Problems:**
1. §12.1 says `DHT Value: IDOC envelope` and separately `Signature: Ed25519 signature over IDOC envelope`, but does not define how the signature is packaged (two fields? concatenation? separate DHT field?).
2. It does not define **which key** signs the DHT record signature (current signing key? genesis?).
3. §12.3 says DHT nodes “MUST verify the identity document signature before storing” which already prevents overwriting someone else’s IID without the corresponding signing key (assuming the update authorization problem B1 is fixed). The extra envelope signature is either redundant or needs a clear purpose.

**Why it blocks:** Storage nodes cannot implement §12 without a concrete value format.

**Actionable fix (choose one):**
- **Option A (recommended):** Remove the extra DHT signature entirely; require nodes to validate the IDOC itself and only store if valid.  
- **Option B:** Define a concrete DHT value structure, e.g.:
  - `value = envelope || dht_sig` where `dht_sig` is 64 raw bytes
  - signature key = `keys.signing.current`
  - verification uses the embedded IDOC to obtain the key
  - require the envelope JSON to be JCS-canonical (§11 fix)

Also specify DHT key input encoding (see B4).

---

### B4. DHT key derivation does not specify string/byte encoding
**Where:** §12.1–§12.2  
**Problem:** `SHA256("post-urbit:identity:" || iid)` is ambiguous unless you specify:
- UTF-8 vs ASCII vs other
- whether `iid` is lowercased before hashing (it should be)
- whether separators are included exactly as shown

**Why it blocks:** Different encodings produce different DHT keys.

**Actionable fix:** Specify:
- bytes = UTF-8 of the literal prefix + IID (IID MUST be lowercase)
- exact prefixes as ASCII
- no terminator, no whitespace  
Example: `sha256(b"post-urbit:identity:" + iid.encode("ascii"))`

---

### B5. Social recovery proof validation is incomplete (cannot be implemented)
**Where:** §9.2–§9.4  
**Problems:**
- The trustee attestation’s **signed payload** is undefined (what bytes are signed? JCS of the attestation without its `signature` field? Include a domain separator?).
- Which trustee key is used (trustee’s **current** signing key at time of verification? key at time of attestation?) and how to resolve it (fetch trustee IDOC? which sequence?).
- Threshold logic is underspecified:
  - requirement that `len(trustees) >= threshold` is not stated (and the example violates it: threshold=3 with 2 trustees).
  - whether multiple attestations from same trustee count once
  - whether attestations must match `subject_iid` and `new_signing_key` exactly
- Cooldown enforcement is underspecified:
  - whether verifiers compute “active” locally from timestamps or trust the `status` field
  - max cooldown bounds (DoS by setting years-long cooldown)
- “contested” state has no verification rules (who can contest? with what signature?).

**Why it blocks:** Two implementations cannot agree on whether a recovery update is valid.

**Actionable fix:** Define a complete recovery verification algorithm:
- canonicalization + domain separation for trustee attestations
- trustee identity resolution rules
- exact threshold counting rules
- exact cooldown evaluation rules
- contest object format and validation rules (or remove “contested” until specified)

## HIGH priority issues (serious divergence/security risk)

### H1. Optional-field “defaults” are not safely defined under signatures
**Where:** §4.3, §6  
**Problem:** The RFC lists defaults for optional fields, but signatures are over the literal JSON. If one implementation omits `recovery` and another includes `{"method":"none","config":{}}`, they produce different signed bytes.

**Actionable fix:**
- Specify: **Defaults are semantic only. Verifiers MUST NOT materialize defaults before signature verification.**  
- Also specify whether producers SHOULD emit fields with defaults (for normalization) or SHOULD omit them (for compactness). Pick one for ecosystem consistency.

---

### H2. Sequence number as a string: lexical ambiguity, leading zeros, and bounds
**Where:** §4.2, §7.2, §8  
**Problems:**
- It’s a string, but constraints do not forbid `"00"`, `"+1"`, `" 1"`, etc.
- “monotonic” is stated but not precisely: must it increment by exactly 1 or just increase?
- uint64 bounds not specified normatively (max = 2^64-1).

**Actionable fix:**
- Require regex: `^(0|[1-9][0-9]{0,19})$` and numeric value ≤ 18446744073709551615  
- Specify: sequence MUST increase by **at least** 1; MAY skip values (or MUST be exactly +1—choose one).

---

### H3. Base64 “no padding” is stated but not enforced by validation rules
**Where:** §5.1, §4.2  
**Problem:** The spec says “Base64 standard, no padding” but never says verifiers MUST reject padded encodings (`=`) or non-canonical variants.

**Actionable fix:** Add explicit validation:
- MUST reject `=` padding characters
- MUST reject non-alphabet chars
- MUST decode to exact lengths (32 bytes keys, 64 bytes sigs)

---

### H4. Domain separation for signatures is missing
**Where:** §6–§8, §12  
**Problem:** Ed25519 signatures are computed over raw JCS bytes. Without domain separation, signatures could be replayed across contexts if the same bytes appear elsewhere.

**Actionable fix:** Prefix signed payloads with a fixed context string, e.g.:
- `payload = b"post-urbit:idoc:v1:" || jcs_bytes`  
Apply similarly for trustee attestations, device docs, revocations, DHT records (if kept).

---

### H5. Revocation objects are not integrated into wire format / canonicalization
**Where:** §10, §11, §12  
**Problem:** Revocation formats are defined, but:
- Not assigned a wire envelope/magic/version
- Not assigned JCS rules for signing
- Not assigned DHT storage keys/records

**Actionable fix:** Either:
- Define separate envelopes (e.g., magic `REVK`, `DDEV`) and DHT record keys, or  
- Define a generic envelope that carries typed canonical JCS JSON objects (`type` field).

---

### H6. Device documents & device index signing/canonicalization rules incomplete
**Where:** §13  
**Problems:**
- No canonicalization scheme stated (assume JCS, but must be explicit)
- DID derivation validation not stated (MUST check `did == derive_did(device_signing_key)`)
- Verification across identity key rotation: must use identity signing key history/previous keys, but not stated
- Storage/discovery mechanism for device docs is not specified (only device index in DHT)

**Actionable fix:** Specify:
- JCS rules for device doc/index signatures (and remove signature field before signing, if applicable)
- how to retrieve device docs from DHT (key derivation)
- how long device docs persist, and how revocation interacts

---

## MEDIUM priority issues (edge cases / interoperability polish)

### M1. Timestamp rules conflict slightly and need exact comparisons
**Where:** §7.2 step 3, §7.3  
**Problems:**
- §7.3 says monotonicity MUST be >= previous timestamp (if known), but also says allow ~5 min skew—unclear how this applies.
- RFC3339 “UTC” requirement should specify: MUST end with `Z`, and whether fractional seconds allowed.

**Actionable fix:** Define:
- parsing requirements (accept fractional seconds or forbid)
- future skew rule uses `now + 24h + skew`, or just `now + 24h`?
- monotonicity rule with an allowed backward tolerance (or none)

---

### M2. Key history entry semantics are underspecified
**Where:** §4.4–§4.5, §7.4  
**Problems:**
- Are `valid_from`/`valid_until` inclusive? Can they overlap? Must they be contiguous?
- What if message arrives with sequence outside known ranges?
- `expires_at` is unclear: cache hint vs security constraint?

**Actionable fix:** Define:
- inclusive/exclusive semantics
- overlap prohibition rules
- whether `expires_at` is informative only, or must be enforced

---

### M3. “Same-sequence conflicts” resolution is not implementable for DHT environments
**Where:** §14.6  
**Problem:** “Prefer first-seen document” depends on local arrival order; DHT lookups will vary.

**Actionable fix:** Provide a deterministic tiebreaker (even if “gameable”), or define a conflict state requiring user resolution, or require exact `prev_doc_hash` linking (see B1) which eliminates same-sequence forks.

---

### M4. Endpoint canonical forms and validation need tightening
**Where:** §4.6  
**Issues:**
- IPv6 bracket form (`[::1]`) is suggested but not normatively required; mixing forms breaks equality checks.
- Hostname normalization (case-insensitive DNS, punycode) not specified.
- `transport` default says quic, but field is “No”; how to treat missing?

**Actionable fix:** Add explicit normalization rules and defaulting behavior.

---

### M5. Size limits are unclear about measurement point
**Where:** §4.7, §11.3  
**Problem:** “Total document 16KB” could mean:
- UTF-8 JSON bytes before envelope
- envelope total size
- parsed object size

**Actionable fix:** Define size limits in terms of **wire JSON UTF-8 byte length** (the `length` field), and separately constrain `extensions` by its canonical JSON byte length.

---

## LOW priority issues (quality, clarity, editorial)

### L1. Example social recovery config is inconsistent

**Problem:** `threshold: 3` with only two trustees.

**Fix:** Correct the example or add a note that it’s illustrative only (better: correct it).

### L2. Media type naming could be improved for JSON vs envelope
**Where:** §16.1  
**Problem:** `application/vnd.post-urbit.idoc` is ambiguous: is it JSON or the binary envelope?

**Fix:** Consider:
- `application/vnd.post-urbit.idoc+json` for JSON
- `application/vnd.post-urbit.idoc` for the envelope, or define both explicitly.

## Test vector completeness review

### TV1. IID derivation vector is incomplete
**Where:** §15.1  
**Problem:** SHA-256 hash is truncated (`...`). Implementers need the full 32-byte hash to confirm correctness.

**Actionable fix:** Provide full SHA-256 hex (64 hex chars), full base32 encoding steps, and confirm no padding.

---

### TV2. Signature vector lacks full signing context definition
**Where:** §15.2  
**Problems:**
- You provide a “Signing seed (hex)” but do not specify the Ed25519 key derivation convention (RFC8032 seed → expanded secret → public). Most libs do this, but specs should be explicit.
- If you adopt domain separation (recommended), vectors must incorporate it.
- No explicit statement that signature is over UTF-8 bytes of the JCS string.

**Actionable fix:** Add:
- derived public key (hex) from the seed (to cross-check)
- exact byte sequence being signed (hex dump of payload bytes or clearly specified prefix+JCS)
- expected signature bytes (already given)

---

### TV3. Missing wire/envelope vectors
**Problem:** There is no test vector for:
- the full IDOC envelope bytes (magic/version/length + JSON) in hex/base64
- parsing round-trip

**Actionable fix:** Provide an envelope hex string for the genesis document.

---

### TV4. Missing key rotation / recovery vectors
**Problem:** No vectors for:
- a key rotation update doc with both signatures
- validation of `signatures.previous`
- a recovery-based update with attestations and cooldown rules

**Actionable fix:** Add at least one rotation vector and one social recovery vector (with trustee seeds/keys + attestation signatures).

---

### TV5. Missing DHT key derivation vectors
**Problem:** No vectors for:
- `DHT Key = SHA256(prefix||iid)` output bytes/hex

**Actionable fix:** Provide the expected DHT key hash for Alice’s IID (and device index key).

---

## Minimal “must-clarify” checklist for v1.0 interoperability

If you only fix a few things to unblock implementations, fix these first:

1. Define bootstrap verification / chain rules across rotations (B1)  
2. Require JCS canonical JSON inside the envelope (B2)  
3. Define DHT record value format + remove/define extra signature (B3)  
4. Fully specify social recovery attestation signing & verification (B5)  
5. Tighten `sequence` string constraints + base64 canonical constraints (H2, H3)  
6. Add missing test vectors (TV1–TV5)
