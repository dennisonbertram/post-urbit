## Overall coherence rating: **7 / 10**

The suite is conceptually strong (clear privilege boundary, multi-webview isolation, single IPC entrypoint, Rust-authoritative lifecycle, defense-in-depth). The main coherence loss comes from **naming drift**, **event model inconsistencies**, and a few **critical “missing glue” specs** (session bootstrap, how apps call the bridge without exposing broader Tauri APIs, and how “app events” are delivered if apps can’t use `@tauri-apps/api`).

Below is a structured review against your checklist.

## 1) Command/method names: consistency review

### What’s consistent
- **Bridge method naming** (`resource.get_budget`, `events.poll`, `clipboard.write`) is internally consistent within `04-SECURE_BRIDGE_PROTOCOL.md`.
- **Shell events** use a clear namespace pattern: `shell://{domain}/{event}` in `01-SHELL_ARCHITECTURE.md`.

### Key inconsistencies / collisions
1) **Shell app lifecycle commands: `shell_*` vs `app_*`**
   - `01-SHELL_ARCHITECTURE.md` defines:
     - `shell_launch_app`, `shell_close_app`, etc.
   - `02-APP_SANDBOX_ISOLATION.md` defines:
     - `app_launch`, `app_show`, `app_hide`, `app_close`.
   - Capability examples in `02` also reference permissions like:
     - `postbridge:allow-app-launch`, etc.
   **Issue:** unclear final API surface and permission mapping. Also “postbridge:*” is used both for bridge and shell lifecycle permissions.

2) **External URL open: shell command vs bridge method**
   - Shell command: `shell_open_external_url` (shell-only) in `01`.
   - Bridge method: `external.open_url` in `04` (app-initiated, prompt-always).
   **Issue:** not specified whether `external.open_url` is implemented purely in Rust, or routes through shell UI via a shell-only command.

3) **App→Rust events naming uses `app://...` in Resource spec**
   - `03-RESOURCE_CONSTRAINTS.md` defines events like `app://resource/pressure`, `app://resource/evicting`.
   - `04-SECURE_BRIDGE_PROTOCOL.md` states backend→app push is via **long-poll** (`events.poll`), not Tauri event listeners.
   **Issue:** `app://...` event naming implies Tauri event emission, but apps likely cannot subscribe if Tauri JS APIs are not injected.

### Remediation actions (commands/methods)
- **Pick one naming scheme** for shell-only lifecycle commands and use it everywhere:
  - Recommended: `shell_app_launch`, `shell_app_show`, `shell_app_hide`, `shell_app_close` (explicitly shell-only, avoids confusion with bridge).
- **Separate namespaces for permissions:**
  - `bridge:allow-invoke` (or `postbridge:allow-invoke`) strictly for the single command
  - `shell:allow-*` for shell commands
  - Avoid `postbridge:allow-shell-*` in examples unless it’s a real permission grammar you’re implementing.
- Define how `external.open_url` is executed:
  - Option A: Implement fully in Rust (prompt mediated via shell events/UI)
  - Option B: Implement as “prepare/execute” and require shell confirmation before calling plugin shell open  
  Either way: document the exact flow.

## 2) Data types and enums: consistency review

### Inconsistencies
1) **Hot/Warm/Cold represented as both enums and strings**
   - `02` defines `AppRunState` enum.
   - `03` uses `state: String // "hot" | "warm" | "cold"` in `AppResourceUsage`.
   **Impact:** drift risk and serialization bugs.

2) **Bridge error type differs between specs**
   - `02` example: `postbridge_invoke(...) -> Result<Vec<u8>, String>`
   - `04` defines: `-> Result<Vec<u8>, BridgeError>`
   **Impact:** breaks the “strict envelope” story and makes error-handling ambiguous.

3) **Session validation signatures don’t match**
   - `02` calls: `validate_request(&request.session, &request.token, &request.id, request.ts)`
   - `04` proposes: `validate_request(&BridgeRequest, webview_label, derived_app_id)`
   **Impact:** unclear canonical source of anti-replay / timestamp validation.

4) **Resource pressure level types duplicated**
   - `03` defines `PressureLevel` (Rust) and TS `level: 'normal' | 'constrained' | 'critical'`.
   - Bridge spec has its own error enums and permission tiers; fine, but you should ensure resource pressure values are single-sourced.

### Remediation actions (types/enums)
- Introduce a **single canonical schema module**:
  - `docs/specs/SCHEMAS.md` (or `/schemas/`) containing:
    - `AppRunState`, `PressureLevel`, `EvictionReason`, bridge envelope types
  - Generate Rust + TS from it (or declare Rust as source and generate TS via `ts-rs` / `specta`).
- Normalize `postbridge_invoke` to **always return CBOR-encoded `BridgeResponse`** and use `BridgeError` consistently (never raw `String`).
- Make all “string enums” in Rust actual enums with `#[serde(rename_all = "snake_case")]`.

## 3) Security invariants: maintained or violated?

### Maintained well
- **Identity-from-infrastructure** is consistently emphasized:
  - webview label `app-{app_id}` → derive `app_id` → validate session binding.
- **Default deny** is present in method registry, CSP baselines, navigation blocking.
- **Shell-only command verification** by webview label is explicitly required.

### Where invariants become ambiguous / at risk
1) **Apps must call `postbridge_invoke`, but “no Tauri APIs/globals” is also required**
   - Spike 0.4 pass criteria expects `__TAURI__` and `__TAURI_INTERNALS__` absent.
   - But if apps cannot access any IPC primitive, they cannot call `postbridge_invoke` at all.
   **This is a core coherence gap**: the spec needs to explicitly define the *minimal injected IPC surface* allowed.

2) **Event delivery to apps conflicts with “no Tauri JS API”**
   - Resource specs describe emitting app-directed events like `app://resource/pressure`.
   - Bridge spec says long-poll subscriptions.
   **Risk:** implementing the wrong mechanism could accidentally re-enable Tauri event APIs in app webviews.

3) **CSP allowances**
   - App CSP includes `'wasm-unsafe-eval'`. That may be acceptable for WASM-heavy apps, but it’s a deliberate weakening—needs to be explicitly justified and gated (e.g., only if required, or behind a manifest flag).

### Remediation actions (security)
- Define a **Minimal App IPC Surface Contract**, for example:
  - “App webviews do not get `@tauri-apps/api` or `__TAURI__`, but do get a single injected global `window.__POSTBRIDGE__` with one method that can only call `postbridge_invoke`.”
  - Or explicitly allow `__TAURI_IPC__` but document why it’s safe given capability lockdown + shell-only checks.
- Align Spike 0.4 to the above:
  - Update “suspicious globals” list to reflect what you *intentionally* expose.
- Make “app push events” exclusively bridge-based:
  - `events.subscribe(topic="resource.pressure")` etc.
  - Remove `app://resource/...` naming unless it’s purely an internal Rust routing name.

## 4) Contradictions between specs

### Direct contradictions
- **Backend→app events mechanism**
  - `03`: “Emitted to each app” (implies push)
  - `04`: long-poll only
- **App isolation comms**
  - `02` matrix says: “postMessage to parent ALLOWED” — but multi-webview apps don’t have a parent frame relationship. This reads like iframe legacy wording.
- **ADR numbering / references**
  - `01` lists ADR-003..ADR-008 (not in repo), and mislabels ADR-003 as “Shell Navigation Model” while ADR-003 file is multiwebview isolation.

### Remediation actions (contradictions)
- Replace “postMessage to parent” line with something accurate for multi-webview (likely “N/A; no parent frame. All IPC via bridge.”).
- Fix ADR references (see cross-reference section).
- Choose one definitive app event mechanism (bridge subscriptions) and update `03` accordingly.

## 6) Overall architecture coherence

### Coherent aspects
- Clear separation:
  - Shell = privileged UI, full Tauri API
  - Apps = untrusted, no direct privileged APIs
  - Rust = authoritative enforcement point
- Good defense layering:
  - Capability files + label checks + protocol CSP + navigation hooks + bridge auth/rate limits
- Resource model is thorough and operationally realistic (LRU, hysteresis, grace period, metrics).

### Architectural “seams” needing explicit glue
- **Session bootstrap**: bridge requires `session` and `token`, but no canonical “how does the app obtain them securely?” flow is defined.
- **IPC surface**: how apps can call `postbridge_invoke` without enabling broader Tauri JS APIs is not fully specified.
- **Storage quota enforcement**: spec describes quotas, but doesn’t define the enforcement mechanism given browser-managed storage.

## 7) Critical gaps in the combined specification (highest priority)

1) **Bridge session bootstrap / handshake**
   - Missing: method(s) or injection mechanism to provide `{session_id, token, kid, expiry}` to the app.
   - Recommended approach:
     - On webview creation, Rust injects an initialization script defining `window.__POST_URBIT_SESSION__` and `window.__POSTBRIDGE__.invoke(...)`.
     - Session still bound to webview label so token leakage is not usable cross-webview.

2) **Definitive app event delivery design**
   - Decide and document:
     - All backend→app notifications go through `events.subscribe/poll` topics.
   - Update `03` to not claim direct emission of `app://resource/*` unless those are internal topics carried over bridge.

3) **Capabilities/config unification**
   - One authoritative list of:
     - Tauri commands (shell-only, app-allowed)
     - Capability files and identifiers used by `tauri.conf.json`
   - Right now there are multiple example capability identifiers that don’t line up (`shell-only` vs `shell-capabilities` etc.).

4) **Storage quota enforcement mechanism**
   - Need at least one of:
     - OS/webview-level storage partitioning + periodic measurement + eviction/clearing policies
     - SDK-level storage virtualization through bridge (authoritative Rust storage)
     - A documented “best-effort” approach if hard enforcement isn’t possible on all platforms

5) **Security hardening for custom protocol**
   - `canonicalize()` can fail if the file doesn’t exist; handling is not shown (you should return 404, not crash/500).
   - Ensure consistent header set for all responses including error responses (CSP, nosniff, etc.).
