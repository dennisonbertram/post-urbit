## Overall coherence rating: **6/10**

The specs are directionally aligned (multi-webview isolation, single `postbridge_invoke`, CSP via `postapp://`, capability-based authorization), but there are several **system-level inconsistencies** that will cause implementation churn unless resolved now—especially around **method naming/versioning**, **event delivery**, **SDK envelope semantics**, and **ADR numbering**.

---

## 1) Naming consistency (commands, methods, types, enums)

### 1.1 Bridge method naming: **versioned vs unversioned (major mismatch)**
- **04 (Secure Bridge Protocol)** hard-codes examples like `storage.get`, `storage.set`, etc.
- **05 (Protocol Registry)** defines **versioned** methods like `storage.v1.get`, `storage.v2.get`.
- **07 (SDK)** uses `storage.v1.get`, `storage.v1.set` (aligned with 05).
- **00 planning** example uses `storage.get` (unversioned).

**Remediation:** choose **05 as authoritative** and update 04 + 00 examples to use `*.vN.*` consistently.

### 1.2 Duplicate “MethodRegistry” definitions (authority conflict)
- **04** defines a `MethodRegistry` with `MethodSpec`.
- **05** defines the **Protocol Registry** as the single source of truth with a richer `MethodSpec`.

This creates an **architectural contradiction** (“registry is authoritative” vs “bridge has its own registry”).

**Remediation:** 04 should delegate authorization/spec lookup to 05’s registry (or explicitly state 04’s `MethodRegistry` is a placeholder that will be generated from 05).

### 1.3 Shell commands: `app_*` vs `shell_*` (inconsistent)
- **02** defines shell-only lifecycle commands: `app_launch`, `app_show`, `app_hide`, `app_close`.
- **01** and **08** define shell-only commands: `shell_launch_app`, `shell_show_app`, `shell_hide_app`, `shell_close_app`.

**Remediation:** standardize on **`shell_*`** for shell→Rust commands. Reserve `app_*` for app→bridge methods (if ever needed), but currently apps only have `postbridge_invoke`.

### 1.4 Event names to shell: inconsistent topics
- **01** uses:  
  - `shell://apps/installed_changed`, `shell://apps/running_changed`, `shell://windows/changed`, etc.
- **08** uses:  
  - `shell://apps/installed`, `shell://apps/updated`, `shell://apps/state_changed`, etc.

**Remediation:** pick one canonical set (recommend 08’s more explicit lifecycle events) and update 01’s Zustand sync wiring accordingly.

### 1.5 Type naming drift: `PermissionTier` variants
All specs mostly agree on:
- `AlwaysGranted`, `GrantOnce`, `PromptAlways`, `ShellOnly`

But **semantics drift** exists (see section 4).

### 1.6 App identity naming / label conventions: mostly consistent
- **02/04/08/07**: webview label `app-{app_id}`; derive identity from label. Good.

## 2) Event delivery model consistency (long-poll vs push)

### 2.1 Apps: long-poll in 04/07, but “push events” implied elsewhere (major mismatch)
- **04**: apps receive events via **long-poll**: `events.subscribe` + `events.poll`.
- **07**: implements the same model.
- **02/03/06/08** frequently describe events as if Rust “emits” directly to apps:
  - `app://resource/pressure`, `app://resource/evicting`
  - `app://lifecycle/*`
  - `app://permissions/revoked`
  - `app://navigation/external_requested`

But apps are explicitly sandboxed away from Tauri APIs, so “emit” cannot mean Tauri event subscription unless you introduce a separate mechanism (e.g., `webview.eval()` dispatching DOM events).

**Remediation decision required:** pick one model and rewrite the others to match:

**Option A (recommended): “All app events are bridge events”**  
- Treat `resource.pressure`, `resource.evicting`, `lifecycle.*`, `permissions.revoked` as **topics** delivered through the existing `events.*` long-poll system.
- Replace `app://...` naming with `events` topic strings (or explicitly state `app://foo` is just a topic name, not a transport).

**Option B: “Rust push via webview.eval dispatches DOM CustomEvents”**  
- Keep `app://...` as an in-webview DOM event namespace.
- Specify how Rust injects/dispatches them safely.
- Then the SDK should provide `onAppEvent()` that hooks `window.addEventListener(...)`.

Right now the specs mix A and B without defining the transport, which is the core inconsistency.

### 2.2 Shell: push via Tauri events is consistent
Shell uses `listen('shell://...')` (01) and that’s fine because shell webview is privileged.

## 3) Session/bootstrap model alignment (bridge, SDK, lifecycle)

### 3.1 “Handshake” language vs actual bootstrap injection
- **04** references “handshake completes in < 100ms” but the mechanism is not actually defined as a protocol exchange.
- **07/08** define a concrete model: Rust creates session + token, injects `__POSTURBIT_BOOTSTRAP__`, app uses it immediately.

**Remediation:** clarify that **bootstrap injection is the handshake**, and remove/rename any implied multi-step handshake unless you truly intend one.

### 3.2 Request ID format mismatch (major)
- **04** recommends UUID (UUIDv7 preferred).
- **07** generates request IDs like: `"{sessionPrefix}-{counter}-{timestamp}"` (not UUID).

**Remediation:** SDK should generate **UUIDv7** (or UUIDv4) to match bridge expectations and simplify replay cache keys.

### 3.3 Envelope field placement mismatch (major)
- **04** defines envelope optional fields:
  - `trace_id`, `idempotency_key`, `deadline_ms` at **top-level** of `BridgeRequest`.
- **07** incorrectly injects:
  - `__idempotency_key` and `__trace_id` into **params**.

This will break schema validation once 05’s schema enforcement is implemented.

**Remediation:** SDK must set envelope fields properly (top-level), not mutate params.

### 3.4 SessionManager return type bug (internal inconsistency)
- **08**: `create_session(...) -> Result<AppSession, SessionError>` but returns `Ok((session, token))`.

**Remediation:** fix signature to return a struct or tuple consistently across specs:
- e.g. `Result<(AppSession, String), SessionError>` or `Result<SessionCredentials, SessionError>`.

## 4) Permission tier consistency (permission spec vs registry vs bridge)

### 4.1 Tier semantics vs UI choices (major semantic drift)
- **06** UX says prompts should offer: **Allow once / Allow session / Always allow / Deny** broadly.
- But tier definitions say:
  - `PromptAlways`: “Prompt every time”, “Once (not stored)”, “Every invocation”
  - That conflicts with offering “Always allow” for `PromptAlways`.

**Remediation:** introduce “allowed grant scopes” per capability (or per method), e.g.:
- `allowed_scopes: [once, session]` for `clipboard:write`
- `allowed_scopes: [persistent]` for `system:identity:read`
…and make UI options conditional.

### 4.2 `permission.request` exists in 06 but missing from 07 generated method list
- **06** defines `permission.request`.
- **07** generated `MethodName` list omits it (also omits `permission.grant/revoke/list` which are shell-only, but those may intentionally be excluded from app SDK).

**Remediation:** decide:
- Either **remove** `permission.request` (apps rely on calling the real method which triggers PromptAlways flows), or
- Add it to registry + SDK types and define exact use cases distinct from `prepare_action`.

### 4.3 TOCTOU error signaling mismatch
- **07**’s `withPermission()` polls by string-matching error messages like `"not confirmed"`.
- **04/06** don’t specify a stable error code for “pending action not confirmed”.

**Remediation:** add a dedicated error code (or structured `CONFLICT` details) such as:
- `CONFLICT` + `details.reason = "PENDING_ACTION_NOT_CONFIRMED"`
so SDK behavior is deterministic and localizable.

## 5) Package format alignment (08 lifecycle vs 09 trust)

### 5.1 `.postapp` contents: `FILES` manifest missing from 08
- **09** requires `FILES` and a richer `SIGNATURE` document (manifest hash + files hash, co-signatures, timestamps).
- **08** describes `manifest.json`, `SIGNATURE`, `main.wasm`, `ui/…` but no `FILES`.

**Remediation:** update 08’s package format + install pipeline to incorporate:
- ZIP safety profile (09)
- `FILES` verification
- signature payload canonicalization rules

### 5.2 Source policy duplication
- **08** defines validation by source type.
- **09** also defines `VerificationPolicy::for_source()`.

**Remediation:** designate 09 as the security authority; 08 should reference 09 and avoid re-specifying verification logic.

## 6) State machine consistency (InstallState, AppRunState)

### 6.1 `AppRunState` consistent enough
- Hot/Warm/Cold appears consistently across 02/03/08.

### 6.2 Install state vs UI status mismatch
- **08** has `InstallState` {Uninstalled, Installed, Disabled, Corrupted}.
- **01** UI model uses `status: 'installed' | 'running' | 'disabled' | 'error'`.

**Remediation:** normalize UI model to mirror backend:
- `install_state: installed|disabled|corrupted`
- `run_state: hot|warm|cold`
and derive “running”/“error” as computed UI flags.

## 7) Error code taxonomy alignment

### 7.1 Bridge errors mostly consistent (04/07)
- `INVALID_REQUEST`, `UNAUTHORIZED`, `PERMISSION_DENIED`, etc match across 04 and 07.

### 7.2 Non-bridge (shell-only) errors not integrated
- **08** defines `LifecycleErrorCode` (SCREAMING_SNAKE_CASE).
- **01/08** shell commands return `Result<_, String>` in examples, losing typed error info.

**Remediation:** define a typed `ShellCommandError { code, message }` for shell-only commands (not the same as BridgeError), and keep codes aligned with 08’s lifecycle error taxonomy.
